1 · 两处出口为什么是同一份数据

建议只有一份（服务端每轮最多生成一次，内存里存 2–3 条整句）。差别只在接受动作：
舱位槽位接受动作为什么不这么做的反面
芯片conversation.input.dock（order 10） setDraft(text) → submit() 若直接 conversation.send(text)，就绕过了宿主的输入守卫与提交机（队列、权限、plan 模式、附件、去重）
幽灵conversation.input.overlay 仅 setDraft(text) + persistDraft() 若只改草稿 store 而不进编辑器，Lexical 的文档模型不知道有字，下一次 commit 会覆盖

2 · 幽灵的显示条件（十项全真才出现）

芯片的六条（有建议 / 是最新已完成回合 / 不在运行 / 没用过没关掉 / 没被审批占用 / 不在发送中） 再加四条：draft === ''、phase === 'plain'（命令菜单打开时 Tab 属于宿主）、 无附件、输入栏聚焦。任何一条为假就整个不渲染，而不是渲染一个空壳。

3 · 键位

键行为
Tab填入草稿、光标落句尾、不发送；本地标记本轮已用
Escape本轮隐藏幽灵（不回写服务端）
Shift+Tab / Ctrl+Tab不拦截，交还宿主
输入法组字中（isComposing）不拦截，否则中文拼音会被 Tab 打断

4 · 三条视觉纪律（别让后来的人改掉）

① 芯片是一句话，不是「标题 + 说明」——需要二次阅读的标签会让人多想一秒，而这一秒正是功能要省掉的东西。
② 幽灵是灰斜体且与真实文本不同色，否则用户会以为输入栏里已经有字了。
③ Tab 渲染成键帽，绝不并进提示词文本，否则会被读成句子的一部分。
④ 芯片区用虚线与人分开、上方留白，别做成输入框的一部分。

5 · 一份「不该照抄」的清单

Qoder 的芯片也是点击即发送，但它的建议不持久化、随消息删除清空、且只保留最新一轮； 它 0.4.2 修过的一个缺陷是「建议生成阻塞了下一个请求」——所以我们的生成是 fire-and-forget，任何路径都不 await 模型。 t3code 的实测数据（Codex 小线程 ~11k input tokens/次）来自「把整条线程发过去」；我们沿用面板已有的 Transcript.snapshot 渲染体（≤6000 字符），这是量级上最大的一个差别。
