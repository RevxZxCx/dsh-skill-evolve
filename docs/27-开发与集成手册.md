# 27 · 开发与集成手册

**这是本仓库的唯一入口。** 新会话的第一件事是读完本文件，然后才动手改代码或写文档。

它回答三个问题，而且只回答这三个：

1. **怎么把它装进宿主、怎么让改动真的生效**（§1、§6）——集成。
2. **一次改动要走完哪些步、每一步用哪条命令**（§2、§3）——开发。
3. **哪些数字是不能碰的、什么时候必须量性能**（§4、§5）——约束。

历史、论证、某个决定为什么这么做**不在本文件**：那在 `handover/`（只增不改的原始记录）与 `docs/01`–`docs/26`。本文件只写「现在要做什么」，不写「当初为什么」。

## 1 · 集成：把它装进宿主

两个插件分别安装（不是装整个仓库），各自带 `cordis.patch.yml`：

```bash
npm install                                          # 从 checkout 装必须先装依赖
dsh plugin --profile desktop add F:/dsh-plugin/dsh-skill-evolve/packages/skill-evolve
dsh plugin --profile desktop add F:/dsh-plugin/dsh-skill-evolve/packages/ui-evolve
# 重启宿主
dsh plugin --profile desktop list --depth=0             # 两行都在，才算装好
```

四条规矩，每条都踩过：

1. **从 checkout 装必须先 `npm install`。** 工作区包之间按名字 import（`@revxz/dsh-evolve-core`），没装依赖时宿主会在 `apply()` 里报模块找不到，而那行报错看起来像代码 bug。
2. **不要手动把插件写进 profile 的 `cordis.patch.yml`。** 每个包自带 patch 自己注册；再手写一条会产生重复 loader id，宿主直接起不来。
3. **客户端 bundle 的注册 id 必须逐字等于包名**（`lib/client.js` 注册 `@revxz/dsh-ui-evolve`）。宿主拒绝 id 不匹配的 bundle，重复 id 直接抛错。
4. **`lib/client.js` 是手写 bundle，没有构建步骤。** 它需要别的模块的东西只能被复制进来，复制由 `node scripts/sync-gutter.mjs` 完成，`test/gutter-drift.test.mjs` 比对不一致就红。**不要手改 `client.js` 里那段内联几何。**

### 改完什么时候必须重启宿主

**任何 `lib/*.js` 的改动都需要重启宿主。** 宿主在启动时加载这些模块，进程内的 ESM 缓存不会因为磁盘上的文件变了而失效——于是活宿主会继续答旧答案，而你对着它验收会得出「改动没生效」的错误结论。这条踩过不止一次（例如白名单搬家那次，`deliverable.js` 已改但真机仍按旧表判定）。

客户端 bundle（`lib/client.js`）与 `package.json` 的改动**额外**需要重启才会被扫到；只改 `package.json` 不会触发重扫。

### 真机验收怎么做

签名 cookie 的三个细节（`secret` 要先 base64url 解码成 32 字节、载荷的 `authority` 必须逐字等于 `127.0.0.1:19387`、时间戳是毫秒）与 CDP 注入的完整步骤在
[`handover/index.md`](./handover/index.md) 的「更正 2026-11-14：截图可以是宿主实拍」一节。**本文件不重复抄它**，因为那份记录已经被真机验证过，抄一遍只会先过期。

最短的一条检查（不需要浏览器，已封装 cookie 签名与探活）：

```bash
npm run verify:live                                  # 探活 /api/ui-evolve/config
npm run verify:live -- --session <session-id>        # 探活指定会话的 /api/ui-evolve/panel
```

`/panel` 回 200 且载荷里能看到你刚改的那个字段，才算真机生效。

## 2 · 一次改动要走完的十步

**这十步不是建议，是每次都要走的。** 少走哪一步，就有一类问题没有人看见。

**加一个新功能**（不是修缺陷）先过 §7：那四个问题答完再回到第 1 步。§7 还会告诉你
代码里有哪几处要登记，而漏掉的那一处不会报错——它只会让功能「有时候不生效」。

### 第 1 步 · 先量 diff，再决定谁审

```bash
git diff --stat
```

记下**改了几行**，这个数字决定 §2 第 6 步用哪条审查路径。**先量再改**，因为改完再量会把顺手的重构也算进去。

### 第 2 步 · 改代码

只改这件事需要的文件。骑进来的无关重构要么单独一个提交，要么撤掉——它会让审查单元变大、让回滚变难。

### 第 3 步 · 跑全量断言与快速门禁

```bash
npm run gate:fast                    # 全量断言 + 文档/注册点/锚点/活跃视图校验 + 性能预算
node test/run.mjs api                # 单套件（按名字）；开发过程中快速验证
```

**全量必须跑一次。** 单套件快，但它不证明你没弄坏别人——按行发断言的循环、共享 fixture、状态版本门控都只有全量才看得见。

### 第 4 步 · 跑受影响的变异套件

```bash
npm run gate:mutate -- --changed     # 根据 git diff 自动挑选并串行运行受影响的变异套件
npm run gate:mutate -- --list        # 查看全部 11 套变异脚本
```

详见 §3 的表：**改动落在哪个模块，就跑到那套归零为止**；不确定范围时用 `npm run gate:mutate -- --all`。全绿不代表有判别力——只有变异能证明「测试会红」。

### 第 5 步 · 变异条目与计数同步

`test/mutations.test.mjs:202-205` 维护每套脚本的 `expected` 条目数，判据是 `anchors.length >= expected`：

- **增加条目**：不会红，但请顺手把 `expected` 加上去——它是一个声明，不是一个上限。
- **删除或收窄条目**（把一条变异收成只覆盖一半）：**必须同步下调 `expected`**，否则锚点审计直接红。
- **一条变异声明两个以上套件**：必须留 `// Measured:` 写明两套都实测失败过（`test/mutations.test.mjs:310` 检查这条）。

### 第 6 步 · 用 `bounded-diff-code-review` 技能审查

**这一步是硬性的**（用户 m06781：每次改代码后都必须审查；针对审查意见的修复必须再审，多轮直到收敛）。

技能名为 **`bounded-diff-code-review`**（`~/.dsh/skills/bounded-diff-code-review/SKILL.md`）。它规定的不是「审什么」，而是**「审多大一块」**，因为审查质量由单元大小决定，与审查者数量无关：

| 改动行数 | 路径 | 做法 |
| --- | --- | --- |
| **≤ 200** | 一次 `dsh_code_review` | 不切分、不派 subagent。多数改动到这里就结束 |
| 200–600 | `dsh_code_review` **串行** 2–3 次 | 每次 `input` 只点这一单元的文件与关注点 |
| **> 600** | 每单元一个 `subagent`，**并行** | 每个 prompt 内联技能里那段「什么算 bug」的八条 |

三条必须照做的：

1. **审查单元 ≤ 200 行、≤ 3 个文件**，按**关注点**切，不按文件数切（一个修复和它的测试是一个单元）。
2. **每个单元先写一句契约**：这个单元要做什么、什么算做错。没有契约的审查者只会报风格意见。
3. **发现要结构化**：`[P0|P1|P2|P3] <file>:<line> — 什么坏了 — 怎么触发`。散文报告无法去重、无法计数，那正是「第五轮看起来还有必要」的原因。

**停止规则**：P0/P1 一批修完；P2 局部且显然就同批修，否则记下来；**P3 本轮只记不修**（修 P3 会生成新 diff，招来下一轮，这是实测烧掉 100 分钟的那个循环）。复核**只跑一轮，且只喂 delta**（上一轮的发现清单 + 修复产生的 diff），不重发原始 diff。

### 第 7 步 · 性能自检（触发条件见 §5）

改了 `/panel` 装配、状态文件、SSE 帧、客户端轮询或摘要调用中的任何一项，跑：

```bash
node scripts/perf-budget.mjs
```

七条预算与理由写在 [`28-性能审查手册.md`](./28-性能审查手册.md)。**超了就修，不要改预算**——改预算需要在这里写清为什么，并在 `handover/02-decisions.md` 落一条 D。

### 第 8 步 · 写分片交接条目并刷新活跃视图

自 2026-11-26 起（D-255），**不再往冻结的 `01`–`04` 单文件里追加**，避免多 Agent 并行合并冲突。在 [`docs/handover/entries/`](./handover/entries/README.md) 下按一件事一个文件新建条目：

| 什么时候写 | 文件命名（`docs/handover/entries/`） |
| --- | --- |
| 每个大阶段结束 | `YYYY-MM-DD-status-<slug>.md`（含 `baseline` 与 `pending_verify`） |
| 做出一个非显然的决定 | `YYYY-MM-DD-decision-<slug>.md`（`id: D-xxx`） |
| 修完一个缺陷 | `YYYY-MM-DD-defect-<slug>.md`（`id: DEF-xxx`，**必须写「为什么测试没抓到」**） |
| 每轮审查收敛 | `YYYY-MM-DD-review-<slug>.md`（`id: R-xxx`） |

写完后必须运行刷新命令（`gate:fast` 会校验视图是否过期）：

```bash
npm run handover:build               # 刷新 ACTIVE-STATE.md 与 ACTIVE-DECISIONS.md
```

若本次属于多 Agent 协作任务，同步更新 [`docs/tasks/`](./tasks/README.md) 中对应任务单的 `Verification Matrix` 与 `Handoff Note`。

### 第 9 步 · 同步索引

- 新增一份编号文档 → 在 `docs/00-文档索引.md` 的清单表加一行（状态栏限一句话，**维护规矩第 4 条**）。
- 新增分片交接条目 → 运行 `npm run handover:build` 同步活跃视图。
- 删除某个机制 → 同一提交里让机制名在文档与代码中的 grep 命中数归零（D-254），否则留下的散文会继续描述一个不存在的东西（DEF-187 就是这么来的：README 讲了四个已删除的采集器）。

### 第 10 步 · 提交、推送、重启、真机看一次

```bash
git status                                              # 核对改动文件，确认无临时产物
git add <本次改动的文件列表>                              # 严禁盲目 git add -A
git commit -m "fix(ui-evolve): <一句话说清改了什么>"
git -c http.proxy=http://127.0.0.1:7890 -c http.sslBackend=openssl push
# 重启宿主，然后跑 npm run verify:live
```

**推送必须带 `-c http.sslBackend=openssl`。** 只带代理会报 `schannel: failed to receive handshake, SSL/TLS connection failed`，它不是网络问题，是 Windows 的 TLS 后端问题——**没有这一步你会以为是代理坏了，然后花时间去查网络**。

提交信息用 conventional commits 的形态（`fix(ui-evolve): …`、`docs: …`、`perf(ui-evolve): …`），packages 名写在 scope 里。

**新增或收窄条目时同步 `expected`**：判据是 `anchors.length >= expected`（`test/mutations.test.mjs:241`），所以**加**条目不会报错（要自己把数字加一），**删**或收窄会让它红。一张变异挂两个套件时，必须写明实测（`// Measured:`，规则在 `:310`），否则另一个套件从不失败的声明没人验证过（DEF-145/146 就是这条规则把自己漏掉的历史）。

**性能这条也在这里**：`scripts/perf-budget.mjs` 不是变异套件，但它是六条预算的唯一判据。它的 `stat-per-reported-row` 在 ceiling 输入上恒等成立（200 行全可交付，`stats ≡ rows`），只能靠 `real` 输入抓「过滤被删掉」；退出码 **0 = 全部测到且通过、1 = 有预算被突破、2 = 有预算没测到**——2 不是通过，别把「绿了几行」当通过。比较用原始比值、打印才四舍五入；判定时仍可看 `--verbose` 的 `X rows / Y stats`（`X` 必须等于 `Y`）。

**跑法**：串行，一次一套。中断会把变异副本留在磁盘上；`mutate-guards.mjs` 发现 `gutter.js` 与 HEAD 不一致会拒绝启动，那是保护，不是坏了——先把副本恢复再跑。

**改完 `gutter.js` 还要跑生成器**：

```bash
node scripts/sync-gutter.mjs     # 把几何复制进 client.js
node test/gutter-drift.test.mjs  # 不一致就红
```

## 4 · 硬性约束

「违反会怎样」这一栏是这条约束存在的理由；理由丢了的约束，下一个人会在不方便的时候把它抬走。

| # | 约束 | 出处 | 违反会怎样 |
| --- | --- | --- | --- |
| 1 | Node.js **≥ 20**，纯 ESM，npm workspaces | `package.json` 的 `engines` 与 `workspaces` | 低版本没有 `import.meta.dirname` 等；CJS 会与宿主 loader 冲突 |
| 2 | `lib/client.js` **是手写 bundle，不许手改内联块** | `scripts/sync-gutter.mjs`、`test/gutter-drift.test.mjs` | 漂移测试红；下次同步会覆盖你的手改 |
| 3 | 几何唯一来源是 `lib/gutter.js`，两端夹在 **220–460 px** | `MONITOR_MIN_WIDTH` / `MONITOR_MAX_WIDTH`（`gutter.js:281,290`） | 宿主面板在窄宽度下画不出内容 / 拖到超出原型宽度 |
| 4 | 客户端 bundle 注册 id **逐字等于包名** | `lib/client.js` 头部 | 宿主拒绝加载，或重复 id 直接抛错 |
| 5 | 四包**不许合并、不许改名** | `packages/*/package.json`（宿主按名字 import） | 另一侧按名字 import 找不到模块 |
| 6 | `mcp-evolve` 的 `apply()` **故意抛错** | 根 `README.md:157-163` | 「修好」它等于把一个占位包伪装成可用包 |
| 7 | 卡片上限 `MAX_CARD_PATHS = 40`、`MAX_DELIVERED_ENTRIES = 160` | `transcript.js:103,114` | 超过就截断，且声明与产量的优先级只在 40 行内成立 |
| 8 | `MAX_TOUCHED_FILES = 200`、`MAX_PATHS = 200` | `api.js:596`、`session-state.js:95` | 载荷与状态文件按 200 行付费，性能预算立即被突破 |
| 9 | 状态文件 `STATE_VERSION = 3`，只读 v3 的 `paths` | `session-state.js:60,160` | 旧版空描述会冒充交付（DEF-179/180）；`restorable` 是那道门 |
| 10 | 交付判断**只有一处白名单** `lib/deliverable.js` | `deliverable.js` | 两张表分叉，卡片与 API 各信一套（DEF-186） |
| 11 | 写盘合并 **1 秒**，会话文件 **≤ 500 个**，每 **5 分钟**裁剪一次 | `WRITE_DELAY_MS:50`、`MAX_FILES:59`、`PRUNE_INTERVAL_MS:68` | 每事件写盘会打爆 IO；不裁剪会让目录无限增长 |
| 12 | 账本 **≤ 5 MB** | `packages/core/lib/store.js:35` | 账本无限增长，最终读到的是内存问题 |
| 13 | 摘要**每回合至多一次模型调用**，输入 ≤ 6000 字符，超时 20 s，失败冷却 60 s | `summarise.js:56,59,62,81` | 每事件摘要会把成本乘上事件数；不冷却会把失败变成重试风暴 |
| 14 | `handover/` 历史 `01`–`04` 原地冻结，新条目一律在 `handover/entries/` 分片追加，**只增不改** | `handover/index.md`、D-255 | 一份可被悄悄修改的记录不能用于追责（用户 m20052），且单文件追加会导致多 Agent 并发冲突 |
| 15 | 新增编号文档必须同步 `docs/00-文档索引.md` 清单表 | 本文件 §2 第 9 步 | 索引的「状态」栏失去意义，读者不知道哪份能信 |

## 5 · 什么时候必须做性能自检

七条触发条件，**命中任何一条就要跑 `node scripts/perf-budget.mjs`**：

1. 改了 `/panel` 的装配路径（`readPanel`、`statTouchedFiles`、载荷字段）。

## 7 · 加一个新功能：先答四个问题，再进 §2

§2 那十步是「怎么改完」，这一节是「从哪开始」。差别在于：改一个缺陷时，你要碰哪儿
由缺陷替你决定；加一个功能时，**碰哪儿由你决定**，而漏掉的那一处永远不报错——它只会让
功能「有时候不生效」，然后在下一次真机上被用户发现。

四个问题按顺序答，答不出来的那个就是还没想清楚的地方。

### Q1 · 它属于哪个包

四个包的分工是硬的（§4 第 5 条：不许合并、不许改名），所以「先写在哪」不是风格问题。

| 包 | 职责 | 放什么都合适 | 放进去就是错的 |
| --- | --- | --- | --- |
| `packages/core` | 纯库：账本、路径、公共谓词 | 两个以上包都要用、且不依赖 Cordis 的东西 | 需要 `apply()` 的东西——`core` 没有 `apply` |
| `packages/skill-evolve` | 检测器：`skillEvolve` 服务的唯一提供方（它自己 `inject = ['tools', 'systemPrompt']`，`packages/skill-evolve/lib/index.js:79`） | 事件观察、候选生成、工具、命令 | 任何 `/api/…` 路由（它不注册 webServer） |
| `packages/ui-evolve` | 面板：HTTP 路由 + 客户端 bundle | 路由、载荷装配、卡片、几何、摘要 | 检测逻辑（那会让只装面板的人被迫装检测器） |
| `packages/mcp-evolve` | 占位，`apply()` 故意抛错 | 暂时没有任何东西 | 真的实现——先读根 `README.md:167-175` 说明为什么它是空的 |

判据一句话：**先问「只装这一半的人还需要它吗」**。需要 → 它属于那个包；一半需要一半
不需要 → 它该被拆成两半，而不是放进 `core` 当折中。

### Q2 · 有没有先例可以照搬

按这个顺序查，每处都写明「照搬了什么、没照搬什么」：

1. **Qoder 逆向**：`docs/09`（产出文件机制）、`docs/22`（数据链）、`docs/23`（侧栏产出区）、`docs/24`（重定为交付文档）、`docs/26`（完整通道方案）。**先读它们记的「Qoder 没做/我们不该照抄」那一节**：十项里绝大多数在 `docs/26` 的 §5.4 表与 §5.5，另外两份 `docs/09`/`docs/23` 没有这一节（它们只有「本文没有证明的事」），不是每份都有。
2. **宿主自己的插件**：`F:\DSH\resources\app.asar\dsh\node_modules\@deepseek-ai\` 下的官方包。上一轮 SSE 就是从 `dsh-client-hmr` 的 `/plugins/events` 照抄的（wire 格式、`writeHead` + `: connected` 提交 header、`Set` 收集连接、dispose 时 `res.destroy()`），比自创可靠得多。
3. **本仓库删掉的历史**：`handover/02-decisions.md` 里被否决的方案。**四路采集（git 差分 / mtime 走查 / 工具路径 / shell 解析，共六个文件 1,566 行）在 2026-11-21 被整块删除**——如果新功能看起来像「再采集一次文件变更」，先读 D-241 与 `docs/24` 的 §3（为什么我们不照抄 Qoder 的通道 1）和 §5（删掉了什么）再动手；它的 §8 是「本文没有证明的事」，不是删除理由。

三处都查不到先例，就在方案文档里写一句「没有先例」，不要跳过——跳过的人会重写一遍被删掉的东西。

### Q3 · 它会不会让「每个事件」多走一次

这条是历史事故最集中的地方（§5 第 6 条）。真实密度：一轮平均 **1,252 秒**，`tool/call` **0.057 次/秒**，全部会话事件 **0.394 次/秒**。七处 `revisions.bump` 已经让最坏会话一轮产生约 **36 帧**，每帧客户端都 `load()`。

所以新增一条「每事件都走」的路径，必须同时回答：
- 一轮会走几次？（把 Q3 的那个密度乘上去）
- 走的这一下里有没有 syscall、模型调用、序列化？
- 客户端收到帧之后会不会整块重渲染？（`panelSignature` 会不会挡住？）

答不出次数的新路径，先按 §5 跑一次 `node scripts/perf-budget.mjs` 再说。

### Q4 · 怎么知道它成了

写一句**可验证的话**加**一个数**，例如「切回看过的会话应在毫秒级，实测 3.8–5.1 ms（本机，`/panel` 热路径，见 `handover/01-status.md`）」或「卡片列出交付文档而不是全部变动文件，真实 181 行降到 55 行」。然后这句话进 §2 第 10 步的真机验收。

反例（本轮之前真实出现过）：「更快了」「应该没问题」「看起来对了」——这三句都无法在两个月后判断是否成立，也无法在审查时被否掉。

### 什么时候必须先写一份方案文档

命中任一条，就**先写 `docs/NN` 再写代码**。`docs/00-文档索引.md` 不重复这张单子，只回指这里：判据只有这一份，免得两处各写一半、谁都不全。

1. **跨包**（一个新的东西同时要改两个包以上）。
2. **改协议或状态格式**（状态文件字段、载荷形状、`ROUTE_PREFIX` 之外的新入口）。
3. **换数据来源**（卡片的答案从哪儿来、摘要由谁算）。
4. **删既有机制**（哪怕只是删一个采集器、一张噪声表）。
5. **改用户可见行为**（卡片长什么样、什么时候刷新、什么默认开）。

（`docs/24` 与 `docs/26` 大体是照这个顺序写的；`docs/17` 用的是另一套六章
——决策 / 接口契约 / 改动清单 / 测试计划 / 验收 / 风险——不必照搬，它早于这份模板。）

模板六段，缺一段就不算方案：

1. **问题**（现在的行为是什么，谁受影响）
2. **真实数据**（多少会话/多少行/多少毫秒，附可重跑的脚本路径）
3. **选项与代价**（至少两个，含「不做」）
4. **选择与理由**（以及被否决的那个为什么被否决）
5. **验收判据**（Q4 那句可验证的话 + 数）
6. **明确不做**（这一轮不碰什么，防止范围长大）

不命中的改动不必写方案文档——一张卡片挪 4 px 不需要六段。

### 维护这张表

**这张表由 `test/registration.test.mjs` 守着，不靠记性。** 规则只有三条：

1. **红了是加行，不是改判据。** 测试的失败信息里写了缺哪个名字、该在哪一块加一行。把 `KINDS` 里的正则放宽、或者把某一类删掉，等于把「有人会漏」重新变成「没人知道」——那是这张表存在的全部理由。
2. **本文件不需要改。** 名字是**从代码里数出来**的（路由数 `path === `${ROUTE_PREFIX}/x``，配置键数 `z.` 行，工具数 `name:` 行……），所以新增同类注册点只改 §7 那几块表，`registration.test.mjs` 一个字都不用动。
3. **只有出现一整族新的注册面才改 `KINDS`。** 比如将来有人用 `ctx.commands.register` 或新的宿主 API。那时要：`KINDS` 加一项（`id` / `label` / `find` / `add`）、§7 加一块；**如果它是一族全新的东西，还要在 `FAMILIES` 里加一项（`id` / `label` / `signal` / `files`）**——只加 `KINDS`，那一组不知道新族存在，「新文件里出现了这一族调用」永远不会报。

**它不覆盖什么**：它保证「表与代码同名同数」，不保证每一行写的「必须同时改什么」是对的——那是散文，测试读不懂。所以每行第三列宁可写「同步某文件的某张表」，也不要写「注意一致性」：前者能在审查时被核对，后者不能。

**它也不假装穷举**：上面这十一族是今天这个仓库会碰到的全部。将来宿主给了新的注册面（例如新的 slot 类型或新的事件源），除非有人把它加进 `KINDS`，否则这张表不会知道——所以 Q1 那四个问题的最后一条永远是「你碰的东西，是不是这十一族之一？不是的话，先把表补上」。
