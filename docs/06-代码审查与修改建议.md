# dsh-skill-evolve 代码审查与修改建议

> 面向开发此插件的 agent：这是一份修复任务说明，不是要求重写插件。优先兑现现有的证据、审批和持久化承诺，再推进新功能。

## 1. 审查基线与结论

- 审查日期：2026-10-28。
- 代码基线：`9e729cb`，包版本 `0.1.0`；见 [package.json:3](../package.json#L3)。下文行号均针对该基线，修改后请按函数名重新定位。
- 方法：核心代码阅读、两路独立审查、现有测试执行，以及隔离环境中的定向复现。
- 测试结果：逐个执行 25 个测试脚本并检查真实进程退出码，共 1,335 个断言通过；真实 Cordis 挂载套件因未安装依赖而跳过。
- 验证边界：没有调用真实模型，没有安装市场技能，没有启动真实宿主或浏览器联调。以下模拟复现不等于生产环境攻击验证。
- 此次交付仅新增文档，不包含代码修复，也没有改变宿主配置或真实技能库。

**总评：设计方向值得保留，但几个核心约束尚未由实现保证。测试数量较多，不代表跨步骤和跨状态的关键行为已经受到保护。**

现在的主要风险不是“检测不够聪明”，而是：假证据可以经工具回显获得可信身份；审批不能绑定最终正文；正常修订和并发操作可以回退状态；辅助摘要在持续失败时没有调用预算。

另见 [方案评价与升级路线](07-方案评价与升级路线.md)，其中的新能力建议不应混入本轮修复范围。

## 2. 应保留的设计

1. 默认提出候选、由人决定，不把每个会话都变成技能生成任务。
2. 重复检测和回合反思并行，且有提示预算、去重和缩短机制。
3. 候选与可加载技能隔离，使用所有权标记拒绝普通路径上的非本插件文件覆盖。
4. 目录压缩配套本地搜索，而不是只删掉描述、让技能无法发现。
5. 市场安装复用审批前下载的同一份内容，缓存缺失时拒绝安装而不是重新下载。
6. 可选服务惰性解析、路由等待宿主服务激活，避免面板故障阻断核心插件。

这些是现有优势，不要在修复中回退成“提示词约束”“无条件覆盖”或“审批后再重新下载”。

## 4. P1：核心约束修复

### F01：证据回显自证

**代码位置**

- [lib/tools.js:115](../lib/tools.js#L115)，`describeGate()` 原样回显失败引用。
- [lib/tools.js:166](../lib/tools.js#L166)，工具渲染器把错误变成文本结果。
- [lib/evidence.js:262](../lib/evidence.js#L262)，`lanesFromEvents()` 按事件类型归类。
- [lib/evidence.js:300](../lib/evidence.js#L300)，所有 `tool/result` 的文本均进入工具证据车道。

**最小复现**

1. 构造没有任何真实引用的会话。
2. 提交候选，引用为 `This fabricated observation was never made by any user or external tool.`，类别为 `tool`。
3. 首次结果是 `no-verified-evidence`。
4. 将该工具通过自身 `output.render()` 产生的错误文本，按宿主工具结果结构加入会话。
5. 原样再次提交：返回 `ok: true`、`survived: 1`，候选进入队列。

**根因与影响**

当前的“工具结果”是传输层分类，不是来源可信度。模型提交的内容，经插件回显一次，就获得了“机器观察”的身份。即使没有恶意行为，普通重试也可能触发。

**建议修法**

- 用 `tool/call` 与 `tool/result` 的 `callId` 关联来源；不能假设每种宿主结果都直接携带工具名。
- 至少排除插件自己的提交、列表、预览和反馈回显作为独立事实证据的来源。插件自己的记录可以用于审计，但不应为其原始内容提供新的证明。
- 不再只保存合并后的大字符串；引用应能定位到单条事件、工具调用及文本片段，避免跨事件拼出不存在的引用。
- 区分“命中了真实记录”与“该记录足以支持此结论”。任意 shell 打印和外部页面内容仍可能由模型或第三方控制，不能因排除自己的工具就宣称解决了所有污染问题。
- `user-approval` 当前也进入人类车道，见 [lib/evidence.js:273](../lib/evidence.js#L273)。应核对真实收据载荷；授权执行某个动作，不等于人类认可收据中全部自然语言事实。

**验收**

- 上述连续两次提交必须都被拒绝。
- 经候选列表、预览或摘要转述的假引用不能获得新的独立来源。
- 真实用户原话、真实工具输出仍可被定位；错误信息仍足以帮助模型纠正引用。
- 跨事件拼接引用拒绝；含相同句子的两条事件不能被错误合并为两个独立证据。

### F02：审批未绑定最终制品

**代码位置**

- [lib/index.js:1532](../lib/index.js#L1532)，`approve()` 仅设置 `approvedAt`、`awaitingFinal`。
- [lib/index.js:1665](../lib/index.js#L1665)，`finalize()` 查找候选后直接使用新的描述和正文。
- [lib/tools.js:227](../lib/tools.js#L227)，`final: true` 不再做提案证据校验。

**最小复现**

在会话 A 提交并批准“检查构建输出”的草稿；会话 B 使用相同名字、完全无关的正文和 `final: true`。实际可以写入，且仍报告原草稿有一条已验证证据。

跨会话确认不是问题；**内容未经确认地发生改变**才是问题。不要通过禁止跨会话操作来掩盖它。

**建议修法**

- 把审批绑定到候选 ID、内容摘要和目标基础版本，而不仅是名字与布尔值。
- 内容摘要应覆盖 `name`、`description`、`whenToUse`、`body` 以及明确纳入授权范围的字段；使用确定性序列化。
- 选择一个清晰协议：先由模型生成最终稿，再由人批准并原样发布；或者保留两步确认，但最终稿发生实质变化时重新进入审核。
- 原会话证据可以继续复用，不要求在新会话重新说一遍旧引用；证据与某个草稿版本的关联必须保留。
- 一次审批只能消费一次。失效候选、已撤回候选和旧版本审批不能被重放。
- 记录“准备完成”“已批准”“已发布”的不同状态，不能用成功文案代替实际发布事件。

**验收**

- 相同内容跨会话确认可成功。
- 改正文、改适用范围或改描述时，旧审批不能直接写入。
- 两个并发 `final` 只有一个能消费审批。
- 候选被丢弃或目标内容被编辑后，旧审批失效。
- 写失败时不能同时报告已发布并消费掉唯一的重试依据。

### F03：修订恢复旧状态

**代码位置**

- [lib/tools.js:273](../lib/tools.js#L273)，提案保存 `base.stage` 和 `base.uses`。
- [lib/index.js:1583](../lib/index.js#L1583)，`writeApproved()` 优先使用这些旧值。
- [lib/index.js:1619](../lib/index.js#L1619)，整条替换 registry 项。
- [lib/candidates.js:114](../lib/candidates.js#L114)，基础版本检查目前只比较正文摘要。

**最小复现**

提案时技能为 `unverified / 2 uses`；等待审批期间正常使用，变为 `active / 3 uses`；正文没有改变。审批该修订后又变成 `unverified / 2 uses`。已存在的 `pinned` 也可能消失。

**建议修法**

- 分离“不可变内容版本”与“可变使用统计”。基础内容摘要用于防止覆盖他人编辑，旧计数不能成为恢复目标。
- 在真正发布的受保护操作内读取最新统计，保留当前计数、身份与排名字段。
- 不要因为发生了正常使用就把内容修订全部判为过期；这会把数据回退错误变成无法审批错误。
- 正文、描述及适用条件都可能被人编辑，需要定义完整的内容基础版本；不要只保护正文而静默覆盖其他字段。
- `auto` 修订走不同构造路径，见 [lib/tools.js:306](../lib/tools.js#L306)。必须单独补同类保留测试，不能只修人工审批路径。

**验收**

- 上述例子审批后仍为 `active / 3 uses`。
- `helpful`、`harmful`、稳定身份、创建时间及排名标记不因普通修订消失。
- 修改技能内容不能自动抹掉既往负面记录；如果以后采用版本级质量统计，应显式迁移和展示，而不是直接归零。
- 内容冲突仍拒绝写入，正常计数增长不导致内容冲突。

### F04：单次 mutation 串行不等于整段业务操作原子

**代码位置**

- [lib/store.js:170](../lib/store.js#L170)，`serialize()` 串行化单次存储操作。
- [lib/index.js:1430](../lib/index.js#L1430)，`applyLifecycle()` 使用调用方传入的快照。
- [lib/index.js:1483](../lib/index.js#L1483)，随后把旧快照计数重新写回 registry。

**复现结果**

初始 `uses=helpful=2`，两次 helpful 操作交错完成，预期最终为 4；迟到的旧生命周期写回可使结果回退到 3，技能文件也回退。这发生在同一宿主，不依赖两个进程共享目录。

**建议修法**

- 统一同一技能的“读取最新状态—应用事件—计算阶段—更新制品/记录”边界。
- 不把锁外计算出的旧计数原样覆盖到锁内最新值。
- 可以先实现宿主内的完整串行操作，无须立即引入数据库或分布式锁。
- 如采用版本检查与重试，重试必须重新读取状态并重算，不能重试旧覆盖操作。
- 注意 `Store` 的队列并非可重入锁：不要在已持有队列的回调里等待一个再次排入同一队列的高层方法，否则可能死锁。
- registry、技能文件和账本是不同持久化对象。内存锁解决交错，不解决进程中断；明确失败恢复责任，不要把两者混为一谈。

**验收**

使用可控制的 Promise 屏障固定交错顺序，而不是靠随机 `sleep`：

1. helpful + helpful：两次增量均保留。
2. 使用 + harmful：使用计数与负面计数均保留。
3. 发布修订 + 使用：新正文与最新统计均保留。
4. 晋升 + 排名修改：两项变化均保留。
5. 某次写入失败：后续操作不永久卡住，调用方不能拿到虚假的成功结果。

### F05：摘要失败后的重试无界

**代码位置**

- [lib/summarise.js:350](../lib/summarise.js#L350)，只命中成功缓存或当前在途请求。
- [lib/summarise.js:403](../lib/summarise.js#L403)，错误或空输出不写缓存。
- [lib/api.js:394](../lib/api.js#L394)，读取面板时执行摘要。
- [lib/client.js:54](../lib/client.js#L54)、[lib/client.js:703](../lib/client.js#L703)，每 8 秒轮询。

**复现与影响**

对同一轮快照连续请求 5 次，模型准备桩被调用 5 次。只要面板继续挂载、模型持续快速失败，单个面板约每小时产生 450 次尝试。不是每一种失败都会收费，但持续请求量和潜在费用没有每轮上限。

**建议修法**

- 为同一摘要键保存失败状态、尝试次数和下一次允许重试时间。
- 配置错误、授权失败等确定性错误停止自动重试；临时错误使用有限次退避。
- 示例起点可以是每轮最多 3 次自动尝试，但这是待校准的产品参数，不是已证明最优值。
- 提供显式重试，模型路由或输入真正变化时创建新的尝试上下文。
- 更清晰的后续设计是把“读取面板”与“发起有成本的摘要任务”解耦；短期修复至少保证轮询不能无限触发新模型调用。
- 记录尝试次数、失败类型和可获得的 token 使用量；缺少 usage 时标为未知，不能标为零成本。

**验收**

- 持续失败、空输出、鉴权错误、超时均不会被轮询无限重试。
- 同一摘要的并发请求仍只产生一个模型调用。
- 成功后复用缓存；手动重试、切换模型和开启/关闭摘要行为明确。
- 用假时钟验证退避，不访问真实付费模型。

## 5. P2：功能与可靠性修复

### F06：stale 阶段没有正常触发路径

证据：[lib/lifecycle.js:119](../lib/lifecycle.js#L119)、[lib/store.js:311](../lib/store.js#L311)、[lib/index.js:1765](../lib/index.js#L1765)。

`decideStage()` 可以把旧 active 判为 stale，但统计读取不运行它；使用/反馈调用前又刷新了 `validated`。模拟 200 天未验证的 active 技能，统计仍显示 active。

建议在明确的读取投影或维护入口按当前时间重新判断，不必首先增加常驻定时器。清楚区分持久阶段和派生展示状态，确保列表、统计和面板使用同一个口径。

验收：通过真实插件入口读取超期技能能看到 stale；下一次符合条件的使用可以恢复 active；不因超期自动删除技能。测试时注入时钟。

### F07：反模式警告重复包裹

证据：[lib/index.js:1455](../lib/index.js#L1455)、[lib/index.js:1463](../lib/index.js#L1463)、[lib/lifecycle.js:166](../lib/lifecycle.js#L166)。

当前按“阶段是 inverted”而不是“首次进入 inverted”调用 `invertBody()`。计数更新触发重写时，已经有警告的正文再次成为包装输入；复现中警告数量由 1 增为 3。

建议只在阶段转换时创建包装，或者从明确保存的原始正文进行幂等渲染，不要用脆弱的自然语言字符串匹配猜测是否已处理。

验收：进入 inverted 后连续加载或反馈 10 次，警告仍只有一层，正文长度不随计数增长，原始操作说明不丢失。

### F08：面板会话切换的响应竞态

证据：[lib/client.js:677](../lib/client.js#L677)。

A 请求挂起，切换 B，B 返回后再让 A 返回，旧回调仍直接写状态，导致 B 的面板展示 A 的摘要和文件路径。

建议使用请求代次或会话身份校验阻止过期结果写入，并在卸载/切换时清理。AbortController 可节省资源，但仅取消请求并不替代结果身份检查。跨会话切换时应立即清空旧会话数据，不能只把旧数据标成 loading。

验收覆盖 A→B、A→B→A、旧请求失败、新请求成功、卸载后返回；还应覆盖同一会话旧轮次请求迟到覆盖新轮次。

### F09：转录缓存内部没有真正限量

证据：[lib/transcript.js:184](../lib/transcript.js#L184)、[lib/transcript.js:208](../lib/transcript.js#L208)、[lib/transcript.js:253](../lib/transcript.js#L253)、[lib/transcript.js:309](../lib/transcript.js#L309)。

文本不断进入 `said`，输出时先拼接再截为 1,200 字符；完成回合后原数组仍保留。模拟中 2,097,152 字符留在内部，虽然外部快照看起来已限长。`view()` 还反复生成快照。

建议在接收边界限量保存摘要真正需要的文本，避免全量 join；完成回合后只保留有界快照。根据真实需求选择保留开头、结尾或两端，不能把单纯截断误写为完整总结。

验收检查内部保留量，不只检查返回字符串长度；覆盖超长单条文本、多文本块、完成回合、切换和会话销毁。阈值应按实际字节或明确的字符单位定义。

### F10：尝试编辑被误报为成功产出

证据：[lib/transcript.js:218](../lib/transcript.js#L218)、[lib/transcript.js:240](../lib/transcript.js#L240)、[lib/api.js:417](../lib/api.js#L417)、[lib/summarise.js:160](../lib/summarise.js#L160)。

路径在调用发生时就进入列表，工具失败不撤销；文件存在只能说明它此前存在，不能说明本轮编辑成功。摘要又把这些路径写成 `Files edited`。

建议按调用 ID 跟踪 attempted/succeeded/failed/unknown，产出列表只采纳有成功依据的变更。缺少结果时标未知，不能默认成功。即使工具成功，也应把它表述为“工具报告编辑成功”，而不是凭空声称产出质量合格。

验收：既有文件编辑被拒绝、工具报错、结果丢失、同一文件先失败后成功、先成功后失败；最后一种情形不能错误抹掉本轮确实发生过的成功编辑。

### F11：off 语义与实际行为不一致

证据：[lib/config.js:19](../lib/config.js#L19)、[lib/index.js:451](../lib/index.js#L451)、[lib/tools.js:183](../lib/tools.js#L183)。

配置注释承诺不检测、不提交；实际只关闭检测等入口，新候选提交仍能成功。主审以 `mode: 'off'` 调用提交工具，得到 `ok: true` 并新增一条候选。

建议明确产品语义并统一入口。较符合现有注释的选择是：禁止新提案和自动生成，允许查看/丢弃/处理历史候选，并保留已有技能的使用记账。摘要是否继续属于另一项配置，不要用一个模糊的“off”暗示所有模型调用都已停止。

验收：工具、命令、面板提案入口遵守同一语义；对已有技能的人工管理不被无意禁用。若选择其他语义，必须同步工具描述、配置和用户说明。

### F12：测试运行器可能把异常退出判为成功

证据：[test/run.mjs:34](../test/run.mjs#L34)。

总运行器解析 `N passed, M failed` 文本后累加计数，没有检查 `spawnSync()` 的 `status`、`signal` 或 `error`。如果子进程先打印“0 failed”后异常退出，汇总仍可能成功。

这是静态确认的问题；本次 1,335 条断言的结论来自独立逐套检查退出码，不依赖这个遗漏。

建议以非零退出、信号终止、启动错误和超时作为失败条件，计数字符串仅用于展示，并显式汇总 skipped。

验收注入以下子进程：正常通过、正常断言失败、打印成功后非零退出、没有输出、启动失败、被信号终止。不要为了通过测试把不可用的宿主集成套件悄悄当作成功。

## 6. 不应误报为漏洞、但必须说明的取舍

### 6.1 已知取舍

- 技能加载在 dispatch 时计数，不能直接当作任务成功。这一语义可以保留，但指标命名必须诚实。
- 多宿主共享同一目录不是现有承诺；本轮必须修的是同一宿主内的状态交错。
- 结构重复不代表语义上值得沉淀，因此保留模型判断和人工审核有价值。
- 关键词检索不理解所有同义词；不应因这一限制立即引入大型向量服务。
- 外部市场文件通过路径检查和人审，不等于脚本安全或未来执行已获授权。

### 6.2 后续加固项，不冒充本次已复现缺陷

- 非正常中断时 registry、候选、技能文件和账本之间的恢复协议。
- 符号链接目录、文件替换、写入中断与平台差异下的所有权/路径围栏。
- 全宿主技能目录的同名遮蔽：当前提案查本插件目标根目录，不等价于检查宿主最终可见目录。需要真实 provider 优先级用例后再下结论。
- 源会话消失或包含敏感引用时，证据保留、脱敏与删除策略。
- 格式解析支持范围：不要把当前简化 frontmatter 解析器当作完整 YAML 解析器。

## 8. 推荐实施顺序与完成标准

### 第一批：不改变产品定位，先修核心保证

1. 加入 F01、F02 的失败测试，再修证据来源和审批绑定。
2. 加入 F03、F04 的顺序/交错测试，统一最新状态的写入边界。
3. 加入 F05 的假时钟测试，封住持续失败的成本出口。

### 第二批：兑现生命周期与显示语义

处理 F06–F11。优先复用现有模块，不把修复变成全面架构重写；改动客户端时，需要在真实可用的宿主页面验证会话切换、加载失败、折叠和恢复，并明确未能验证的平台。

### 第三批：补验证可信度与文档

修 F12；补真实 Cordis/宿主契约测试；同步说明。可以拆成按不变量划分的提交或 PR，不按机械文件数量拆分。

## 9. 给开发 agent 的最后提醒

不要用增加一个“请不要伪造”的提示来修证据来源，也不要用更多布尔值掩盖审批状态。最有价值的改进，是把重要承诺写成明确的不变量，并用经过真实工具渲染、事件交错和持久化边界的测试去证明它。

先使“记下来的内容可信、批准的内容一致、积累的数据不会倒退”成立，再讨论插件是否真的能让下一次任务更好。
