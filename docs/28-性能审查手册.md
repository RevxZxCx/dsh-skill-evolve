# 28 · 性能审查手册

本仓库出过四次性能事故，每次都不是「代码很慢」，而是**同一份数据被算了太多遍**：把改过的文件当成要交付的文件（一次装配做了 181 次 `stat`）、把一个回合的摘要做成每个事件的摘要、把每个宿主事件都推一帧、把已经写下的摘要在重启后重买一次。

所以这份手册只做一件事：**把「一屏面板允许花多少」写成可执行的命令与数字**，让下一次开发在改之前就知道线在哪。

配套命令：`scripts/perf-budget.mjs`。它量三个数并按预算判定，退出码非零表示有预算被突破。

---

## 1 · 预算表

判定是命令，不是段落。七条，每一条都写了为什么是这个数——理由丢了的预算，下一个人会在不方便的时候把它抬走。

| 预算（id） | 量什么 | 上限 | 今天实测（2026-11-23，本机 Windows） | 为什么是这个数 |
| --- | --- | --- | --- | --- |
| `stat-per-reported-row` | `stat` 次数 ÷ 报告行数 | **× 1** | 真实会话 55 / 55；200 行全交付 200 / 200 | 交付过滤必须在 `readStat` 之前，被丢掉的行一个 syscall 都不该付 |
| `payload-real-session` | 真实会话的 `files` 行数组字节（UTF-8） | **32 KB** | 15,984 B（181 行进 → 55 行出，126 行被丢；含 51 条描述共 1,744 字） | 真实会话是几十行；32 KB 约为实测的 2 倍 |
| `payload-ceiling-session` | 200 行全交付时的 `files` 数组字节（UTF-8） | **80 KB** | 60,923 B（200 行 × 约 305 B，随临时目录路径长度在 54–61 KB 间浮动） | `MAX_TOUCHED_FILES` 的算术上限；再高就不是 stat 而是载荷本身成了成本 |
| `elapsed-real-session` | 真实会话一趟 `statTouchedFiles`（进程内首次触盘） | **200 ms** | 3.8–5 ms | 面板打开路径上的一次装配；200 ms 是人开始等的点，约实测的 40 倍 |
| `stat-when-nothing-is-deliverable` | 无交付行时的 `stat` 次数 | **0 次** | 0 次（对照：不过滤 200 次 / 5.2 ms） | 一条交付行都没有的会话没有任何东西可 stat，这正是过滤存在的理由 |
| `state-file-bytes` | 单次状态文件的**磁盘**大小 | **64 KB** | 最大 41,941 B（本机 244 个会话文件，占上限 64%） | 状态文件每次改动都要重写；超过这个量级，写盘本身成为成本 |
| `sse-frame-bytes` | SSE 一帧携带的字段 | **只带 `{agent, revision}`** | 由 `test/api.test.mjs:1124,1154,1398` 钉住 | 帧是唤醒信号，不是数据传输；载荷走 `/panel` 一次 |

两个 `payload-*` 量的是 `/panel` 回包里随路径数增长的那一部分——`files` 行数组。整包还有摘要正文（另有 6,000 字符上限）、技能名与工具名，它们不随行数增长，所以不在这条预算里；把它们算进来会让这条预算同时监视两件互不相关的事。

前六条由 `node scripts/perf-budget.mjs` 判定，退出码 **0 = 全部测到且通过、1 = 有预算被突破、2 = 有预算没测到**（2 不是通过）；`sse-frame-bytes` 是结构判据，由上面那三条断言钉住（脚本量不到它，也不假装量）。

**基线会变，方法不变。** 上表右列是我这台机器今天的数；换机器、换会话数量都会变。**判据是左边那一列的上限与 `scripts/perf-budget.mjs` 的退出码，不是右边的数字。**

## 2 · 怎么跑

```bash
node scripts/perf-budget.mjs            # 量三组输入并按预算判定
node scripts/perf-budget.mjs --verbose   # 同时打印「不过滤」那一遍，用来看过滤值多少
```

三组输入，回答三个不同的问题：

| 输入 | 是什么 | 回答什么问题 |
| --- | --- | --- |
| `real` | 本机状态目录里最多八个会话（按行数取前四个、按交付行数取前四个），行与描述都取自读取器今天真正会交出去的内容 | **产品会不会让人等** |
| `ceiling` | 200 个真实存在的文件，每一行都可交付 | **算术上限**会不会失控（`MAX_TOUCHED_FILES`） |
| `nothing` | 200 行全是 `.py`，一条都不可交付 | 过滤是否**真的在 syscall 之前** |

读法：

```
real sessions: 9 with rows, measuring 5 (largest by rows and by deliverable rows)
   ok   stat-per-reported-row [real]  1 x rows  (limit 1)
        session: session-….json (55 rows reported)
   ok   payload-real-session [real]  15984 bytes  (limit 32768)
        session: session-….json (55 rows reported)
```

- `real: X rows / Y stats` 里 **X 必须等于 Y**。不等就说明过滤挪到了 `readStat` 之后，或者某条路径被 `stat` 了两次。
- `(no filter: … , 126 dropped)` 是过滤省下的量。这条不判定，它只是回答「这个开关值不值」。
- **每条预算按所测会话里最坏的那一行判定**，并通过 `session:` 一行指向是哪一个会话。只看「最大的那个会话」会让载荷预算在便宜的会话上通过、在贵的会话上从未被测到。
- **没有会话目录、只有 v1/v2 文件、或临时目录不可写时，那一行打印 `NOT measured`，退出码是 2。那不是通过。** v1/v2 文件按面板的真实行为算作零行：读取器不读它们的 `paths`，加载器还会把 `previous.paths` 改写为空，所以它们的路径一个都不会出现在面板上。
- 比较用的是**原始比值**，打印时才四舍五入：57 次 `stat` / 55 行 = 1.036，四舍五入会变成 1.0，而那正是这条预算存在的理由。

## 3 · 性能审查流程

四步，每次触发条件命中时都走一遍（触发条件在 [`27-开发与集成手册.md`](./27-开发与集成手册.md) §5）。

**第 1 步 · 改之前先量基线。** 先跑一次 `node scripts/perf-budget.mjs`，把三个数抄到你的笔记里：`stat` 次数、载荷字节、耗时。**改完再量会失去对照**，因为你已经不知道哪个数是改动前的。

**第 2 步 · 改代码，然后只跑受影响的输入。** 只改 `deliverable.js` 就只看 `real` 与 `ceiling` 与 `nothing` 三行；改了状态文件就别只跑 `perf-budget`，还要跑 `mutate-persistence`。

**第 3 步 · 再量并与基线比三项，不比一项。**

```bash
node scripts/perf-budget.mjs        # 三条 real 预算 + 两条 ceiling/nothing 预算
```

比的时候问三个问题，缺一个都会看漏：

- `stat` 次数变多了吗？（变多 = 多出来的 syscall 是谁付的）
- 载荷字节变多了吗？（变多 = 多了哪些字段、谁会读它们）
- 耗时变多了吗？（耗时是最弱的一条：热缓存下 4 ms 变 8 ms 也是 2 倍，但它不告诉你为什么）

**第 4 步 · 把数字写下来，不要写「更快了」。**

`handover/01-status.md` 的那一节里写 **「55 stats / 13.7 KB / 4 ms（改前 181 stats / 8.5 KB / 7.8 ms）」**，不写「性能改善了」。前者下一个人能比，后者只能被相信。

**超预算怎么办**：先找「多出来的那部分工作」，而不是换机器或调大上限。今天三条真实来源分别是：过滤放在了 syscall 之后、载荷带了一个没人读的字段、每个事件都推了一帧。**改预算需要理由**，理由落成 `handover/02-decisions.md` 的一条 D。

## 4 · 不靠测量也能判断的七条

这七条是**结构**判据：违反它们的改动，即使今天量出来很快，也会在会话变大时变慢。

1. **不是每个事件都值得一帧。** 只对「能改载荷的事件」计数。实测：一个真实会话里宿主每秒 0.394 个事件、其中 `tool/call` 只有 0.057 个/秒——每个事件都推帧会比它替换掉的 8 秒定时器还忙，而且推的是没变的载荷。
2. **帧里不放载荷。** 帧只说「有变化，来取一次」，载荷走 `/panel`。把载荷塞进帧等于把一次装配乘以帧数（今天 7 处 `revisions.bump`）。
3. **过滤在 syscall 之前。** 判断「这一行会不会被报告」是纯字符串运算；先 `stat` 再丢，等于为丢掉的行付系统调用。
4. **渲染期不 `stat`。** 卡片拿到的是 `/panel` 已经量好的 `size` / `state` 字段；在渲染里补一次 `stat`，每帧都会付，而且没有人能看见它。
5. **一个回合至多一次模型调用。** 摘要按回合缓存，键里带回合号（`summary.key` 含 `<session>:<turn>:<hash>`）；按事件触发摘要会把成本乘上事件数（实测 2.8 秒/次）
6. **缓存的是答案，不是问题。** 失败要冷却（`SUMMARY_FAILURE_TTL_MS = 60000`），否则一次超时会变成每个事件重试一次。
7. **大表只在读侧收窄一次。** 交付白名单只有一处（`lib/deliverable.js`）；两张表分叉时，卡片与 API 会各信一套（DEF-186）。

## 5 · 四次真实事故

每条都写「当时的现象 → 根因 → 数字 → 判据」，因为**判据比修法更值钱**：修法只睡一次，判据能挡住下一次。

### 事故一 · 一次装配做了 181 次 `stat`（2026-11-21，F1）

- **现象**：卡片改成「只显示交付文档」之后，`/panel` 仍为历史路径逐条 `stat`，其中约 92% 被客户端在渲染前丢掉。
- **根因**：`statTouchedFiles` 先 `stat` 再让 `readPanel` 过滤；`deliverable` 字段在过滤之后才算出来。
- **数字**：修复前 38 行进 → 38 次 `stat` / 8,489 B；修复后 4 次 `stat` / 932 B（8.1 倍）。今天同一判据在更大的会话上是 181 → 55。
- **判据**：**`stat` 次数必须等于报告行数**，这条今天由 `scripts/perf-budget.mjs` 的 `stat-per-reported-row` 自动检查。
- **同时学到的**：报告里有一处量错了对象——量的是「文件里写了什么」，不是「读取器交出去什么」；`STATE_VERSION` 门控之后有 2,647 条旧路径根本不会被读取。**性能审查量读取器的输出，不量磁盘上的存量。**

### 事故二 · 摘要被重启重买（2026-11-21）

- **现象**：每次宿主重启，同一回合的摘要被重新买一次。
- **根因**：摘要只活在摘要器的内存里，没有落盘；键里也没有回合号。
- **数字**：**2.8 秒/次**（`packages/ui-evolve/README.md:381`），每回合一次模型调用，输入 ≤ 6000 字符、超时 20 s。
- **判据**：摘要必须落在会话文档里（`summary: { key, text, at, model, routeKey }`），键含回合号；重启后同一回合从文件答，不再买。

### 事故三 · 每个事件推一帧（2026-11-20 之前）

- **现象**：面板被每个宿主事件唤醒，载荷没变也重取。
- **根因**：`revisions.bump` 接的是「有事件发生」，不是「载荷会变的事件」。
- **数字**：真实会话 0.394 事件/秒，其中 `tool/call` 0.057/秒；每事件推帧约 2.5 秒一次，比被替换的 8 秒定时器更忙。
- **判据**：**只对能改载荷的事件 bump**；今天共 8 处调用点（`grep -c 'bump(' packages/ui-evolve/lib/index.js`），帧只带 `{agent, revision}`，心跳 30 s 一次。

### 事故四 · 活宿主继续答旧答案（反复发生，最近一次 2026-11-22）

- **现象**：改了 `lib/*.js` 之后真机仍按旧逻辑回答，对着它验收会得出「改动没生效」。
- **根因**：宿主在启动时加载这些模块，进程内 ESM 缓存不会因为磁盘变了而失效。
- **数字**：不是延迟，是**零**——改的那份代码从未被执行。
- **判据**：**任何 `lib/*.js` 改动都要重启宿主再验收**；客户端 bundle 与 `package.json` 额外需要重启才会被扫到。

## 6 · 这份手册不保证什么

- **不量浏览器渲染**：`perf-budget.mjs` 只量服务端装配（`statTouchedFiles` + 载荷序列化）。客户端的重排、绘制、DOM 数量由 `test/checklist-panel.test.mjs` 与真机截图回答。
- **不量真实模型延迟**：摘要的 2.8 秒是历史实测，不是这个脚本量的；改摘要只验证「每回合至多一次调用」与缓存键，不验证模型响应速度。
- **不量并发**：单进程、串行测量。多个会话同时刷新时的争用没有覆盖。
- **基线是本机、Windows、热缓存**：换机器或冷缓存会变。判据是预算上限，不是这张表里的数字。
- **不替代 §4 的七条结构判据**：脚本只能看见它量的那三样；「帧里放载荷」「渲染期 stat」这类问题，脚本量不到，要靠结构判据在审查时看出来。
