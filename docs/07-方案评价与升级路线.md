# dsh-skill-evolve 方案评价与升级路线

> 面向插件作者和开发 agent：不是把更多能力装进插件，而是让每次沉淀可追溯、每次发布可撤回、每项升级都能证明净收益。

## 1. 阅读说明与核心判断

- 研究日期：2026-10-28；本地实现基线：`9e729cb`、`0.1.0`。
- 本文综合当前实现、仓库已有五份研究/设计文档，以及文末列出的一手规范、论文和工程资料。
- 文中严格区分三类信息：**现状**是代码或已有实验能支持的事实；**外部证据**是原资料在其特定实验条件下的结论；**建议**是本插件尚未实现、需要验证的设计。
- 外部研究并不证明本插件能获得相同收益。没有运行新的真实任务对照实验，也没有执行付费模型评估。
- 已确认代码问题与修复验收见 [代码审查与修改建议](06-代码审查与修改建议.md)。先完成其中的核心修复，再考虑本文升级。

**总体判断：现方案已经是一套有价值的“经验提案与技能治理”基础设施，但尚不是经过证明的持续自我改进系统。它的下一步不应是更积极地自动写技能，而应是更可靠地判断哪些经验值得写、在哪些场景有效，以及新版本是否真的优于旧版本。**

建议保留轻量、宿主内、人工可控的路线。优先级为：

```text
可信来源与授权
    → 不丢状态的版本化发布
    → 有对照的收益评估
    → 有边界的技能检索
    → 在证据支持时扩大自动化
```

不是：

```text
更多触发器 → 更多自动生成 → 更大的技能库 → 默认假定能力更强
```

## 2. 对当前方案的评价

### 2.1 它已经解决了什么

| 方面 | 评价 | 依据与边界 |
| --- | --- | --- |
| 提案入口 | 双触发比纯重复检测更完整 | 结构重复和回合反思覆盖不同信号，但仍依赖模型正确归纳 |
| 默认行为 | 默认 suggest 是合理选择 | 人工审核能限制写入，但当前审批绑定仍需修复 |
| 提示成本 | 对预算、稳定性、缩短有实际投入 | 不能从字符减少直接推出真实费用等比例下降 |
| 技能管理 | 已有修订、候选过期、反馈和排名 | 状态更新与阶段触发有缺陷，不能只看纯函数是否齐全 |
| 可发现性 | 压缩目录与本地搜索配套 | 关键词检索和截断描述的真实路由效果尚未量化 |
| 市场接入 | 审批绑定实际下载内容是正确方向 | 安装许可不等于执行许可，路径安全不等于内容安全 |
| 宿主适配 | 对服务生命周期、事件格式和客户端空间约束有研究 | 部分行为依赖宿主内部契约，需持续集成验证 |
| 效果验证 | 回放和回归测试证明了部分机制行为 | 没有证明生成技能改善后续独立任务 |

主要实现依据：[lib/index.js:451](../lib/index.js#L451)、[lib/index.js:541](../lib/index.js#L541)、[lib/hint.js:245](../lib/hint.js#L245)、[lib/catalog.js:220](../lib/catalog.js#L220)、[lib/search.js:154](../lib/search.js#L154)。

### 2.2 最大的断层：从“发生过”到“值得复用”

目前可以观察到的链路是：

```text
某个过程发生过
  → 模型写出说明
  → 引用命中会话文本
  → 人同意保存
  → 技能被加载若干次
```

它尚未等价于：

```text
提炼出的说明正确
  → 适用条件明确
  → 在独立任务上可复现
  → 比没有该技能更好
  → 收益超过检索、上下文、审核和维护成本
```

必须分开回答四个问题：

1. **来源真实**：引用确实来自那条记录吗？
2. **主张有据**：该记录能支持正文中的结论吗？
3. **技能有效**：依照它执行，任务能完成吗？
4. **技能有增益**：不用它也能完成时，它是否仍节省时间、费用或减少错误？

第一个问题适合确定性校验；第二个需要主张与证据对应及人工判断；第三个需要验证器；第四个需要对照实验。把四个问题合并成一个 `authoritative` 或 `confidence`，容易产生“看起来可信”的错觉。

### 2.3 哪些结论值得保留，哪些需要改写

**保留**：不自动改用户指令文件、不默认开 auto、不把没使用等同于没价值、不为几百个技能默认引入重型平台。

**改写为可检验假设**：

- “额外模型提炼必然更差”过强。现有集成失败只能证明那条路径有问题；昂贵的全会话二次提炼通常不划算，但对用户选中的高价值候选做受预算约束的审查可以评估。
- “单机无法独立验证”过强。单机也可以使用独立留出任务、隔离工作目录、确定性测试和盲评；它不能证明所有环境都有效，但能显著强于同一个模型自述“成功”。
- “3 次使用足以 active”“90 天足以 stale”“有害反馈权重为 4”都应明确为启发式参数，而非已经校准的概率模型。
- “压缩目录节省 X% 字符”是机制测量，不是检索质量或账单节省的完整证据。

## 3. 外部资料带来的有效启发

本节只抽取可迁移机制，不把外部项目整体搬进本插件。

| 来源 | 可核实的关键机制或结论 | 对本插件的启发 | 不能直接照搬之处 |
| --- | --- | --- | --- |
| Agent Skills 官方规范与评估指南 [S1–S3] | 技能采用渐进式加载；输出效果与描述触发可以分别评估；效果评估比较有/无技能或新/旧版本 | 对“选对技能”和“执行得更好”建两套测试；保持可移植制品格式 | 格式合法不代表质量合格；不同宿主对可选字段的支持不同 |
| Anthropic agent eval 工程指南 [S4] | 区分 task、trial、grader、outcome；组合代码、模型和人工评估，考虑运行波动 | 验证实际文件和任务状态，而不只检查模型说了什么 | 一套 grader 不可能覆盖全部开放式任务 |
| SkillsBench [S5] | curated skills 与自生成 skills 的效果不同；领域、模型和内容组织方式影响收益 | “模型能写技能”不能替代增益验证；优先精炼、针对任务的技能 | 其自生成条件不等于本插件的执行后沉淀，不能据此断言本插件必然无效 |
| Voyager [S6] | 可执行技能库、执行反馈与自我验证配合迭代 | 入库前后的验证比单次漂亮总结重要 | 原环境是 Minecraft，可执行代码与确定性环境比通用办公/编码任务更容易评估 |
| ACE [S7] | 把上下文视为可积累的 playbook，采用生成、反思、整理与增量更新，关注反复重写导致的信息丢失 | 修订可以是局部补丁；保留原条目和来源，不必每次重写整篇 | 不必引入完整多角色代理流水线；角色职责可由普通代码和人工审核承担 |
| XSkill [S8] | 区分任务级技能与动作级经验，通过整理与检索复用 | 不是每条有价值的教训都必须立刻成为技能 | 原方法包含多模态、多路径经验积累；轻量插件不应默认承担离线 rollout 成本 |
| Microsoft 记忆安全指南 [S9] | 持久记忆既是数据，也是影响后续行为的控制面；需要来源、授权、隔离、生命周期可观测性 | 对技能写入、检索和删除分别设边界；不要把持久化文本视为天然权威 | 单用户插件不必复制企业身份平台或安全运营系统 |

**最重要的新启发不是再加一个“反思 agent”，而是补齐来源、效果、版本和适用范围之间的关系。**

## 4. 推荐升级一：把证据从字符串变成可追溯记录

### 4.1 目标

从“这句话出现过”升级到“这条主张依据哪个事件、什么结果、什么环境”。这首先修复证据回显问题，也为未来的质量评估和故障追踪提供数据。

### 4.2 最小可行设计

保留现有提案工具，后台为每条引用生成稳定的来源记录。以下是建议的数据形状，不是当前已经存在的 API：

```json
{
  "candidateId": "candidate-42",
  "contentVersion": "sha256:...",
  "evidence": [
    {
      "sessionId": "session-a",
      "eventSeq": 217,
      "callId": "call-9",
      "sourceKind": "tool-result",
      "toolName": "bash",
      "quote": "12 tests passed",
      "normalizedQuoteHash": "sha256:...",
      "resultStatus": "succeeded",
      "claimIds": ["claim-tests-pass"]
    }
  ]
}
```

约束：

- 字段来自宿主事件，不信任模型自行声明的来源身份；不存在的信息标为未知，不伪造 seq、状态或时间。
- 同一条观察的多次转述仍是一条观察，不增加“独立证据数量”。
- 插件自己的总结、拒绝回显和候选预览可追溯到原始记录，但不是新的事实来源。
- `resultStatus` 表示工具是否成功完成；它不自动证明其输出命题为真，也不证明技能对整个任务有效。
- 对使用多个事件支持的主张，保存多个引用，不允许通过合并文本伪造单条逐字引用。

### 4.3 不要用第二个模型取代来源校验

第二个模型可以指出“引用只证明测试执行过，不能证明性能提升”，但不能代替事件定位、授权和内容哈希检查。把模型审查当作有成本、会出错的补充 grader，而非新的安全边界。

### 4.4 隐私与作用域

目前写入根目录是全局技能根，候选虽保存 workspace，却没有因此获得宿主级的强作用域隔离；见 [lib/index.js:240](../lib/index.js#L240)、[lib/tools.js:294](../lib/tools.js#L294)。

建议：

1. 审批时明确显示“项目内适用”还是“个人全局适用”，不要默认把某项目的路径和约束泛化为全局规则。
2. 优先使用宿主实际支持的项目技能 provider；若只添加 sidecar 的 scope 字段，必须明确它不自动限制宿主加载权限。
3. 只保留验证与审计必要的短引用；提案前检测明显凭据和敏感标识，供人确认。脱敏后的展示文本与来源校验应分开，避免脱敏后又拿它去做逐字匹配。
4. 对用户主动删除证据的请求提供可理解的处理方式，包括派生摘要和版本快照；不要以“永不删除技能”的产品原则阻止隐私删除。
5. 哈希用于完整性，不是匿名化，也不能证明原始内容真实性。

## 5. 推荐升级二：把技能发布看作一个小型发布流程

### 5.1 不可变内容与可变统计分离

建议区分：

- **skill identity**：同一逻辑技能的稳定身份。
- **content version**：正文、描述、适用条件、支持文件构成的内容摘要。
- **approval**：批准谁把哪个版本发布到哪个目标，是否已经消费。
- **observations**：哪个版本在什么任务中被加载、验证、评价。
- **user ranking**：pin/demote 等用户决定，不因普通内容更新消失。

这样既能保留总使用历史，也能避免旧版本的成功记录自动为新版本背书。旧版本被报告有害时，也不会永久把修正后的新版本当作完全相同的内容。

### 5.2 不再让一个 stage 承担所有含义

当前 `unverified/active/stale/inverted` 混合了使用频率、质量、时间和告警处置。建议逐步分离三个维度，不必一次引入庞大状态机：

| 维度 | 回答的问题 | 示例 |
| --- | --- | --- |
| 发布/授权状态 | 是否允许进入技能目录 | draft、approved、published、disabled |
| 验证状态 | 当前内容是否经过独立检验 | unmeasured、provisional、validated、regressed |
| 新鲜度 | 何时、在哪种环境验证过 | lastVerifiedAt、environmentFingerprint、compatibilityUnknown |

保留现有显示作为迁移投影即可。重要的是不要把“被加载三次”直接显示成“经过验证”。

### 5.3 最小发布协议

```text
提案并固定内容版本
  → 可选的验证报告
  → 人审核内容差异、适用范围和结果
  → 审批绑定该内容摘要
  → 检查目标基础版本与所有权
  → 发布并记录操作 ID
  → 确认宿主可见
```

- 模型在审批后改稿，需要新审批；跨会话处理仍可支持。
- 先支持单个技能的版本快照和恢复，不必先引入 Git 自动提交。
- 回滚恢复的是已知内容，不应粗暴回滚累积的用户反馈或最新权限设置。
- 恢复前校验当前目标是否仍是本插件管理、是否被人另行编辑。
- 一次用户拒绝可以记录为“过于具体”“已有技能覆盖”“证据不足”等结构化原因，但只有明确拒绝才是负反馈，沉默不是。

### 5.4 JSON 还是 SQLite

**近期建议：保留 JSON，先修正确的临界区与恢复语义。** 不要为了一个状态回退 bug 先做整个存储迁移。

出现以下需求后，再评估 SQLite：

- 需要同机多个宿主并发写入。
- 版本、审批、观察之间需要可靠唯一约束和事务查询。
- JSON 全量读写已成为测量到的瓶颈。
- 已经愿意承担备份、迁移、诊断和恢复工具的维护成本。

SQLite 可以把数据库内的关联更新放入事务，但 **不能自动把外部技能文件写入也纳入事务**。若采用它，应先提交带操作 ID 的发布意图，再幂等生成制品并记录完成，重启后对未完成操作进行可解释的恢复。不能宣称“一加 WAL，跨文件问题就消失”。

WAL 仍只有一个 writer，要求同机共享内存，不适合把数据库放在跨主机网络共享目录中 [S11]。本项目声明 Node >=20，见 [package.json:15](../package.json#L15)；选择 SQLite 接口时还需检查运行时和打包兼容性，不能因为当前机器 Node 较新就使用所有宿主都没有的 API。

另外，现有账本超过大小上限会裁掉旧行，见 [lib/store.js:115](../lib/store.js#L115)。如果增加版本回滚，不应假定今天的日志足以从零重建全部历史。

## 6. 推荐升级三：建立“技能净收益”评估，而不只统计使用次数

### 6.1 两套评估必须分开

**A. 路由评估：应该加载时是否加载，不应该加载时是否保持安静。**

官方描述优化指南讨论了正例、近似负例和留出查询 [S3]。可从 20–30 条人工检查过的查询起步，包含中英文表达、近义词、边界条件和明确不适用场景。

**B. 效果评估：加载后实际结果是否更好。**

官方技能评估指南建议有技能/无技能或新版本/旧版本对照，记录输出、时间和 token [S2]。只测试触发率，会优化出“什么任务都想接”的描述；只测试已经手动加载后的执行，会掩盖技能根本选不中的问题。

### 6.2 最小实验方案

选择 10–20 个真正会复现、可安全重跑的任务族，数量只是启动规模，不是证明效果的充分样本量。每个任务族保留开发样本和独立测试样本。

初始主对照：

| 条件 | 含义 | 回答的问题 |
| --- | --- | --- |
| A | 无该技能 | 原模型本来能做到什么 |
| B | 一条短提醒 | 是否只需要一个提示，而不是完整技能 |
| C | 当前插件生成并批准的技能 | 完整技能的边际收益 |

对于修订任务，优先比较“旧版本 vs 新版本”；人工精炼版可以作为第二阶段参考，不必首次就运行所有组合。

执行约束：

- 固定模型版本、宿主版本、工具集合和起始文件状态，并记录这些条件。
- 用全新上下文和隔离目录，防止前一次答案、记忆或技能泄漏到基线。
- 同一任务的条件顺序随机化；必要时重复运行，例如每条件 3 次。3 次仍不是统计显著性的保证。
- 提案产生的会话与最终效果测试任务分开；同一仓库同一解法的小变体也可能泄漏，应尽量按任务族划分。
- 开发集可以用于改写技能，留出集不能反复用来调提示。保留最终未见样本。
- 涉及外部发布、真实账户、删改用户文件的任务先不纳入自动重跑。

### 6.3 验证器如何选择

优先级建议：

1. 确定性结果：编译/测试结果、结构化输出、文件内容、行数与业务约束。
2. 环境状态：是否真正修改了目标，是否产生越界副作用。
3. 盲评或人工评价：开放式解释是否有用、风格是否合适。
4. 模型评分：补充难以程序化的部分，记录评分依据及不确定性。

**不要以“出现 completed 字样”“模型声称完成”“skill 工具被调用”作为任务完成判据。** 也不要让生成技能的同一次模型调用同时生成唯一标准答案并给自己打分。

技能包自带的验证脚本同样是代码执行输入。市场来源或新生成的脚本先审核，在隔离环境中运行；不得因为文件名叫 test 或 verifier 就绕过宿主审批。

### 6.4 建议的指标

| 指标 | 用途 | 常见误读 |
| --- | --- | --- |
| held-out task success rate | 独立任务完成比例 | 不等于某条技能的因果贡献 |
| success delta | 有技能相对基线的变化 | 小样本差值可能只是波动 |
| route recall / false activation | 选中正确技能与误触发情况 | 提高触发率不一定提高效果 |
| token、延迟和总费用差值 | 衡量使用收益 | 字符数不能代替缓存后账单 |
| 审核耗时与拒绝原因 | 记录用户负担和提案质量 | 接受率高不必然是技能更好 |
| regression count | 新版本是否破坏旧能力 | 只测新增场景会漏掉回退 |
| unsupported-claim rate | 检查正文超出来源的结论 | 有引用不意味着正文全部受支持 |

可用下面的概念式做决策，不要把它包装成已校准的精确分数：

```text
预期净收益
  = 后续复用所节省的成本与错误损失
  - 提案、验证、审核、检索、上下文和维护成本
```

若没有足够复用数据，就明确显示“尚未验证净收益”。不要为了让仪表盘完整而把缺失数据填成零。

### 6.5 两类变异测试

现有项目已经对 bundle 和测试锚点做过变异工作，不应把“增加变异测试”冒充全新想法。下一步是把同样的思想用在两个不同对象上：

- **软件变异**：移除审批哈希检查、让旧响应写状态、让计数覆盖，测试应失败。
- **技能内容变异**：删掉关键验证步骤、反转一个条件、去掉失败场景，效果评估应能检测退化。

两者都通过时，才更有理由相信既验证了插件，也验证了插件产出的技能。

## 7. 推荐升级四：从“每条教训一个技能”走向有门槛的整理

这是受 XSkill 的经验/技能区分 [S8] 和 ACE 的增量整理 [S7] 启发的建议，不是要求新增通用长期记忆平台。

### 7.1 先判断知识形态

| 观察 | 更合适的承载形式 |
| --- | --- |
| 某次任务的临时进度、绝对路径 | 不应成为长期技能 |
| 用户明确的长期协作偏好 | 由宿主相应偏好/指令机制处理，需尊重授权 |
| 某版本依赖的具体坑 | 项目范围、带版本条件的经验或已有技能补丁 |
| 多步骤、可参数化、可验证的重复过程 | 独立技能 |
| 已有技能缺失的反例或前置条件 | 修订已有技能，而不是再造一个近义技能 |

不要自动编辑 AGENTS 或其他用户指令文件。这里的分类用于提示和审核，不授予插件新的写权限。

### 7.2 用现有候选队列做“经验待观察区”

比新建全套记忆系统更小的起点：

1. 候选增加明确的观察类型、适用范围和相关技能。
2. 单条经验先保留为待审核记录，不立即进入全局可加载目录。
3. 新会话出现相关独立证据时，可以建议合并或修订。
4. 展示“为什么现在值得升级为技能”：重复需求、稳定步骤、验证结果或用户明确要求。
5. 没有复用迹象就继续安静，过期只影响可审批性，不偷偷删除用户数据。

这不是把所有候选都永久存下来的理由。候选原始证据要有保留策略，队列上限不能只限制 live 项而完全不考虑累计存量。

### 7.3 增量修订优于反复整篇重写

提案可以直接描述：

- 增加一个适用条件。
- 修正一个命令参数。
- 添加一个失败案例。
- 替换一个已经过时的验证步骤。

审核界面展示最小差异、对应来源和受影响的测试。底层仍输出完整技能文件，保持宿主兼容；“增量”是修改和审核协议，不是要求宿主支持特殊补丁格式。

也不要把所有旧内容无条件保留。若旧步骤已被证据否定，应明确修订并保存历史版本，避免正文随着历史解释无限增长。

## 8. 推荐升级五：先改进低依赖检索，再决定是否需要向量化

### 8.1 当前最值得验证的缺口

[lib/search.js:154](../lib/search.js#L154) 使用宿主技能快照，避免自己遍历目录后与宿主遮蔽规则不一致，这是应保留的选择。

但当前关键词排名、有限正文读取和目录描述压缩不能保证：

- 中文需求能找到英文描述的技能。
- 名称很像、适用条件相反的技能不会混淆。
- 只在正文后部命中的技能能进入有限读取预算。
- 40 个以上技能退化到名字列表后，模型仍能主动调用搜索。

### 8.2 低成本优先顺序

1. **补路由信息**：短而明确的描述、人工确认的中英别名、正例和近似负例。
2. **词法改进**：更合理的分词和字段加权；必要时引入本地全文索引，不先部署远端向量数据库。
3. **应用范围过滤**：在权限和宿主 provider 允许的范围内，优先项目、环境兼容和当前任务相关项。
4. **候选解释**：展示匹配在哪些字段、为何被降权、是否版本过期。
5. **最后再做混合检索实验**：只有留出查询表明确证实词法召回不足时，试小型本地 embedding 与词法融合。

Embedding 不能替代作用域限制、审批或来源校验。它更擅长找相似项，不擅长判断相似技能是否适用。

### 8.3 目录策略也需要对照

比较以下三个策略，而不是直接宣布 top-k 更先进：

- 完整目录。
- 当前压缩目录 + 搜索。
- 稳定的轻量目录 + 小块相关技能提示 + 可发现的搜索入口。

保持宿主权威的 `source.entries` 和 provider 决策；任何选择性展示都不能偷偷把技能标成“不可用”，也不能因改写导致宿主不断重发目录。

在 40/200/500 技能规模下记录触发召回、误加载、总上下文、费用和延迟。小库可能完整目录最好，不必为了架构统一牺牲简单场景。

## 9. 不应忽视的辅助系统：面板、摘要与真实成本

面板有价值，但不能成为与核心进化无关的无限模型调用源。

### 9.1 推荐的读取模型

```text
回合结束形成有界快照
  → 按明确策略创建一个摘要任务
  → 记录 pending/succeeded/failed 与尝试预算
  → 面板读取已有状态
```

也可以保留首次打开面板时惰性触发，只要重复 GET 不会无限制造新付费工作。多窗口可以共享同一轮任务，但跨会话不能共享错误的展示状态。

### 9.2 摘要不应反过来成为独立事实依据

摘要是压缩后的解释，不是新的观察。尤其当前产出列表曾把编辑尝试当成成功，更需要保证：摘要引用原始事件时不提升其信任等级；摘要的同一句话不因被另一个工具读出就算第二条证据。

### 9.3 重新衡量“缓存友好”

Claude Code 文档区分 cache creation、cache read 和普通输入统计 [S10]。这是特定产品/供应商的实例，不能直接假定所有 DSH provider 一样。

本插件应记录宿主实际可提供的 usage、路由及计费条件。评估提示缩短时，同时观察：

- 输入、输出、缓存写入和缓存读取 token。
- 首次请求与后续复用的区别。
- 哪一层动态内容变化，是否影响既有前缀复用。
- 技能被选错后的重试成本。
- 摘要、检索和离线评估额外调用。

真正的结论可能是“字符更少但误加载更多”，也可能是“多留一行适用条件反而降低总成本”。应接受实验推翻直觉。

## 10. 制品格式、模块边界与宿主兼容

### 10.1 兼容 Agent Skills，但不盲目迁移字段

官方规范以 `name` 和 `description` 为基础，并支持 `metadata`、`compatibility` 以及 scripts/references/assets 等结构 [S1]。当前自定义 frontmatter 足以服务本宿主，但不是完整的跨宿主互操作保证。

建议：

- 先做导出验证，检查标准要求和宿主实际解析能力。
- 若把自定义生命周期字段搬入 metadata，必须同步升级解析器并测试已有技能，不能只改序列化一端。
- 默认保留少量、任务相关的说明，把长参考材料放入按需加载资源；不机械规定“文件越短越好”。
- 外部技能允许工具字段是否生效由宿主决定；它不能替代本插件或宿主的真实执行授权。

### 10.2 代码拆分应服务于可测试边界

主入口目前同时承担事件、审批、生命周期、面板等编排。建议在核心修复过程中逐步形成清楚的职责：

- 事件来源解析。
- 候选与审批服务。
- 技能版本发布与状态更新。
- 面板快照和摘要任务。

不要求创建一套通用事件总线、工作流引擎或插件框架。保留现有纯函数模块；消除工具反馈与命令反馈的行为分叉，比机械减少文件行数更重要。

### 10.3 宿主升级的契约测试

至少覆盖：真实服务注入限制、迟到的 webServer、tool/call 与 tool/result 的关联、命令返回协议、技能 provider 遮蔽、目录摘要计算方式、会话恢复和销毁。

纯 mock 可以证明逻辑，却不能证明宿主没改协议。也不要因为本地缺依赖而让关键集成 skip 从汇总中消失。

## 11. 方案对比与推荐路线

| 路线 | 收益 | 成本与风险 | 建议 |
| --- | --- | --- | --- |
| A：修补现有流程，保留 JSON 和人工审核 | 最快降低真实错误，投入小 | 不直接证明技能有效 | 立即做，作为其他路线前置 |
| B：版本化发布 + 来源记录 + 小规模对照评估 | 同时提高可信度、可回滚性和收益可见性 | 增加数据建模与测试负担 | 最推荐的中期方向 |
| C：大规模跨会话整理 + 混合检索 | 在较大库和重复任务中可能更有价值 | 去重、隐私、维护和评估成本上升 | 以路线 B 的测量结果决定 |
| D：全自动多 agent 提炼、重写、自评与发布 | 自动化程度高 | 成本、自评偏差、污染传播和维护复杂度都高 | 现在不推荐 |
| E：向量库、分布式记忆或强化学习平台 | 可能服务于不同规模的问题 | 偏离当前本地轻量插件目标 | 没有明确需求和证据前不做 |

### 阶段 0：可靠性基线

- 完成第一份文档中的 P1 修复以及关键 P2。
- 输出：能够复现旧错误的回归测试、明确的 mode/审批/状态语义、真实宿主验证记录。
- 通过条件：不再发生已确认的回显自证、审批换稿、计数回退、无限重试。

### 阶段 1：可追溯版本与最小评估

- 加入版本摘要、来源引用、批准对象和单技能回滚。
- 从少量高频、可验证任务开始 A/B 或新旧版本对照。
- 输出：每个被试技能的版本、测试条件、任务结果、成本和审核结论。
- 通过条件：数据能够支持继续投资的判断；结果不佳也应如实报告。

### 阶段 2：低依赖检索与经验整理

- 中英别名、近似负例、任务族留出测试。
- 基于真实拒绝原因与复用记录，区分新技能、修订和不值得沉淀。
- 输出：路由基准、误触发样本、合并/修订建议。
- 通过条件：在不增加错误使用和总成本的前提下改善发现能力。

### 阶段 3：条件式自动化

只在前两阶段有明确收益时讨论，而不是默认终点：

- 用户明确授权的范围内，自动整理候选或自动运行已经审核的只读验证器。
- 自动生成低风险候选与自动发布是两种不同权限。
- 修改长期指令、可执行脚本、外部访问或破坏性操作相关内容仍需要明确审核。
- 内容分类器只能辅助判断风险，不能成为唯一授权依据。

## 12. 暂缓事项与可证伪假设

### 暂缓事项

- 不先做大型向量基础设施，先证实词法检索在哪些样本失效。
- 不先增加第三个、第四个反思 agent，先量化它们能发现多少现有校验发现不了的问题。
- 不自动改 AGENTS、不扩大技能执行权限、不因实验方便绕过审批。
- 不把全部会话复制到长期经验库；保留最小必要证据。
- 不拿更多生成数量、更多调用次数、更多绿色测试当作能力提升的替代指标。

### 值得用小实验回答的问题

| 假设 | 最小实验 | 什么结果会推翻它 |
| --- | --- | --- |
| 完整技能比一行提醒有价值 | 同任务族比较短提醒与技能 | 正确率相同，技能成本更高 |
| 目录压缩是净收益 | 完整目录 vs 当前压缩策略 | token 下降，但误加载和重试抵消节省 |
| 自动提案值得用户审核 | 记录审核耗时、拒绝原因和后续复用 | 大部分提案不复用，审核负担持续上升 |
| 同义词扩展优于引入 embedding | 留出查询上比较词法增强与混合检索 | 词法仍显著漏掉关键技能且成本优势不足 |
| 负面反馈能指导修订 | 把反馈关联版本与实际失败样本 | 反馈无法复现或指向的是环境变化而非技能错误 |

实验结论可以是“不增加这一功能”。让插件学会安静地不写，也是一种进步。

## 13. 给开发 agent 的设计提醒

1. **技能越权往往发生在阶段之间。** 不是某个字段没校验，而是提案、批准和发布的对象悄悄变了。
2. **自我进化需要不同性质的证据。** 模型提出假设，代码验证机械事实，人决定授权，独立任务衡量增益；不是多叫几个模型互相同意。
3. **最有价值的新功能可能是更好的拒绝。** 能准确指出“这条经验只适用于当前项目”“已有技能只需补一个条件”，比生成另一个近义名字更有用。
4. **版本历史不是为了做漂亮时间线。** 它让我们知道一次失败来自哪个版本、能否恢复、哪些旧结论不再适用。
5. **指标应该帮助推翻设计。** 如果系统只能证明自己很活跃，不能证明自己值得保留，它还没有完成进化闭环。

## 15. 最终建议

选择路线 B，但从路线 A 的修复开始：先建立可追溯、可授权、可回滚的技能版本，再用小而独立的任务证明收益。只有当数据说明更积极的整理、检索或自动化确实有价值时，才增加相应复杂度。

真正的升级目标不是“让 agent 更容易写出技能”，而是“让未来会话更少重复失败，同时让用户始终知道哪些内容被记住、凭什么被相信，以及如何撤回”。
