## 二、现成方案能不能直接用

### 2.1 `csyangwen/dsh-memory-evolve` ★422 —— 能力最全，但和本机冲突

**它已经做到的**（读 `lib/review.js`、`lib/skills.js` 源码确认，非 README 转述）：

- 主模型自审，`agent/turn-stopping` 计数，每 `reviewInterval` 轮触发
- 计数器**永不自动清零**，只有 `memory_review_status complete` 才归零
- 技能走 pending 队列：`<memoryDir>/pending-skills/`，用户在面板批准后 move 进正式目录
- `patch` 要求先读后改（`hasReadSkill` 门禁）
- 技能管理面板、技能目录浏览、禁用/编辑
- 快照注入用静态文本，不击穿 prompt cache

**不能直接用的三个原因**：

1. **和已装的 `@michengai/dsh-skills-manager` 1.2.8 撞车**。它的 README 明写：「原独立插件 dsh-skills-manager 已合并进本插件，旧插件用户升级前先按安装文档卸载旧插件」。两个插件都注册 `settings.section` 面板、都管技能目录。
2. **它是个巨型插件**（228 个文件）。除了记忆和技能，还塞了待办、无限画板、COI 调度、会话广播、会话评审、通知、搜模型、搜本机会话……**用一个 228 文件的插件换一个技能提炼功能，代价过高**，任何一个子系统出问题都会连坐。
3. **版本面向旧宿主**。`lib/review.js` 里有一大段注释在适配 `DSH 0.1.2-alpha.4+` 的 `Session` 不再暴露 `.events` 的问题（`ownEvents?.() ?? .events ?? []`）。本机是 `0.2.1-rc.2`。

> **结论**：它是**绝佳的参考实现**，不是合适的安装目标。

### 2.2 两个 `dsh-skill-forge`

| | `necos98/dsh-skill-forge` | `@dsh-cortex/dsh-skill-forge` |
|---|---|---|
| 触发 | 工具名重复序列（无 LLM 成本） | 每 10 个用户回合 fork 子 agent |
| 人审 | ❌ 政策文本明确"不问人" | ✅ 只有面板「入库」按钮 |
| 落地 | `.agents/skills/<name>/SKILL.md` | 技能 + 经验 + USER.md |
| 硬伤 | peer 锁死 `0.2.0-rc.2`，本机 `0.2.1-rc.2` 判不兼容 | 作者本机 `disabled: true`，多项未实机验证 |

**`necos98` 的"工具名重复检测"值得单独抄**（§4.3），但它的**"不问人直接写"与本需求相反**——用户要的是"能挑"。而它的版本锁死意味着安装要走版本豁免，那是显式风险接受。

**`@dsh-cortex` 的设计（暂存人控入库）方向是对的**，但作者自己都禁用着，且 fork 子 agent 天然丢上下文。

### 2.3 `@michengai/dsh-skills-manager` 1.2.8（已装）

- 模型侧只有 **一个**工具：`create_skill`（`lib/index.js:316`），name/description/body → 写 `SKILL.md`
- 有一层门禁：`tools/pre-execute` 钩子返回 `{kind: "ask", reason: "Create a new skill under DSH_HOME/skills"}`（`lib/index.js:343-346`）——即**每次调用都会弹给用户确认**
- ClawHub 检索**存在但只走 Web 路由**：`/api/dsh-skills-manager/catalog/search`、`/clawhub/search`、`/skills-sh/search`。模型调不到。

**它的边界很清楚**：
- ✅ 覆盖 B（建档）——但需要用户主动说"存成技能"
- ❌ 覆盖不了 A（不会自己想起来该存）
- ❌ 覆盖不了 C（检索能力锁在 UI 里）

> **这就是用户最初痛点的精确位置**：不是"建不了技能"，是**"想不起来该建"**。

## 三、宿主能力核实（决定能不能做）

全部从 `F:\DSH\resources\app.asar` 内的 `dsh/node_modules/@deepseek-ai/` 提取确认，非推测。

### 3.1 技能注册 `ctx.skills`

`dsh-skill/lib/index.js` 里的 `SkillRegistry` 方法全集（正则扫描确认）：

```
register, registerProvider, list, get, resolve
```

**`registerProvider(create)` 签名**（源码注释原文）：

> Register a borrowed same-process provider synchronously during plugin apply, **into the calling context's layer**: a scoped context (**an agent preset's standing mount**) registers **for that scope alone**, an unscoped context registers **globally**. Duplicate names within one layer and reserved names throw; remote initialization belongs in `list()`. **Fiber disposal unregisters the provider and invalidates catalog caches.**
>
> @returns the exact Cordis effect disposer that unregisters this provider

`create` 收到的 `control` 对象：`{ signal: AbortSignal, invalidate: () => void }`。provider 必须有 `name`（`runtime` 是保留名，用它会抛错）。

**这条注释直接回答了"会话级技能能不能做"**：
- 注册落在**调用上下文的 scope 层**
- 某个 scope 的注册**只对该 scope 生效**
- **fiber dispose 自动注销**

所以**技术上可做**：在某个会话/预设的 scope 内注册临时技能，会话销毁即失效。但**前提是插件能在会话作用域内执行注册**——这需要确认能否拿到会话级的 cordis 上下文，而非插件 apply 时的全局上下文。**这是本方案唯一未验证的技术点**（见 §6.1）。

`register(skill)` 用于内存态技能，`validateRuntimeSkill` 的必填项（源码）：

```js
if (!SKILL_NAME.test(skill.name)) throw new Error(`invalid skill name "${skill.name}"`);
if (skill.description.length === 0) throw new Error(`skill "${skill.name}" requires a description`);
validateInvocation(skill.invocation, `runtime skill "${skill.name}"`);
```

> **同名 runtime 注册在一个层内是"先到先得 + 警告"**——不是覆盖。

### 3.2 动态上下文注入 `ctx.systemPrompt`

方法全集：`section`, `getSectionOrder`, `getContextOrder`, `context`, `suppressRuntimeContext`, `tools`, `variable`, `refreshContext`, `assemble`。

`context(context)` 的注释：

> Register ordered dynamic context **in the calling context's scope**. **Scoped entries shadow global entries with the same name.**

`CONTEXT_ORDERS` 里有 `WORKING_DIRECTORY: 100`、`SANDBOX_POLICY: 110`、`APPROVAL_POLICY: 115`、`SUBAGENT_DELEGATION: 120`、`TEAM_IDENTITY: 125`。

**关键约束**：`refreshContext` 会在**每个 step 重新解析**上下文 provider。这意味着：
- ✅ 可以注入"当前有哪些待审技能"
- ⚠️ **注入内容一变，prompt cache 就废**

> **设计结论**：注入的必须是**静态文本**（"每轮结束检查一下有没有值得沉淀的经验"），**不能注入待审技能列表**。列表要靠工具去查。这正是 `dsh-memory-evolve` 的做法。

### 3.3 工具定义 `defineTool`

`dsh-tools/lib/index.js` 导出（确认）：

```
CodeRunFailedError, JsonSchemaError, RUN_CODE_NAME, TOOL_ABORTED, TOOL_ABORTED_BEFORE_DISPATCH,
TOOL_RUNTIME_SCHEDULER, ToolArgsError, ToolNotFoundError, ToolOutputError, ToolRuntime,
assertObjectJsonSchema, assertSupportedJsonSchema, defineContentToolFixture, defineTool,
jsonSchemaToPy, jsonSchemaToTs, parameterSchemaSpecToJsonSchema, renderToolsSdk, renderToolsSdkPy,
validateArgs, validateJsonSchemaValue, valueSchemaSpecToJsonSchema
```

`defineTool(options)` 签名要素：`name`、`description`、`parameters`、`output.schema`、`execute`、可选 `timeoutMs`（必须正有限数）、`finalizeContent`、`presentCall`、`presentResult`、`isConcurrencySafe`。

### 3.4 客户端面板

已装 `@michengai/dsh-skills-manager` 的 client 半部分（扫描确认）：

```js
t.slots.inject("settings.section", ...)
t.slots.register({ name: "settings.section", id: "skills-manager", order: 25, label, icon: "skill", locale })
```

即：client 侧 `inject: ["slots", "locale"]` + 注册 `settings.section` 插槽。宿主侧走普通 HTTP fetch 到 `webServer` 注册的 `/api/` 前缀（`rpc|bridge|ipc|invoke(` 全部无命中，**不是自建 RPC 通道**）。

### 3.5 版本豁免机制（绕开 peer 精确锁）

`dsh-app-boot/lib/index.js`：

```js
function evaluatePluginCompatibility(manifest, exemptions = {}, runtimeVersion = getDshRuntimeVersion()) {
  const fields = objectOf$1(manifest, "Plugin manifest");
  const requirements = unmetRequirements(fields, runtimeVersion);
  if (Object.keys(requirements).length === 0) return void 0;
  const key = `${name}@${version}`;
  return { name, version, runtimeVersion, requirements,
    exempted: (Object.hasOwn(exemptions, key) ? exemptions[key] : void 0)?.includes(runtimeVersion) === true };
}
```

`installable(compatibility) => compatibility.compatible || compatibility.exempted`。

> **对本项目的意义**：如果参考 `necos98` 把 peer 写死，本机能装但需豁免。**自研时不要写死 peer 版本**，用范围。

## 四、要做成什么样（功能需求清单）

按 P0/P1/P2 分级。**P0 是"没有它功能就不成立"，P1 是"没有它体验不成立"，P2 是"锦上添花"。**

## 六、未验证的技术点与风险

### 6.1 会话级作用域（唯一阻塞项）

`registerProvider` 的注释说"a scoped context (an agent preset's standing mount) registers for that scope alone"，且"fiber disposal unregisters"。

**已验证**：层机制存在，作用域注册语义存在，dispose 会注销。
**未验证**：**插件在运行时能否拿到某个会话（agent）的 cordis 上下文**并在此注册。

如果不能：
- 退路 A：不做"会话级临时技能"，只做"待审队列 + 人审落盘"（**砍掉 F 里关于会话级的部分，其余不受影响**）
- 退路 B：注册到 preset 层，靠预设切换模拟作用域

> **这个点决定"临时技能随会话消失"能否成立。** 建议在动工前用 30 行探针验证，不要拿整个方案赌。

### 6.2 风险清单

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| **提炼质量不稳定** | 高 | 用户失去信任 | 默认全审；不承诺覆盖率；Qoder 同款免责表述 |
| **LLM 去重判定不稳** | 中 | 重复技能堆积 | 用 `description` 相似度做**参考**，最终人来判 |
| **提示词污染** | 中 | 技能多了以后系统提示词被稀释 | F5 淘汰机制；技能 `description` 强制简短 |
| **"自进化"名不副实** | 高 | 期待落差 | 文档明确：这是"笔记本 + 签字"，不是自主进化 |
| **第三方技能注入风险** | 中 | 陌生文本进系统提示词 | F6.3 绝不自动安装 |
| **与已装 skills-manager 面板冲突** | 中 | 两个技能面板 | 先不做 F7 |

### 6.3 工作量估算

| 阶段 | 内容 | 估时 |
|---|---|---|
| P0 探针 | 验证 §6.1 会话作用域 | 0.5 天 |
| **P0 核心** | 节奏器 + 主模型自审 + 待审队列 + 命令行批准 | **1 天** |
| P1 | 写前校验、归属标记、分级采纳、使用计数 | 1 天 |
| P1 | 外部检索（F6） | 0.5 天 |
| P2 | 面板 | 2 天 |

> **最小可用版本 = P0，约 1.5 天。** 面板占总工作量 60% 以上，建议最后做或不做。

## 七、最终建议

### 立即可做的两件事（不用写代码）

1. **先用现成的心态把痛点降一半**：本机已装的 `create_skill` 能用，问题只是"想不起来"。可以在 `AGENTS.md` 里加一条规则——"任务结束时，如果用了可复用的多步流程，问用户要不要存成技能"。**零成本，立刻生效。**
2. **装 `dsh-skill-hub` GitHub main 1.0.0 补齐 C**（如果外部检索是高频需求）。但注意它和已装 skills-manager 的功能重叠。

### 该不该自研

**如果只想要 A+B：不值得。** 加一条 `AGENTS.md` 规则 + 现有的 `create_skill` 就能覆盖 80% 的价值，自研要花 1.5 天换剩下的 20%。

**如果想要 A+B+C+淘汰：值得，但要先验证 §6.1。** 因为矩阵里没有第二个方案同时有 C 和淘汰机制，而这两个恰好是"用一段时间以后"才暴露的痛点。

### 一句话

> 这不是"自进化"，是**给 agent 加了本笔记本，并要求你签字**。把它当笔记本设计（好写、好找、好撕），不要当大脑设计（自动、自主、自动变强）。
