# 15 · 上一轮总结卡优化建议

> 对照对象：Qoder 0.5.7 的「任务回顾」（recap）。
> 本文只分析**现有「上一轮」卡**该怎么改，不涉及复刻 Qoder 其它模块。
> 只读逆向，未改动任何代码。

## 结论摘要

一句话：**本项目的摘要「写什么」不差，「怎么延续、怎么显示失败」差得远。**

| 维度 | Qoder recap | 本项目「上一轮」 | 判断 |
| --- | --- | --- | --- |
| 生成单位 | 会话级一条，随进展增量更新 | 每轮一条，互相独立 | **本项目弱**：长会话里前后不连贯 |
| 上下文 | 上次 recap + 最近 6 条消息 + 会话标题 | 本轮完整 transcript（截 6000 字） | 各有取舍，见 §2 |
| 长度 | 目标 150–190 字，上限 220 字 | 最多三句，上限 400 字 | 本项目偏长 |
| 输出格式 | 强制 JSON，本地清洗兜底 | 纯文本，只 `trim()` | 各有取舍：不要 JSON，但缺清洗（见 §5.1） |
| 语气约束 | 14 条 systemPrompt，含人称/周报体禁用 | 3 条（不要开头、不要列表、要诚实） | **本项目弱** |
| 提示词版本 | `prompt_version` 入库存档 | 无版本概念 | 改提示词后旧缓存仍命中 |
| 失败展示 | 卡片直接不出现 | 直接把英文 `reason` 显示给用户 | **本项目错**：`the model call failed: ...` 会出现在中文界面上 |
| 更新时间 | 卡片上显示「更新于 {{time}}」 | 完全不显示 | **本项目缺**：用户无法判断摘要是否陈旧 |
| 生成时机 | 后台定时预生成，UI 永不等待 | 拉取时现算，**首开最长等 20 秒** | **本项目弱**：见 §5.7 |
| 折叠 | `line-clamp-7` + 整条底部展开热区 | `max-height:9.3em` + 卡片点击 | 本项目更省空间，Qoder 更易点 |

## 一、Qoder 的 recap 到底在做什么

### 1.1 它不是「本轮总结」，是「会话进度条」

这一点是最容易被忽略的差异。Qoder 的 recap：

- **按会话存一条**，主键是 `session_id`（`chat_session_recaps` 表），不是按轮次存多条。
- 每次生成**把上一条 recap 一起送进提示词**，要求模型「接着写」而不是「重新写」。
- 提示词里有一条硬规则：

  > If a previous Recap is provided and there is no meaningful new information, return it unchanged.

  也就是说，没有新进展时**不消耗一次改写**，原样返回。

所以它天然是连贯的：第 20 轮看到的文字，是第 1 轮那段文字被逐步「续」出来的。

本项目的「上一轮」是第 N 轮独立生成，第 20 轮和第 19 轮之间没有任何继承关系。会话越长，两张相邻卡片越像两个不同的人写的。

### 1.2 完整 systemPrompt（14 条，已从混淆字符串表解出）

```
You are writing a brief session Recap for the Qoder task monitor.
Return only a JSON object: {"recap":"..."}, without code blocks or additional explanation.
Use the primary language of the current conversation for the Recap. Write a single plain-text paragraph, without a heading, prefix, list, or Markdown.
Quietly follow a piece of work as it moves forward, remembering what the user truly cares about, what has changed, and the loose ends that remain.
Leave a short note for someone temporarily away from the task so that, when they return, they can quickly recall why this work is being done, what just happened, and what deserves the most attention now.
Speak naturally, like someone familiar with the user. Keep the tone light, brief, sincere, and helpful, as if handing a thread of this work back to the reader.
Do not write a daily progress report, product summary, operation log, retrospective conclusion, weekly report, list of conclusions, or customer-service script.
You may address the reader directly as "you". Do not use an observer's perspective such as "the user", "he/she", or "this session".
Prioritize what is being worked on now and the latest progress. Small but real steps forward matter more than vague summaries.
You may naturally stop at an unresolved judgment, a blocker, or the next point worth picking up, but do not urge, arrange, or manage the reader's next steps.
Ignore tool noise that did not change the outcome. Do not invent completed work, files, tests, or decisions.
Use at most 220 characters, preferably 150 to 190 characters.
If a previous Recap is provided and there is no meaningful new information, return it unchanged.
When context is insufficient, summarize only facts that can be confirmed.
```

值得抄的四条（后文 §3 会再提）：

1. **「像熟人说一句话，不像周报」**——它用 4 条负面清单（不要日报、产品总结、操作日志、复盘结论）把事情说清楚。
2. **人称规则**——直接对「你」说，禁止「用户」「他/她」「本会话」这种旁观者视角。
3. **「忽略没有改变结果的工具噪音」+「不要编造」**——这两条合在一起，是防止摘要变成「我跑了 8 个命令、改了 3 个文件」的关键。
4. **「小但真实的进展比笼统概括更重要」**——这条直接决定摘要的信息密度。

### 1.3 用户提示词的骨架

四段拼装，字段顺序固定：

```
Session title: <会话标题>
Context source: Bounded message material and the previous Recap
Previous Recap: <上一条 recap，截 200 字；没有则 (none)>
New material: <最近消息，每条截 600 字、总长截 4000 字>
```

「New material」的取法有两种：

- **有覆盖点时增量**：从上一条 recap 覆盖到的 `covered_message_id` 之后取，最多 **6** 条。
- **没有覆盖点时**：取最后 **6** 条。

注意只有 6 条。不是整段 transcript，就是最近 6 条消息。这是它能把摘要写得「像刚发生的事」的原因——它只看刚才发生了什么，历史压缩在 previousRecap 那一行里。

### 1.4 生成时机与去重

- **首次延迟 12 秒**，**后续增量延迟 35 秒**。用 `setTimeout` 排队，不是回合结束立刻跑。
- **消息数阈值 3**：`coveredMessageId < 3` 时直接跳过，不为刚开始的会话生成。
- **去重键** = `promptVersion + ":" + sessionId`。同一个键且不需要带历史时，直接 return，不重跑。
- **失败不写库、不重试**，只上报埋点 `{sessionId, model, incremental, durationMs, errorKind}`。

### 1.5 输出清洗（这一步很多人会漏）

模型返回后要过一遍 `jhx()`：

1. 去掉 ```` ``` ```` 代码块围栏；
2. 尝试 `JSON.parse`，取 `.recap`；
3. 失败则正则抠 `{...}` 再 parse；
4. 再失败则正则抠 `"recap":"..."` 并反转义；
5. 去 `recap:` 前缀、**去掉所有 markdown 记号** `[*_`#]`、压空白；
6. 空则回落到上一次的文本；
7. **超过 240 字直接硬截断加省略号**——不重新生成。

也就是说：Qoder 不相信模型会老实输出 JSON，它把「模型不听话」当成常态来设计。

### 1.6 落库字段

```sql
CREATE TABLE IF NOT EXISTS chat_session_recaps (
  session_id TEXT PRIMARY KEY,
  text TEXT NOT NULL,
  covered_message_id TEXT NOT NULL,
  source_signature TEXT NOT NULL,
  prompt_version INTEGER NOT NULL,
  model_key TEXT NOT NULL,
  updated_at INTEGER NOT NULL
);
```

下发给渲染层的只有 `{ text, updatedAt }` 两个字段——其余都是内部状态。

`source_signature` 是「这条 recap 基于哪条消息、什么状态、内容哈希」的指纹，用来判断摘要是否过期。本项目没有对应物。

### 1.7 卡片显示

- 外层渐变卡片（`from-fill-quaternary` → `to-bg-layout`）+ 双层阴影，和普通列表项明显区分。
- 头部只有两样：一个渐变色图标 + **「更新于 {{time}}」**。
- 正文 `line-clamp-7`，超 7 行截断。
- 展开热区铺满卡片底部整条（不是一个小按钮），内部圆形图标**默认透明**，hover 才显形。
- **文本为空时，整张卡不渲染**——连空态都不做。

## 二、和本项目对比，哪些是真差距

### 2.1 不是差距的部分（本项目做对了，不要动）

| 项 | 本项目 | 说明 |
| --- | --- | --- |
| 指令走 user turn 而非 system | 是 | 注释里记了原因：`role: "developer"` 会被网关 400。这是踩过坑换来的，比 Qoder 的 `systemPrompt` 更稳 |
| 失败不重试 | 是 | 与 Qoder 一致 |
| 缓存避免重复调用 | 是 | 键含 turn + body 哈希 + 语言句，比 Qoder 的 `promptVersion:sessionId` 更细 |
| 语言跟随界面 | 是 | 11 种语言 + 繁体判定；Qoder 只写「跟随会话主语言」 |
| 防注入包装 | 是 | `<transcript>` 标签 + 把闭合标签换成全角，Qoder 没有这层 |
| 三句上限 | 是 | 和 Qoder 的 220 字目标同量级 |

**结论：摘要的「输入治理」本项目做得比 Qoder 细。**不要为了像 Qoder 而把这些拆掉。

### 2.2 真差距一：没有「续写」概念

本项目每轮从零生成。后果：

- 第 3 轮说了「正在改 A」，第 4 轮说「改了 B」，两张卡并列，读者无法拼出全局。
- 同一件事被反复概括，读起来像复读。
- 会话越长，早期卡片越没用，但依然占位。

### 2.3 真差距二：失败路径把内部英文诊断直接给用户看

`client.js:2131-2135`：

```js
summary?.text 非空 ? String(summary.text)
  : String(summary?.reason ?? (state.status === "no-session" ? "open a conversation first" : "no completed turn yet"))
```

而 `reason` 的取值是这些（`summarise.js`）：

- `'turned off in settings'`
- `'no completed turn yet'`
- `'the turn left nothing to summarise'`
- `'no model service available'`
- `'no model route is available'`
- `` `the model call failed: ${failure}` ``
- `'the model returned nothing'`
- `'the summary call timed out'`

**全部是英文，且全部会原样出现在中文界面的卡片正文里。** 一个中文用户配错模型后，看到的是一行 `the model call failed: ...`。

这不是设计取舍，这是调试信息泄漏到产品界面。

### 2.4 真差距三：没有更新时间

卡片头部只有「N 调用 / N 命令 / N 文件」，**没有任何时间信息**。用户无法判断：

- 这段摘要是刚刚生成的，还是十分钟前这个会话还活着时生成的？
- 切回一个旧会话，卡片是新的还是旧的？

Qoder 只多一行 `更新于 {{time}}` 就解决了这个问题，成本极低。

### 2.5 真差距四：语气约束太薄

本项目 `INSTRUCTION` 只有 3 条约束（不要以 The assistant 开头、不要列表、失败要说失败）。缺的是：

- 不要写成操作日志/周报（这是模型最自然的退化方向）
- 忽略没有改变结果的工具噪音（否则摘要 = 命令清单的散文版）
- 不要编造完成的工作/文件/测试/决定
- 优先讲最新进展，而不是从头讲

这四条一句一条，加起来不到 200 字符，但决定了摘要是不是「有用」还是「换了个说法的日志」。

### 2.6 不是差距：长度上限

本项目 400 字上限、Qoder 240 字上限。看起来 Qoder 更严格，但 Qoder 是**硬截断**，本项目的 `slice(0, 400)` 也是硬截断。两边半斤八两。真正的差别是 Qoder 在提示词里给了「目标区间 150–190」，而本项目只说「最多三句」。

**这一条可以顺手改，但不是主要矛盾。**

## 三、建议怎么改（按性价比排序）

### P0 · 把失败文案从英文诊断换成中文人话

成本：半小时。收益：立刻消除界面上最难看的东西。

做法：在 `client.js` 里加一层 `reason` → 中文的映射，映射表覆盖上面 8 个值；未知值统一回落到一句人话。

```
'turned off in settings'        → 摘要已在面板设置里关闭
'no completed turn yet'         → 还没有完成的一轮
'the turn left nothing to summarise' → 这一轮没有可总结的内容
'no model service available'    → 宿主没有可用的模型服务
'no model route is available'   → 没有可用的模型通道
'the model call failed: ...'    → 摘要生成失败，稍后会自动重试
'the model returned nothing'    → 模型没有返回内容
'the summary call timed out'    → 摘要生成超时
```

注意最后一条：本项目实际上**不会自动重试**（每轮最多跑一次），所以文案不能说「会自动重试」。

### P1 · 卡片头部显示更新时间

成本：一小时（`summarise` 返回值加 `at`，`api.js` 透传，`client.js` 渲染）。

- 后端已有：缓存条目本来就存了 `at`，只是没吐出来。
- 前端位置：`dsse-head-stats` 后面追加一个 `dsse-head-stat`，格式「3 分钟前」。
- 陈旧判定：超过 10 分钟用次要色，避免误导。

### P2 · 回合结束就预生成，别让面板等模型

成本：一天。见 §5.7——这是七项「不做」里唯一被我误判过的一项。

做法：在 `index.js:371` 回合结束处，除 `rememberPaths` 外再 fire-and-forget 调一次 `summariser.summarise(...)`。不 `await`，失败无所谓（下次拉取还会再试一次）。面板打开时命中缓存，**首开 0 等待**。

要点：

- 必须 fire-and-forget，不能把回合结束拖慢；
- 已有 `inflight` Map 做去重，同键并发不会打两次模型；
- 缓存键已含 body 哈希，天然不会串轮次。

### P3 · 摘要改成「接着上一条写」

成本：半天到一天。这是唯一触及生成逻辑的改动。

做法：

1. `summarise()` 入参增加 `previousText`（上一条成功摘要的文本）；
2. prompt body 前面加一段 `Previous summary:\n<上一条>`；
3. `INSTRUCTION` 增加一句：「如果这一轮没有实质进展，就把上一条原样返回」；
4. 缓存键加入 `previousText` 的哈希（否则续写结果会被错误复用）。

风险：一旦引入前序依赖，「同一条摘要」不再是单轮的函数，缓存命中率会下降，且一条坏摘要会污染后续所有轮次。

**建议这一条先不做**，除非 P0/P1 做完后仍觉得卡片串联不起来。理由：本项目的卡片是「每轮一张」并列展示，本来就不承载「会话全局进度」这个职责；硬要给每张卡加前序继承，会和「并列展示」这个前提打架。真要解决连贯性，更干净的办法是**另起一张「会话总览」卡**（只一条，会话级），而不是改造每轮卡。

### P4 · 补三条提示词约束 + 一段输出清洗

成本：十分钟。收益：中。

在 `INSTRUCTION` 里追加（英文，与现有风格一致）：

```
Do not write it as a log, a progress report or a changelog — say what changed
for the reader, not what commands ran.
Ignore tool output that did not change the outcome. Never claim work, files,
tests or decisions that the transcript does not show.
Lead with the latest progress; do not retell the turn from the beginning.
```

同时把「at most three sentences」旁边的长度期望写明：`Keep it under about 240 characters.`

### 明确不做

| 不做 | 理由 |
| --- | --- |
| 强制 JSON 输出 + 清洗链 | 纯文本已经够用，JSON 只是给「模型不听话」兜底；本项目没有解析需求，加这层是自找麻烦 |
| `source_signature` 过期指纹 | 缓存键已含 body 哈希，功能等价且更简单 |
| `prompt_version` 入库 | 缓存是进程内的，重启即失效，版本号的收益接近零；除非将来做持久化摘要 |
| 6 条消息窗口 | 本项目要「讲清这一轮做了什么」，只给 6 条会丢掉前半段；这是有意取舍，不要抄 |
| 渐变卡片 + 双层阴影 | 面板是紧凑侧栏，装饰性阴影会让卡片彼此挤压；现有 `.dsse-card` 已足够 |
| 铺满底部的展开热区 | 现有 `Clip` + 卡片点击已经够用，再加一层绝对定位热区会和行内按钮抢点击 |
| 12s/35s 延迟生成 | 定时器 + 持久化 recap 配套，本项目没有那套前提。**但首开延迟是真问题，见 §5.7** |

## 四、给决策的四个问题

1. **P0 + P1 要不要一起做？** 两条加起来一个半小时，覆盖了用户能直接看见的全部缺陷。
2. **P2（预生成）要不要做？** 一天。它解决的是「首次打开面板最长等 20 秒」。不做不影响正确性，但影响第一印象。
3. **P3 做「续写」还是做「另起一张会话总览卡」？** 我倾向后者：不污染现有每轮卡，也不让一条坏摘要拖垮全局。
4. **P4 的提示词要不要改？** 改了会失效全部缓存（缓存键含 body，body 变了自然重算），代价是改完之后头几轮要重新等模型。

## 五、七项「不做」的逐条说明

上一节只给了结论。这一节说清每一项**是什么、解决什么问题、不做会差在哪**。
结论先说：**七项里有五项确实不用做，一项是纯装饰，还有一项（延迟生成）我上次的说法有问题，它藏着一个真问题。**

### 5.1 强制 JSON 输出 + 清洗链

**Qoder 是什么**：systemPrompt 第一条硬要求 `Return only a JSON object: {"recap":"..."}, without code blocks or additional explanation.` 拿到回复后过 `jhx()`：

1. 去掉 ```` ``` ```` 围栏；
2. `JSON.parse` 取 `.recap`；
3. 失败则正则抠 `{...}` 再 parse；
4. 再失败则正则抠 `"recap":"..."` 并反转义 `\n \r \t \" \\`；
5. 去 `recap:` 前缀、**删掉所有 `[*_`#]` markdown 记号**、压空白；
6. 空则回落到上一次文本；超 240 字硬截断加省略号。

**真正的作用不是 JSON，是输出卫生**。它要防三件事：

- 模型自作主张加 `Here is the summary:` 这类前言；
- 模型输出 `**加粗**`、`- 列表`、``` 代码块 ```，而卡片是纯文本渲染，这些符号会原样显示；
- 模型输出超长（硬截断比重新生成便宜）。

**本项目现状**：`summarise.js:539` 只有 `text.trim().slice(0, MAX_SUMMARY_CHARS)`。没有去围栏、没有去前言、没有去 markdown 记号。

**不做的代价**：低但不是零。你们的 `INSTRUCTION` 已经禁了列表和 bullet，风险大幅降低；但它**没有禁前言**。模型完全可能返回「以下是对这一轮的总结：……」，这句话会一直挂在卡片第一行。

**修正建议**：不要 JSON，但值得抄那 5 步清洗，尤其第 2、5 步（去前言、去 markdown 记号）。成本十几行代码。

### 5.2 source_signature 过期指纹

**Qoder 是什么**：`source_signature` = `[最后一条消息 id, 它的状态, sha256(内容).slice(0,16)].join(':')`，与 `covered_message_id` 一起入库。`PJe(已存, 当前)` 用它判断「库里这条 recap 还对不对应当前消息列表」。

**它为什么必须有这个**：因为 Qoder 的 recap 是**持久化 + 增量**的。App 重启后数据库里躺着三天前生成的 recap，必须先回答「它过期了吗」才敢显示。没有指纹，用户重启就会看到一个陈旧段落冒充当前进度。

**本项目现状**：缓存是**进程内 `Map`**，键 = `agentId:turn:bodyHash:语言句`。body 哈希覆盖了整个快照内容，内容一变键就变；进程一重启缓存就空。**因此结构上不存在「显示出陈旧摘要」这个问题**。

**不做的代价**：**零**——前提是继续不持久化。

**但记一笔**：哪天要做「打开面板立刻显示上次摘要」（省掉等待），就必须持久化；持久化那天，就必须有这个指纹。它和 5.3 是一起到的。

### 5.3 prompt_version 入库

**Qoder 是什么**：表里 `prompt_version INTEGER NOT NULL`，并且拼进去重键 `${promptVersion}:${sessionId}`。作用：**当你改了提示词，旧 recap 自动失效并重算**。

**本项目现状**：`summaryKey()` 哈希的是 **body（对话内容）**，不是 `INSTRUCTION`。所以**改提示词不会让进程内缓存失效**——同一个进程里，改完 `INSTRUCTION` 后旧轮次仍会命中旧摘要。

**不做的代价**：很低。改提示词通常伴随插件重载（本项目的客户端 bundle 本来就必须重启宿主才生效），进程一换缓存自然清空。真正的尴尬只发生在「同一进程内热改提示词然后反复看面板」，属于开发期摩擦，不是用户问题。

**建议**：现在不做，但把「缓存键不含提示词」写进代码注释，免得后人以为它含。

### 5.4 6 条消息窗口

**Qoder 是什么**：`MJe()` 只取 6 条消息——有覆盖点时取其后最多 6 条，没有时取最后 6 条。每条截 600 字，总长截 4000 字。

**它敢只取 6 条的前提**：历史被压缩在 `previousRecap` 那一行里送进去了。6 条 + 上一条摘要，合起来才构成完整上下文。

**本项目现状**：`renderPromptBody()` 送的是**结构化摘要**——工具调用统计（名字×次数、失败数）、改动文件（12 条 + `(+N more)`）、最后几条命令、助手说了什么——总共截 6000 字。不是原始消息列表。

**不做的代价**：**零，而且做了会更差**。你们没有 `previousRecap`，把输入砍到 6 条等于让模型只看这一轮的后半段。这条是**不同设计下的不同取舍**，不是差距。

### 5.5 渐变卡片 + 双层阴影

**Qoder 是什么**：`bg-gradient-to-b from-fill-quaternary from-[24.342%] to-bg-layout` + `shadow-[0px_4px_6px_rgba(0,0,0,.04),0px_2px_4px_rgba(0,0,0,.02)]`。

**作用**：让「任务回顾」在一堆列表分区里读起来像**一段叙事**，而不是又一条列表项。

**本项目现状**：`.dsse-card` 已有 `bg-layer-1` + 1px 边框 + `0 2px 8px rgba(15,17,21,.04)` + 11px 圆角。**你们本来就有卡片化处理**，只是更平。

**不做的代价**：纯视觉，零功能差异。而且这里有个反向考虑：你们面板里的五张卡**共用一套外壳**，这是「没有哪张卡自称更重要的」的表达。给上一轮卡单独加渐变，会打破这个一致性。

### 5.6 铺满底部的展开热区

**Qoder 是什么**：`line-clamp-7` 截断 + 一个绝对定位的 `-inset-x-3 bottom-[-8px] h-10` 按钮铺满卡片底部，内部圆形图标 `opacity-0` → hover 才显形。点淡出区域任意位置都能展开。

**它为什么要这样**：卡片右上角有个「更多操作」菜单按钮。如果整卡可点，点菜单会同时触发展开。它必须把「展开」限制在底部一条，才能和右上角共存。

**本项目现状**：整张卡可点（`onClick` 切 pin/展开），`::after` 那条 34px 渐变是 `pointer-events:none` 的纯装饰。

**不做的代价**：**没有差距，甚至你们更好**——小侧栏里可点面积越大越好。而且你们没有那个「右上角菜单」的冲突，不需要为它让步。

### 5.7 12s / 35s 延迟生成 —— 这项我上次说错了

**Qoder 是什么**：每会话一个 `setTimeout`，首次 12 秒、增量 35 秒，到点再校验控制令牌后真正生成，后台跑，结果推给 UI。另加消息数阈值 3（刚开的会话不生成）。

**它的作用**：① 防抖——回合刚结束可能还有后续动作，等一会儿再总结；② **UI 永不等待模型**——面板打开时摘要已经在那儿了。

**本项目现状**：拉取式。`api.js:903` 在 `readPanel()` 里 `await` 摘要，**面板请求要等模型返回才响应**，超时 20 秒。

我上次说「你们没有后台调度器」就跳过了这项。**这个说法是错的**——不是因为缺调度器所以不用做，而是：

> **你们有一个 Qoder 没有的问题：一轮结束后第一次打开面板，最长要等 20 秒。**

有缓存、有 inflight 去重、有 20s 超时，这些缓解了重复等待，但「新一轮的第一次」躲不掉。

**所以这项要拆成两半**：

- **不抄的**：12s/35s 这两个具体数字、以及它们背后的定时器生命周期。那是 Qoder 为了配合持久化 recap 做的调度，你们没有那套前提。
- **必须解决的**：**首开延迟**。而且解法比 Qoder 更简单——不要定时器，要**事件驱动**。`index.js:371` 已经在回合结束时调 `rememberPaths(agentId, ended)`，在那里顺手 fire-and-forget 触发一次摘要生成即可。等你打开面板时，结果已在缓存里。

这不是「复刻延迟生成」，是「把计算提前到用户看不见的时候」。方向和 Qoder 相反，达到的效果相同。

**优先级**：我把它排在 P0 和 P1 之后、P2 之前。它不影响功能正确性，但直接影响第一次打开的手感。
