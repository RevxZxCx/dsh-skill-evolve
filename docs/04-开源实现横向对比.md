## 一、先说三个推翻性发现

这一轮读完，有三条结论比之前更清楚，其中一条**直接质疑本项目的前提**。

### 发现 1：知识载体有四种，`SKILL.md` 可能不是最优的

| 载体 | 谁在用 | 特点 |
|---|---|---|
| **SKILL.md**（Markdown 技能文件） | Hermes、self-learning-skills、Acontext、`dsh-memory-evolve`、两个 forge | 人可读、可 diff、可 git；按 description 匹配加载 |
| **带置信度的规则条目**（playbook bullet） | cass-memory、mengram | 每条规则独立计分，可衰减、可反转成反模式 |
| **结构化 Gene/Capsule**（带验证命令的资产） | evolver | 机器可校验、可组合、可设安全围栏 |
| **经验编译包 / 训练数据** | Stash、agent-apprenticeship、Agent-KB | 面向"改进模型/提示词"，不是给 agent 当场读 |

**evolver 团队的论文（arXiv:2604.15097）直接拿这个做了对照实验**：

> Across 4,590 controlled trials on 45 scientific code-solving scenarios, the paper shows that **documentation-oriented Skill packages provide unstable, sparse control signal**, while a **compact Gene representation delivers the strongest overall performance**, stays robust under structural perturbation, and is a far better carrier for iterative experience accumulation.
> On CritPt, gene-evolved systems lift their paired base models from 9.1% → 18.57% and from 17.7% → 27.14%.

翻译：**面向文档的技能包给出的控制信号不稳定且稀疏**，而紧凑的 Gene 表示更强、对结构扰动更鲁棒、更适合累积经验。

> **这条如果成立，说明"把经验写成 SKILL.md"这个做法本身就有效率损失。** 需要注意利益相关：这是 evolver 自家产品的论文，且 evolver 的商业叙事是"我们的 Gene 比别人的 SKILL.md 好"（同期还在指控 Hermes 抄袭其设计）。**独立复现之前应视为待证命题，不是结论。** 但它指出的方向——**知识条目要紧凑、要结构化、要能被机器校验**——和 cass-memory 的规则条目、evolver 的 validation 数组是一致的。

对本项目的直接影响：**写 SKILL.md 不是唯一选择**。如果目标是"下次做得更好"，那么"一条带适用条件和验证方法的紧凑规则"可能比"一份完整操作手册"更有用。但 SKILL.md 有一个无法替代的优势：**人能读懂、能改、能拒绝**。这个取舍必须在设计时明确。

### 发现 2：淘汰和归因这两个我一直说"没人做好"的问题，cass-memory 做完了

我在 01 文档里说"没人解决技能库长到 50 条以后怎么办"，03 文档里补了 Hermes Curator。这轮又找到一个更细的：**`Dicklesworthstone/cass-memory`（★）的置信度衰减系统**。

它的规则不是文件，是**带分数的条目**：

| 机制 | 具体参数 |
|---|---|
| **90 天半衰期** | 90 天未再验证，置信度减半 |
| **4 倍有害权重** | **一次错误计 4 倍于一次成功** |
| **成熟度进阶** | `candidate` → `established` → `proven` |
| **反模式自动反转** | 一条规则被标记 harmful 3 次，**自动反转成警告**：`"Cache auth tokens for performance"` → `"PITFALL: Don't cache auth tokens without expiry validation"` |

原文对反模式的表述：

> Bad rules don't just get deleted—they become **warnings**.

**这是我在整个调研里见过的最好的"淘汰"设计。** 理由：

1. 它不是删除，而是**保留否定形式**——"不要做 X"比"删掉关于 X 的记录"信息量大得多
2. "一次错误抵四次成功"这个不对称权重符合工程直觉：错误代价高于收益
3. 半衰期让规则**自然过期**，不需要人维护
4. 三档成熟度给了"新规则先观察"的空间

**唯一缺的**是"这个技能到底帮到我没有"的直接归因——但 cass-memory 用"成功/有害标记"变相实现了：用户或 agent 每次使用后打一个反馈，就有了归因。

> 这比 Hermes 的 `use_count` 更进一步：`use_count` 只知道"被用了"，cass-memory 知道"用了之后好还是坏"。

### 发现 3：验证有成熟形态了，而且阈值可以照抄

我一直说"自动提炼最大的问题是没法验证"。**SkillClaw 给了完整的工程答案。**

它的模式叫 **background validation worker**，默认关闭，开启后流程是：

1. evolve server **把候选技能暂存为 validation job**，不直接发布
2. 客户端**只在本地 proxy 空闲时**领任务（`validation.idle_after_seconds: 300`）
3. 客户端在后台验证候选技能，把结果写回
4. 后续 evolve 周期**只在阈值满足时才发布**

阈值是显式配置：

```bash
EVOLVE_PUBLISH_MODE=validated \
EVOLVE_VALIDATION_REQUIRED_RESULTS=1      # 至少 1 份验证结果
EVOLVE_VALIDATION_REQUIRED_APPROVALS=1    # 至少 1 票批准
EVOLVE_VALIDATION_MIN_MEAN_SCORE=0.75     # 平均分不低于 0.75
EVOLVE_VALIDATION_MAX_REJECTIONS=1        # 最多容忍 1 次拒绝
```

客户端侧限流：

```bash
skillclaw config validation.max_jobs_per_day 5    # 每天最多验 5 个
skillclaw config validation.poll_interval_seconds 60
```

**可抄的点**：
- **验证和提炼分离**，且验证在**空闲时**做（不抢资源、不打断用户）
- **阈值是四个独立旋钮**，不是一个模糊的"质量检查"
- **每天上限**防止验证变成新的负担
- 默认**关闭**——这是第二次看到"自动维护类功能应该默认关"（第一次是 Hermes Curator）

## 二、四种架构形态

读完后发现这些项目可以清楚地分成四类，**它们解决的问题其实不一样**。

### 形态 A：代理拦截型 —— 不改 agent，在 API 层偷看

**代表：SkillClaw（★2720）、mengram**

做法：起一个本地 proxy 挂在 `/v1/chat/completions`、`/v1/messages` 上，agent 以为在直连模型，实际所有请求都过它。

**SkillClaw** 的双组件设计：

1. **Client Proxy**（本地）——拦截请求、记录会话产物、管理本地技能库
2. **Evolve Server**（可选，独立进程）——读共享存储里的会话数据，进化/创建技能，写回

两者**只通过共享存储（local / OSS / S3）相遇**，不直接通信。这个解耦很干净：单人只装 client，团队加一个 server。

它对 Hermes 的定位说得极准（原文）：

> The problem isn't that Hermes doesn't learn enough — it's that nobody helps it **digest**.
> SkillClaw doesn't make Hermes learn more — it makes everything Hermes has learned **actually count**.

两种进化引擎：`workflow`（固定三段 LLM 流水线：Summarize → Aggregate → Execute）/ `agent`（OpenClaw 驱动的工作区，直接编辑技能）。

**mengram** 的 proxy 挂点更细，直接挂在 agent 生命周期的每个钩子上：

```
Session Start  →  载入认知画像（/clear、压缩、重启后都触发）
Every Prompt   →  搜历史会话找相关上下文（自动召回）
After Response →  后台保存新知识（自动保存）
Before a Bash  →  命令匹配到"记录薄弱"的已学工作流时，先问你（策略闸门）
Before compact →  写下工作状态：最后几个 prompt、改过哪些文件、最后几条命令、停在哪
After compact  →  把这些状态原样放回去，紧挨着宿主的摘要，并告诉你一句
```

> **"Before a Bash → 如果命令匹配到记录薄弱的工作流，先问你"** 这是策略闸门（policy gate），我在这轮调研里只见到这一个实现。

**形态 A 的代价**：要改用户的网络配置（base_url 指向 proxy），且**只能在有 proxy 概念的宿主上用**。DSH 的插件体系不需要 proxy——插件本来就在进程内。

### 形态 B：记忆库型 —— 知识存在库里，靠检索取用

**代表：cass-memory、Acontext、Agent-KB、Stash**

这一类的分歧在**检索方式**。

**Acontext** 明确反对语义检索（原文）：

> **Progressive disclosure, not search** — The agent can use `get_skill` and `get_skill_file` to fetch what it needs. Retrieval is by tool use and reasoning, **not semantic top-k**.

它的核心主张是 **"Skill is Memory, Memory is Skill"**：

> Acontext builds memory **in the agent skills format**, so everyone can see and understand what the memory actually contains.
> **Plain file, any framework** — Skill memories are Markdown files. Use them with LangGraph, Claude, AI SDK, or anything that reads files. **No embeddings, no API lock-in.** Git, grep, and mount to the sandbox.
> **You design the structure** — Attach more skills to define the **schema, naming, and file layout** of the memory.

提炼流程：

```
会话消息 → 任务完成/失败 → 蒸馏 → Skill Agent 决定存哪（已有技能 or 新建）→ 更新技能
```

**注意触发点是"任务完成或失败"，不是"回合结束"。** 这是第三次看到"以任务结果为触发"优于"以回合为触发"。

**cass-memory** 是三层记忆：

```
EPISODIC（episodic memory：cass 里的原始会话日志，ground truth）
    ↓ cass search
WORKING（Diary：结构化会话摘要 = accomplishments / decisions / challenges / outcomes）
    ↓ reflect + curate（自动）
PROCEDURAL（Playbook：蒸馏出的规则，带 confidence / anti-pattern / feedback / decay）
```

它的**证据闸门**值得单独提：

> New rules aren't blindly accepted. Before a rule joins your playbook, it's validated against your cass history:
> Proposed rule: "Always check token expiry before auth debugging"
> → Evidence gate: Search cass for sessions where this applied
> → Result: 5 sessions found, 4 successful outcomes → **ACCEPT**
> Rules without historical evidence are **flagged as candidates until proven**.

还有一个降级设计，我认为非常成熟（原文）：

| 条件 | 行为 |
|---|---|
| 没有 cass | 只用 playbook 打分，无历史片段 |
| 没有 playbook | 空 playbook，命令照常工作 |
| 没有 LLM | **确定性反射，无语义增强** |
| 离线 | 缓存的 playbook + 本地 diary |

> "You always get value, even in degraded conditions." —— **每个组件缺失时都还有降级路径**，这个设计纪律在同类项目里罕见。

**Agent-KB**（OPPO，ICML 2025 workshop）的做法是把经验**字段化**：

```json
{
  "question": "",
  "agent_planning": "",
  "search_agent_planning": "",
  "agent_experience": "",
  "search_agent_experience": ""
}
```

> **planning 和 experience 是两个字段**。这个拆分意味着它认为"怎么做"和"踩过什么坑"是两种独立的知识，不该混在一起写。这是一个可以直接借用的数据结构建议。

**Stash**（Fergana Labs）走的是**奖励模型**路线，最特别的是它从**人的反应**里提取训练信号：

> Stash derives preference pairs from **reviewer comments and user reactions, including approval, disappointment, and corrections**. A classifier attributes each judgment to a response and **keeps the source quote**; **unclear reactions are excluded from training**.
> Training needs **at least two grounded comparisons**.

**"unclear reactions are excluded" + "keeps the source quote"** —— 只采信能追溯到原话的反馈，模糊的不要。这和 `distill-kura` 的引文闸门是同一个思想。

### 形态 C：元技能型 —— 不写代码，只写提示词教模型自己存

**代表：self-learning-skills（★970）、pskoett/self-improving-agent、hermes-skill-factory（★556）**

这一类最轻：**一个 SKILL.md 文件，装进任何 agent 就行，零依赖零代码。**

**self-learning-skills** 的定位很精确：

> It's a *meta-skill*: it doesn't do the work, it captures **how** the work got done — **including the failures, since skipping a known dead-end next session is often worth more than the win itself**.

四个识别信号（原文）：

1. A task that **only worked after several tries**
2. A **non-obvious command**
3. A **project fact you didn't know up front**
4. An operational workflow likely to recur
5. 或者你**直接说 "remember this"**

它按工具分派落盘位置：

| 工具 | 存到哪 | 怎么自动加载 |
|---|---|---|
| Claude Code / Codex / Agent Skills | `skills/<name>/SKILL.md` | 技能描述匹配 |
| Cursor | `.cursor/rules/learned/<name>.mdc` | 规则描述 / globs |
| Zed、Aider、Gemini CLI… | `AGENTS.md` | 总是被读取 |

> **"总是被读取"这条是重要的**：对不支持技能加载的工具，落盘到 `AGENTS.md` 是唯一能保证生效的路径。DSH 正好两者都支持（`AGENTS.md` + skills）。

**pskoett/self-improving-agent** 的细节值得抄一句：它把学习记录放在 **`.learnings/` 目录**，和技能代码分开，并在卸载说明里写：

> Review `.learnings/` before deleting — it contains **your captured learnings, not skill code**.

**形态 C 的根本缺陷**：**可靠性完全取决于模型是否照做。** README 是提示词，不是执行代码。一个模型可能连续十次会话都不触发。这是它轻量的代价。

### 形态 D：进化引擎型 —— 把经验当可演化的资产

**代表：evolver（★8690）**

evolver 的做法和所有人都不一样：它**不写技能，它产出"GEP prompt"**。

每个进化周期：

1. 扫 `memory/` 目录找运行时日志、错误模式、信号
2. 从本地 GEP 资产库选最匹配的 **Gene** 或 **Capsule**
3. **输出一个严格的、协议约束的 GEP prompt** 到 stdout
4. 写一条可审计的 **EvolutionEvent** 到 `memory/`

它明确声明自己**不是**代码修改器：

> **Evolver is a prompt generator, not a code patcher.**
> It does **NOT**: automatically edit your source code / execute arbitrary shell commands / require an internet connection for core functionality.

资产结构：

```
<workspace>/.evolver/gep/
  genes.json      # 基因
  capsules.json   # 胶囊
  events.jsonl    # 审计事件
```

**安全模型是我见过最细的**。`solidify.js` 会执行 Gene 里 `validation` 数组里的命令，所以加了五道闸：

1. **前缀白名单**：只允许以 `node`、`npm`、`npx` 开头
2. **禁命令替换**：反引号和 `$(...)` 任何位置都拒绝
3. **禁 shell 操作符**：剥掉引号内容后，`;`、`&`、`|`、`>`、`<` 一律拒绝
4. **超时**：每条命令 180 秒
5. **限定 cwd**：在仓库根目录执行

外部资产（从网络进来的 Gene/Capsule）走**隔离候选区**，晋升到本地库要求：显式 `--validated` 标志 + 重新审核 validation 命令 + **永不覆盖同 ID 的本地 Gene**。

其他值得一提的：要求 **git 仓库**（用 git 做回滚、爆炸半径计算、solidify）；`EVOLVE_STRATEGY=balanced|innovate|harden|repair-only` 控制意图平衡；**信号去重防止修复循环**。

**但要注意它的定位**：

> **Not For**: One-off scripts without logs or history / Projects that require free-form creative changes / Systems that cannot tolerate protocol overhead.

而且 `--loop` 模式有个反直觉的限制（原文）：

> `--loop` is **not** a real-time agent assistant. Loop mode is for background self-maintenance... **Its stdout is consumed by evolver itself, not by a running host agent**. If you want evolver to observe and advise a live agent session, call `evolver` from **inside** that agent session.

> **这意味着 evolver 的"后台持续进化"和"辅助当前会话"是互斥的。** 它更适合"定期体检项目并给建议"，不适合"边聊边学"。

## 四、五个可以直接抄的机制

按"对 DSH 插件的价值"排序，每条都给出**为什么**和**怎么落地**。

### 抄点 1：反模式反转（cass-memory）

**做法**：一条规则被标记有害 N 次后，**不删除，反转成 PITFALL 警告**。

**为什么重要**：这是唯一同时解决"淘汰"和"避免重蹈覆辙"的方案。删掉一条错规则，agent 下次还会犯同样的错；反转成"不要这样做"，错误本身成了资产。

**怎么落地**：技能文件加一个 `outcome` 字段（`helpful` / `harmful` / `unknown`）。`harmful` 计数 ≥3 时，插件自动把技能正文前置一段 `## PITFALL` 段落，并保留原内容作为上下文。

**注意**：反转需要判断"这条规则的失败是不是规则本身导致的"，这个归因很难。cass-memory 交给人工标记。**所以这个功能必须有用户反馈入口**，不能纯自动。

### 抄点 2：置信度衰减（cass-memory）

**做法**：90 天半衰期 + 一次错误抵四次成功 + 三档成熟度。

**为什么重要**：Hermes Curator 用"未使用天数"淘汰，**但"没用过"和"没用了"是两回事**。一条规则可能因为项目停了而没被用，但依然正确。置信度衰减是**基于使用结果**而不是**基于使用次数**的淘汰，更准确。

**怎么落地**：技能 frontmatter 加
```yaml
confidence: 0.85
last_validated: 2026-10-22
success_count: 7
harmful_count: 1
```
读取时按 `confidence * 0.5^(days/90)` 排序注入。**这意味着技能目录的顺序会变——但目录内容不能变，否则击穿 prompt cache。**

> **冲突警告**：置信度衰减会让"排序"动态变化。如果把置信度写进注入的技能目录，每 90 天缓存就全失效。解法：**置信度只在"挑选要不要注入"时用，注入后的顺序必须稳定**。或者干脆像 Hermes 一样，让衰减只影响归档决策，不影响注入内容。

### 抄点 3：验证工人 + 四阈值（SkillClaw）

**做法**：候选技能不进库，进 **validation job 队列**；空闲时由一个 worker 验证；四个独立阈值都满足才发布。

**为什么重要**：这是把"自动提炼"从"要么全自动要么全人工"的二选一里救出来的关键设计。**验证可以异步、可以后台、可以限流**，用户不必任何事都在场。

**怎么落地**：
```
新候选 → pending 队列
    ↓ 空闲时（用户无活动 > 5 分钟）
验证：在同一会话里试运行一次？或让模型自评？
    ↓
results ≥1 && approvals ≥1 && mean_score ≥0.75 && rejections ≤1
    ↓ 发布
```
**难点**：DSH 插件里"验证一个技能"具体做什么？最现实的是**让模型自己拿技能跑一个 dry-run 并自评**，但这有自我确认偏差。SkillClaw 靠**多客户端**（不同的人/机器）来消除偏差——**单机做不到**。

> 所以这条在单机 DSH 上只能实现成"模型自评 + 人批准"，**不能实现成"独立验证"**。这是必须承认的局限。

### 抄点 4：证据闸门（cass-memory + distill-kura 的共同点）

**做法**：新规则必须先在你自己的历史里找到支撑（"这条规则适用过的 5 次会话里，4 次成功"），找不到就只能是 candidate，不能进主库。

**为什么重要**：这直接回答"这个技能到底有用吗"。不需要用户打分，只需要**检索历史**。

**怎么落地**：DSH 有 `dsh-session-query` 能查历史会话。提炼时让模型输出候选技能 + `evidence: [sessionId, turnIndex]`，插件去查这些会话是否真的存在对应模式。**证据不成立的候选直接丢弃。**

> 这是本轮我认为**最值得实装**的一条：它不需要额外 LLM 调用、不需要用户参与、不需要多客户端，纯靠本地历史就能过滤掉大量幻觉技能。

### 抄点 5：planning / experience 字段分离（Agent-KB）

**做法**：经验记录里，"怎么做"（planning）和"踩过什么坑"（experience）是**两个独立字段**。

**为什么重要**：对应到技能文件，就是**正文（怎么做）** 和 **PITFALL 段（别怎么做）** 应该分开维护。混在一起会导致：改流程时把坑的记录一起删掉。

**怎么落地**：SKILL.md 结构固定为

```markdown
---
name: ...
description: ...
---
## When to use
## Procedure        ← planning
## Pitfalls         ← experience
## Verification
```

**这条零成本，立刻可做。**

## 五、对 DSH 插件的具体结论

### 结论 1：架构上应该走"形态 C + B"，不走 A 和 D

| 形态 | 为什么不走 |
|---|---|
| **A 代理拦截**（SkillClaw / mengram） | DSH 插件本来就在进程内，不需要 proxy；再加 proxy 是自找麻烦 |
| **D 进化引擎**（evolver） | 它的价值在"协议约束 + 审计"，但代价是用户要学 GEP 概念、要维护 Gene 库、要 git。**对个人用户太重** |
| **C 元技能** | **零成本起步**，写一个 SKILL.md 教模型在踩坑时存技能。这是 P0 |
| **B 记忆库** | 需要插件代码，但是 C 的自然升级：C 靠模型自觉，B 靠钩子保证 |

**推荐路径：先做 C（一天），验证模型确实会在这个 DSH 里主动沉淀，再升级到 B。**

> 这个顺序很重要。如果模型在 C 阶段就不愿沉淀，那 B 做得再好也只是把"没人用的提醒"变成"没人用的自动化"。

### 结论 2：技能文件格式应该固定下来，现在就定

综合 Agent-KB 的字段分离 + cass-memory 的反模式 + Hermes 的"记教训不记流水账"：

```markdown
---
name: kebab-case-name
description: 一句话，含触发条件
confidence: 0.5          # 初始 0.5，不假装确定
last_validated: 2026-10-22
success_count: 0
harmful_count: 0
---

## When to use
（什么情况下该加载这个技能）

## Procedure
（步骤。**只写规则，不写故事**——不带日期、不带 PR 号、不带引用的聊天）

## Pitfalls
（踩过的坑。这条最重要，往往是技能里唯一真正有价值的部分）

## Verification
（怎么确认这次做对了）
```

**四个段落缺一不可**，尤其 `Verification`——没有它，技能永远无法自证。

### 结论 3：必须承认单机验证的天花板

SkillClaw 的验证靠**多客户端**（不同人、不同机器、不同项目）来消除自我确认偏差。**单机 DSH 插件没有这个条件。**

所以只有三条路：
1. **模型自评 + 人批准**（可靠但费人）
2. **证据闸门**（自动，但只能证明"历史上出现过"，不能证明"这次会有用"）
3. **延迟验证**：技能先入库但标记 `unproven`，等它被用了 3 次且每次会话成功，才晋升

**第 3 条是唯一能自动化又不自欺的**。它和 cass-memory 的 `candidate → established → proven` 是同一个思路。**建议采用第 3 条 + 第 2 条做入口过滤。**

### 结论 4：这一轮的净增量

相比 03 文档，本文新增的、真正会改变设计的：

| 新增 | 影响 |
|---|---|
| **反模式反转** | 淘汰不是删除，是转成警告。**改设计了** |
| **置信度衰减（按结果不按次数）** | 比 Hermes 的按天数归档更准。**改设计了** |
| **证据闸门** | 可以纯本地过滤幻觉技能，**是最高性价比功能** |
| **验证四阈值 + 空闲 worker** | 给了"异步验证"的具体参数 |
| **Gene > SKILL.md 的对照实验** | 质疑载体选择，需要权衡 |
| **planning/experience 分离** | 零成本、立刻可做的格式改进 |
| **mengram 的回归闸门** | 修复 A 不能破坏 B。技能越多越重要 |

## 六、调研方法补充

**有效的做法**：
- GitHub REST API + `Accept: application/vnd.github.raw` 抓 README，`api.github.com` 直连可用
- 8 组关键词（`skill evolution` / `self-improving agent` / `agent memory` / `experience distillation` / `self-evolving` / `skill library` / `agent learning loop` / `procedural memory`）**换着搜**——单次按 stars 排序只给头部
- 先读**所有 README 的 headings**（`grep "^#\{1,3\} "`）判断结构，再决定读哪几段，避免整篇灌进上下文

**踩的坑**：
- `print()` 非 ASCII 在 GBK 控制台直接 `UnicodeEncodeError`，必须写文件再读
- `curl` 不加 `--compressed` 会把 gzip 当文本打印
- awesome 类仓库（`Awesome-Self-Evolving-Agents`）里 80% 是学术 RL 论文，**不是工程实现**，读完 44KB 只捞到一个有用的（`OPPO-PersonalAI/Agent-KB`）。**下次先 grep 关键词再决定要不要深读**
- `Agent-on-the-Fly/Memento` 返回 301 重定向，仓库已改名/迁移

**没做完的**：
- 没有实际跑任何一个方案（都是读文档）
- cass-memory、Acontext、Stash、mengram 的 star 数没记——它们不是靠 star 排序找到的
- 没验证 evolver 那篇论文的结论（4,590 次对照实验无法本地复现）
