## 1. 问题

一轮回答结束后，人面对的是同一件事：**下一步该说什么**。现在 DSH 里这一步全靠人自己想，而「刚才那轮停在哪、还差什么、下一步最自然的动作是什么」恰好是模型最清楚、人最费劲的部分。

用户要两件事，它们是同一个能力的两处出口：

1. **底栏芯片**：一轮结束后，在对话回答之后、输入栏之上，显示 2–3 个「下一轮提示词」按钮。**点一下 = 用这句话开下一轮**（等价于人自己打完按回车）。
2. **TAB 填充**：输入栏为空、光标在里面时，显示一条「最可能的提示词」幽灵补全。按 `Tab` **填入输入栏但不发送**，人可以改完再发。

两处的数据是同一批建议；差别只在**接受动作**：芯片是「填 + 马上发」，幽灵是「只填」。

### 这件事不是「加一个按钮」

真实的失败模式有三种，方案必须逐一回答：

- **它会让每一轮变贵**。建议必须由模型生成（见 §3：无模型的启发式版本被否掉了），而每轮多一次模型调用，就对每个会话的每一轮都生效。本仓库有一条硬纪律（docs/27 §7 Q3）：任何让「每个事件都多做一点事」的改动，先算密度再动手。
- **它会给出陈旧的建议**。上一轮的建议留着，用户已经又聊了三轮，芯片还在那儿指着已经翻篇的事。t3code 的解法（见 §2.2）是「只认该线程最新一次已完成回合」，本方案照此办理。
- **它会骗人**。建议必须是「点下去就对」的整句话，不能是「继续优化一下」这种需要二次解释的碎片；而且点击必须走宿主自己的发送通道，不能自己拼一个请求——否则队列、权限、plan 模式、附件、去重全都绕过一遍。

## 2. 真实数据

### 2.1 Qoder 的现成实现（逆向所得）

本地解包副本 `/f/dsh-plugin/_qoder_rev`（`main.js` 21 MB）约为 **0.5.7（2026-11-09）**，因此**只有底栏芯片，没有 TAB 填充**；TAB 是 0.5.11 才加的。两层都已还原：

| 层 | 事实 |
| --- | --- |
| 数据 | 建议是**纯字符串数组** `suggestedPrompts`，挂在会话状态上（`chatSession.suggestedPrompts`），随控制状态广播；生成在 Agent SDK 侧，开关 `promptSuggestions` 作为启动参数传入 |
| 渲染 | 组件 `mm2`：容器 `mx-2 mt-1 border-t border-dashed pt-5`，属性 `data-conversation-prompt-suggestions`；每项 = 单行药丸 + 14px 箭头图标，`text` 与 `prompt` 是同一个字符串，**无标题、无副标题、无分类** |
| 门控 | `!只读 && 设置开关 && phase === "idle" && !本地发送中 && 建议非空` |
| 接受 | **点击 = 直接发送**，`send({ …, prompt, fromPromptSuggestion: true, optimisticUserMessage: true })`，成功后立刻 `dismissSuggestedPrompts`；失败只弹 toast，不重试 |
| 失效 | 消息被删除/回退时，广播同时带 `removedMessageIds` 与 `suggestedPrompts: []` |

官方 changelog 里还有两条对本方案有直接约束的记录：

- **0.5.11**：*"Qoder can proactively suggest what to do next when the composer is idle and empty. **Press Tab or Right Arrow** to insert a suggestion into your draft, then review and send it."* —— 用户描述的第二个交互就是它。
- **0.4.2 修过的缺陷**：*"Fixed an issue where Prompt Suggestion processing could block the next request; suggestion generation no longer delays subsequent chat responses."* —— **生成绝不能阻塞下一轮**。这是官方踩过的坑，不是假想风险。

一条排除记录，避免下一个人重走：`nD1` 不是建议组件，是「技能进化建议」浮层（文案在 `chatSession.skillEvolution.*`），正确入口是 `suggestedPromptsObs`。

### 2.2 竞品的成熟约束（一手材料）

**Claude Code（VS Code 文档）**：建议渲染为**输入框内灰色斜体幽灵文本**，`Tab` 接受；文档明说 *"Each suggestion uses a short background request that counts toward your plan's usage limits or API costs."*

**t3code PR #28047（已合并，作者 t3dotgg）** —— 目前最完整的一手工程实现，直接可作为我们的验收清单：

- **默认关闭**（Labs 选项），理由是每次建议都是一次额外模型请求。
- **实测成本**：Codex 小线程约 **11k input tokens/次（97% 命中缓存）+ 20–50 output tokens**，随线程增长——因为它把整个线程发过去。
- **只对「人主动驱动的线程」给建议**，本地子 agent / 委派任务里跳过。
- **跳过第一轮**（第一轮没有「上一轮」可接），接近用量上限时不给。
- **不持久化**，内存里每线程保留最新一条；**绝不为已删除线程返回**。
- Composer 规则（逐条采纳见 §7.4）：只认最新一次已完成回合；绝不覆盖审批/提问提示；不与上下文 chip 同排；发送飞行中隐藏；`/clear` 后隐藏；**`Tab` 走与其他插入相同的路径**（因此输入守卫能看到它）；`Escape` 在该回合内关闭；**「Tab」提示单独渲染成键帽**，避免被读成提示词的一部分。
- 明确未做：移动端（没有 Tab 键）、样品评测、键处理器单测。

### 2.3 宿主 DSH 有什么（已核实到源码）

本仓库 `docs/02` 的结论是「宿主能力先核实再设计」，这一节就是核实结果，全部可复现。

**① 两个挂载点都是公开槽位**

| 槽位 | 类型 | 挂载位置 | 用途 |
| --- | --- | --- | --- |
| `conversation.input.dock` | `list` / `session` | `composerStack` 里、`inputBar` **正上方** | 底栏芯片 |
| `conversation.input.overlay` | `list` / `session` | 输入卡片内 `<div data-composer-overlay>` 浮层锚点 | 幽灵补全 |

`conversation.input.dock` 的一等公民先例：**待办面板**（`id: "todo", order: 0`）与**队列面板**（`id: "queue", order: 20`）——同样是「输入框上方一叠东西」，本方案取 `order: 10` 插在两者之间。

**② 填草稿有正式动作面，不用摸编辑器**

宿主 `conversation` 服务（根单例）持有 `input` = 每会话输入机器注册表；每个会话的 facade（`SessionInputShell`）通过**标准 provide 通道**把两样东西发给 composer 的子槽位：

```
useInput      —— 已发布的 InputState（draft / phase / attachmentIds / …）
inputActions  —— { captureInsertion, insertText, setDraft, persistDraft,
                   addAttachments, removeAttachment, pruneAttachments, submit }
```

三个先例把这条路走通了：

- **语音输入插件** `dsh-experimental-client-ui-voice-input`：`inputActions.insertText(转写文本, inputActions.captureInsertion())` —— 把一句话塞进草稿，**正是 TAB 填充要的动作**。
- **工作区插件** `dsh-client-ui-workspace`：`ctx.get("conversation").input.requestDraftInitialization(binding, options)` —— 新建会话时预置草稿。
- **宿主自己切会话时**：`next.setDraft(draft); from.setDraft("")` —— 搬运草稿。

`setDraft(text)` 的语义（源码注释）：*"Placeholder-sanitized; newlines split paragraphs; the caret lands at the end. Merged into history so a seed is not an undoable step of its own."*

**③ 发送一轮也有正式动作**

`inputActions.submit()` 走宿主自己的提交机（队列/直发、附件、权限、plan 模式全在），**与用户按回车是同一条路**。这比 `conversation.send(text)` 更好：后者是另一条入口，绕过了「输入守卫」。

**④ 输入区是 Lexical 富文本，不是 textarea**

所以「给 textarea 塞 value 再 dispatch input」那套 React 技巧在这里**不成立**；幽灵文字也不能往 Lexical 里插 DOM。结论见 §4 选项 B/C。

### 2.4 本仓库现状

- 全量基线：**4011 passed / 0 failed**；性能预算 6 项 exit 0（2026-11-24 复现）。
- 每轮已经**有**一次模型调用：`summarise.js` 的上一轮总结（≤6000 字符输入、300 tokens 输出、20 s 超时、60 s 失败冷却、每轮最多一次）。
- 真实密度（docs/27 §7 Q3）：一轮平均 **1,252 秒**（20 分钟），tool/call 0.057 次/秒。**每轮多一次调用，在时间与成本上都可忽略**；真正要防的是「每轮 × 每个会话 × 每个事件」的乘法，而建议是**每轮一次**，不是每事件一次。
- 每轮的成本必须能被关掉：本仓库所有模型调用都有开关（`panelSummary`）。

## 3. 选项与代价

### 选项 0：不做

用户继续自己想下一步。代价：0。收益：0。放在这里是因为它是必须被否掉的基线——这个功能的全部价值就是省掉「回想上一轮停在哪」的那 10 秒。

### 选项 1：接在现有总结调用上（一次调用出两样东西）

把 `summarise.js` 的指令改成「先写摘要，再写 `SUGGESTIONS:` 和 3 行建议」，解析时按标记切分。

- 成本：**零额外调用**。这是它唯一的、也是决定性的优点。
- 代价：让本仓库审查最密的模块（6 个突变套件 + 总结全套测试）承担一个双职责 prompt；建议 JSON 解析失败有可能连累摘要卡（一张坏的摘要卡比没有建议更严重）；两个功能无法独立开关（关掉面板摘要的人仍在付建议的钱，反之亦然）。
- 违背：D-241 之后「一个模块一件事」的取向。

### 选项 2：独立的每轮一次调用（推荐）

新模块 `lib/suggest.js`，回合结束时一次结构化调用，独立开关、独立节流、独立失败冷却。复用现有的路由解析与模型服务，**不碰** `summarise.js`。

- 成本：每轮 +1 次调用。输入沿用 `Transcript.snapshot` 渲染体（≤6000 字符，**不是**整条线程——这是与 t3code 11k tokens 的关键差别），输出 ≤200 tokens，15 s 超时，60 s 失败冷却，每轮最多一次。
- 收益：开关独立、失败隔离、可单独测量与单独关停。
- 代价：多一次网络往返；需要新增一节性能预算。

### 选项 3：按需生成（客户端打开输入栏时才生成）

- 成本：比选项 2 更省——没人看就不花钱。
- 代价：用户在**最需要它的那一刻**（回合刚结束、手指已经在输入栏）等 1–3 秒。芯片的价值在于「不用想」，等它出来的时候人已经开始打字了。
- 位置：**作为选项 2 的降级路径**保留，不做主路径（见 §7.3 的「有人在看」闸门）。

### 选项 4：不用模型（规则拼装）

从「最近改过的文件」「失败的测试」「上一次的工具名」拼出候选，如 `继续修 <file>`。

- 成本：0。
- 代价：**会骗人**。拼出来的句子语义上经常不成立（「继续修 config.js」在那一轮已经修完时），而人的信任是一次性的——出现两次胡说，整个功能就被关掉了。这恰好是本仓库 `deliverable.js` 那类白名单机制反复强调的：宁可不出，也不出错的。

## 4. 选择与理由

**选选项 2 为主体，选项 3 作为「没人看就不生成」的闸门；否掉选项 1/4。**

理由按重要性排序：

1. **独立失败，独立关停。** 建议是一个「锦上添花」的功能，摘要卡是面板主体。把两者绑在一次调用里，等于让锦上添花的东西拥有拖垮主体的能力。选项 1 省下的那一次调用，买不到这个隔离。
2. **不阻塞下一轮（Qoder 0.4.2 的教训）。** 生成是 fire-and-forget：回合结束事件里只做「记账 + 起一个受超时保护的异步任务」，**任何路径都不 await 模型**。选项 1 天然做不到这一点——摘要调用现在就在回合收尾路径上。
3. **成本需要一道乘法闸门，而闸门的位置在「有没有人在看」。** 后台会话、子 agent、没人打开的旧对话，都不该产生调用。ui-evolve 已经知道哪些 agent 最近被读过（面板请求就带 `agent`），这条信息现成可用，所以闸门是 `watched(agent)` 而不是一句「默认关闭」。t3code 用「默认关闭」解决同一个问题，代价是没人打开它；我们能做得更好。
4. **接受动作必须走宿主的路。** 芯片 = `setDraft` + `submit`，幽灵 = `setDraft`。**两者共用同一个填入函数**，只是一次多调一个 `submit`。这不是洁癖：`submit()` 走的是宿主提交机，队列/权限/plan/附件/去重全部保留；`conversation.send()` 是绕过输入守卫的另一条路。t3code 的原话是「Tab 走与其他插入相同的路径，因此输入守卫能看到它」。
5. **幽灵文字画在我们自己这一层，不碰 Lexical。** 见 §7.4 的失败模式与降级。

被明确否掉的实现方式（记录，避免下次再试）：

| 想法 | 为什么不行 |
| --- | --- |
| 往 `contenteditable` 里塞 DOM / 直接改 `textContent` | Lexical 持有文档模型，外部改动会在下一次 commit 被覆盖或直接抛错 |
| 模拟 `input` 事件给编辑器 | 同上，Lexical 不读 DOM 值 |
| `conversation.send(text)` 作芯片主路径 | 绕过输入守卫与提交机；只有 `inputActions` 缺席时才作降级 |
| 把建议写进会话 state JSON | 会逼出 STATE_VERSION 4，且 64 KB 状态文件预算是硬的；建议本来就是易失的（t3code：不持久化） |
| 复用 `/events` SSE 帧携带建议正文 | 帧被 `test/api.test.mjs:1124,1154,1398` 钉死为 `{agent, revision}`；带正文的推送会把每轮流量乘以建议长度 |
| 用 `panelSummary` 开关兼管建议 | 两件事的价值不同：有人只要卡片摘要，有人只要建议 |

## 5. 验收标准

**一句话**：在真实会话里，一轮回答结束后 **3 秒内**，输入栏上方出现 **2–3 个**可点击的下一轮提示词；点其中一个，下一轮的用户消息**与芯片文字逐字相等**，且输入栏**不残留草稿**；输入栏为空时按 `Tab`，幽灵补全**填入输入栏但不发送**，光标落在句尾。

**数字**：

| 指标 | 上限 | 怎么量 |
| --- | --- | --- |
| 每轮建议模型调用 | **≤ 1**（无人观看时 **0**） | `suggest.js` 内部计数器，测试断言 |
| 建议输入长度 | ≤ 6000 字符（沿用 `MAX_INPUT_CHARS`） | 单元测试 |
| 建议输出 tokens | ≤ 200 | 常量，测试断言 |
| 建议调用超时 | 15 s | 常量，测试断言 |
| 失败冷却 | 60 s（同路由） | 单元测试 |
| `GET /suggestions` 载荷 | ≤ 2048 B | 新增 perf-budget 项 |
| 回合结束 → 芯片可点 | p50 ≤ 3 s（含一次模型调用） | 真机手测 + `at` 时间戳 |
| 每轮客户端 `load()` 帧 | **不增加**（复用现有 revision 提升） | `test/api.test.mjs` 既有断言不变 |

## 6. 明确不做

- **不持久化**：重启即失（与「面板开关是内存态」同一立场）。不引入 STATE_VERSION 4。
- **不给没有「上一轮」的场合**：第一轮、空会话、子 agent 会话不出建议。
- **不做无模型的启发式兜底**：宁可没有，也不出会骗人的句子。
- **不覆盖审批/提问提示**：宿主在等用户批准时，输入栏上方是审批卡，我们的芯片让位。
- **不做移动端点按替代**：本轮只有 `Tab`（以及芯片点击）。触屏没有 Tab 键这件事记在已知缺口里。
- **不做埋点**：本仓库没有遥测通道，不为这个功能开一个。
- **不做建议的「历史/更多」**：只保留最新一轮的 2–3 条。
- **不改 `skillEvolve` 服务的六成员契约**：建议与技能检测无关，`ui-evolve` 不新增对 `skillEvolve` 的依赖。
- **不做建议的自动刷新**：用户已经在改草稿时，幽灵不跟着变。

## 7. 固定 spec

### 7.1 数据流（一张图）

```
                     ┌──────────────────────── ui-evolve（服务端） ────────────────────────┐
一轮结束(session/event) │                                                                    │
   │                  │  watched(agent)?  ──否──▶ 什么也不做（等客户端来问）                 │
   └─────────────────▶│        │是                                                          │
                      │        ▼                                                            │
                      │  suggest.js: 取 Transcript.snapshot → 渲染 prompt body（≤6000 字符） │
                      │        → 一次结构化调用（≤200 tokens / 15 s / 每轮最多一次）            │
                      │        → 解析出 2–3 条「整句提示词」→ 存内存 map(agent → 记录)          │
                      │        → revisions.bump(agent)                                       │
                      └────────────────────────────────────────────────────────────────────┘
                                          │ SSE {agent, revision} （帧格式不变）
                                          ▼
                     ┌──────────────────── ui-evolve（客户端） ───────────────────────────┐

                     │      │                                                               │
                     │      ├─▶ 芯片：conversation.input.dock（order 10）                    │
                     │      │      点击 → setDraft(text) → submit() → 本地标记已用            │
                     │      └─▶ 幽灵：conversation.input.overlay                            │
                     │             ｜门控：本轮最新 & idle & draft=="" & phase=="plain"      │
                     │             ｜     & 无附件 & 输入栏聚焦 & 无菜单                     │

                     └────────────────────────────────────────────────────────────────────┘
```

### 7.2 服务端：`packages/ui-evolve/lib/suggest.js`（新文件，约 320 行）

**导出**：`createSuggestions({ llm, t, … })` → 一个实例，接口与 `summarise.js` 同构：

```js
{
  /** 一轮结束时记账。绝不 await 模型。 */
  note({ agentId, turn, snapshot, routeKey }) -> void
  /** 是否有可给的建议（客户端拉取时用于降级判断）。 */
  peek(agentId) -> { turn, items, dismissed } | undefined
  /** 取走并标记已用（点击/填充后调用）。 */
  consume(agentId, { turn }) -> void
  /** 本轮已用过（客户端据此不再显示）。 */
  isUsed(agentId, turn) -> boolean
  /** 清空（消息删除/回退、会话被删）。 */
  forget(agentId) -> void
}
```

**常量**（全部写成可被测试断言的导出常量）：

| 常量 | 值 | 理由 |
| --- | --- | --- |
| `SUGGEST_COUNT` | `3`（可配置 1–3） | Qoder 前 3 条；再多就不是「最可能」 |
| `SUGGEST_MAX_TOKENS` | `700` | **设计时写的 200 是错的**（落地后改成 700）：推理模型把思考算进同一个输出预算，220 时全部预算都花在思考上、正文为空。实测 700 才能既容下思考又留下答案 |
| `SUGGEST_TIMEOUT_MS` | `20000` | **设计时想的 15 s 也是短的**：实测一次 700 token 的调用要 12.6 s，客户端则等 25 s（必须先于服务端放弃），详情见 §8.6 |
| `SUGGEST_FAILURE_TTL_MS` | `60000` | 与摘要一致 |
| `SUGGEST_WATCHED_MS` | `90000` | 「最近 90 秒内这个 agent 被读过」＝有人在看 |
| `SUGGEST_MAX_ITEM_CHARS` | `120` | 超过就是一段话，不是一句可点的提示 |
| `SUGGEST_MEMORY` | `32` 个 agent | 与摘要缓存同量级的上界 |

**Prompt 形状**（必须与 `summarise.js` 的三条既定纪律一致，理由见那边的注释）：

- 单条 `role: "user"`，指令在前、`<transcript>` 块在后 —— **不用 `system`**，因为 `openai-completions` 适配器会给推理模型发 `role: "developer"`，网关不认就 400。
- `<transcript>` 用 `defuseMarkers()` 同样的规则防闭合（复用现成实现，不重写）。
- 指令明确：**输出整句、可直接发送的中文/与用户同语言的句子**；每条一个动作；不要「继续优化」这种需要二次解释的碎片；不要编号、不要前缀；给不出就输出空。
- 输出格式：每行一条，最多 3 行，行首不要符号。**解析时逐行 `trim()`**，丢掉空行、丢掉 >`SUGGEST_MAX_ITEM_CHARS` 的行、丢掉以 `-`/`*`/数字加点的行首标记（模型偶尔还是会给）。**解析失败 → 本次无建议，不发补丁请求**。

**闸门顺序**（每一步都能单独断言）：

1. `config.suggestions === false` → 不生成。
2. 该 agent 最近 `SUGGEST_WATCHED_MS` 内没有面板/建议请求 → 不生成，只记 `pending(agent, turn)`。
3. 本路由 60 s 内失败过 → 不生成。
4. 本轮已经生成过 → 不生成（每轮最多一次）。
5. 渲染出的 body 为空（那一轮没有可说的内容）→ 不生成。

**内存记录形状**（不落盘）：

```js
{ turn, at, routeKey, items: [text…], used: false, dismissed: false }
```

**与既有模块的关系**：`suggest.js` **不 import `summarise.js`**，两者只共享一件东西——调用方注入的 `route()` 闭包（`index.js` 里已有 `routeFor()`），因此「换模型」对两者同时生效、失败冷却互不影响。`defuseMarkers` 若被两处需要，抽到 `lib/markers.js`（纯函数，两行正则，抽出来反而更容易测）；**若评审认为不值得动 `summarise.js`，就在 `suggest.js` 里写一份并加注释指向那边**——这是唯一允许的重复，且必须有测试保证两份规则一致。

### 7.3 服务端：路由与事件

**新路由** `GET|HEAD /suggestions?agent=<id>`

- 与既有路由同一 `ROUTE_PREFIX`（`/api/ui-evolve`），同一鉴权/签名 cookie 规则。
- `GET` → `200 { agent, turn, items: [string…], used, dismissed }`；无建议 → `200 { agent, turn: null, items: [] }`（**不是 404**：404 会让客户端把「没有」当成错误，本仓库 `absence` 一律不用哨兵字符串表达）。
- `HEAD` → **无正文 200**（与所有既有路由同规矩，`test/api.test.mjs` 有一条总断言对此计数）。
- 每次 `GET` 刷新该 agent 的 `watched` 时间戳——「有人在看」这条信息就是靠它维护的。
- **命中 `pending` 时**（闸门 2 挡住过，现在有人来问了）当场生成一次，并复用同一次结果；这就是选项 3 的降级路径。

**事件侧**（`index.js`）：

- 现有回合结束路径里，加一行 `suggestions.note({...})`。**必须是同步调用**，不得 `await`。
- 建议就绪 → `revisions.bump(agent)`。**SSE 帧不变**（仍是 `{agent, revision}`）。
- 现有「消息删除/回退」路径 → `suggestions.forget(agent)`（Qoder 的做法：删消息即作废建议）。
- 既有 `agent/disposed` → `forget(agent)`。

**配置**（`packages/ui-evolve/lib/config.js` 新增 2 键，登记进 docs/27 §7 的配置表）：

| 键 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `suggestions` | boolean | `true` | 总开关。默认开：闸门 2 已经挡住绝大多数无谓调用 |
| `suggestionCount` | number | `3` | 1–3，越界夹到最近合法值（不报错） |

模型路由：复用摘要那条（`summaryProvider` + `summaryModel` 成对设置 → 会话自己的路由 → 目录遍历）。**不新增 provider/model 键**，避免配置面翻倍。

### 7.4 客户端：`packages/ui-evolve/lib/client.js`（新增一节，约 420 行）

手写 bundle，无 import、无构建；两处 UI 各自注册一个槽位，**沿用文件里既有的写法**（`window.__ModuleLoader__.load`、`ctx.slots.inject`、`--dsw-*` 主题变量）。

**舱位 A · 芯片**：`conversation.input.dock`

```js
ctx.slots.inject('conversation.input.dock', () => ctx.slots.register({
  name: 'conversation.input.dock', id: 'suggestions', order: 10, locale: NS,
}, SuggestionChips))
```

显示条件（**全部为真**才渲染，任何一条为假都整个不渲染而不是渲染空壳）：

| 条件 | 来源 |
| --- | --- |
| `config.suggestions` | 配置 |
| 有建议，且 `turn === 本站已知的最新已完成回合` | `/suggestions` + 本地 transcript 的 turn |
| 会话不在运行（`!running`） | `useSession` |
| 没有被用过、没有被关掉（`!used && !dismissed`） | 路由载荷 + 本地 |
| 输入栏没有被审批/提问占用 | 宿主既有状态 |
| 上次发送不在飞行中 | 本地 flag |

**交互**：

- 点芯片 → `setDraft(text)` → `submit()` → 本地 `used = true`（立即隐藏，不等服务端）。
- 键盘可达：`Tab`/`→` 在芯片间移动焦点，`Enter` 激活（t3code：可用性不是可选）。
- 不许出现「点了没反应」：`submit()` 抛错或返回假 → 把文字留在输入栏并显示一条提示（**这是刻意的**：用户的目标是发出去，草稿还在就还能重试）。

**舱位 B · 幽灵**：`conversation.input.overlay`

渲染：一个绝对定位、`pointer-events: none` 的层，**每次显示时现场测量**编辑器的 `getBoundingClientRect()` 与 `getComputedStyle().font*`，把幽灵文字画在光标行的起点。坐标**从不缓存**（宿主改边距就会漂）。

尾部键帽：`Tab` 单独渲染成一个 `<kbd>`，不并入提示词文本（否则用户会以为「Tab」是句子的一部分）。

**必须压掉宿主的 placeholder**：输入框为空时，宿主自己会画一行灰色占位符（「继续这个任务…」），位置与我们幽灵的起点完全相同，两者会叠在一起。做法：幽灵可见时给输入卡片根节点加一个属性（`data-dsse-ghost`），配一条作用域 CSS 把占位符 `content` 置空。这一条是原型渲染时实际撞出来的（第一版两个字符串叠在同一坐标），**不是设想**；测试里要有一条断言：幽灵可见时占位符不可见。

**TAB 填入之后芯片仍然在**：填充只作废幽灵，不发消息；芯片要等真正发送（点击）或回合结束才换。这样人按了 `Tab` 改了半句、又决定换一条建议时，不用等一轮。

显示条件：芯片那六条 **加** 下面四条：

| 条件 | 为什么 |
| --- | --- |
| `input.draft === ''` | 有草稿就不该覆盖人的输入 |
| `input.phase === 'plain'` | 命令菜单/引用选择进行中时，`Tab` 属于宿主 |
| `attachmentIds.length === 0` | 带附件时「最可能的下一句」通常不成立 |
| 输入栏处在聚焦状态 | Qoder 的「idle and empty」 |

按键（**捕获阶段**监听，只在上述条件全真时拦截）：

- `Tab`（无修饰键、`!isComposing`）→ `setDraft(text)` + `persistDraft()` → 本地 `used = true` → `preventDefault()`。**不发送。**
- `Escape` → 本轮隐藏（`dismissed` 仅本地，不回写服务端）。
- 其余键一律不拦截（尤其不能吞 `Shift+Tab`、`Ctrl+Tab`）。

**动作面的缺席规则**（本仓库硬规矩）：`inputActions` 拿不到时返回 `undefined`，**不返回假的空对象、不返回 `'unavailable'` 字符串**——那会让上游把「填失败」当成「填成功」（`index.js:398-411` 记过这个教训）。降级：幽灵整个不出现；芯片仍可点，走 `conversation.send(text)`。

**两次渲染的契约**：芯片与幽灵共用同一个「填入」函数 `fillDraft(text)`；芯片 = `fillDraft(text) + submit()`。这样「填充」只有一处实现，测一次覆盖两处。

### 7.6 原型

文本原型（真机样式见 `docs/prototypes/29-suggestions.html`，独立可开）：

```
┌──────────────────────────────────────────────────────────┐
│ 助手：改完了。三个测试文件都过，注册表加了 3 个断言。      │
│                                                          │
│ ┌──────────────────────────────────────────────────────┐ │  ← 舱位 A：conversation.input.dock
│ │  ↳ 跑一遍全量测试，确认没有回归                  →   │ │     （order 10，todo 与 queue 之间）
│ │  ↳ 把这次的改动写进 01-status 和 04-reviews       →   │ │
│ │  ↳ 顺手看看求和逻辑在空草稿时的边界              →   │ │
│ └──────────────────────────────────────────────────────┘ │
│ ┌──────────────────────────────────────────────────────┐ │
│ │ 让它把这次改动的测试覆盖补上        Tab              │ │  ← 舱位 B：幽灵（灰斜体，键帽独立）
│ │                                                      │ │     点 Tab 只填入，不发送
│ │                                                    ▷ │ │
│ └──────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────┘
```

按 `Tab` 之后：

```
┌──────────────────────────────────────────────────────┐
│ 让它把这次改动的测试覆盖补上▏                        │  ← 真实文本进编辑器，光标在句尾，可改
└──────────────────────────────────────────────────────┘
```

三条视觉纪律（写进客户端注释，别让人后来改掉）：

1. 芯片是**一句话**，不是「标题 + 说明」。Qoder 的 `text` 与 `prompt` 是同一个字符串是有原因的：任何需要二次阅读的标签都让人多想一秒，而这一秒就是功能要省掉的东西。
2. 幽灵是**灰斜体 + 键帽分离**，不与真实文本同色——否则用户会以为输入栏里已经有字了。
3. 芯片区有**虚线分隔 + 上方留白**（Qoder 的 `border-t border-dashed pt-5`），别做成输入框的一部分。

## 8. 风险与失败模式

| 风险 | 触发方式 | 兜底 |
| --- | --- | --- |
| 建议拖慢下一轮 | 生成被 `await` 在回合收尾路径里（Qoder 0.4.2 的坑） | `note()` 同步返回；测试断言「`note()` 返回时未发生任何模型调用」 |
| 幽灵位置漂移 | 宿主改输入卡片内边距/字号 | 每次显示现场测量，不缓存坐标 |
| 吞掉宿主的 Tab | 命令菜单打开时也拦 `Tab` | 条件含 `input.phase === 'plain'`；菜单打开时不监听 |
| 芯片指向翻篇的事 | 用户又聊了两轮，旧建议还在 | 只认「最新已完成回合」；turn 不匹配即不渲染 |
| 用完的建议还在 | 点过一次又出现 | 本地 `used` + 服务端 `consume` 双写 |
| 状态文件爆预算 | 把建议写进会话 JSON | **不落盘**（§6）——这条是硬的 |
| 每轮调用变成每事件调用 | 在 `session/event` 主链上无差别挂生成 | 只在回合结束（`usage`/`outcome` 那条既有路径）记一次账 |
| 幽灵与芯片文案不一致 | 两处各自拼字符串 | 共用 `fillDraft` 与同一份 `items` |

**回滚**：`config.suggestions = false` 一处即全关（服务端不生成、客户端不渲染）；文件级回滚只需删 `suggest.js` + 还原 `client.js` 那一节 + 去掉路由，四处，互不牵连。

## 8.5 落地之后：与设计不同的六处，与两轮评审改掉的东西

四个决策都按 §9 的建议执行（默认开、芯片=填入并发送、3 条、放进 `ui-evolve`）。实现完成后再回看，设计文档有四处必须改口，因为落地时发现了更真实的做法：

| 原设计 | 落地 | 为什么改 |
| --- | --- | --- |
| 第五道闸门是「有人在看」：`viewed` 集合 + `turn/end` 预热，90 秒内没人读就不生成 | **没有 `turn/end` 处理器**。只有 `GET /suggestions` 被 composer 索要时才生成 | 按需本身就是「有人在看」的证据；省掉一个会被遗忘的闸门，也彻底消掉「生成挡住下一轮」这一类缺陷（Qoder 0.4.2 的公开缺陷） |
| 载荷 `items: [{text}]` | `items: string[]` | 数组里只有一句话，对象是多余的壳；客户端同时接受两种形状，免得下次改线形时两半各自绿 |
| 「15 分钟 TTL 作废」 | 服务端 TTL + 客户端 `at` 判新鲜度，且 `at` 还是「这是不是新答案」的标识 | 只按时间作废不够：一次缓存的回放会让刚点过的芯片回到行上 |
| 逐行兜底「遇空行结束」 | 段落模型：列表可跨空行继续（只认项目符号），纯文本列表只在行数不够时才跨 | 一条规则不能同时做到「不被结尾那段公关话骗」和「不丢模型用空行隔开的三个项目」 |
| 「取最后两个回合 + 第一个回合」的抽样规则 | **只有一个回合**：`view.previous`。`view.turns` 是**数字**（看过多少个人类回合），不是回合快照数组 | 第一次真机验收时发现读错了字段，见 §8.6 |
| 组件直接 `props.useInput()` 读输入状态 | `props.useInput((state) => state)` | 宿主的 `use<Name>` 是 `useSyncExternalStoreWithSelector`，第一个参数是选择器，见 §8.6 |

两轮评审改掉的东西（全部已修并有断言钉住）：

- **P0**：服务端发字符串、客户端读 `item.text`，两个界面永远画不出来（DEF-193）。
- **`<turns>` 的闭标记没有消毒**：回合里引用一行含 `</turns>` 的日志就提前闭合数据块。`defuseMarkers` 因此加了 `tag` 参数。
- **句末判据**：ASCII 的 `.!?` 只在后随空白时才算句末（否则 `packages/ui-evolve/lib/suggest.js` 会被切成 `.../lib/suggest.`）；窗口里不能出现 `$`，它匹配的是窗口自己的末端。
- **JSON 尾巴**：`{"suggestions":[…]}` 后跟一句寒暄时，整段 JSON 会变成一个芯片。改为「只从正文开头的括号解析」，并且解析失败才落到行读取器。
- **`[fix] xxx` 这类合法条目**：标记守卫只属于行读取器，不能拦所有候选。
- **退役与新鲜度**：点过的芯片立刻退役；只有 `at` 变了（真的重买了一份答案）才让退役清空；15 分钟到点由一只定时器叫醒渲染。

## 8.6 首次真机验收：两处测试完全看不见的缺陷

两个界面在真机上**一个都没画出来**，而全量 4338 条断言、61 处突变、两轮评审都是绿的。两处缺陷都在「测试替身与真实线形不一致」这一类里，和 DEF-193 同一族：

**DEF-197：`useInput` 是选择器钩子，不带选择器就抛。** 宿主用 `useSyncExternalStoreWithSelector` 生成每个 `use<Name>`，第一个参数是选择器，内部按 `selector(snapshot)` 调用。组件写成 `props.useInput()`，于是渲染时抛 `TypeError: selector is not a function`——而这条异常被宿主的槽位错误边界吞掉，只在控制台留下一行 `slot entry crashed in 'conversation.input.dock'`。外面看到的现象只是「composer 上方没有那一行」。测试替身写成 `useInput: () => inputState()`，一个忽略参数的桩，永远发现不了自己少传了什么。

**DEF-198：`view.turns` 是计数不是数组。** `transcripts.view(agentId)` 返回 `{ turns, current, previous }`，`turns` 是**数字**（`this.turns = this.turns + 1`），`previous` 才是那个已结束回合的快照。`renderSuggestBody` 把它当数组过滤（`Array.isArray(view?.turns) ? … : []`），于是真实会话里 body 恒为空，路由永远回 `the turn left nothing to go on`，而测试夹具传的正是数组，一路绿。

两处的共同教训写进 DEF 记录：**替身必须复现被替身对象的签名，而不只是它的返回值。** 修法是让桩自己校验参数（`inputHook` 在没收到函数时直接抛），并把「计数字段」当成一条独立断言——只有同时喂过「数组」和「数字」两种形状，才能证明代码读的是哪一种。

修完之后，客户端套件 1044/0、`suggest` 206/0、突变 61/61，并且新增了一条突变专门钉住选择器：把 `hook((state) => state)` 改成 `hook()` 必须让套件变红。

## 8.7 席位迁移：从输入框上方挪到正文末尾

真机跑通之后，你给了一张截图和两句话，把这三条建议的**位置**判成了不合格。这一段记录为什么原来的位置是错的、新位置为什么是对的，以及新的对齐方式是怎么量出来的——因为这里每一个数字都是量出来的，不是抄来的。

### 原来的位置为什么错

第二版把三条建议注册在 `conversation.input.dock`：宿主画在**输入卡片正上方**的那条 strip。它在代码上没错（确实紧挨输入框，`order: 30` 排在 todo 的 0 与 queue 的 20 之后），但那个 strip 是**宿主的工具栏**，不是你回答的结尾：

- 它同时承载宿主的待办面板和队列面板。截图里那块地方当时正被「任务 9 已完成」占着，三条建议挤在同一片区域，既不像是「上面这段回答的下一步」，也不像输入框的一部分——两个身份都不是。
- 队列面板描述的是**已经提交的消息**，而这三条描述的是**你还没做的事**。同一个 strip 里放这两样，读者没法从位置判断哪个是过去、哪个是将来。
- 更要紧的是：它跟「回答」之间隔着一个输入框。Qoder 把建议放在回答末尾，是因为这三条在语义上**属于上面那段回答**——「这轮做完了，接下来可以做这些」。

### 新位置：`conversation.chat.turnTail`

宿主为每一轮对话在正文末尾留了一个槽位 `conversation.chat.turnTail`（`kind: "list"`，`scope: "session"`），渲染时把 `{ turn, seq, openFile }` 一并交给注册者。宿主自己的交付文件卡片、计划预览、排期卡片都注册在这里——也就是说，这是宿主认可的「这一轮的结尾」这个位置。

代价是它**每轮画一次**，所以这一行必须认领自己属于哪一轮，否则同一份建议会挂在每一个回合下面。

**第一版用数字认领，是错的**，而错法很值得记下来：答案里带的是 `previous.turn`，而 `transcript.js` 明确说这个数字是**本地**计数（*"The host numbers turns from the start of the session, and resuming an old conversation begins mid-sequence — using its number would make the panel announce 'turn 41' for the first turn a person actually saw"*），宿主 `props.turn` 是**绝对**号。两者只在「这个插件从宿主第 1 轮就看起」的会话里相等。续聊的旧会话里，建议会被取回、付钱、然后一个都不显示——最坏的一种失败：花着钱、界面空白、日志里全是成功。

改成的判据是**顺序**，不是编号：宿主每结束一轮就往 DOM 里追加一个 `[data-turn-tail]`，按顺序排；这三条描述的是**最新那一轮**之后的下一步。

```js
const tails = document.querySelectorAll("[data-turn-tail]")
const mine = node.closest("[data-turn-tail]")
const last = tails.length === 0 || tails[tails.length - 1] === mine
```

没有任何 tail 时（harness、页面跳转中）算作最新——那不是一个针对这一行的证据。`suggest.turn` 仍然随答案返回，但它不再参与判断：它现在只用来标记「这份答案描述的是哪一轮」，而认领交给顺序。

顺带删掉了一个闸门：原来芯片要求输入机 `phase === "plain"`。turn tail 只为宿主已知的回合存在，所以那个 phase 说明不了这一轮的任何事——它只说明你正在打字或正在发送。而「你正在打下一句」恰好是这三条最有用的时刻（改到一半，想对照另外两条）。幽灵仍然要求输入机静止，因为它是**替**输入框显示提示，输入框不空的时候那条提示就是谎话。

但**点击**仍然要门。删掉 phase 门之后芯片在回合进行中也能点，而点击的实现是「先 `setDraft`，再在一个微任务里 `submit()`」：机器忙碌时会拒绝那次 submit，种子却已经落进编辑器——读者正在打的那半句话被一条从没发出去的建议顶掉了。所以可见性与可点性分开：

```js
const armed = gates.idle === true && gates.empty === true   // 静止 且 输入框为空
```

三个界面因此各说各的：**幽灵**（输入框为空时才有）负责「按 Tab 开始」；**芯片**（一直可见）负责「点一下就发」，但只有在那一下真的能发出去时才可点；**两者都不动你正在打的字**。

顺带删掉了一个闸门：原来芯片要求输入机 `phase === "plain"`。turn tail 只为**已经关闭的回合**存在，所以那个 phase 说明不了这一轮的任何事——它只说明你正在打字或正在发送。而「你正在打下一句」恰好是这三条最有用的时刻（改到一半，想对照另外两条）。幽灵仍然要求输入机静止，因为它是**替**输入框显示提示，输入框不空的时候那条提示就是谎话。

### 对齐：为什么必须量，而不能写死

宿主没有把正文列的几何交给插件，插件也不该假设它。实测（1922px 视口）：

| 元素 | left | width |
| --- | --- | --- |
| 输入卡片（`[data-composer-overlay]` 的父元素） | 390 | 952 |
| 正文列（`[data-turn-tail]` / `[data-chat-turn]`） | 406 | 920 |

**正文列左右各内缩 16px。** 这个 16 不是主题常量，而是那一层 `padding` 的结果，并且会话区域是可拖宽的，窗口也会变。所以：

```js
const card = document.querySelector("[data-composer-overlay]")?.parentElement ?? null
const outer = node.parentElement.getBoundingClientRect()   // 父元素，不是自己
const target = card.getBoundingClientRect()
setBox({ left: Math.round(target.left - outer.left), width: Math.round(target.width) })
```

**原点必须是父元素，不能是这一行自己。** 第一版写的是 `node.getBoundingClientRect()`，而这一行随后被赋予的正是 `marginLeft: left`——于是它量的就是自己上一次写下的东西：16 进来、0 出去、16 又进来，无依赖数组的 layout effect 每帧重入，直到 React 报 `Maximum update depth exceeded`，然后整行被槽位边界吞掉。父元素的左边缘不受这一行的 margin 影响，所以这个减法里没有回路。

- **量不到就不猜**：找不到输入卡片时（harness、页面跳转中）不写内联样式，让这一行用正文列自己的宽度。稍微窄一点可以接受，钉死一个猜出来的像素不行。
- **跟着变**：`ResizeObserver` 观察自己和输入卡片，另外监听 `window.resize`（拖动会话区域不一定触发前者）。
- **反复量不等于反复重画**：`setBox` 里先比较再存，值没变就返回旧对象，渲染跳过。

### 回车符号在前

每一行以 `↵` 开头，`aria-hidden="true"`（按钮本身有 `title`，读屏不该把记号念成提示词的一部分）。它**不是 hover 提示**：鼠标移上去只是变深一点。记号的意思是「回车会把这句发出去」，只有在指针到达之前就在那儿才成立——三行常驻的箭头会被读成菜单，而三行常驻的 `↵` 会被读成「这三件都是可以按回车的」。

### 还有一件：事件流不能跟着席位走

搬进 turnTail 之后，拥有 `EventSource` 的组件从「每会话一个」变成了「每轮一个」。十个回合的会话会开十条 `/events` 连接，而浏览器对同源的 HTTP/1.1 连接上限是六个——到第六个，宿主的请求开始排队。

所以流留在**幽灵**身上：composer 每个会话只有一个，幽灵是它的子槽位；芯片只是读同一个 store。这不是随手挪的，是席位决定的：**一个每轮都挂载的组件不能拥有任何每会话的资源。**

### 这一段的教训

**「紧挨着」不等于「属于」。** 第一版把建议放在输入框上方，是因为它在几何上最近；但语义上的归属是上面那段回答。位置是产品语言的一部分：放错地方的正确内容，会被读成另一种东西（工具栏 vs 回答的结尾），而这个误读没法靠文案修正。第二个教训更细：**能量出来的几何就不要写死**——16px 是这一台机器、这一个主题、这一次窗口宽度下的差值。

第三个教训来自搬座位之后连着的两处：**一个位置换了，它的两个假设也一起作废了。** 数字认领假设「插件和宿主从第一轮一起数」，那在旧席位（输入框上方，与回合无关）下无所谓；事件流假设「这个组件每个会话只有一个」，那在旧席位下也成立。两处都不是新写的代码有 bug，是旧代码被搬到新前提上以后不再成立——所以搬座位时该问的不是「这行代码还能跑吗」，而是「它当初为什么可以这样写」。

### 第三处：两百二十个 token 全花在思考上（DEF-200）

前两处修完、宿主重启之后，路由仍然回空。这一处不是形状错，是**资源**错：`SUGGEST_MAX_TOKENS` 定的 220，而推理模型把思考计进同一个输出预算。同一段 prompt、同一个模型，只改 `max_tokens`：

| max_tokens | finish | 正文 | 用量 |
| --- | --- | --- | --- |
| 220 | `length` | 空 | `completion_tokens: 220, reasoning_tokens: 220` |
| 700 | `stop` | 合法 JSON，21 个答案 token | `completion_tokens: 283, reasoning_tokens: 262` |

于是 220 时**一条建议都不会有**，而且 `finishFailure` 只认 `error`/`aborted`，截断被读成「这个回合没有下一步」，还按正常空答案缓存一分钟。

修法三件：预算改 700（docstring 写上两个实测数字）；`run()` 加截断分支，把 `finish` 匹配 `length|max[_-]?tokens|truncat` 的答案当失败而不是当空；断言从「够不够小」改成正的绝对值 `=== 700`，并补一整块 `finish: 'length'` 的用例。

**这一处教的东西和前两处不同**：形状不对会抛错，资源不对只会安静地返回空——而空在这个功能里是合法且常见的结果（薄回合确实没有下一步）。凡是「调用模型再解析」的路径，替身至少要能表达失败：`finish` 要能是 `length`，正文要能为空，预算要能被断言。写进 `docs/28` §4 第八条同类判断里：**能安静返回空的东西，必须有一条用例让它返回「失败」。**

### 2.4 空答案与「问过了」不是一回事

真机验收里最长的一次误判来自这里：回合结束的帧到得很早，路由按还在沉降的正文回了一份空答案；客户端把「问过这个会话」记成真，于是**此后再也不问**。读者看到的是功能整轮不生效，而手动查同一个会话，路由明明已经返回了新的三条。

规则：

- 空答案装**一只** 15 s 定时器重问一次，用 `retried` 闩住，只试一次。
- 只一次，因为转录沉降是几秒内的事；真的没有内容的会话不该变成轮询——服务端的失败记忆是一分钟，越过它之后的每一次询问都是真花钱。
- 新答案到手时清掉未触发的定时器；切换会话时同样清掉并复位闩。
- 断言必须区分三种状态：拿到答案、读到的是空、读失败（保留旧答案）。三者画出来的树在「没有行」这一点上相同，**只有定时器和请求计数能分辨**。

## 8.8 提示词里的截断：模型读到的最后一句必须说自己是省略

真机第一次跑出三条建议时，第一条是「**补完被截断的第二部分回答，说明与 Qoder 在触发时机上的完整差异**」。上一轮的回答本来是完整的——是我们自己把它切了，切在句子中间，没有留任何标记。模型读到一句停在半截的话，它唯一合理的解释就是「这段没说完」，于是把「补完」当成了下一步。**这不是模型判断失误，是我们在提示词里写了一个错误的句子。**

### 三层裁剪，三层都是裸 `slice`

| 层 | 位置 | 改前 | 预算 |
| --- | --- | --- | --- |
| 快照里的助手正文 | `packages/ui-evolve/lib/transcript.js:582` | `this.said.join('\n\n').slice(0, 1200)` | 1200 字符 |
| 装配好的提示词正文 | `packages/ui-evolve/lib/summarise.js:233` | `lines.join('\n\n').slice(0, MAX_INPUT_CHARS)` | 6000 字符 |
| 建议专用正文 | `packages/ui-evolve/lib/suggest.js:627` | `renderPromptBody(previous).slice(0, MAX_TURN_INPUT_CHARS)` | 4000 字符 |

第一层和第二层各切一次，第三层在**已经带标记**的产物上又切一次——这一层是我修完前两层之后自己造出来的，见下。

### 修法：标记说发生了什么，指令说该怎么办

两件事必须都做，缺一件都不够：

- **标记**（文本自己说）：`packages/ui-evolve/lib/transcript.js` 新增导出 `excerptOf(text, limit, mark)`，超限时优先在最后一个空行处收口，其次在最后一个句末标点处收口（`。！？`，以及后随空白的 `.!?`——被裁的正文里全是 `suggest.js`、`e.g.` 这类文件名与缩写，照单全收会切出 `.../lib/suggest.`），只有边界落在窗口后半段才采用，否则按预算硬切；末尾追加 `\n\n` 加一句 `SAID_CUT_MARK` / `INPUT_CUT_MARK`。
- **指令**（模型该怎么办）：`packages/ui-evolve/lib/suggest.js` 的 `INSTRUCTION` 增加五条，明确「下面这一轮是节选；一句话停在中间意味着节选被切了，不是助手被打断了；永远不要提议补完、继续或复述上一条回答；如果节选看起来没写完，照样提议下一件事」。

只做标记，模型仍会礼貌地补完；只做指令，它得先猜为什么那句话断了。

### 第三层：同一个错误在同一个文件里出现两次

改完前两层、三套测试全绿、82 条突变全杀之后，我逐行读自己的 diff，发现 `renderSuggestBody` 是这么写的：

```js
return renderPromptBody(previous).slice(0, MAX_TURN_INPUT_CHARS)
```

`renderPromptBody` 的返回值从此有了一条约定：**它自己会收口，并在末尾说明自己被收过口**。而这一行在同一个 commit 里就违反了它。摘要预算是 6000，这里是 4000，所以**任何长度落在两者之间的回合，第二次 `slice` 都会把刚加上的标记切掉**——缺陷在那一整段区间上 100% 复现。

修法是把预算往下传，让收口只发生一次：

```js
function renderPromptBody(snapshot, limit = MAX_INPUT_CHARS) { … return excerptOf(lines.join('\n\n'), limit, INPUT_CUT_MARK) }
export function renderSuggestBody(view) { … return renderPromptBody(previous, MAX_TURN_INPUT_CHARS) }
```

钉住它的断言必须落在两个预算**之间**，否则永远碰不到那个窗口：

```js
const between = { turn: 1, asked: 'x'.repeat(5000), said: '', paths: [], tools: [], commands: [] }
const once = renderSuggestBody({ turns: 1, previous: between })
check('a body cut once still says it was cut', once.includes('transcript ends here'))
check('and stays inside its own budget', once.length <= 4000)
```

`5000` 是这条断言的全部要点。写成 `'x'.repeat(12000)` 会同时超出两个预算，第二次切片照样把标记切掉——但那种样本在真机上从来不会出现，因为它连摘要都放不下。

### 这一节的教训

提示词里的每一段文本都是产品的一部分，而它一旦被程序裁过，就必须在文本里说明自己被裁过。**裁剪函数返回的不只是字符串，它是在替我们向产品陈述一个事实；陈述错了，模型就会照着错的做，而且做得很有道理。**

推论有两条，都写进了硬约束：

1. 一个函数一旦开始「替调用方收口」，调用方就不能再收一次口。这条约定要么写进签名（把预算传进去），要么写进断言（长度落在两个预算之间时标记还在）。
2. 长度断言必须问「切点后面像不像话没说完」，而不只是「够不够短」。这一轮之前，三套件里关于长度的断言**全部**是上界与包含关系，没有一条问过截断处长什么样。

### 8.8.1 句末规则的第二轮修正（DEF-207）

第一版的句末判据是 `Math.max(lastIndexOf('。'), lastIndexOf('！'), lastIndexOf('？'), lastIndexOf('. '))`——ASCII 一侧只认「句点 + 空格」，于是 `?` 和 `!` 后面的截断会落在词中间。而 `suggest.js` 里另一份副本写的是 `/[.!?](?=\s)/`，是对的。**同一个判据在一个仓库里有两份实现、一份对一份错，而错的那份正在生产提示词。**

合并成一个函数：

```js
const SENTENCE_END = /[。！？]|[.!?](?=\s)/g
function lastSentenceEnd(window) {
  SENTENCE_END.lastIndex = 0
  let at = -1
  for (let hit = SENTENCE_END.exec(window); hit !== null; hit = SENTENCE_END.exec(window)) at = hit.index
  return at
}
```

三条细节都是踩出来的：

- **`/g` 正则的 `lastIndex` 是跨调用状态**，必须在入口清零。`test/registration.test.mjs` 在 DEF-191 里栽过同一个坑，这是同仓库第二次。
- **`(?=\s)` 不能写成 `(?=\s|$)`**：窗口是切片，`$` 会匹配切点本身，于是每个窗口都以「句子」结尾。这条变异在变异表里跑过——它永远杀不死，因为在窗口末字符处 `stop + 1` 恰好等于 `window.length`，与硬切兜底同解。**已作为等价突变移入 `known` 并写下推导，计数 84 → 83。**
- **ASCII 句点必须后随空白**：被切的正文里全是 `suggest.js`、`e.g.` 这类东西，裸句点绝大多数时候是词的一部分。少了这一条，切点会落在 `.../lib/suggest.` 后面，然后把它叫做句子。

对应的断言写法也变了：`test/transcript.test.mjs` 现在有两个**互斥**样本——段落分支的样本让句末分支产出不了，句末分支的样本让段落分支产出不了；再加上 `?`/`!` 样本与「路径里的句点不是句末」样本。判据的每条分支都有一个只为它存在的样本，这是这一轮唯一真正的新方法。

## 8.9 提示词改成分区预算：规则不计入，数据三区，预测而不是建议

§8.8 之前的那版提示词，实测下来是「指令占 90%、数据占 10%」：会话 `session-796ca485` 第 2 轮的完整请求 2194 字符，其中 `INSTRUCTION`（9 条）1979 字符，数据只有 215 字符 —— 一句用户提问、两个工具计数、一条编辑路径、一句回答。命中率低是必然的：模型几乎没读到发生了什么，却被九条规则管着怎么写。

用户据此给出五条裁决（m08783），照抄在下面，因为它就是本节的验收口径：

> 1. 前置的规则等内容不计入实际的统计……将字数限制分成不同区域的预算，而不是总预算。
> 2. 将用户的输入改成多轮，不作轮次限制但是作字数限制，超出限制之后自动淘汰旧的输入……需要用提示词标识过去的轮次输入只是参考，实际建议的生成是按照最近一轮生成的。
> 3. 模型输出内容部分……dsh 完成一轮后有一个汇报工作的动作，这个汇报往往是信息价值最高的，我们只根据这个汇报来生成。
> 4. 对于模型的工具调用、模型的文件编辑，这些我认为对建议生成基本没有帮助。
> 5. codex 的预测我认为很正确……对于允许弃权，codex 的方式也可以应用，字数上限也可以采用 codex 的写法。

### 请求的形状

一条 `user` 消息，两段，中间一条 `---` 分界：

- **规则区**（固定成本，不占数据预算）：12 条，含口径、长度、单一动作、名字从哪来、截断怎么说、怎么弃权。
- **数据区**（`<session>` 包住，三块，各自有预算）。

规则区仍然放在同一条 user 消息里而不是 `options.system`：`summarise.js:149-166` 已记录过，reasoning 模型在 `supportsDeveloperRole` 取默认值的 provider 上会被改写成 `role: "developer"`，网关随即回 `400 unsupported message role: developer`。

### 三块数据区与预算（字符）

| 区块 | 上限 | 淘汰规则 |
| --- | --- | --- |
| `<latest_request>` | 600 | 无（这一轮就是它） |
| `<requests note="earlier requests, oldest first; background, not the thing to answer">` | 合计 600，单条 200 | 自旧向新整条淘汰，最多 24 条 |
| `<report note="what the last turn reported when it finished">` | 1200 | 按句/段落收口并自报截断 |

- **「汇报」不是整轮叙述，是该轮最后一条助手正文**（`transcript.js` 的 `report: this.said[this.said.length - 1]`）。DSH 完成一轮时最后说的话就是结论，前面的是过程。旧的 `renderPromptBody` 把整轮拼接塞进来，结论被埋在中间。
- **工具调用、编辑路径、命令一律不再渲染**（裁决 4）。它们曾经占掉 215 字符里的一大半，而模型从「ops_inspect_local_file×1」里读不出下一步。
- 历史请求是**会话级**的：`transcript.js` 新增 `this.asks`（旧→新），`endTurn` 在 `this.previous = this.snapshot()` 之前 `rememberEarlierAsk(this.asks, this.asked)`；被放弃的回合上面那个分支已清空 `asked`，所以不污染历史。两道淘汰：单条 200 字符（带 `[request cut for length]`）、合计 600 字符与 24 条。
- 历史区在提示词里明确标注 `background, not the thing to answer`，并在规则里写「Build on the latest request and on the report of the last turn. The earlier requests are background」——这是裁决 2 的后半句：模型看得到过去，但只按最近一轮生成。

### 40 字符这个数是怎么来的（不再猜）

用户要求「先测试多少字符会触发换行，然后设置一个不超过阈值的上限」。实测结论和预期不一样：**芯片根本不换行** —— `.dsse-suggest-text` 上是 `white-space: nowrap; overflow: hidden; text-overflow: ellipsis;`。所以在 680px 的行里（文字区 642px）实测的是**省略号临界**：

| 内容 | 到第几个字符出省略号 |
| --- | --- |
| 纯中文 | 44（43 刚好放得下） |
| 纯英文单词 | 80 |
| 中英混排 | 122 |

「120 字符不会换行」只对混排成立，一句中文建议到 44 字就被截成省略号 —— 而建议里中文是最常见的情况。所以上限取 **40**，三种输入都留了余量。要保留 120 就得让芯片 `white-space: normal` 折两行，那是另一个设计决定，没有在这次里做。

### 允许弃权之后暴露的两处真缺陷

`MIN_SUGGESTIONS` 从 2 降到 1（裁决 5：允许弃权、一条也画），立刻暴露原来的「必须两条」配额一直在替后处理挡刀：

- `parseSuggestions` 里 `items.length < MIN_SUGGESTIONS` 会把**整组**丢弃，于是「I cannot help with that」这种整句拒答因为只有一条而被顺带扔掉。配额消失后它直接成了芯片。修法是补一张整句拒答表 `REFUSAL`（`NOT_AN_ANSWER` 是整词匹配，看不见整句）。
- 同理 `You could run the tests…` 这类助手口吻靠「少于两条」被挡，现在要 `ASSISTANT_VOICE` 自己认：扩到 `let me / let's / i'll / here's / happy to / you could / you should / consider …`。

第三处是判据用错了常量：`readSuggestionLines` 里「纯文本可以跨空行」原本写 `lines.length >= MIN_SUGGESTIONS`，`MIN_SUGGESTIONS` 是「几条值得画」的语义而且已经变成 1，改用它当「行还短」的判据会把列表后面那段收尾散文拉成第二条。改成字面量 `>= 2`。

### 一条等价突变

`return items.length >= MIN_SUGGESTIONS ? items : []` 改成 `return items` 这条变异，在 `MIN_SUGGESTIONS = 1` 之后**杀不死也不再不同**：两者只在列表为空时不同，而空数组两种写法返回的东西一样。已从变异表移入 `known` 并写下推导 —— 这与 §8.8.1 的 `(?=\s|$)` 是同一类：闸门恒真之后，「带守卫的直通」不再是一种行为。

### 8.9.1 真机采样：模型有一半的时候不按契约回答（DEF-211）

新版提示词上线后，用同一个会话（`session-796ca485` 第 3 轮：把 notetxt 改成 hello world）在本地网关上重放了四次，把**原始回答**与**每条候选的判决**并排打印。四次里只有两次给出契约里的 JSON：

| 第几次 | 原始回答 | 结果 |
| --- | --- | --- |
| 1 | `已将 notetxt 的内容改为 hello world。` | **被当成芯片**（判据没认出这是叙述） |
| 2 | 空字符串 | 无建议（模型什么都没说） |
| 3 | `{"suggestions":["查看 notetxt 当前内容","打开 notetxt 看看内容","确认 notetxt 里是 hello world"]}` | 三条，像人打的字 |
| 4 | `{"suggestions":["查看 notetxt 的内容","读取 notetxt 的内容","检查 notetxt 的字节数"]}` | 三条，像人打的字 |

真机那次（第 3 轮）路由回的是 `the model returned no usable suggestion (1 lines, 18 characters)` —— 与第 1 次同型：模型没有回答契约，而是回答了「已完成」的叙述。

两处修法：

1. **叙述不是下一步**。新增 `NARRATED_DONE = /^(?:已|内容已|现已|done|updated|created|wrote|written|fixed|changed|renamed|moved|added|removed)(?![a-z])/i`，在 `isProseNotAStep` 里直接丢弃。中文侧只留 `已` / `内容已` / `现已` 三个前缀，而不是逐个列动词 —— 第一版列了 `已将|已把|已写入|…`，采样里出现的 `已写入 notetxt` 就不在表里。「没有人会以『已』开头打指令」是这条规则成立的唯一理由；`改为 hello world`、`Change it to hello world` 这类祈使句照旧保留。
2. **被丢掉的那一行要出现在理由里**。理由从 `(N lines, M characters)` 变成 `(N lines, M characters, first: "...")`。旧的理由对「散文」「拒答」「空对象」三种情况是同一句话，而这三种要三种不同的修法 —— 真机上就是因为看不到那一行，整轮调试只能靠猜。

规则区还补了一句收尾：`Reply with that JSON object and nothing else: no sentence before it, no code fence, no explanation after it.` 模型对「最后一句」比「第一段」服从得多。

### 8.9.2 真机第一次给出芯片：判断是对的，但同一个动作出现了两次（DEF-212）

重启宿主后，真机上第一次拿到三条芯片。那一轮的任务是「在 `F:/test` 下新建一个 add.js」，而助手实际写出的文件名是 `addjs`（没有扩展名），于是模型给出的第一条是：

```
重命名为 add.js
把它改名成 add.js
再加一个 subtract 函数
```

前两条是**同一个动作换了说法**。第一条本身是本轮最有价值的建议 —— 它看懂了上一轮的报告（文件名错了）—— 但读者面对两枚一模一样的按钮无法判断该按哪个，这一行的可信度也就没了。

修法两条一起：

- 规则区加一句 `Never offer the same action twice, even worded differently.`（模型能自查的部分交给模型）。
- 后处理加一道**范围很窄**的折叠 `sameOffer(a, b)`：两条都含 `重命名|改名|命名为|命名|rename`，且**结尾的文件名相同**，就只留第一条。结尾取 `/([A-Za-z0-9_][A-Za-z0-9_.\/-]*)\s*$/` —— 中英文祈使句里宾语都落在句末，落在句中的（`把 add.js 的测试补上`）是另一个主语，比较它只能靠猜。
- **为什么不做得更宽**：`运行 add.js` 和 `检查 add.js` 也以同一个文件名结尾，但它们是两个不同的操作，正是好芯片该有的形状。判断「两句话是不是同一个动作」需要意义，后处理没有意义，所以只折叠能靠词表判定的那一族。

代价：别的同义族（例如 `补测试` / `加个测试`）仍然会重复。这条规则是止血，不是治本；治本在规则区那一句。

## 8.10 把思考真正关掉：不是「最便宜的档」，而是「不要那一档」

§8.9 之后仍有一条硬指标没达标：建议要 12~31 秒才出现。速度不是提示词问题，是**思考没关掉**。

### 8.10.1 三层根因

| 层 | 位置 | 事实 |
|---|---|---|
| 宿主适配 | `@earendil-works/pi-ai/dist/api/openai-completions.js` | 只有 provider 声明 `compat.thinkingFormat` 时才发思考参数。`"deepseek"` 分支：`options?.reasoningEffort` 为真 → `thinking: {type:"enabled"}`，为假 → `thinking: {type:"disabled"}`。**effort 的「有」就是「开」。** |
| 配置 | `~/.dsh/settings.yaml` 的 magpie provider | 没有 `compat`，宿主一个思考参数都没发；网关按自己的默认跑（实测「什么都不发」仍有 16 个思考 token）。于是 `low` 与 `high` 在线上毫无区别。 |
| 插件 | `packages/ui-evolve/lib/suggest.js` 的 `withCheapestThinking` | 菜单里没有 disable 档时**退到 `low`**——一个真值。即使前两层修好，这一步仍把「想便宜点」发成「认真想」。 |

### 8.10.2 网关上六种写法的实测

同一句 prompt、同一模型（`my-api/deepseek-flash`）、`max_tokens: 200`：

| 写法 | 思考 tokens | 耗时 |
|---|---|---|
| 什么都不发 | 16 | 541 ms |
| `reasoning_effort: "none"` | 12 | 319 ms |
| `enable_thinking: false` | 12 | 341 ms |
| `reasoning: { effort: "none" }` | 10 | 255 ms |
| `thinking: { type: "disabled" }` | **0** | **221 ms** |
| `chat_template_kwargs: { enable_thinking: false }` | **0** | **215 ms** |

结论：这个网关认 `thinking` 与 `chat_template_kwargs`，**不认** `reasoning_effort: none`。所以「关掉」在协议层长得像「什么都不发」。

### 8.10.3 两处修改

```js
function withCheapestThinking(controls, info) {
  const relaxed = { ...controls }
  delete relaxed.reasoningEffort          // 先退回「不要这一档」
  const efforts = info?.reasoning?.efforts
  if (!Array.isArray(efforts)) return relaxed
  const byId = new Map(...)
  for (const wanted of ['none', 'off', 'disabled', 'disable', 'minimal']) {
    const exact = byId.get(wanted)
    if (exact !== undefined) return { ...relaxed, reasoningEffort: exact }
  }
  return relaxed                          // 没有 disable 档就是「不发」
}
```

provider 侧加 `compat: { thinkingFormat: deepseek }`（备份在 `~/.dsh/settings.yaml.bak-thinking`），让「不发 effort」落成 `thinking: { type: "disabled" }`。

### 8.10.4 为什么测试没抓到

所有既有断言都在问「有没有按菜单里的 id 请求」——`reasoningEffort === 'low'`。没有一条问「请求里**不该**有什么」。补的两条反向断言：

- `'reasoningEffort' in stream === false`（菜单只有 `low/high`，或宿主已经解析出一个 `high`）
- 菜单同时给 `minimal` 与 `none` 时，必须选 `none`

第二条还顺手钉住了顺序：`minimal` 排在 `none` 前面时，模型会「礼貌地想一想」，仍是 12 秒而不是 221 毫秒。

### 8.10.5 教训

一个能力有三档（开 / 便宜 / 关）时，「选最便宜的」与「关掉」是两件不同的事，中间那一档经常贵得看不出来。设计开关前先问「关」在这个协议里长什么样——这里它长得像「什么都没有」。

## 8.11 「上一轮」不等于「刚刚那一轮」：中断的回合不画建议

### 8.11.1 缺陷

宿主 `turn/end` 的 `reason.kind !== 'completed'` 时，`packages/ui-evolve/lib/transcript.js` 的 `endTurn` 走丢弃分支：清空 `calls/delivered/produced/commands/said/asked`、把 `turn` 置回 `undefined`、**不产生 `previous`**、不写用户请求历史。

于是 `/suggestions` 读到的 `previous` 仍是**上一个完成的回合**。那一行建议会画在刚被中断的那一轮底下，内容却是更早那一轮的「下一步」——读者看到的是「我按了停止，它在给一件已经过去的事出主意」。

### 8.11.2 为什么不能靠 `previous` 自己判断

`previous` 的语义是「最近一次**完成**的回合」，这本身是对的：它是面板摘要、也是建议的原料。缺的是另一个事实——「最近关闭的回合是不是被丢掉了」。这两个事实不能从一个字段推出来：`previous` 为空只说明「从没完成过」，不能说明「刚刚停下」。

所以 store 多记一个布尔：

```js
/** Whether the turn that closed most recently was abandoned by the host. */
this.interrupted = false
```

- `endTurn` 的丢弃分支：`this.interrupted = true`
- `endTurn` 的完成分支：`this.interrupted = false`（**必须清**，否则一次中断会让这个会话往后的建议全部静默）
- `view(agentId)` 把它一起交出去：`interrupted: transcript.interrupted`

### 8.11.3 闸门放在买东西之前

`packages/ui-evolve/lib/suggest.js` 的 `suggestions()` 里，闸门紧跟「回合在跑」那条，位于 `renderSuggestBody` 与缓存查询之前：

```js
if (view?.interrupted === true) {
  return { enabled: true, items: [], reason: 'the last turn was interrupted', turn: previous.turn }
}
```

位置很关键：放在缓存查询**之前**，意味着中断的回合既不会画旧答案、也不会付一次新调用。读者按下停止，最诚实的回答是安静。

### 8.11.4 断言与变异

- `test/transcript.test.mjs`（228 → 231）：中断后 `view.interrupted === true`；随后一个完成回合把它清回 `false`；从未关闭过回合的 store 是 `false`。
- `test/suggest.test.mjs`（313 → 318）：`interrupted: true` 时 `items` 为空、`reason` 是 `the last turn was interrupted`、`turn` 是那个已完成回合、`prepare` 零次调用、且**不是 `busy`**（否则客户端会把唯一一次重试花在中断上，DEF-202 同型）。
- `scripts/mutate-suggest.mjs`（126 → 130）：`the store forgets that the last turn was interrupted`、`the view never reports an interrupted turn`、`a finished turn leaves the interrupted flag standing`、`an interrupted turn is offered the previous turn anyway`。

第三条是最容易漏的：标志只在一处被置回 `false`，删掉那一行之后**第一次**中断就足以让整个会话再没有建议，而所有针对单轮的用例仍然全绿。

## 8.12 补审之后补修的三处

`docs` 的第一版把这三处写成「未改」，用户问「有问题为什么不修复？」之后全部修掉了。留下来的是修法与代价，不是待办。

1. **中断标记穿过进程边界。** `snapshotOf` 多交一个 `interrupted`，`session-state` 写它、认它（只有它一条事实时也算有内容）、读回时同时留进快照并交给 `restore`，`transcript.hydrate` 接收它，但合并分支只在 `existing.ended !== true` 时接收——本进程里结束过的那一轮比磁盘新。见 DEF-220。
2. **恢复的那句不再画成芯片。** 恢复分支无条件 `stale: true`：它是给输入栏幽灵的，不是给这一轮回答下面的一行裁决。见 DEF-221。
3. **回合边界与答案落地的先后。** 边界不再清空，而是记住「屏幕上是第几轮」（`closeOffer`），芯片只在屏幕仍停在那一轮时隐藏；这个记忆四秒后自行放手，用来兜住另一种顺序——标记恰好指向它本该显示的那一行，而没有下一帧来纠正。`forgetOffer` 留给「新一轮开始」。见 DEF-222。

三处共同的教训只有一句：**「发现了但先记下来」是把仓库当笔记本**。评审报告的每一条要么变成代码，要么变成一条写明在等什么的裁决，第二种情况需要读者本人点头。
