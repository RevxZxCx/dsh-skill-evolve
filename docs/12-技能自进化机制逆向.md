# 12 · Qoder 技能自进化机制逆向

> 逆向对象：Qoder 0.5.7（`F:\Qoder\resources\app.asar`）。
> 本文与 [01-调研报告.md](./01-调研报告.md) 的关系：01 记录的是**产品层面**看到的「Skill evolution suggestions」（Settings → General）；本文补上**实现层面**能读到的服务、状态机与错误码。
> 与 [11-侧栏与面板机制逆向.md](./11-侧栏与面板机制逆向.md) 的分工：11 讲面板容器，本文讲面板里那一块「技能自进化」的业务逻辑。

## 一句话结论

Qoder 的技能自进化是**「会话结束后产出建议 → 人在侧栏看到 → 采纳后开一个新会话去执行」**的三段式。它不直接写 skill 文件，**采纳动作的产物是一个新会话**。

这一点决定了它整套设计：建议对象必须带 `sourceSessionId`（因为要回到原会话取上下文）；采纳必须能失败（新会话可能起不来）；建议必须能过期（原会话的上下文可能已经变了）。

## 一、运行时数据：先看真机

在 `C:\Users\26903\.qoder` 下能找到的自进化相关文件只有一个：

**`skill-usage.json`**

```json
{
  "qoder-helper:skills": { "usageCount": 1, "lastUsedAt": 1792900970758 },
  "qoder-canvas:canvas": { "usageCount": 2, "lastUsedAt": 1794374617908 }
}
```

三条事实：

1. **键是 `pluginId:skillName`**。技能归属于插件，不是全局扁平命名。
2. **只有 `usageCount` 和 `lastUsedAt` 两个字段**。没有候选、没有分数、没有 stale 标记、没有证据。
3. **没有「建议」的本地存储**。建议由主进程侧生成并下发，渲染层只消费。

其他文件均与自进化无关：`state.json` 只有 `{"lastLoginMethod":"job_token"}`；`settings.json` 只有 `enabledPlugins` 三项；`memory/` 下是用户画像（`user-profile.md`，frontmatter `metadata.type: user`）；`tasks/` 下 9 个 UUID 目录。

**结论**：**Qoder 把「技能使用计数」和「自进化建议」彻底分开了**。前者是本地朴素计数，后者是主进程按会话生成、随会话过期的临时数据。没有候选队列文件，也没有审批台账。

## 二、服务：`skillEvolutionService`

类 `g$`，服务 id `ns1 = n0("skillEvolutionService")`，通过 cordis 注入。

### 2.1 两个快照，两层模型

| 名称 | 键 | 内容 |
| --- | --- | --- |
| **全局** | `skillEvolution.model` | `{ ...iD1, status: "idle" }`，含 `enabled`、`suggestions`、`revision`、`pendingIds`、`batchPending` |
| **会话级** | `skillEvolution.sessions` | 以 sessionId 为键的对象，每项同样含 `status` / `enabled` / `suggestions` |

不支持的宿主用一份 `Hv0 = { ...H_, status: "unsupported" }` 兜底；初始 `H_ = { status: "idle", enabled: false, suggestions: [] }`。

**为什么要两层？** 因为「总开关」是全局的，但**建议是按会话生成的**。面板上要显示的是「这个会话产生了哪些建议」，而订阅必须全局——用户在会话 A 里，也要能知道会话 B 攒了建议。

### 2.2 订阅：引用计数 + 作用域版本

```js
watchSession(sessionId) {
  this.sessionConsumers.set(sessionId, (this.sessionConsumers.get(sessionId) ?? 0) + 1)
  this.scopeRevision++
  this.reload()
  this.loadSession(sessionId)
  let disposed = false
  return () => {
    if (disposed) return
    disposed = true
    const left = (this.sessionConsumers.get(sessionId) ?? 1) - 1
    if (left) this.sessionConsumers.set(sessionId, left)
    else { this.sessionConsumers.delete(sessionId); this.dropSessionModel(sessionId) }
    this.scopeRevision++
    this.reload()
  }
}
```

四个细节：

1. **引用计数**：同一会话被多处订阅时只加载一次。
2. **`disposed` 幂等**：重复调用 dispose 不会把计数减成负数。
3. **归零时 `dropSessionModel`**：不看这个会话了就把它的建议移出内存，避免长期会话把 `skillEvolution.sessions` 撑大。
4. **`scopeRevision` 单调递增**：用来标记「当前作用域变过了」，配合 `reload` 丢弃迟到的响应。

### 2.3 采纳：`actInSession`

```js
async actInSession(sessionId, id, action) {
  if (this.model.get().pendingIds.includes(id)) return
  this.patch({ pendingIds: [...this.model.get().pendingIds, id] })
  try {
    const result = await this.requestSessionAction(sessionId, id, action)
    if (result.sessionId) {
      this.navigation.push({ kind: "chatSession", sessionId: result.sessionId, surface: "conversation" })
    }
  } finally {
    this.patch({ pendingIds: this.model.get().pendingIds.filter(x => x !== id) })
    await this.loadSession(sessionId)
  }
}
```

**核心在 `result.sessionId` 那一行**：采纳成功后，主进程返回一个**新会话 id**，前端直接 `navigation.push` 跳过去。

也就是说：

> **Qoder 的「采纳」不是「写入 skill 文件」，是「创建一个执行任务的新会话」。**

这解释了所有相关文案——`create:"创建任务"`、`createSuggestion:"根据 {{name}} 的建议创建任务"`、`createAll:"为所有建议创建任务"`。**全是「创建任务」，一次都没出现「创建 skill」。**

`finally` 里两件事：清 `pendingIds`（即使异常也要清，否则按钮永久转圈）、`loadSession` 重新拉取（因为主进程的建议列表已经变了）。

### 2.4 批量：`actManyInSession`

```js
async actManyInSession(sessionId, ids, action) {
  if (this.model.get().batchPending) throw new Error("unavailable")
  const unique = [...new Set(ids)]
  const pending = new Set(this.model.get().pendingIds)
  const fresh = unique.filter(id => !pending.has(id))
  const succeeded = []
  const failed = unique.filter(id => pending.has(id)).map(id => ({ id, reason: "unavailable" }))
  this.patch({ batchPending: true, pendingIds: [...pending, ...fresh] })
  try {
    for (const id of fresh) {
      try { await this.requestSessionAction(sessionId, id, action); succeeded.push(id) }
      catch (error) { failed.push({ id, reason: error instanceof Error ? error.message : "unavailable" }) }
    }
    return { succeededIds: succeeded, failed }
  } finally {
    // 同样清理 pendingIds + batchPending，再 loadSession
  }
}
```

五个设计点：

1. **`batchPending` 是全局互斥**，为真时再点批量直接抛 `unavailable`。不做队列，直接拒绝。
2. **串行，不并发**。逐条 `await`，因为每次 `accept` 都会开一个新会话——并发开一堆会话不是用户想要的。
3. **已在 `pendingIds` 的先去重并记为失败**，理由是 `unavailable`，而不是静默跳过。用户能看到哪些没处理。
4. **部分失败不中断**，继续处理剩下的，最后返回 `{ succeededIds, failed }`。
5. **失败原因取第一条**：`bulkFailed({{reason: errors[failed[0].reason]}})` —— 一次只报一个原因，不堆叠。

### 2.5 单条动作：`requestAction`

```js
async requestAction(id, action) {
  const fn = action === "accept" ? this.client.acceptSkillEvolution : this.client.dismissSkillEvolution
  if (!fn) throw new Error("unavailable")
  let result
  try { result = await fn(id) } catch { throw new Error("unavailable") }
  if (!result.success) throw new Error(result.reason)
  return result
}
```

**三条错误路径全部归一成 `unavailable` 或主进程返回的 `reason`**。渲染层不自己编错误码，只做映射：

```js
h1.error(t(`chatSession.skillEvolution.errors.${error instanceof Error ? error.message : "unavailable"}`))
```

### 2.6 快照合并：`apply` 的版本守卫

```js
apply(snapshot) {
  if (snapshot.revision < this.model.get().snapshot.revision) return   // 丢弃旧快照
  this.patch({ snapshot, status: "ready" })
}
```

**迟到的旧快照不能覆盖更新的快照。** 这是异步订阅里最常见的一类 bug，Qoder 用单调 `revision` 一行挡掉。

### 2.7 变更订阅与失败态

```js
client.onSkillEvolutionChanged(() => {
  this.reload()
  for (const sessionId of this.sessionConsumers.keys()) this.loadSession(sessionId)
})
```

任何变更 → 重拉全局 + 重拉所有订阅中的会话。

会话级加载失败时：

```js
patchSession(sessionId, { ...H_, status: "error", suggestions: [] })
```

**清空建议列表**，而不是保留旧数据配一个 error 标记。理由是过期的建议如果还能点，点下去必然报错。

## 三、React 侧的接法

```js
function VD(sessionId) {
  const service = t1(ns1)
  const model = p1(service?.modelObs)
  useEffect(() => {
    if (sessionId) return service?.watchSession(sessionId)
    service?.initialize()
  }, [sessionId, service])
  return { model, service }
}
```

- 有 `sessionId` → `watchSession`，返回 dispose。
- 没有 `sessionId` → `initialize()`（全局模式，只看开关状态）。
- **会话模型取不到时回落全局 model**：`p1(...) ?? model`。这样即使会话级加载失败，面板至少还能显示开关状态。

## 四、建议怎么渲染（与 11 交叉）

建议**不是独立卡片**，而是「技能与 MCP」分组里的一批行：

```js
function sD1(suggestion) {
  return {
    id: `skill-evolution:${suggestion.id}`,
    kind: "runtime",
    origin: "automatic",
    label: suggestion.skillName,
    detail: "skill",
    target: { type: "message", messageId: suggestion.id },
    messageId: null, toolUseId: null, evidenceId: null, turnId: null
  }
}
```

一条建议被临时包装成一条 `kind:"runtime"` 的通用行，复用 `q41` 的行渲染。`detail:"skill"` 决定图标走 skill 分支。

分组过滤在面板层：

```js
const suggestions = !sideChat && model.snapshot.enabled
  ? model.snapshot.suggestions.filter(s => s.sourceSessionId === sessionId)
  : []
```

**按 `sourceSessionId` 过滤**：只在产生建议的那个会话里显示。侧边会话（`sideChat`）永不显示。

分组渲染：

```js
<TitledSection title="技能与 MCP" action={<SuggestionPopover suggestions={...} />}>
  {suggestions.map(s => <GenericRow item={sD1(s)} sessionFileStatusEnabled={false} />)}
</TitledSection>
```

`sessionFileStatusEnabled: false` —— 建议行不参与文件存活检查。`onRemove: () => {}` —— 空函数，只因为签名需要。

## 五、建议列表弹层

`nD1`，hover 触发的 popover：

| 行为 | 参数 |
| --- | --- |
| 打开延时 | `onPointerEnter` 120ms，且 `pointerType !== "touch"` |
| 关闭延时 | `onPointerLeave` 100ms |
| 位置 | `side:"left"`、`align:"start"`、`sideOffset:8`、`collisionPadding:16`、`surface:"solid"` |
| 最大高度 | `min(400px, calc(var(--radix-popover-content-available-height) - 38px))` |

**键盘与鼠标两套路径分开**：`onPointerDown` 把 `hoverIntent` 置假，`onKeyDown` 把 `keyboardNav` 置真。意思是——鼠标划过时自动打开，但一旦点下去就不要自动关了；键盘操作时则固定打开。

**渐变遮罩用 `ResizeObserver` 判断**：`scrollHeight - clientHeight > 1` 时才显示。同时 observe 容器和 `firstElementChild`，因为内容高度变化不一定改变容器高度。

## 八、状态机（从代码反推）

```
        会话结束
            │
            ▼
      [主进程生成建议]
            │  onSkillEvolutionChanged
            ▼
   status: "idle" ──reload()──> "ready"
            │                     │
            │                  有 suggestions
            │                     ▼
            │            pendingIds: []
            │                     │
            │             点「创建任务」
            │                     ▼
            │            pendingIds: [id]     ← 按钮转圈
            │                     │
            │          ┌──────────┴──────────┐
            │          ▼                     ▼
            │     success + sessionId     throw
            │          │                     │
            │   navigation.push()      toast(errors.X)
            │   （跳到新会话）               │
            │          │                     │
            └──────────┴───── finally ──────┘
                            │
                     pendingIds: []
                     loadSession()
```

**关键分支**：

- 没有 `sessionId` 返回 = 采纳成功但不开会话（可能只是更新了状态）
- 有 `sessionId` 返回 = 采纳成功且开了新会话，跳过去
- 抛错 = 什么都不做，只 toast

## 九、与本项目的对照

这一节只陈述事实，判断留给方案文档。

### 9.1 本项目的候选生命周期

配置键（`packages/skill-evolve/lib/config.js`）：

| 键 | 默认 | 作用 |
| --- | --- | --- |
| `candidateTtlDays` | 30 | 未批准候选的过期天数 |
| `staleAfterDays` | 90 | active skill 多久没验证算 stale |
| `maxCandidates` | 50 | 队列上限 |
| `approvalMode` | `'confirm'` | `confirm` / `direct` |
| `verifyCandidateSource` | `true` | 是否校验来源 |
| `promoteAfterUses` | 3 | 用多少次后晋升 |
| `invertAfterHarmful` | 3 | 多少次有害反馈后反转 |
| `hintRequired` | `false` | 是否必须有提示才会触发 |

**比 Qoder 完整得多**：有 TTL、有 stale、有队列上限、有晋升与反转。

### 9.2 采纳语义的差异（最大的一处）

| | Qoder | 本项目 |
| --- | --- | --- |
| 采纳动作 | 创建新会话 | 直接写 skill 文件 |
| 中间态 | 新会话里「确认方案」 | `{ staged: true }` = 批准后等模型写定稿（`candidate.awaitingFinal`） |
| 失败原因 | 7 个错误码，含 `hash_invalidated` | `{ ok: false, error }` |
| 过期 | `expired` 错误码 | `candidate.stale` 字段，`stale===undefined` 才是 live |

`packages/skill-evolve/lib/commands.js:88` 的 `/skill-review` 把队列分成 live 和 stalled 两组分别列出，stalled 的标注「可读不可批」。

`commands.js:135` 的 `/skill-capture <name> [--preview|--discard]` 负责批准/丢弃。里面有一条注释解释了为什么用 `findByName` 而不是 `find`：

> 同名旧候选 stale 而新候选 live 时，`find` 会误丢 stale 项并谎报成功。

### 9.3 面板不能自己造候选

`packages/skill-evolve/lib/index.js:1788` 的 `requestProposal`：

```js
requestProposal(agentId, skillName) {
  if (config.mode === 'off') return 'off'
  return hints.publish({
    agentId,
    signature: `panel:${skillName ?? 'any'}`,
    steps: [],
    text: [ ... ],
    kind: 'repeat'
  })
}
```

**它只往下一个 step 里塞一条提示**，让模型自己决定要不要调 `skill_candidate_submit`。注释写得很清楚：

> The panel cannot file a candidate itself — only the model knows what the procedure was — so the button publishes a hint into the next step and lets the model decide whether there is anything worth submitting.

**这与 Qoder 相反**：Qoder 的建议由主进程生成、前端只消费；本项目的候选由模型在会话里提交、前端只能「请求模型再投一次」。

### 9.4 本项目没有的东西

| Qoder 有 | 本项目无 |
| --- | --- |
| 批量采纳（`createAll` / `ignoreAll`） | 只能逐条 `/skill-capture` |
| 采纳后开新会话 | 直接写文件 |
| `hash_invalidated` 内容哈希守卫 | 无（只有 `stale` 时间判断） |
| 建议按 `sourceSessionId` 归属 | 候选是全局队列，不归属会话 |
| `revision` 单调版本号防旧快照覆盖 | 无（面板每次全量重读） |
| 引用计数的会话订阅 | 无（面板只管当前会话） |
| 全局开关 `skillEvolution.enabled` 与设置页 | 有 `mode: 'suggest' \| 'auto' \| 'off'` |

## 十、能抄 / 不能抄

### 10.1 能抄（纯业务逻辑，与宿主无关）

| 项 | 为什么能抄 |
| --- | --- |
| **`revision` 单调递增防旧快照覆盖** | 一行 `if (snapshot.revision < current.revision) return`，任何异步订阅都用得上 |
| **引用计数的会话订阅 + 归零清除** | 面板收起时释放内存，实现不依赖宿主 |
| **`finally` 里清 `pendingIds`** | 异常也要解锁按钮，否则永久转圈 |
| **幂等 dispose** | 重复调用不减成负数 |
| **批量串行 + 部分失败继续** | 逐条 await，返回 `{ succeededIds, failed }` |
| **错误码统一归一 + 前端只做映射** | 前端不编错误码，只用 `errors.${reason}` |
| **加载失败时清空建议列表** | 过期建议如果还能点，点下去必然报错 |
| **「有坐标 = 钉住」** | 见 11，同一思路：一个状态代替两个布尔 |

### 10.2 不能抄（语义不同，抄了就是错）

| 项 | 为什么不能抄 |
| --- | --- |
| **采纳 = 开新会话** | 本项目的采纳是直接写文件。抄「开新会话」等于砍掉自己更强的能力 |
| **建议由主进程生成** | 本项目没有主进程；候选只能由模型在会话里提交（`skill_candidate_submit`） |
| **`hash_invalidated`** | 需要内容哈希基建。本项目只有 `stale` 时间判断，加哈希是另一个工程 |
| **按 `sourceSessionId` 过滤建议** | 本项目候选是全局队列，没有会话归属字段 |
| **`createAll` / `ignoreAll`** | 本项目没有批量 API，`/skill-capture` 一次一个 |

### 10.3 值得警惕的一点

Qoder 的 `expired`、`hash_invalidated`、`not_pending` 三个错误码，对应的是**「建议在被看见之后、被点击之前，世界变了」**这一类竞态。

本项目用 `stale` 字段做了时间维度的处理，但**没有内容维度的处理**：一个 skill 文件在候选生成后被改动，现在的代码不会拦住。这是可以补的，但要先决定哈希存在哪、什么时候算。

## 十一、还没查清的

1. **建议是怎么生成的**。触发时机（会话结束？多少轮一次？）、用什么模型、prompt 长什么样——全在主进程压缩代码里，`main.js` 中 `skillEvolution` 22 处全是字符串或注入点，读不出逻辑。
2. **建议对象的完整字段**。渲染层只用到 `id`、`skillName`、`status`、`sourceSessionId`。`_v0` 里还读了 `suggestion.summary`（摘要折叠用），其余未知。
3. **`revision` 由谁生成**。只知比较发生在渲染层 `apply()`。
4. **`accept` 之后主进程到底做了什么**。返回 `sessionId` 说明开了会话，但会话里预置了什么内容（prompt？任务描述？）不可见。
5. **`skillEvolution.enabled` 与 `skill-usage.json` 的关系**。前者控制建议生成，后者是使用计数，两者之间没有找到写入关联。

**这一条边界必须重复**：本文所有关于「采纳后开新会话」的结论来自渲染层 `navigation.push` + `result.sessionId` 判断 + 文案「创建任务」，**是强证据但不是直接读到主进程实现**。
