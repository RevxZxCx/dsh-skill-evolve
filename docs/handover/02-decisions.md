## D-01 · 双触发电机：结构检测 + 回合反思

**决策**：两个独立触发源。结构检测看工具/命令序列是否重复出现；回合反思按回合数与工具调用数门槛定期问模型"这一轮有没有值得记的"。

**理由**：结构检测只看结构，对**非结构性知识全盲**——哪个 API 返回零行、为什么放弃第一种做法、人真正想要什么。这些恰好是最有价值的部分，而它们不会表现为"同样的三个工具又来一遍"。反思补这个盲区，但反思贵且噪声大，所以必须与确定性的检测器并存，而不是替代它。

**可观测的证据**：真实会话回放里，同一工具序列在 2 次后触发；反思路径在修复 `service()` bug 后 12 轮精确发布 2 次。

## D-02 · 证据闸门按角色分档，禁止模型自证

**决策**：证据分四类（`user` / `tool` / `action` / `self`），不同类支持不同强度的结论。`action` 类引文（模型自己做过的事）**不能单独支撑**一条技能。插件自己的 7 个工具从所有 lane 排除。

**理由**：如果模型能引用自己刚说的话作为"证据"，闸门等于没有——它会为任何提案找到"证据"。插件自己的工具经 `tool/call`/`tool/result` 到达，外观与第三方机器输出一样，所以必须按名字排除。

**代价**：跨会话批准需要候选在**源会话**里已通过校验。这条曾导致全部 candidate 卡在 `no-evidence`，见 `03-defects.md` 的 DEF-07。

## D-03 · 技能列表只列"本会话加载过的"

**决策**：面板第二模块显示本会话实际加载过的技能（按新到旧），不是已安装的全部。

**理由**：技能库可以有几十个，全列出来回答的是"没人问的问题"，还把真正重要的那一个埋了。**已安装 ≠ 被用过。**

## D-04 · MCP 列表从 `tool/call` 事件归集

**决策**：不从 `mcp_connector` 的存储或配置文件读 MCP 服务器，而是从插件自己监听的事件流里按 `mcp__<server>__` 前缀归集实际出现过的 server 名。

**理由**：配置文件写的是"配了什么"，不是"现在能用什么"。自己解析 connector 的存储会与其真实连接状态不一致，而**当前实际被调用过的**才是可信的。

## D-05 · 先写确定性检测器，反思作为补充

**决策**：P0–P2 阶段先做不依赖 LLM 的检测器并跑真实回放定阈值；反思是后来的补充。

**理由**：确定性部分可以离线验证、可以变异测试、不烧钱。把一个统计问题先做成确定性的，才知道反思该在哪些点上补。

## D-06 · 面板放在对话列旁的浮层，不占用宿主右栏

**决策**：用 `shell.overlay` + 绝对定位，贴在对话列一侧的空隙；不注册到宿主右栏。

**理由**：右栏是宿主放文件预览的地方，占了它意味着面板与预览不能同时出现。宿主也**没有**提供"对话列内部"的扩展点（会话级插槽只有 header 与 composer）。所以唯一的空间是对话列两侧的空隙。卡片**故意不设 `z-index`**，让宿主决定层级，侧栏展开时自然遮挡。

**被否决的替代方案**：
- 宿主右栏 tab —— 与文件预览互斥。
- `conversation.content` 全接管 —— 官方指引禁止，等于替换整个会话体。
- 固定偏移 —— 窗口一改或宽度手柄一拖就错，所以几何全部由 `measure()` 测量。

## D-07 · 面板可写，但只走同一个 `approve()`

**决策**：`POST /candidates` 委托给 `/skill-capture` 用的同一个 `approve()`。路由自己不实现批准。

**理由**：在路由里自己写文件等于**多开一扇没锁的门**——证据闸门与 confirm 握手都会被绕过。任何"为了快"而重实现批准的路由，都会在半年后变成两个行为不同的批准路径。

## D-08 · 候选按 `id` 解析，`id` 命中不了就是 miss

**决策**：`byIdThenName(queue, id, name)`——给了 `id` 就按 `id` 精确找，找不到返回 `undefined`（报 not-found）；只有调用方**没给** `id` 时才回退名字。

**理由**：同名候选可以共存（旧条目 stale 后模型再次提案同名），而 `findByName` 优先返回 live 行。于是「按名字操作一条 stale 行」会打到它的 live 孪生体——忽略会删错行，批准更会把用户没看过的候选写成技能。第一版为"兼容只传名字的旧客户端"而回退，这个回退就是缺陷本身。

## D-09 · 总结调用不使用 `system` 通道

**决策**：总结的指令拼进唯一的 `user` 消息正文前部，`options` 里删掉 `system` 字段。指令自带分隔符（`<transcript>`），正文入参前把该标签洗掉。

**理由**：宿主把 `system` 渲染成 wire 上的 `developer` 角色，有些 provider 直接拒绝——面板曾在被正确选中的模型上报 `400 unsupported message role: developer`。拼进 user 消息是**任何 wire protocol 都接受**的做法。分隔符必须洗掉，否则一个内容里带 `</transcript>` 的工具输出会提前结束块，让剩余部分被当作指令读。

## D-10 · 总结默认借用本会话自己的模型路由

**决策**：默认从会话自己的 `request/context` 事件读路由，而不是从目录里挑第一个模型。

**理由**：会话正在用的路由**已知可达且对这个账号有授权**；目录条目只证明某个 adapter 声称支持它。早期版本挑目录第一个，在用户机器上报 "no model route is available"——那就是信任目录而非信任正在跑的会话的失败模式。

## D-11 · 测试必须配变异验证，`NOT APPLIED` 算失败

**决策**：每个守卫断言要有一个"把实现改坏"的变异证明它真的会失败。变异脚本必须先断言源码真的变了；锚点失配报 `NOT APPLIED` 并计入失败。

**理由**：不能失败的测试等于没在测。而**"变异没应用"会被误读成"存活"**——本仓库历史上多次因此得出错误结论（一次引号转义导致 `replace` 未命中，报 SURVIVED，实际什么都没改）。

## D-12 · 删除不可观测的参数，而不是为它补测试

**决策**：`placeNear` 的 `alignTop` 参数已删除。它的两条臂是同一表达式（`clampTop` 幂等），126 组合零差异。

**理由**：守它的变异"存活"，看起来像覆盖缺口，会诱导下一个人去覆盖一个**任何输入都到不了**的分支。**不可观测的参数比没有参数更糟。**

## D-13 · 技能收益先补 L1

**决策**：先做「加载后发生了什么」的观察窗口（`outcomeTurns`，默认 2 个回合，写 `skill_result` 账本行），不做逐技能验收，不做对照实验。

**理由**：
- `uses` 的语义是**加载次数**，不是"用了并且有效"。
- `helpful`/`harmful` 是模型自评——刚花一回合照技能做完事的模型，最不可能判断这技能值不值。
- 真实账本里 `helpful`/`harmful` **全为 0**，效应侧是**空的**，不是差的。
- 需要先有一条"加载之后发生了什么"的记录，才谈得上收益。验证器只对声明了验收条件的少数技能存在（要改技能格式），且验证脚本是被执行的输入，需要单独审。
- 对照实验不该做进插件：无法保证隔离、会烧钱、属于实验设计，合理形态是仓库里的 CLI 脚本。

## D-14 · 三卡同屏与点击式候选审核

**决策**：保留分卡片侧栏，不用页签隐藏信息。「上一轮」「技能与 MCP」「产出文件」三张卡同时展示；技能和 MCP 在同一张卡内分组。「从本轮提炼」与「候选审核」是两个独立动作，审核使用点击打开的 modal，不再使用双层 hover 清单。

**理由**：用户需要同时扫读多种信息，页签会制造不必要的视图切换。hover 把发起提炼与查看队列混在一个按钮上，连续两层 hover 也让键盘和触摸操作不可靠。modal 让候选列表、证据和审批动作处于同一个明确上下文。

**保留的边界**：审批仍按候选 `id` 走既有 `/candidates` 与 `approve()`；confirm 模式保留行并显示等待定稿，stale 只读且可忽略，不新增第二条写入路径。

## D-15 · 排版实时跟随宿主

**决策**：面板、头部开关和 modal 不声明平台字体栈。客户端读取会话计算样式中的 `fontFamily`、`fontSize`、`lineHeight`，从宿主 `code` / `pre` 读取等宽字体，并监听宿主属性变化及代码元素插入/删除。

**理由**：硬编码字体会让插件在宿主修改字体、中文字体或辅助阅读字号后显得突兀，甚至破坏布局。使用计算样式而不是猜测宿主变量名，可以跟随当前实际渲染结果。

**实现约束**：普通流式文本插入不触发重复排版写入，只有相关属性或代码元素变化才同步；插件卸载时必须断开 observer 并移除全部 `--dsse-font-*` 变量。

## D-16 · 合并活动列表、空卡隐藏与紧凑操作行

**决策**：技能与 MCP 不再分区，合并为一个按最近使用排序的列表，用不同图标区分；没有内容的卡片默认隐藏；面板顶部不再显示标题块，只保留刷新、候选审核、设置一排。

**理由**：用户扫读面板时关心“这个会话最近用了什么能力”，分区和标题都会增加视觉成本。空卡片只会制造“这里应该有内容但没有”的疑问。顶部标题不承载操作，占用的是一排宝贵空间。

**实现约束**：最近使用需要一个跨类型可比较的序号，因此 `index.js` 维护单一 `recentUse` 时钟，技能加载和 MCP 工具调用都写入；`/panel` 为两类行输出 `lastUsed`，客户端只负责合并排序。没有 `lastUsed` 的旧响应保持稳定顺序，不会乱跳。

## D-14 · 面板配色只用宿主主题 token，不自带一套

**决定**：面板里所有颜色、边框、字体都写成 `var(--dsw-alias-*, 回退值)`，且回退值只作为「宿主样式表还没加载」时的兜底，不作为任何模式下的主色。

**理由**：宿主用 `body` 与 `body[data-ds-dark-theme]` 两套变量切换明暗主题，插件若自带颜色就必然要自己实现一遍深色模式，而它对宿主的配色演进永远滞后。用 token 则天然跟随，代价是名字必须真实存在 —— 这正好是 DEF-25 踩的坑：四个名字是照着假 fixture 抄的，取不到值就静默落到浅色回退上，浅色下看起来正常，深色下错得离谱。

**代价与对策**：token 名字属于宿主的内部契约，升级可能失效。因此把它变成可回归的：`scripts/extract-host-tokens.mjs` 从 asar 解出宿主当前定义的全部 token 写入 `test/host-tokens.txt`，`test/tokens.test.mjs` 断言 bundle 引用的每个 token 都在清单里。宿主升级后重跑抽取脚本即可，测试会在名字失效当天失败而不是等到某个人在深色模式里发现。

**被否决的替代方案**：
- 自带一套明暗配色：要维护两份，且在宿主的主题切换上再叠一层自己的判断，容易出现「插件是深色、宿主是浅色」的错配。
- 只在浅色下保证可读、深色交给用户：面板是常驻元素，深色下不可读等于坏了。

## D-15 渐隐是否出现由测量决定，不由 CSS 常量决定

**决定**：`Clip` 组件用 `useLayoutEffect` 比较 `scrollHeight` 与 `clientHeight`，据此设置 `data-clipped`；CSS 只在 `data-clipped="true"` 时画遮罩。`max-height` 保持无条件生效。

**理由**：截断高度是排版预算（标题栏是按这个高度设计的），所以它必须恒定；但是否溢出是运行时的布局事实，写成常量就必然在两种情况下错：短摘要被遮罩压暗，或长摘要被截断却没有提示。这两件事的判据不同，就不该共用一个开关。

**为什么用 layout effect 而不是 passive effect**：passive effect 在浏览器已经绘制之后才运行，首帧必然出现「文字被切、但没有渐隐」。对没有布局阶段的环境（测试桩、未来的非 DOM 渲染器）回退到 `useEffect`。

**被否决的替代方案**：
- 全用 `useEffect`：每次进入会话闪一帧，正是用户报告的「闪烁」这一类体感。
- 用 CSS `mask-image` 让遮罩自然只在溢出时出现：无法区分「溢出」与「刚好填满」，且 `mask-image` 在不支持的宿主里会静默失效，退化成无提示的截断。
- 按字符数估算：中英文混排与换行位置让字符数完全不能预测高度。

## D-16 面板隐藏卡片时保留设置弹窗

**决定**：卡片全空时返回 `settings`（通常是 `null`），而不是无条件 `return null`。

**理由**：设置弹窗由 `settingsOpen` 状态驱动。把整棵返回树短路掉，DOM 被卸载而状态仍为 `true`，等下一次有卡片时弹窗会自己复活 —— 用户没有重新打开它。渲染分支的短路只能吞掉「没有状态支撑的东西」，不能吞掉由状态驱动的节点。

**代价**：空态时返回的顶层节点从 `div.dsse-rail` 变成 `null` 或 `section.dsse-dialog`，宿主 overlay 里这个插槽的 DOM 结构会跳变。这是可接受的：overlay 是 `pointer-events:none` 的绝对定位层，没有布局依赖它。

## D-17 待审候选算作内容

**决定**：`hasAnyCard` 纳入 `pendingCandidates > 0`。

**理由**：顶栏那个「建议」按钮是面板里通往候选审核弹窗的唯一入口。一个没有上一轮内容、没有技能、没有文件、但队列里躺着三条待审候选的会话，如果按「没内容就全隐藏」处理，用户就只剩 slash 命令一条路。可见性规则的目的不是「空就干净」，而是「别让空面板看起来像面板」—— 有工作可做时不适用。

## D-18 按功能拆包，不按层拆

**决定**：拆成 `core` / `skill-evolve` / `ui-evolve` / `mcp-evolve`，其中 `ui-evolve` 与 `skill-evolve` **平级**，不是它的「前端」。

**理由**：`ui-evolve` 的四个模块（`api.js` `client.js` `transcript.js` `summarise.js`）在插件内**零 import** —— 它自己订阅 `session/event`、自己维护 transcript 与 recency、自己有 5 个配置键。它与技能侧唯一的接触面是候选队列，而那是运行时服务。按「前端/后端」拆会得到一个什么都不知道的渲染层，它的 12 个端点与 payload 形状全部由别人定义。

**代价**：两个包各订一份 `session/event`，同一批事件被读两遍。这是有意的：形状不同（一个要检测用的工具序列，一个要展示用的轮次摘要），共享状态会把两个包锁死在同一份数据结构上。

**被否决的替代方案**：① 保持单包、用配置开关隐藏卡片 —— 用户装的是「技能进化」，却拿到一整个客户端 bundle；② 把 ui 段做成 core 的一部分 —— core 会因此依赖 `webServer` 与 `react`，不再是纯库。

## D-19 面板与技能侧靠 cordis 服务连接，不靠编译期依赖

**决定**：`ctx.provide('skillEvolve', {...})` + 每请求 `ctx.get('skillEvolve')`。

**理由**：两包可以独立安装。`api.js` 里那 6 个依赖函数本来就用 `typeof deps.x !== 'function'` 判空后返回 `unavailable` —— 接口早就按「另一方可能不存在」设计，只是当时另一方在同一进程同一个 `apply()` 里。

**关键细节**：查找**不缓存**。cordis 的插件激活顺序不保证，缓存会在「面板先挂、技能后挂」时永久降级。`service()` 必须走 `ctx.get` 而不能用可选链 —— 未声明的服务在属性读取本身就抛错。

**代价**：类型上无法保证服务形状。两个包各自写下六成员的约定，改一处要同时改两处；靠 `test/index.test.mjs` 的 `mountBoth()` 端到端覆盖。

## D-20 测试留在仓库根，不随包走

**决定**：`test/`、`scripts/` 保持在根，四个包只带 `lib/`。

**理由**：1805 条断言里有一批是完整链路测试（面板路由 → 技能队列 → 落盘 `SKILL.md`）。按包拆散后它们要么变成跨仓依赖，要么被删掉——这是本插件唯一真正验证「两个插件配合正确」的地方。

**代价**：单包发布时 `npm pack` 不带测试，买家无法在本地跑这套断言。

## D-21 · ui-evolve 的观察数据自己留一份，不向 skill 侧要（2026-11-02）

**背景**：接手时看到 `lib/index.js:151-160` 的注释与 `lib/transcript.js` 的存在，容易误判为「面板读的是 skill 侧的 transcript」。

**决定**：面板侧**独占**自己的 `TranscriptStore`、`mcpToolsSeen`、`recentUse`、`loadedInSession` 四份状态，全部由它自己订阅 `ctx.on('session/event')` 填充；不与 skill 侧共享任何一份。

**理由**（`lib/index.js:151-160` 原文的三条）：

1. 两侧关心的字段不同——skill 侧要 `tool/call` 的 name/arguments，面板侧要完整的一轮。
2. 共享会让任一方的字段需求变成另一方的回归风险。
3. 每个事件都调一次服务，等于把检测器放进面板的关键路径，换不来任何收益。

**代价**：同一批事件被解析两次。**这是有界的**：每个会话几个短字符串，`agent/disposed` 时清掉（`lib/index.js:354-360`），不会随宿主 uptime 增长——除了 `mcpToolsSeen` 这个 Set 显式不清（`lib/index.js:293-295` 注释承认了这一点，理由是每个不同的 `mcp__<server>__<tool>` 只占一个短字符串）。

**注意**：这条与 `docs/08` 第 5 节的「建议复制而非共享」结论一致，但 `08` 当时说的是 `transcript.js` 归谁。最终归属是 **ui-evolve**，skill 侧有自己的一套读取逻辑，两边都不叫 `transcript`。

## D-22 · 上一轮卡片：展开用一个 prop 进 Clip，交互状态留两个布尔在 Cards（2026-11-03）

**背景**：需求是「hover 展开、移出缩回；点击后一直展开，再点缩回」，并明确要求**点击只改非 hover 时的状态**。

**决定一**：`Clip` 只接收 `expanded: boolean`，自己不持有 hover/click 状态。

理由：指针和点击都落在**卡片**上，不是落在摘要上。若让 `Clip` 自己监听，需要它向外申请更大的点击区域，等于用两层事件处理去模拟一层。`Card` 已经是事件落点，状态因此上提到 `Cards`。

**决定二**：`Cards` 用 `turnHover` 和 `turnOpen` **两个**布尔，卡片读 `turnHover || turnOpen`。

理由：这是需求里点名的冲突。合并成一个布尔在「hover 上去 → 点击 → 移开」下会自相矛盾：点击和指针写同一个槽，移开时清掉的就是刚被点击置上的那个值。两个布尔各自的写入者唯一（指针只写 hover，点击只写 open），冲突在结构上就不存在，而不是靠判断顺序去回避。

**决定三**：`Clip` 在 `expanded` 为真时**跳过测量**。

理由：见 `01-status.md` 同日第四节。一句话是「展开后测量会把可展开这件事本身擦掉」。这条不是优化，是功能性守卫，有专门的变异项守着。

**代价一**：`Cards` 多两个 state，每次 hover 进出都会让整个卡片列表重渲染一次。可接受——列表是个位数卡片，且 hover 本身就是低频交互。

**代价二**：展开没有动画。见 `01-status.md` 同日第五节，`max-height` 无法过渡到 `none`，任何绕法都会让时长与文本量成正比。

**代价三**：`Clip` 的测量结果要通过 `onClipped` 回调上抛给 `Cards`，多了一跳。选择它而非让 `Cards` 自己测量，是为了让「有没有隐藏内容」只有**一个**判定源——否则 `aria-expanded`、渐隐、`clickable` 三处可能各测各的、给出互相矛盾的结论。

## D-23 · 点击的理由按轮次标记，而不是按轮次清空（2026-11-03）

**背景**：D-22 定的两布尔模型在单轮内正确，但 `turnOpen` 不随轮次重置。首轮审查据此报了一处 P2。进一步的探针显示它和另一处 P1（`onClick` 未门控）合起来能把卡片送进「展开但没有关闭入口」的状态。

**决定**：`pinnedTurn` 存**在哪一轮被按下**（`""` 表示没有），`turnPinned = turnId !== "" && pinnedTurn === turnId`；测量同理，`clippedTurn` 记它描述的是哪一轮。两者都在读取处比较，不在写入处清理。

**为什么不选「切换轮次时清空」**：清空需要一次跨渲染的比较。放在渲染里就是在渲染期间写 state，React 会警告并要求额外一帧；放在 effect 里则中间隔着一帧，那一帧里旧值仍然成立——正是要消除的那个窗口。标记法没有窗口：值从写下的那一刻就带着适用范围，跨轮时在读取处直接不成立。

**代价**：多一个 state（`clippedTurn`）、多一次字符串比较，`turnId` 的计算提到渲染顶层。都是常数级。

**连带约束**：`turnId !== ""` 不可省。省掉它，`pinnedTurn` 的初始值 `""` 会匹配「没有轮次的会话」，把每张卡渲染成展开。`test/client.test.mjs` 里有一块专门构造「载荷没有 `turn` 字段」守着这行。

## D-27 · 一个字符串承载「测过哪一轮」和「有没有隐藏内容」两个事实（2026-11-04）

**背景**：D-23 之后 `turnClipped: boolean` 和 `clippedTurn: string` 并存。要表达「这一轮测过、没有隐藏内容」必须同时写 `turnClipped=false` 和 `clippedTurn=turnId`，漏写一半就得到一个自相矛盾的状态；`""` 这个 tag 本身也已经能表达「没有」，两个 state 有一半是冗余的。

**决定**：删掉 `turnClipped`，只留 `clippedTurn: string`。非空且等于 `turnId` = 这一轮测过且有隐藏内容；`""` = 测过、没有；其他轮次 = 结论作废。

**理由**：让两个事实**无法**不一致。这不是省一个 state 的问题——分离的布尔和 tag 之间没有不变量能自动维持，只能靠每个写入点记得同时写。

**连带约束**：`clippedTurn` 的 `""` 与 `pinnedTurn`/`hoverTurn` 的 `""` 语义必须一致（都表示「不成立」），否则三个 tag 的比较逻辑会分叉。

## D-28 · 轮次标记在会话切换处清空，而不只按轮次比较（2026-11-04）

**背景**：D-23 引入的 `pinnedTurn` / `clippedTurn` / `hoverTurn` 都以轮次号命名，但轮次号只在**一个会话内**唯一——每个 transcript 从 0 起算，两个会话停在同一轮次是常态。第三轮审查用探针证明：换会话后过期标记照样匹配，卡片为一个没人在看的会话展开；又因为展开时跳过测量（D-26 的门），这个状态无法自愈。

**决定**：在 `React.useEffect(..., [sessionId])` 里清空三个标记。

**为什么这不与 D-23 冲突**：D-23 拒绝的是「每一次渲染都比较上一轮与这一轮」——那需要在渲染期写 state（React 会警告）或在 effect 里留一帧窗口（旧值仍活）。**切换会话是一个事件**，不是每次渲染都要回答的问题，在事件发生的地方清空没有那个窗口。两条规则的适用时间尺度不同：D-23 管轮次之内，本条管会话边界。

**没选「把 sessionId 拼进标记」**：也可行（`${sessionId}:${turnId}`），但需要每个写入点都拼对，且让三个标记的语义从「轮次」变成「会话+轮次」的复合键。清空只在**一个**地方写三行，且读处保持不变。复合键的好处是「即使忘了清也不串」，但目前只有一处创建标记，清空更简单；若将来标记的写入点增多，应重新考虑复合键。

**代价**：切换会话时多三次 `setState`。都在同一个 effect 里，React 会合并成一次重渲染。

**连带**：清空必须放进已经存在的那个 `[sessionId]` effect，而不是新开一个。两个 effect 做同一件事会依赖顺序，而顺序在两个 effect 之间没有保证。

## D-29 · 测试的恢复步骤不能挂在可能失败的探测命令后面（2026-11-04）

**背景**：验证「新测试能否抓住 P2」时，把 `client.js` 备份为 `.bak`、删掉三行、跑测试，然后用 `node test/client.test.mjs 2>&1 | grep -E "^FAIL" && python -c "...os.replace 恢复..."` 串起来。这个仓库的失败行不是 `^FAIL` 开头，grep 匹配不到、返回码 1，`&&` 短路，**恢复那一步没跑**，源码保持在缺三行的状态。

## D-32 · 面板状态按会话持久化，单快照覆盖写，不回滚（2026-11-03）

**背景**：面板此前把所有观察数据放在进程内存里，宿主重启就空。用户（`m01350`）要求持久化「产出、技能和 MCP 调用」，并明确「界面并不是作为上一轮的展示，而是显示当前对话的状态」。同一轮还暴露了一个更要紧的错误：`mcpToolsSeen` 与 `recentUse` 是**进程级**的，会把 A 会话的 MCP 服务器显示在 B 会话名下——它先是一个正确性问题，然后才是一个持久化缺口。

**决定**：
1. 一个会话一个文件：`$DSH_HOME/plugin-data/skill-evolve/sessions/<sessionId>.json`（`packages/ui-evolve/lib/session-store.js`）。
2. 一个文件装全部三类事实（技能、MCP 服务器与工具、上一轮的 `previous` 快照）+ 两个版本号（信封 `VERSION`、内层 `STATE_VERSION`）。
3. **单快照覆盖写，不保存历史版本**。`write()` 只有「写临时文件 → rename」一条路径，没有 `.bak`、没有版本目录。
4. 三个累积器全部改为**按会话**，旧的进程级形状直接删除而不是留着并存（`packages/ui-evolve/lib/session-state.js`）。

**理由**（按选择逐条）：
- **为什么不是一个文件装所有会话**：归档与删除是**按会话**发生的，一个共享文件意味着「删掉一个会话的状态」要重写整个文件，而那是一次可能断电的读改写。
- **为什么不是三类各一个文件**：三类事实描述同一场对话在同一时刻的样子，面板在 `GET /panel` 里一次读完。三个文件 = 每次更新三次 rename、三份可能对不上「这是第几轮」。
- **为什么不做回滚**：用户明确说持久化不重要到需要回滚。面板展示的是**状态**，不是账本；丢一次写在写盘瞬间的变更，比让用户面对「哪个版本才是刚才那个」的界面更符合定位。代价要写在明面上：强杀点附近丢掉最后一次变更，而不是回退到某个更早的好版本。
- **为什么删掉进程级的旧形状**：留着并存会让两套数据在面板里竞争同一行显示，而它们的更新时机不同。用户要的是「当前对话」，进程级数据不可能是那个答案。

**代价**：
- 每次 `GET /panel` 在内存缺失时读一次盘（每会话只读一次，`SessionState.load()` 会把结果装进 transcript store，见 `packages/ui-evolve/lib/api.js` 的 `viewOf()`）。
- 进程级 MCP/技能数据消失后，**面板不再显示「这个宿主上用过的全部 MCP」**，只显示本会话用过的。这是有意的收窄。
- 写入合并到一个秒级定时器，`release()` 必须 flush，否则丢掉最后 1 秒。

**连带约束**：`agent/disposed` 上只能 `release()`，不能 `forget()`。宿主退出会 dispose 所有 agent，在 disposal 里删文件等于每次重启清空持久化——正是本决策要修的问题。测试 `test/persistence.test.mjs` 的 `'a disposed session still describes the skills it loaded'` 守这一条。

## D-33 · 随会话归档/删除清理，靠 `workspaceRegistry` 而不是事件（2026-11-03）

**背景**：需求 5 要求存储「随会话的归档和删除自动移除」。最初的两个实现假设在勘查后**都不成立**：

1. **`session/disposed` 不能当删除信号。** 宿主 asar 原文：「Emitted once when an announced session leaves the store, including publication rollback」——**宿主正常退出也会触发**。用它删文件等于每次重启清空持久化。
2. **归档不删磁盘。** `workspaceController.archiveSession` 的描述是 `Hide one known Session from Workspace grouping surfaces.`。实测 `~/.dsh/storages/workspace.json` 的 `global.archivedSessionIds` 有 6 条，而 `~/.dsh/sessions/*/*` 的 290 个会话目录**全部还在**，包括这 6 个。所以「写进会话目录就会随归档消失」也不成立。

宿主的 31 个 cordis 事件里**没有 archive / delete 事件**。

**决定**：清理依据是 `workspaceRegistry` 的两个方法，经 `service('workspaceRegistry')` 每次现查：
- `archivedSessionIds`（getter）→ 归档即删；
- `sessionKnown(id)`（async）→ 返回 `false`（确定不存在的缺席）才删。

驱动方式是 `packages/ui-evolve/lib/index.js:380` 起的 `ctx.effect` + `setInterval(..., PRUNE_TICK_MS = 60 * 1000)`，内部再受 `PRUNE_INTERVAL_MS = 5 分钟` 节流；`unref()` 以免挂住宿主退出。

**理由**：
- `sessionKnown()` 的官方注释就是「Only a definite miss returns false — a failing `sessionPersistence.list()` propagates so storage faults never masquerade as an unknown session」。**这是宿主自己给出的判据**，插件照抄比自创规则安全。
- 定时器而不是「只跑一次」：会话可能在宿主运行期间被归档，文件必须**当时**消失，而不是等下次重启。用户说的「不是一直保留」指的是前者。
- `workspaceRegistry` 不进 `inject`：它是可选服务，写进 `inject` 会让没装它的 profile 整体拒绝加载（本文件开头第三条硬契约）。

**三条安全规则**（`session-store.js` 的 `prune()`，`:264` 起）：
1. 两个来源都取不到 → **一个都不删**；
2. 宿主抛错 → 保留全部、停止继续问，记 `'session state: keeping everything, the host could not answer'`；
3. 与之独立的上限 `MAX_FILES = 500`，按 `mtimeMs` 删最旧——这一条**不需要宿主回答**，因此不能被前两条的提前返回带走。

**代价**：归档检测最坏延迟约 6 分钟（60 秒 tick + 5 分钟节流），不是即时。这是刻意的：把节流去掉就是每次面板轮询都走一遍目录与宿主索引。

**被推翻的初版实现（记录在此，因为它是一个真 bug）**：`prune()` 最初以 `if (archived === undefined && known === undefined) return 0` 开头。它冗余（每个删除点本就检查来源存在），唯一实际作用是把**上限裁剪也一起跳过**——于是宿主从不回答时目录会无限增长，恰好毁掉「不是一直保留」。已删除，`scripts/mutate-session-store.mjs` 有一条变异专门把它加回去（`'the cap waits for a host that may never answer'`），9 条断言会红。

### D-34 快照在事实到达时捕获，不在写盘时再问 transcript

`SessionState` 的 `schedule()` 里调 `snapshotOf(sessionId)` 并存进 `entry.snapshot`；`document()` 只读那一份，不再问 transcript。

**理由**：关机路径上 `release()`（异步）与 `transcripts.forget()`（同步）之间有窗口，晚到的那次写会在 transcript 已经消失后重新取快照，把一份好文件写成 `turns: undefined, previous: undefined`——而且完全静默，因为空文档是合法文档。

**不选的方案**：把 `index.js` 的 `release`/`forget` 调换顺序。它只把窗口变窄而不关掉（`release` 内部还夹着一次真实的 rename），并且让本模块的正确性依赖调用方的行顺序——任何新调用方都能重新打开这个洞。

**代价**：每会话多存一个快照对象引用（数据本来就在内存里，不复制）；写盘内容描述的是「事实到达时」的会话，而不是「rename 发生时」的会话，两者在正常路径上一致，在关机路径上前者才是对的。

### D-35 能抛的那一个表达式单独守，不守整个函数

`pruneSources()` 里只对 `registry.archivedSessionIds` 这个 getter 读加 try，失败时**只丢掉「归档」这一个问题**，`known`（会话是否还存在）照常提供。tick 层不再另加 try。

**理由**：第一版把整个函数包进 try，再在 tick 里也包一层。探针删掉 tick 那层，测试全绿——函数内的 try 已把异常吃干净，外层不可达。按 D-12 只留一层，留哪层由语义定：`sessionKnown` 是 `async`，同步不抛；唯一同步会抛的就是那个 getter。而「归档列表拿不到」不应该连累「宿主已删除的会话还留着文件」——那是另一个问题，且它的答案在同一 tick 上是可得的。

**代价**：注册表未就绪的那几秒里，归档清理会延后（下一个 tick 再试），但删除清理照常生效。函数不再声明「永远返回对象」，而是「凡是拿不到的问题就不问，不问就不删」。

**钉法**：`scripts/mutate-persistence.mjs` 的 `an archive list that cannot be read takes the whole sweep with it` 把 try 去掉，2 条断言红，其中一条是「宿主说已删的会话文件还留在磁盘上」。

### D-36 不可存储的 session id 不进内存，与不进磁盘同一条规则

`SessionState.load()` 加 `if (this.store.pathFor(sessionId) === undefined) return false`，与 `entry()` 已有的守卫同一条规则。

**理由**：`?agent=` 来自查询参数，`checkOrigin` 不校验格式。不拒绝的话每个不安全 id 都在 `bySession` 里留下一个条目：永远写不出去（store 拒绝）、永远不被 `prune` 清掉（`prune` 只在 `removed > 0` 且 id 在归档集合里时删内存）。这不是文件系统逃逸，是一个任何本地进程都能无上限撑大的 map。

**代价**：`load()` 拒绝时不记日志——它是轮询路径，记日志会变成每个 tick 一行。`entry()` 那条（累积器路径，每个 id 只发生一次）保留日志。

### D-37 `entry.snapshot` 表示「这份条目描述的回合」，由建立它的一方负责填

`load()` 在装条目的同时用同一份磁盘字节填 `snapshot`；`schedule()` 在事实到达时替换它；`document()` 只读它，不问任何活对象。

**理由**：D-34 把「写盘时不要问 transcript」立成规则，但只覆盖了事实路径。`load()` 也建立条目且不调用 `schedule`，所以「读回 → 关机」这条序列上 `snapshot` 是 `undefined`，写盘就把已完成的回合换成空的——而用户只是打开过面板。审查者用真实插件复现，重启后面板显示 `turn = 0`。

**不选的方案**：让 `flush()` 在 `entry.snapshot === undefined` 时跳过写。它会把「确实没有回合」和「有回合但没捕获到」当成同一件事，前者是正常状态且需要落盘（技能列表要写）。

**代价**：`snapshot` 的生命周期由两个地方维护而不是一个。约束写在 `load()` 与 `schedule()` 的注释里：**任何建立条目的地方都必须填它**。

### D-38 删除由执行删除的一方报告，不用事后读文件反推

`SessionStore.prune()` 维护 `this.removed`（本次清扫实际删掉的 id），`SessionState.prune()` 照着删内存条目。

**理由**：`prune()` 原先只按 archived 集合清内存，而 store 删文件有两个理由（归档 / 宿主说会话不存在）。第二种的内存条目残留，下次 flush 把整份文档写回，清理器的成果被一次无关的 disposal 撤销。

**被推翻的初版实现**：对没归档的条目再 `store.read()` 一次，读不到就删内存。错误在于**读不到不等于被删**——一次尚未落盘的写之后文件同样不存在，而那个条目里正装着等待写出的三个事实。探针显示它会丢掉正要保存的数据。

**代价**：`SessionStore` 多一个可变字段 `removed`，语义是「最近一次完成的清扫删了什么」，只对刚 `await prune()` 完的调用方有意义。这是刻意的最小暴露——传数组参数或返回结构体会改动 15 条既有变异与全部调用点。

### D-39 没有事实的条目由清扫无条件回收，不等 store 的回答

`load()` 给空记录打 `empty: true`；`prune()` 在任何 store 调用之前先把这个标记的条目全部删掉；`schedule()` 里 `entry.empty = false`。

**理由**：这类条目没有事实，所以永远写不出去，`store.prune` 遍历磁盘时看不到它，也不会有 agent dispose 它。不回收的话，任何本机请求都能用合法但不存在的 id 无上限撑大 `bySession`——第一轮只挡住了格式非法的 id，而那张表的注释写着「不能写、也不能被清」。

**不选的方案**：不进内存（每次轮询都读盘）。面板是轮询的，这让每次轮询变成一次 `readFile`。

**代价**：每 60 秒一次的全表扫描。条目数量级是「打开的会话数 + 一次轮询周期内出现过的幽灵 id 数」，两者都很小。

## D-40 在途的写落地后要回头看条目还在不在

`SessionState.flush()` 在 `store.write()` 的 then 里先确认
`this.bySession.get(sessionId) === entry`，不等就 `store.forget()` 并结束。

- **理由**：清扫按目录列表工作，看不到还没落盘的写；写这边只能自己回头看，
  否则 rename 会把刚被删掉的文件重建出来。
- **不选的方案**：让清扫先取消 `entry.writing` 再删条目——`writing` 是已经交给
  文件系统的 promise，取消它等于要求存储层支持中止，而 rename 一旦发出就不可撤回。
- **代价**：每次写落地多一次 Map 查；「写成功但条目已没了」这条路径要再 unlink 一次。

## D-41 清扫对「没有文件可看」的条目直接问宿主

`SessionState.prune()` 在按存储层报告清完之后，对 `considered` 之外的条目问宿主
（归档集合 + `known`），宿主说没了就删内存。宿主抛错时停止追问、保留其余。

- **理由**：清扫的删除依据来自目录，而在途写没有目录条目。这类会话不再归面板描述时，
  内存条目是唯一的残留，也只有问宿主才能知道。
- **不选的方案**：对每个条目 `store.read()` 一次看不到就删——「读不到」不等于
  「被删」，还没落盘的写同样读不到，会连未保存的事实一起丢。
- **代价**：多一次宿主往返（只对没有文件的条目）；宿主故障时这些条目会留到下一次
  能回答为止。

## D-42 谁做的判断谁报告：`considered` 与 `removed`

`SessionStore` 暴露 `removed`（这一轮删了谁）与 `considered`（这一轮看过谁，
跳过时为 undefined）。`SessionState` 只用这两个，不拿别的事实反推。

- **理由**：调用方要知道「哪些 id 已被这一轮判过」，用 `removed > 0` 或归档集合去近似，
  得到的是另一种语义——第一版这么做，立刻换来两条回归（间隔内重复问宿主、
  每个文件问两次）。
- **不选的方案**：把 `prune(){` 的返回值从数字改成对象——返回值是文件数，
  `index.js` 与测试都在用；另开两个属性改动面最小。
- **代价**：`SessionStore` 多两个可变字段，读之前要先确认本轮是否真跑过。

## D-43 写落地时，条目「被换掉」与「被删掉」是两件事

`SessionState.flush()` 落地后按三种情况分开处理：无条目 → `store.forget`；条目被**新记录**
取代 → 标它脏并再写一次；还是自己 → 正常收尾。

- **理由**：旧写带的是旧事实，新记录带的是面板正在显示的事实。删文件会销毁新事实；
  什么都不做会让磁盘停在会话回来之前的样子。两种错误方向，一种正确动作。
- **不选的方案**：比较「条目存在与否」就决定删不删——这正是第一版，它把「后来者」
  读成了「没人要」。
- **代价**：一次落地可能再多写一次；「写成功但换人」这条路径要多走一轮 flush。

## D-44 删除由执行者在删除的那一刻通知，不在循环结束后汇总

`SessionStore.prune()` 收 `sources.onRemoved`，三个删除点统一走 `drop()`：`forget` →
记 `removed` → `onRemoved(id)`。`SessionState` 用它同步删内存条目。

- **理由**：清扫的循环逐个 await 宿主，把通知放在循环之后等于给每一个 await 开一个窗口，
  窗口里落地的写会以为条目仍然被需要。在删除的那一刻通知，窗口不存在。
- **不选的方案**：循环结束后再统一清内存（第一版）——它只是把窗口缩小到一次函数调用，
  而不是消除；也不同于让写自己再查一次「我还在不在」（那是 D-40 已经证明会误判的方向）。
- **代价**：`sources` 多一个可选回调；`removed` 与回调必须由同一个 `drop()` 维护，
  两处不同步就会让调用方与存储层对「删了谁」有不同看法。

## D-45 空记录不授权任何文件

`SessionState.flush()` 在 `document() === undefined` 时，若持有该 id 的记录是
`empty: true`，先 `store.forget` 再返回。

- **理由**：`empty` 是面板自己的批注——「我看过了，什么都没有」。因此这个 id 下的文件
  不可能是这条记录授权的：它只能来自一条已被清扫判定删除的旧记录的在途写，而那个删除
  决定仍然有效。删在这里而不是等下一轮清扫，是把「文件不会比会话活得更久」变成不变量。
- **不选的方案**：(1) 只在 `flush` 的「换人」分支里判断空记录——只堵住被发现的时序，
  没覆盖别的路径产出的空文档；(2) 让 `load` 在文件不存在时不装空记录——等于每次轮询
  都回文件；(3) 等下一轮清扫——`PRUNE_INTERVAL_MS` 内任何一次 `load` 都会把文件读回来。
- **代价**：`empty` 记录在「无事实可写」时多一次 `unlink` 系统调用（通常 ENOENT，
  吞掉）。这条记录本来就不可能留下文件，代价是一次空调用换一条不变量。

## D-46 轮询频率决定窗口大小，而不是事件频率

- **理由**：`api.js` 的 `viewOf` 会被面板按固定间隔调用，因此「只在某次轮询恰好
  落在两个时刻之间才成立」的状态不是边角情形，而是**常态**。判断一条竞态的危害时，
  要用轮询间隔去乘，不能用事件间隔去乘。
- **代价**：凡是引入「只为省一次 I/O 而驻留内存」的记录，都必须额外回答「它会不会把一个
  应当消失的文件留住」，并在 `document() === undefined` 这类出口处对上答案。

### D-47 · `read` 的 `undefined` 不是「文件不存在」

`SessionStore.read` 返回 `undefined` 覆盖两件事：没有文件，和有文件但这一版读不懂（版本号、信封、
JSON 完整性、内部 session 名）。任何**要删除**的调用方都不能接受这个返回值，必须另问
`SessionStore.exists`。

不选的方案：让 `read` 返回 `{ ok, value }` 把两者分开。理由：`read` 的调用方有六处，其中五处只
关心"我能用什么状态"，改签名会让五处为一次的顾虑付代价；而 `exists` 是一个只有删除路径需要的
问题，加一个方法比改一个到处在用的返回值便宜。

代价：`exists` 与 `read` 之间有一个 TOCTOU 窗口，文件可能在两次调用之间消失或出现。这里接受它，
因为后果只是"多装一条空记录"或"少装一条"，都不是数据丢失。

### D-48 · 删掉别人的文件比留下一个孤儿文件更坏

第五轮用「空文档 ⇒ 删文件」修好了孤儿文件，第六轮证明它删掉的是别人写的文件。两个错误不对称：
孤儿文件让面板多显示一个已死的会话（可恢复、可道歉），误删让用户永久失去整段历史（不可恢复）。

所以现在的规则是：删除只允许由**确定的**证据触发（`archived` 命中、`known(id) === false`、上限
裁剪），"我读不懂"永远不算证据。这条约束的代价是：真正该删的文件如果同时读不懂，会一直留到
`MAX_FILES` 裁剪为止。

不选的方案：在记录里加一个 `foreign: true` 标志代替"不设 `empty`"。理由：那需要给同一个判据两个
反义字段，而"没有 `empty` 键"本身就已经表达了"没有授权"，再加一个就是同一件事的两种说法。

### D-49 · 一次读取回答「有没有」和「能不能用」

`SessionStore.inspect` 用一次 `readFile` 给出 `absent` / `present` / `foreign` 三态，`read` 变成它
的包装。删除权只属于 `absent`。

不选的方案：保留 `exists()`，在 `read()` 之后补一次 `bySession` 复查。理由：那只是堵住第七轮发现的
那个时序，「文件在两次调用之间出现」这条路径还在；而且每多一个可被调用的观测方法，下一个人就会再
问一次「那我该用哪个」。

代价：`read` 与 `inspect` 之间多一层包装，六处调用方看不到 `foreign` 这个事实——它们不需要。所有
读写错误都归为 `foreign`，所以一个真正损坏的文件会永远占着它那一份配额，直到 `MAX_FILES` 裁剪。

### D-50 · 每个 `await` 之后都要复查，不因为这个 `await` 是新加的就不查

`load()` 里 `inspect` 之后的 `bySession` 复查不是为 `inspect` 加的。规则是：异步读取之后，内存
里可能已经有更新的东西；这条规则与读取是什么形状无关。

不选的方案：把复查写进 `inspect` 的回调或者做成 `load` 的装饰器。理由：复查要读的是**调用方的**
内存表，存储层看不见它；把状态放在两个对象之间的回调里，比在两行代码之间多一个 `if` 更难读。

代价：`load` 里有两个看起来重复的 `if (this.bySession.has(sessionId)) return false`。它们守的是
不同的窗口，注释里写了各自守的是哪一段。

## 2026-11-04 · D-51 没读过盘的记录不许写

**决定**：每条记录带 `loaded` 标志；`flush()` 在写盘前先 `await load()`，`load()`
负责把磁盘内容与内存事实合并。只有已经读过盘的记录才免于读盘。

**为什么**：原来的判据是「内存里有这条记录就不读盘」，它把**存在性**当成了**新鲜
度**。宿主重启后会话事件先于面板轮询到达，`entry()` 会用第一条事件建出记录，于是
`load()` 永远不再读盘，第一次写盘就把磁盘上的整段对话换成这几秒钟的历史——7 个
回合、两条技能、一个 MCP server，静默丢失。这不是某条分支漏判，是判据错了。

**合并而非替换**：读盘的结果不能在两处各判一次。`absent`、`foreign`、`present` 三
种情况各自决定「装什么记录」，一遍说完；读盘后再取一次 `bySession`，让读盘期间到
达的事实覆盖文件。

**两个 `at` 计数器不能直接比较**：内存与文件的新近度计数器各自从零开始。合并时把
内存里已有的 `at` 全体按 `state.sequence` 平移，把文件知道的一切排在已发生的一切
之下，各自保序。

**不选的方案**：①「切换会话/ disposing 时清空」——清不掉「事件比轮询先到」这条，
因为记录是在 `entry()` 里建的，不在任何生命周期边界上；②「第一次 flush 时读盘」——
本轮就是这么做的，只是把读盘的判据改对了，没有第二套方案；③「记录里存一个
`fresh` 布尔而不叫 `loaded`」——同一个东西，但 `loaded` 描述的是发生过的事实
（读过盘），`fresh` 描述的是我的判断，前者不可被误读。

**代价**：每记录多一个字段；`flush()` 多一次 await 与两次重取（`entry` 与
`writing` 认领都必须在这个 await 之后），多出「在 await 之后重新认领」这段容易写错
的代码——第一版就写错了位置，靠 `concurrent flushes share one write` 这条断言抓住。

## 2026-11-04 · D-52 外来文件没有否决权，只有免于误删的权利

**决定**：本 build 读不懂的文件（版本不符、信封不符、正文损坏、正文写着别的会话、
读错误不是 ENOENT），记录不给它 `empty` 标志——那是否决 `flush` 删除的唯一依据。
但记录一旦有了自己的事实，下次写盘照常覆盖它。

**为什么**：这两个权利经常被混为一个。免于误删是必需的：用户可能退回旧 build，旧
build 读不懂新文档时不该把它擦掉。但「永不覆写」会让这个会话的全部技能与 MCP 调用
在内存里待到那个文件消失为止——那正是本模块存在的理由的反面（用户要的是重启之后
还记得）。last-write-wins 是第一阶段就定下的规则。

**测试怎么钉**：两半都要测，顺序也要测。先 `load` + `release`（= 关机），断言文件
字节不变；再 `load` + `rememberSkill` + `flush`，断言文件变成 `state: 1` 且带着新
事实。只测第一半会让人以为保护是全面的。

**代价**：旧 build 写过之后，新 build 再写一次就再也读不回旧文档的字段——但那本来
就是 last-write-wins 的定义。

## 2026-11-04 · D-53 变异锚点跟着代码走，报告的数字必须当场复跑

**决定**：改完源码之后，先跑一遍每个变异脚本并读**退出码**，再写任何「N killed /

**为什么**：这一轮审查指出我上一轮报的 `15 killed / 0 survived` 并不成立——真实输出

**判据**：`not applied` 与 `crashed` 都是失败，不是「差不多」。写进文档的数字必须

## 2026-11-04 · D-54 「有没有内容」只有一个判据

`SessionState` 里有两处要回答「这条记录算不算有东西可写」：`document()` 决定要不要写文件，
`absent` 分支决定要不要标成可回收的空记录。它们曾经各自实现，一个看 `snapshot.previous`，
一个看技能/工具计数，于是「只结束过回合」的会话被一边判有内容、一边判空，
文件写出来又被自己删掉。

**决定**：抽成模块级 `hasFacts(entry)`，两处都调它。

**不选的方案**：让 `rememberTurn()` 也往计数里加一个哨兵。那样计数器要表达两种不同的东西，

**代价**：`hasFacts` 是模块级函数而不是方法，读它的人要往上翻一屏才知道判据。

## 2026-11-04 · D-55 清扫的删除不被读盘窗口撤销

`load()` 曾经在每条分支末尾重新装回记录（`if (this.bySession.has(id) === false) set(...)`），
理由是「读到了就应该在内存里」。但清扫恰好在读盘窗口里删掉 id 时，这一句把删除撤销了，
于是被宿主判定不存在的会话又写出文件。

**决定**：`load()` 不装回记录。清扫的删除是决定，读盘是旧消息。

**不选的方案**：让 `prune()` 等所有在途 `load()` 结束。那要把清扫与读盘串行化，
面板轮询会因此阻塞在清扫后面。

**代价**：读盘完成时可能发现自己算出来的结果没人接收——那次合并白做。这是可以接受的，
因为它本来描述的就是一个已经被删掉的会话。

## 2026-11-04 · D-56 同一 id 的读盘单飞；等待用条件，不用时长

两件事写在一起，因为它们是同一次事故的两半。

`load()` 的全部守卫都在 `await` 之前求值，`loaded = true` 在 `await` 之后才设置，
所以同 tick 的两个调用者都能通过守卫、都合并一次文件。**决定**：`loading` Map 让第二个
调用者拿到第一个的 promise。**代价**：`load()` 被拆成 `load` 与 `readInto` 两半，
后者不可直接调用。

测试里等待闸门用的是 `setTimeout`，而被测代码什么时候到闸门是不确定的。
**决定**：`waitFor(condition, timeoutMs)`，超时返回 false 并让断言失败。
**理由**：抛异常不打印 FAIL 行，变异脚本会把整套记成 CRASHED，把测试缺陷伪装成工具缺陷。
**代价**：每个这样的块多一个 `waitFor` 调用和一个显式的 `check`；换来的是 120 次连跑无失败。

## 2026-11-05 · D-57 cap 的减法用 `survivors.length`，不用 `dated.length`

**背景**：`prune` 收集 `dated` 时对每个 id `stat`，失败就 `continue`（文件在列目录与读 stat 之间消失）。
于是 `dated.length ≤ survivors.length`，而删除用的尾参是 `dated.length - this.maxFiles`。
当 `dated.length < maxFiles` 时它是负数，`slice(0, -3)` 是「除最后三个以外的全部」——删掉最新、仍存在的文件。

**决定**：要删的数量是 `const excess = survivors.length - this.maxFiles`，取自 cap 实际衡量的那个列表。

**理由**：`dated` 回答的是「能定出年龄的文件有哪些」，`survivors` 回答的是「要保留的文件有哪些」。
cap 比的是后者。用前者做减法会在两种列表不等长时算出另一个问题的答案。
加 `Math.max(0, …)` 能挡住负尾参，但那是把错误钳成一个安静的错误——真到 `dated.length` 远小于
`survivors.length` 时，钳制后一个都不删，cap 就再也不生效了。

**代价**：要删的数量可能与 `dated` 的长度不一致，循环里 `slice` 自己会截断。
读者需要知道这两个数不同，所以代码里两个变量都留着名字，没有内联。

**连带**：`test/session-store.test.mjs` 的两个既有 cap 用例只放真实文件，两个长度永远相等，所以从未发现。
新用例用替换 `store.list` 追加不存在名字的办法造出这个缝——目录里有名字、磁盘上没有文件，
就是消失文件在代码眼里的样子，且跨平台同一个缝，不依赖 junction/权限。

## 2026-11-05 · D-58 删盘前问文件；但「清扫说它没了」这个判断要留在内存里

**背景**：`entry.empty` 是「我这侧读过盘、当时没事实」，不是「盘上现在没事实」。
两个宿主进程共用一个 `plugin-data` 是已支持的场景（`sequence` 平移就是为它写的），
所以 A 的 `empty` 记录在 `release` 时 unlink，会删掉 B 刚写的文件。

**决定**：`flush` 的「没有文档可写」分支改走 `dropIfOrphan`，重新 `inspect` 一次，
只在 `absent`、或 `present` 且文档里没有已完成回合 / 没有技能 / 没有工具时 unlink；`foreign` 一律留着。

**理由**：`empty` 是对**过去**的观察，`forget` 是对**磁盘**的写操作，中间必须再问一次。
`foreign`（版本更新或形状读不懂）留着，因为它可能是用户能回去的旧版本写的，而这里判断不出它有没有事实。

**代价与新发现的约束**：改完这个之后 `gone`/`archived` 两组用例立刻变红——被清扫删除的会话，
它的文件可能正是**这次删除触发的那次落地写**刚建出来的，于是「问文件」得到「有事实，保留」，
把一个宿主已判定消失的会话救了回来。所以 `SessionState` 增加 `this.condemned: Set<string>`：
`prune` 在删每个 id 的那一刻 `add`，`dropIfOrphan` 第一件事是查它。
它与 `entry.empty` 的区别在于——`empty` 是「我观察到什么」，`condemned` 是「宿主决定了什么」；
前者可以被后来的观察推翻，后者不能被文件推翻。

**不选的方案**：把 `condemned` 改成带时间戳的 map 以支持「会话后来又被恢复了」。
暂不做：宿主没有 unarchive 事件可订阅，时间戳只能靠猜的过期时间，那比没有更糟。

## 2026-11-05 · D-59 源码一律用 `edit`/`write` 改；必须用脚本时先写 `.tmp` 再 `os.replace`

**背景**：`_r11.py` 的 `save()` 写 `open(path, 'w', encoding='utf-8', newline=NL)`，
`NL` 是给 JS 字符串用的两字符转义 `\` + `n`，不是合法 newline 值 → `ValueError: illegal newline value: \n`。
但 `open(path, 'w')` 在 `newline` 参数**校验之前**就已清空文件，所以异常抛出时
`session-store.js` 已经是 0 字节。该文件从未被 git 跟踪，没有 `git checkout` 可退。

**决定**：改源码用 `edit` / `write` 工具。确实需要脚本做批量替换时：
(a) 先断言文本无 `\r`；(b) `newline` 传 `chr(10)`，绝不传含反斜杠转义的字符串；
(c) **先写 `.tmp`，校验通过后 `os.replace`**。

**理由**：`open(path, 'w')` 的破坏发生在参数校验之前，任何「打开再校验」的写法都不安全。
只有「写别处、成功后原子替换」这一种顺序能保证失败不留痕。

**代价**：脚本多几行；`os.replace` 在同一分区内是原子的，跨分区会失败——本仓库的临时文件与目标同目录，不受影响。

**恢复成本**（记下来，因为它说明了这条纪律为什么值得写）：文件无版本副本，靠
`test/session-store.test.mjs` 的 59 条断言、`scripts/mutate-session-store.mjs` 的 15 条锚点、
`session-state.js` 的全部调用点、以及 handover 的文字重建出 420 行。
测试是这次唯一完整的规格说明——**测试写下来的契约，比代码更耐丢**。

## D-60 · 回合计数相加，不取新旧

**背景**：每个 transcript 自己的 `turns` 从零开始数，磁盘上的 `turns` 是上一个进程数到的地方。
两者量的是同一段对话的两截，不是同一件事的两个版本。

**代价**：记录上多一个 `hydrated` 布尔；如果将来出现第三个写者，这个布尔要重新审。

**被否决的方案**：切换会话/重启时清零。清零需要在渲染期或 effect 里比较上一次的值，
两个位置都有窗口期，而标记在读取处就不成立，没有窗口。

## D-61 · 删除的原因随通知一起走

**背景**：`SessionStore.prune` 会因为两种完全不同的理由删文件——宿主的归档/消失列表，
以及文件数超出 `maxFiles` 上限。前者是对**会话**的判断，后者只是目录变大了。

**决定**：`onRemoved(id, reason)`，`reason` 取 `'gone'` 或 `'cap'`。
消费方只对 `'gone'` 清内存、盖 `condemned` 章；`'cap'` 只删文件。

**理由**：澄清一句被写进 `prune` 文档却没人执行的话——「Only files are removed here;
memory follows the agent's own lifetime」。对被 cap 裁掉的**活会话**清内存，
会丢掉它正在产生的事实，下次写盘只剩碎片，而且 `sequence` 从 1 重新开始。

**代价**：`drop` 多一个参数；任何新的删除理由都必须给出名字，不能复用 `'gone'`。

`gesture` 表示人手动打了名字。

**决定**：合并时，只有当「文件说 tool、内存记 gesture」才升级内存的那一条；

## D-63 · 断言要贴着契约写，不写下界

## D-57 勘误 · cap 的减数

第十轮记下的 D-57 写的是「cap 的减法用 `survivors.length`」。第十一轮推翻了它：
用 `survivors.length` 才是错的。`survivors` 是**目录里的名字**，
`dated` 是**能定出年龄的文件**，后者更短；用前者的数量去切后者，
`excess` 会大于 `dated.length`，于是 `slice(0, excess)` 退化成「全部」，
把所有能定年龄的文件都删掉——正确的上限下反而清空。

现在的实现是 `const excess = dated.length - this.maxFiles`：cap 数的是文件，
所以减数与被减数都取 `dated`。**D-57 的结论作废，其余部分（减法要减在同一个数上）仍然成立。**

### D-64 面板每次被读都问一次存储层，不由内存替它回答

`viewOf` 曾经先看 `transcripts.view(agentId)`，有就返回。理由看起来成立——内存里的
比盘上的新——但 `record()` 从第一条事件起就建 Transcript，而宿主重放事件早于任何一次
面板轮询，于是「内存里有」几乎总是成立，`load()` 一次都不跑：重启后回合数从 7 显示成 1。

现在的做法是无条件 `await state.load(agentId)`。这不会把读盘变成每 8 秒一次 I/O，
因为 `load()` 里 `loaded` 标记着一个已经读过盘的记录并直接返回 false。

代价：`viewOf` 变成 async 且多一次 `await`，即使答案来自内存。接受这个代价，因为
「盘上还有没有没读的东西」只有存储层答得上来，面板没有资格替它答。

### D-65 回合数只有一个作者：transcript 相加，存储层取结果

回合数在磁盘与内存里各有一半（上一个进程数到的 + 本进程数到的），必须相加一次。
曾经两个模块都加：`readInto` 合并时加一次，`transcript.hydrate` 再加一次。单个进程内
`hydrated` 挡住了重复，但 `release()` 只清 `session-state` 的记录、不清 transcript store，
于是同一份文件被第二次读进来时又加了一遍——文件里的数比面板上的大一倍。

现在 `readInto` 不在合并里相加，只保留 `current.snapshot`（供 `document()` 在
`restore` 之前使用），合并完成后无条件问 `snapshotOf()` 要一份并覆盖。相加只发生在
`transcript.hydrate` 里，由 `hydrated` 保证一次。

代价：`load()` 多一次对 transcript 的读取。接受，因为「谁是权威」比「少一次函数调用」重要。

### D-66 只有回合数的文件也是要写的文件

`hasFacts` 曾经只认技能、工具和 finished turn。一个所有回合都早退的会话三者皆无，
但它的回合数是真实的、要显示的、且重启后无法从事件重建的——于是它被判定为空，
`document()` 返回 undefined，`flush()` 直接返回，文件永远停在进程启动时的那个数。

现在 `hasFacts` 也认 `Number.isFinite(turns) && turns > 0`。这与 D-54（只有一个判据）
一致：`document()` 与 `load()` 共用它，改一处两边同时改。

### D-67 「有没有内容」仍然只有一份实现，现在连磁盘那边也走它

D-54 立的规矩是「`document()` 与 `load()` 必须给同一个答案」，做法是抽出 `hasFacts`。
D-66 把 `turns > 0` 加进这个答案时，只改了 `hasFacts`——但仓库里还有第三份判据：
`dropIfOrphan()` 判断「磁盘上这份文档是不是孤儿」时，自己重新数了一遍技能、工具和
`previous`，**不认回合数**。于是 D-66 明确要保住的文件，被同一个模块的另一处当成
孤儿删掉。

触发要两个宿主进程共用一个 `plugin-data`（仓库自己的测试就支持这个场景）：
A 先 `load` 到空盘、把记录标成 `empty: true`；B 写下只有回合数的文件；A 退出时
`release → flush → document() === undefined`，走进 `dropIfOrphan`，B 的文件消失。
实测重启后回合数从 4 变成 0，且没有任何日志。

现在的形状是 `keepsDocument(facts)`：接四个事实（skills / tools / previous / turns），
`hasFacts(entry)` 把记录的形状映射上去，`dropIfOrphan` 把文档的形状映射上去。两个
读者，一份判据，映射函数只做取值不做判断。

代价：磁盘侧的判据要单独读 `found.value.previous` 与 `found.value.turns`——它们在文档
顶层，`readState()` 不返回。这一点没有变，只是现在明确写在一处，而不是散在三处。

教训：**「把判据抽出来」只对当时在场的读者成立。** 下一个读者出现时，它不会自动
走到那份判据前面——它只会按自己看到的字段重数一遍。所以抽完之后还要问一句：
这个问题的答案现在有几个持有者？

## D-68 卡片头部不留固定高度，空出来的那条是已删按钮的遗产（2026-11-06）

**背景**：用户报「上一轮标题的下方没有任何显示，却空出了一条」，并指出另外两张卡也有同样情况。

**根因**：`packages/ui-evolve/lib/client.js` 的 `.dsse-card-head` 上写着 `min-height:42px`。那个高度是当年为了容纳「从本轮提炼」按钮而定的——按钮被删掉之后，标题行只剩一行字，42px 里约 40px 是空的。三张卡共用同一个 `Card` 组件，所以一处遗留变成三处。

**决策**：删掉 `min-height`，`padding` 从 `9px 11px` 收到 `7px 11px`，让头部高度重新由内容决定。

**理由**：固定高度只在「内容高度不可预测」时有用。这里的头部内容是标题加可选统计，高度本来就可预测，固定值唯一的作用是在内容变小时留下空白。删掉它之后，头部高度就是一行字加 14px 内边距。

**代价**：头部高度不再有下界。若某天标题被换成图标，头部会缩到比现在更矮。这是可接受的——真出现那天，需要的是一个下界而不是 42px 这个具体数字。

**连带**：这条推翻了 DEF-27 修复时「头部要撑住统计条」的隐式假设，但那条缺陷的主体（总结正文没有高度上限）不受影响。

## D-69 展开只由点击决定，hover 只表示「这里有东西可以展开」（2026-11-06）

**背景**：D-22 决定「hover 展开、移出缩回，点击常驻」，并为此用了 `turnHover` 与 `turnOpen` 两个布尔。用户这次要求改成：**hover 不展开，只在卡片下方居中显示一个提示，点击才展开**，且**触发域尽量大，整张卡片最好**。

**决策**：

1. `const expanded = turnExpandable === true && turnPinned === true` —— 展开只认点击。
2. `const turnHinted = turnExpandable === true && turnPinned === false && turnHovered === true` —— hover 只点亮提示。
3. 提示不是独立按钮，是卡片里的一个 `div`，带 `pointer-events:none`，因此点提示等于点卡片，整张卡都是触发域。

**理由**：原来的两个布尔是为了让「点击」和「指针」不写同一个槽。现在两者写的东西本来就不同——点击写「开着」，指针写「显示提示」——互斥关系由 `turnPinned === false` 这个前提保证，不需要再靠两个布尔抢同一份语义。

第三条的理由值得单说：把提示做成按钮，就得让按钮自己处理点击、自己进 Tab 序、自己有无障碍名称；而它本来只是卡片上的一行说明。`pointer-events:none` 让这一行在事件层面不存在，点击穿透到底下的卡片，键盘用户则直接用卡片自己的 Enter/Space。

**代价一**：提示挂在摘要下方，hover 进出会挂载/卸载它，卡片因此长高 26px。这是**接受**的取舍：另一种做法（提示浮在文字上）会遮住正在读的那一行，而 D-22 那种做法（hover 展开）会把文字在指针下推走六行。26px 比六行便宜。

**代价二**：`'点击收起'` 这个提示文案再也到不了——`turnHinted` 要求 `turnPinned === false`，而展开要求 `=== true`。第一次实现里留了一个三元写它，第三轮审查把这个不可达分支指出来，于是简化成只有 `'点击展开全文'` 一种。

## D-70 面板的状态变化走事件流，不走时钟（2026-11-06）

**背景**：用户问「这些统计数字能不能实时更新」，此前是 8 秒轮询。

**决策**：服务端持有 `LiveHub`（`packages/ui-evolve/lib/live.js`），在每个被消费的 `session/event` 之后 publish 一次；客户端用 `EventSource` 订阅 `/api/ui-evolve/live?agent=<id>`，收到 `panel` 事件就重新 `load` 一次。

**理由**：轮询是在猜「什么时候可能有变化」，事件流是被告知。8 秒既太慢（一轮工具调用里数字不动）又太勤（一个安静的会话每次都在问同一个答案）。

**关键细节一**：流里**没有载荷**，只有「这个会话动了」。内容仍由 `/panel` 唯一装配。理由是装配逻辑（读 transcript、读存储层、算统计）已经在服务端有一份，若流里再带一份快照，就有两个地方决定「面板长什么样」。

**关键细节二**：`transcript.record()` 改成返回 boolean。宿主把每个事件都送进这个函数，其中很多不会画出任何卡片（`session/token` 就是），为它们唤醒客户端是没人看得出理由的通知。

**关键细节三**：每写一个 chunk 都必须 `res.flush?.()`。node 会缓冲小写入，缓冲中的事件就是客户端还没收到的事件——测试里有一条 `and each write is flushed` 专门数 `res.flushed === res.chunks.length`。

**代价**：多了一条长连接和一套订阅生命周期（幂等 teardown、req/res 双向 close、25 秒心跳且 `unref`）。这些都在 `test/live.test.mjs` 的 66 条断言和 `scripts/mutate-live.mjs` 的 26 条变异里。

## D-71 卡片只在真会话上显示，判据是宿主发布的 `data-content-phase`（2026-11-06）

**背景**：用户报卡片在非会话页面也会出现。

**先否掉一个错误判据**：「找得到 `[data-conversation-content]` 就是有会话」。宿主在三种页面上都渲染那个元素，所以这个判据恒真。

**决策**：读同一元素上宿主自己发布的 `data-content-phase`：`active` = 真会话，`settling` = 正在打开，`hero` = 启动器/新会话页。`Overlay` 只在 `phase === "hero"` 时返回 `null`。

**理由**：让宿主告诉我们它现在放的是哪种页面，比我们从 DOM 形状去猜可靠。属性已经在 DOM 上，不需要新协议。

**关键取舍**：**属性缺失时保留卡片**（判据写成「等于 hero 才隐藏」而不是「不等于 active 就隐藏」）。理由是宿主版本可能比插件旧；对没有发布这个属性的宿主，保守做法是维持原行为，而不是让整个功能消失。

**连带**：`phase` 经 `place` 传递，**不走 `bridge`**。`bridge` 的改动只写在构造函数与 `notify()` 里，绕过去会让两份数据打架。

## D-72 「正在加载」用一行字，不画一列空卡片（2026-11-06）

**背景**：用户报进入对话区域时数据加载不全。历史上这个问题被修过一次，当时的做法是「什么都不画」。

**决策**：`const stillLoading = data === undefined`。当没有任何卡片、也没有错误、且还在加载时，画一行「正在加载…」；加载完就什么都不画。

**理由**：上一次「什么都不画」走得太远——加载期间面板整个消失，人看到的是一个空洞，不知道是在加载还是没有内容。而再往前那版「把 loading 当内容」画了一整列空卡片 + reading…，随后整体消失，是闪烁。

`data === undefined` 是这里唯一能区分「还没答」与「答了但确实空」的东西。没有它，后面这个状态会被误当成加载中，于是空会话永远显示「正在加载」。

## D-73 流打开后轮询降频而不是停止（2026-11-06）

**背景**：第一版在 `EventSource` 的 `open` 事件里 `clearInterval` 掉轮询，理由是流是正常路径、轮询是兜底。

**第二轮审查指出两个洞**：

1. `EventSource` 对**不可用**的响应（404、非 `text/event-stream`）会**永久放弃重连**。插件重载期间路由短暂消失，流就死在那里，而错误回调是空的——面板会一直停在旧数据直到切会话。
2. 面板里的 `pendingCandidates` 读的是**全局**候选队列，而流只在**本会话**的事件上 publish。别的会话或斜杠命令新增候选时，这里收不到任何通知。被删掉的轮询是它唯一的手段。

**决策**：`open` 时把 8 秒定时器换成 60 秒定时器（`IDLE_REFRESH_MS`），不删除。卸载时仍然 `stopPolling`。

**理由**：两个洞都不是「流坏了」，而是「流本来就不覆盖这件事」。一个覆盖面更小的通道不能取消覆盖面更大的通道，只能降低它的频率。60 秒对「几分钟才动一次的候选队列」足够，而 8 秒对「已经能收到事件的会话状态」是浪费。

**代价**：一个安静的会话每分钟仍有一次请求。这是刻意的，不是遗漏——它买的是「流死掉之后面板仍会自愈」。

## D-74 没有实时流：轮询是唯一通道，恒定 8 秒（2026-11-06）

**背景**：D-70 引入了一条 SSE 流（`LiveHub` + `GET /api/ui-evolve/live`），
让面板在「本会话有事件」时立刻刷新，并按 D-73 把轮询从 8 秒降到 60 秒。

**决策**：整条流被删除，轮询恢复为唯一通道，恒定 8 秒（`REFRESH_MS`）。

**理由**：用户放弃了这个需求，原话是「我认为这样会占用资源，实际体验并不好」。
技术上的账也对得上——**流替面板做的事，比它拿走的少**：

1. 流只替**一个会话**说话，而面板里的 `pendingCandidates` 读的是**全局**候选队列。
   别的会话、斜杠命令写入候选时，这条会话的流一声不响。
2. `files` 的 size/mtime 来自 `statTouchedFiles()`，**每次读面板时现场 `stat`**。
   别的进程改了被跟踪的文件不会产生任何会话事件——这条通道本来就不由事件驱动，
   只是过去 8 秒一次的定时器顺带把它覆盖了。
3. 于是「让流当快路径」的真实代价是：**唯一覆盖上述两件事的通道从 8 秒放慢到 60 秒**。
   这不是让面板更新鲜，而是让它看得更窄。D-73 已经承认了这一点（降频而非停止），
   这条决策只是把结论走完：既然流没有让面板看见更多，就不该为它付订阅、心跳、
   一条永不结束的响应、以及一个 25 秒一次的 `setInterval`。

**代价**：面板最多陈旧 8 秒。这是可以接受的——卡片上的数字描述的是**上一轮**的结果，
一轮结束到下一轮开始之间本来就没有新事实。

**D-74 取代 D-70 与 D-73。** D-71（只在真会话显示）与 D-72（加载态一行字）不受影响，
它们描述的是渲染，与数据怎么来无关。D-69（只有点击能展开）同样不受影响。

**留下的教训**：D-73 那段「覆盖面更小的通道不能取消覆盖面更大的通道」是正确的，
但它是在**保留流**的前提下写的最优解。真正的问题是更早的那一步——**新增一条更快的
通道时，没有先问它是否同时更窄**。事后再怎么调频率，也只是在弥补覆盖率，不是在恢复它。

## D-75 「不显示」只有启动器这一种页面（2026-11-06）

**背景**：D-71 让卡片只在真会话上显示，判据是 `data-content-phase`。落地后服务端
还发布了第三种取值 `settling`（会话正在打开），代码按「`hero` 才隐藏」处理，
但没有任何断言钉住 `settling` 的行为——它是不是「不算真会话」纯属实现细节的副作用。

**决策**：**`settling` 照常显示卡片**，规则明确写成 `phase === "hero"` 才隐藏。
`test/client.test.mjs` 新增 `a conversation being opened draws its cards`。

**理由**：`settling` 是「正在打开一个真实的会话」，不是「没有会话」。切换会话的那一瞬间
状态被置为 `loading`、`data` 变成 `undefined`、画一行「正在加载…」——这正是 D-72 描述的
加载态，是面板该说话的时候。把它一并藏起来，会在最需要信息的半秒里给出空白。

**为什么它需要单独一条决策**：`phase !== "active"` 这个更「自然」的写法会顺手把
`settling` 一起藏掉，而它在新会话发首条消息（`hero` → `settling` → `active`）的路径上
是最常见的过渡态。**两个断言的夹逼**（`hero` 不画、`settling` 要画）才让这条规则
无法被一次「看起来更简洁」的重写悄悄改掉。

## D-76 展开提示是卡片内底边居中的圆标，不占布局（2026-11-07）

**背景**：D-69 把提示做成卡片下方的一行字，代价一是「hover 进出会挂载/卸载它，
卡片因此长高 26px」。26px 当时被判为「比六行便宜」，但那是两个坏选项里挑一个：
真正的问题是它**还在文档流里**。

**决策**：

1. `.dsse-card` 加 `position:relative`，`.dsse-expand` 用
   `position:absolute;left:50%;transform:translateX(-50%);bottom:8px` 挂在卡片
   底边正中，26×26 的圆（`border-radius:999px`）里放一个 chevron。
2. 显示它不再改变任何布局：hover 进出只是同一位置的元素出现/消失。
3. 展开态 `.dsse-card[aria-expanded="true"] .dsse-card-body{padding-bottom:44px}`
   给徽标让出位置（28px 徽标 + 8px 底距 = 36px，余 8px）。这一条**只在展开态**
   生效，而展开本来就改变卡片高度，因此没有引入新的抖动类别。

**理由**：把元素移出文档流，比在两个都会动的东西之间挑一个便宜。D-69 的 26px
是在「遮住正在读的那行」和「把文字在指针下推走」之间权衡出来的；绝对定位让这个
权衡本身消失——两个都不发生。

**取代 D-69 的代价一。** D-69 的其余部分（展开只由点击决定、提示不是独立按钮、
`pointer-events:none` 让整卡成为触发域）全部继续成立。

## D-77 展开后仍然显示收起入口，且不随指针消失（2026-11-07）

**背景**：D-69 的代价二明确写过「`'点击收起'` 这个提示文案再也到不了」，理由是
`turnHinted` 要求 `turnPinned === false` 而展开要求 `=== true`。第三轮审查当时
发现那个三元分支不可达，把它简化成只有 `'点击展开全文'` 一种。

**决策**：

1. `const turnHinted = turnExpandable === true && (turnPinned === true || turnHovered === true)`
   —— 折叠态仍然只在 hover 时提示，**展开态无条件提示**。
2. `expandHint` 恢复成双文案：`expanded === true ? '点击收起全文' : '点击展开全文'`。
3. chevron 方向随之翻转（`props.up === true ? 'M6 15l6-6 6 6' : 'M6 9l6 6 6-6'`），
   让图标成为「下一次点击做什么」的承诺而不是装饰。

**理由**：收起是唯一回路。把它藏在 hover 后面，等于在读者最想找它的那一刻
（指针已经离开、卡片却开着）把唯一的出口拿走。折叠态不无条件提示仍然是对的——
每张卡都常亮一个「展开」是在喊一件还没发生的事。

**取代 D-69 的代价二。** 那条代价建立在「展开时不需要提示」的假设上，而这个
假设只在提示是纯说明文字时成立；加上方向性图标和收起语义之后它不成立了。

**教训**：一个分支被判为「不可达」然后删掉时，要区分两件事——它是**逻辑上**
不可达（前提互斥），还是**当前设计**不想到达。前者删掉是对的，后者删掉只是把
设计决定藏进代码里，下一个想改回去的人得先猜为什么。

## D-78 · 2026-11-07 · 总结的语言由宿主说了算，不由模型猜

**背景。** 提示词里原本有一句 `Write at most three sentences, in the language the
user wrote in.`，它存在了很久，而用户报告总结有时仍是英文。原因不是这句话写错了，
是它要求模型从对话里推断「用户读什么语言」——一段三句话的对话里塞满英文工具输出时，
这个推断没有依据。用户提的要求是「自动获取当前宿主语言，并且让总结为对应语言」。

**决策。** 宿主在 `<html lang>` 上发布界面语言，客户端读它、经 `?lang=` 交给
`/panel`、由 `summarise()` 拼成一句明确的指令进提示词。模型不再被要求推断。

**理由。**
- 界面语言是用户**读**的语言，对话语言是用户**写**的语言，两者可以不同（中文界面
  里敲英文很常见）。要猜的是前者，而前者恰好可以被直接告知。
- 只说 `Chinese` 不够：中文有两种字形，读者只认其中一种。`zh-CN`/`zh-SG` 与
  无后缀的 `zh` 走简体，`zh-TW`/`zh-HK`/`zh-MO`/`zh-Hant` 走繁体。
- `LANGUAGE_NAMES` 是一张**封闭**的表（11 种语言）而不是查服务或透传标签。多写一句
  `用 ru 写` 而读者其实读英文，等于把猜测还给了模型，只是换了个地方猜。
- 表外但形态合法的标签**不退化成沉默**：给一句通用兜底 `Write it in the language the
  user wrote in.`。一个只帮到表内 11 种语言的改动，不该顺手把表外语言原本就有的那句
  拿走——这是第二轮审查的 P2，原本我确实拿走了。
- 缓存键必须包含**实际生效的语言句**，而不是语言名。表外标签的 `languageName` 是
  `undefined`，用它做键会让「`lang=nl`」与「没有 `lang`」共用一条缓存，而两者的提示词
  并不相同。用渲染后的句子做键自动覆盖了这条。
- 标签来自 query string 并且最终进入提示词，所以 `api.js` 的 `langOf()` 与
  `summarise.js` 的 `LANGUAGE_TAG` 各校验一次：形状不符**丢弃**，不转义。

**代价。** 宿主不发布 `<html lang>` 时一句语言指令都没有（`hostLanguage()` 返回 `""`，
不猜）。这比猜错好：没有这句话时模型退回读 transcript，猜错时它服从一条错指令。

**取代。** 无。这是新增能力，旧的模糊句从 `INSTRUCTION` 中移除。

**教训。** 一个「本该早就生效」的提示已经存在时，先问它为什么没生效，而不是再加一句。

## D-79 · 2026-11-07 · 产出卡是会话的工作列表，不是这一轮的产出

**背景。** 产出卡读 `previous.paths`，也就是刚结束那一轮改动过的文件。用户指出的
三个现象都由此而来：这一轮没改文件，卡片就清空；这一轮重编一个文件，其余十九个像是
没动过；而这张卡在用户心里是「本会话的产出」。

**决策。** 产出卡列本会话累计的、按最近修改排序的文件列表，跨回合与重启都存活。

**理由。**
- 技能卡与 MCP 卡**本来就是**会话累计的（`skillsUsed`/`toolsSeen`/`recency`），产出卡
  是三个里唯一的例外。用户要的是「三张卡都描述会话」，需要的只是把例外去掉。
- 「上一轮」这件事已经有专门的卡片了。用户的说法是「我将上一轮卡片分离出来，就表示只有
  这一个卡片是用来展示上一轮的信息的」。
- 排序键与 `skills`/`servers` **共用同一个 `sequence` 时钟**。三种事实都是「最近用过的
  排前面」，各自维护一个计数器只会让「最近」在两个地方含义不同。
- 重编辑的文件必须 `delete` 再 `set`。Map 的 `set` 更新已有键时保留原插入位置，
  只 `set` 会让「最近编辑在前」不成立——这是一条安静的错误，因为列表看起来仍然有序。
- 上限 200 条（`MAX_PATHS`）。transcript 自己每轮的上限是 40，这里是**整个会话**的，
  所以更大；但没有上限就是每次轮询对每条记录做一次 `fs.stat`。
- `readState` 遇到没有 `paths` 字段的旧文件是**可读状态**，不是坏文件：老会话只是从
  下一轮重新开始积累。

**代价。** 卡片会积累到整个会话的长度，而不是只显示最近几条。上限与 `fs.stat` 的成本
是为此付的账。

**取代。** 无（新增字段）。「上一轮」卡片不受影响——见 D-80 对 `turnFiles` 的说明。

**教训。** 三个并列的卡片里若有两只按同一套语义工作，第三只的例外要么有充分理由，要么
就是漏改。

## D-80 · 2026-11-07 · 中断的回合也要记下它改过的文件，且必须在折叠之前读

**背景。** `index.js` 原本在 `transcripts.record(agentId, event)` **之后**读
`view.previous.paths`。而 `Transcript.endTurn()` 在 `reason.kind !== 'completed'` 时
只清空当前轮、**不改写 `previous`**。于是被中断（或中止）的回合读到的是更早那一轮的
路径：给那些没被碰过的文件逐条加新 tick 顶到最前，同时它真正改过的文件（`paths` 已被
清空）永久丢失。第二轮审查用真实模块复现了这条链路。

**决策。** 在 `record()` **之前**读 `transcripts.view(agentId)?.current?.paths`，把结果
存进局部变量，`record()` 之后再交给 `rememberPaths`。

**理由。**
- 「这一轮改了什么」只有 transcript 知道，而它只在一段时间内知道：`record()` 是把它丢掉
  的那一刻。
- 中断的回合仍然是发生过的工作。用户看不见它被总结（中断轮不生成总结），但文件确实改了，
  把改动丢掉等于因为结论没写完就否认过程。
- 换成「只在 completed 时记」会简单但错误：一次中断的长任务里改的十几个文件会全部消失。

**代价。** 一次代码读起来比「在 `record` 之后问 `previous`」绕，注释必须说明为什么顺序
不能调换，否则下一个人会「简化」回去。

**取代。** 无（修正 D-79 的实现细节）。

**教训。** 「读之前还是读之后」在有折叠语义的存储上不是风格问题，是数据问题。第一轮审查
修 `turnFiles` 时我改对了读取点（头部用单轮数），但没意识到同一个 `record()` 调用的另一侧
还有一个读错轮次的地方。

## D-81 · 2026-11-07 · 路径上限对读盘与合并两条路径同样生效

**背景。** `MAX_PATHS` 的裁剪只在 `rememberPaths` 里发生。第三轮审查用一个普通场景把它
绕过去了：一个进程在**首次 `load` 之前**就收到了 `tool/call`（「事件先到、轮询后到」是
正常顺序），于是内存里有 200 条；`load` 的合并分支把文件里的 200 条也补进来，得到 400；
关机时 `document()` 写的就是这 400 条，下次重启从 400 开始，再合并到 600、800。实测四次
重启得到 200→400→600→800。`readState` 读盘时也不裁剪，所以一个已经被写坏的旧文件会
一直保持它的体积。

**决策。** 三处都裁剪：`rememberPaths`（原有）、`load` 的合并分支、`readState`。

**理由。**
- 上限如果是**一条**写入路径的约束，那它约束的是那条路径，不是数据。任何能产生超出上限
  数据的路径都必须收口，否则「有上限」这个说法是假的。
- 合并分支里 `trimPaths` 的位置是**有讲究**的：必须在 `current` 的 tick 整体平移之后
  （`shift` 之后），这样文件条目的 tick 全部低于内存条目，升序删除天然从文件最旧的开始，
  不会误删内存中较新的。审查用 300 轮随机 fuzz 校验了四条不变量。
- `readState` 里裁剪**不改 `sequence`**：`sequence` 单调递增且始终 ≥ 所有已发放的 tick，
  所以「被裁条目的 tick 大于 `sequence`」不可能出现，`load` 的 `shift` 计算也不失真。

**代价。** 三处裁剪看起来像重复。注释必须写清每处的必要性，否则下一次重构会把其中两处
当成冗余删掉。

**取代。** 无（补全 D-79 的上限语义）。

**教训。** 加一个上限时，要问的不是「写入的地方有没有裁」，而是「有没有第二条能产生
超限数据的路径」。这里的第二条是合并。

## D-82 · 实时输出速度是一个两秒滑动窗口，用字符估算，按 provider 的真实计数校正比例

**背景。** 宿主的 tok/s 胶囊是**整个会话的加权平均**（`decodeTokens / decodeMs`，跨所有上报
usage 的步骤累加），回答的是「这段对话写得快不快」，不是「现在还在动吗」——到第二十轮时它
主要在描述前十九轮。面板需要的是后者。

**决定性事实。** 事件流里**没有流式 token 计数**。`usage` 块只在 `message_stop` 之后出现
一次，那正是无趣的部分结束的时刻。所以生成期间能说的只有「已经到货多少字符」：宿主自己
在需要事前估算时也是这么换算的（`Math.ceil(length / 4)`）。

**决策。** 每收到一个 `text-delta` 记一条 `(时间, 估算 token)`，读数 = 窗口内 token ÷ 窗口
秒数；`usage` 落地时把「provider 计数 ÷ 我们的估算」记成比例，应用到之后的估算上。

**理由。**
- **两秒窗口**：够长，数字不会每个 delta 都跳（delta 每几毫秒一个）；够短，回答的是「现在」
  而不是「刚才」。
- **除数下限 `MIN_SPAN_MS = 500`**：第一个 delta 的经过时间接近零，除下去就是三百 tok/s，
  而那一刻正是人最可能看屏幕的时候。
- **字符估算 + 比例校正而不是纯估算**：四字符一 token 是宿主的规则，但不同内容的密度不同；
  只估算会是一个永久的谎言，只等 `usage` 则生成期间无话可说。
- **比例存下来而不是差值**：下一条消息还要用同一个估算器，差值只对那一条消息成立。
- **比例有上下限（0.25..4）**：一轮异常（重放、续轮、provider 换了计数口径）不该重定义
  之后所有数字。

**代价。** 生成中的数字是估算值乘以学到的比例，它不是 provider 的计数。

**取代。** 无。

**教训。** 宿主已经在显示一个数字时，先问清它回答的是哪个问题；「同一个名字」不代表
「同一个问题」。

## D-83 · 实时速度走 `agent/assistant-stream`，不走 `assistant/chunk`

**背景。** 第一版监听 `assistant/chunk`。测试全绿，因为测试自己 `emit` 了那个事件。

**决定性事实（在 `app.asar` 上核过）。** `append("assistant/chunk"` 在宿主里出现 **0 次**；

## D-84 · 学习比例时排除推理 token 与带工具调用的消息

**背景。** `outputTokens` 包含 `reasoningTokens`（宿主的用量弹窗把它显示为「其中推理 N」，
是子集）。而同一条消息里的 `tool-call` 参数从未作为 `text-delta` 流过。

**决策。** settle 前减掉 `reasoningTokens`；`message.content` 里含 `tool-call` 块时整条消息
不参与学比例。

**理由。** 分母只是文本，分子必须也是文本，否则一条「少量文字 + 四千字符工具参数」的消息
（写文件、str-replace 很常见）会把比例顶到上限，之后每条纯文本都显示成八倍的假速度。
推理同理：思考与回答速率不同，混起来报的是读者没在看的速度。

**代价。** 一次带有工具的回合不贡献校正样本，那一段的比例沿用上一次学到的值。

**取代。** 无。

**教训。** 「同一条消息里的所有 token」不是「同一条消息里的所有文本」；分子分母的
构成必须能一句话说清。

## D-85 · 新 attempt 清累加量但保留窗口

**背景。** `settle` 只在收到 `usage` 时清零。Esc 中断走的是 `interruptedBlocks()` 分支，
provider 从没发过 `usage`，于是那一轮的量会留在累加器里；下一条干净消息的分母翻倍，比例
被压到下限，读数只有真值的四分之一——而且此后整场会话都偏小。

**理由。** 窗口里的 delta 真的发生过，两秒读数说的是「屏幕上正在出现文字」，不是「哪个

**代价。** 中断的那一段不贡献校正样本。

**取代。** 无。

**教训。** 「什么时候重置」有两个不同的量（累加量与窗口），把它们当成一个量会让其中一个

## D-86 · 速度走独立 `/speed` 路由与三档节拍

**决策。** 新增 `GET|HEAD /api/ui-evolve/speed?agent=<id>`，返回
`{ tokens, ms, tps, active }`；客户端按三档定时器轮询：窗口内有东西时 250ms，刚空时 2000ms，
长期空闲 10000ms，最后一次真实读数在窗口空后仍显示 4 秒。

**理由。**
- **独立路由**：面板在回合结束时变，速度在回合进行中变。并成一条，要么把面板拖到四分之一秒
  一次（不该变得那么快的数字），要么让速度最多陈旧八秒（等于整段生成）。
- **三档而不是一档**：四分之一秒是「活读数」的必要代价；两秒是「刚结束、下一轮随时开始」的
  猜测；十秒是「面板开着几小时但没人在看」的答案。
- **10000 而不是 8000**：两个定时器用同一个节拍，就是对「谁在问」无法推理。任何之后要按
  delay 过滤已记录定时器的人（测试、剖析）只有这个数字可依据。
- **4 秒 linger**：读者最想读这个数字的时刻，正是回复结束的那一刻。

**代价。** 长期空闲后最长十秒的空窗期：新回复的头一两秒不会有数字，读数从句子中间开始。

**取代。** 无。

**教训。** 轮询间隔不是一个数字，是三种不同的问题问同一个端点。

## D-87 · 速度徽章不是 live region

**决策。** 徽章用 `aria-live="off"`，不用 `role="status"`。

**理由。** `role="status"` 隐含 `aria-live="polite"`，而徽章每 250 毫秒变一次——读屏会在
整个生成过程里持续播报数字，把真正的回答挡在后面。数字是视觉的旁注，`aria-label` 让想要
它的人能取到，就够了。

**取代。** 无。

**教训。** 「这是个状态」与「这个状态值得播报」是两个判断，前者不蕴含后者。

## D-88 · 速度徽章常驻，空闲时显示破折号而不是 0

**决策。** 速度徽章一旦被宿主答过一次，就在顶行常驻：窗口里有字时显示数字，窗口空后四秒内显示最后一个真实读数，之后显示淡化的破折号 `—`。只有一次都没被成功答过的宿主才什么都不画。这取代 D-86 里「最后一次真实读数在窗口空后仍显示 4 秒」的收尾方式。

**理由。**
- **「只在生成时出现」等于看不见。** 第一版就是这么做的，而用户的第一反馈正是「界面中没有看到对应的速度显示」——他看的时候那一轮早已结束。一个只在事件发生时存在的读数，需要用户在正确的那一秒往正确的角落看，而它想回答的问题恰恰是「刚才有多快」。
- **破折号与 0 是两个不同的陈述。** `0 tok/s` 是一次测量：声称正在以零速率输出。空闲时真相是「现在没有输出」，没有速率可言。把这个区别抹掉，读数在最常见的状态下就在说假话。
- **破折号与旧数字也不同。** 保留最后一个真实数字、只把它变灰，看着像实时但实际不是，会被读成关于此刻的事实。破折号不会。

**代价。** 顶行多了一个常驻元素，空闲时它只显示一个破折号——一块占着位置的空白。这比「找不到想找的读数」便宜。

**取代。** 取代 D-86 的 linger 收尾（四秒后消失）。

**教训。** 「这个读数什么时候有价值」与「这个读数什么时候应该存在」是两个问题。把它们合成一个，就得到一条只在发生后四秒内可读的曲线。

## D-89 · 「这台宿主会不会测速」跨会话保留，「这个会话的读数」随会话清空

**决策。** 组件里有两个状态，生命周期不同：`known`（这台宿主是否成功答过一次 `/speed`）跨会话保留；`held`（最后一个真实读数与其时刻）和 `reading`（当前应答）在切换会话时清空。

**理由。**
- **`known` 问的是宿主，不是会话。** 一个从会话 A 切到会话 B 的面板不会换一台宿主。清掉它，新的会话会先闪一下空白再出现徽章——而空白正是这次要修的东西。
- **`held` 问的是会话。** React 复用同一个组件实例，不清空的话，切过去之后最长四秒里新会话显示的是旧会话的速率。那个数字看起来完全合法，而且完全错误。
- **两个判断混在一个状态里会让其中一个必然出错**：要么切会话时徽章消失（错了），要么旧数字跟着过来（也错了）。

**代价。** 一次成功应答之后，徽章在整个面板生命周期里都在（包括后续会话），即使后端随后坏掉——那时它显示破折号而不是消失。这是有意的：消失会被读成「这个功能没了」，破折号会被读成「现在没有输出」。

**取代。** 无。

**教训。** 一个状态该活多久，取决于它描述的是什么。把「关于宿主的事实」和「关于会话的事实」放进同一个变量，是一个会以两种方式同时出错的合并。

## D-90 · 停下来之后显示最近几条的加权平均，与实时读数共存

**决策。** `SpeedMeter` 在每条消息 settle 时留下一条 `{ tokens, ms }` 样本（provider 报的真实
`outputTokens` 与该消息自身的时长），只保留最近 `AVERAGE_SAMPLES = 5` 条；`read()` 除了原有的两秒
窗口读数 `tps`，再返回一个 `average`。客户端按 **实时 > linger 内最后读数 > 平均 > 破折号** 的优先级
显示，平均态用 `dsse-speed-average` 稍微调暗，`aria-label` 说「最近 N 次的平均输出速度」。

**理由。**
- **两个数字回答两个问题。** 两秒窗口答「现在多快」，只在有字到达时存在；平均答「这个 provider 多快」，
  从第一条消息落定起一直存在。读者抬头看的时刻正是回复结束之后——那恰好是窗口说不出话的时刻。
- **必须加权，不能取各条速率的算术平均。** 一条 4 token / 0.5s 的消息与一条 1000 token / 20s 的消息
  不该等权；`Σtokens / Σms` 才是「这几条合计多快」，算术平均会让一次碰巧很快的短回答压过一条长回答。
- **样本用 provider 的真实计数，不用估算。** 样本在学完比例之后记录，所以平均值不依赖估算器——估算错了
  只会影响窗口读数，不会污染这个数。
- **只留最近五条。** 开了一下午的会话该报 provider 现在的表现，不是午饭时的平均；五条约等于一屏回合，
  长到一条慢回复不能定义这个数。
- **linger 仍然优先于平均。** 四秒内最新鲜的陈述是刚落幕的那个窗口，不是五条消息的均值；换成平均会让
  一个很快的回答在结束的一瞬间看起来变慢。
- **`begin` 不再清 `messageAt`。** `push` 在累加量为空时本来就会重新打时间戳，那行是删掉也无人能观测的
  装饰——这与 `settle` 里删掉四个被遮蔽守卫是同一条原则。

**代价。** 五条样本是进程内状态，重启后从零开始；一条超长的会话里最早那几条会被挤掉，所以「平均」指的是
最近一屏，而不是全会话。

**取代。** 取代 D-88 中「窗口空后显示破折号」的收尾：破折号现在只在**从未有任何消息落定**时出现。

**教训。** 「现在多快」和「刚才多快」是两个问题，一个读数不可能同时是两者的答案；把两者做成同一个数字，
得到的永远是回答另一个问题的那一个。

## D-91 · 生成中显示最近两秒，停下来后显示「上一轮这一条」并常驻

**决策。** `SpeedMeter` 在每条消息 settle 时只保留**最后一条** `{ tokens, ms }`（provider 报的真实
`outputTokens` 与该消息自身的时长），扔掉 `AVERAGE_SAMPLES` 与加权平均；`read()` 用 `last` 取代
`average`。客户端按 **实时（生成中，最近两秒）> linger 内最后读数 > 上一轮** 显示，上一轮态用
`dsse-speed-previous` 稍微调暗，文案是「上一轮输出速度 N tok/s」。同时 `read()` 与 `revisionOf()` 暴露一个
单调递增的 `revision`，`GET /speed?after=<n>` 在 `revision` 未变时把请求**挂着**（最多 25 秒），变了立刻
回答。

**理由。**
- **「最近五条的平均」回答的是没人问的问题。** 读者刚看完一轮输出，想知道的是「刚才那轮多快」，而平均
  值把这一轮和四个更早的回合混在一起——刚看到的那个数字越极端，被稀释得越厉害。成熟实现（OpenWebUI、
  LM Studio、ollama）都是「生成中实时，结束后把上一轮的数字留在原地」。
- **「只闪过一下」的根因不是渲染，是发现延迟。** 徽章此前靠定时轮询，空闲时十秒一次，而一条回复通常
  三到八秒就结束——徽章在回复结束前根本没被问过。宿主本来就有推送（`agent/assistant-stream`、
  `sessionStatus`），但本插件是 HTTP 路由，拿不到那些 subject；能拿到的等价物是**让请求等事件**：
  长轮询把「多久问一次」换成「有事就叫醒我」。
- **`revision` 必须把 `push` 也算进去。** 若只在 settle 时递增，长轮询要等一整条消息结束才醒，实时读数
  依然只在最后出现一次——那正是要修的症状。
- **比较基准是调用方报的 `after`，不是请求到达那一刻的读数。** 用后者会把「两次轮询之间发生的变化」
  当成没变化：回复恰好在间隙里落定是最常见的情形，请求会为一个早已确定的数字挂满 25 秒。
- **客户端必须能撤回首请求。** 长轮询按设计二十五秒不回答，被放弃的会话会各留一个连接与服务端的
  100ms 定时器；连续切换几次，新会话的首次请求会排在这些僵尸后面。`AbortController` 一 abort，服务端
  的 `close` 监听就是那条不用等截止时间的出口。

**代价。** `last` 与 `revision` 都是进程内状态，宿主重启后从零开始（与 D-90 相同）。长轮询期间一个会话
占用一个 HTTP 连接；同源并发受限的宿主上，切换会话必须真的 abort，否则会排队。

**取代。** 取代 D-90 的「最近五条加权平均」；D-88 的「徽章常驻」仍然成立，只是常驻的内容从平均值换成了
上一轮这一条。D-89 的 `known` 语义不变。

**教训。** 用一个「多久问一次」的数字去追一个由事件驱动的现象，采样间隔迟早会长过现象本身；发现延迟
必须由被观察的一方决定，而不是由观察者的闹钟决定。

## D-92 · 产出卡按「被编辑的先后」排，不按 mtime

**决策。** `readPanel` 不再把文件列表交给 `fs.stat` 的 `mtimeMs` 重排（`client.js` 里 `const ordered = files`
就是全部，删掉了 `files.slice().sort((a, b) => (b.mtimeMs ?? 0) - (a.mtimeMs ?? 0))`）。顺序来自数据源：
`filesSeen()` 走会话状态里的 path map 反向，本来就已经是「最近被碰过的在前」；回落源 `previous.paths`
是 transcript 按调用顺序追加的数组（最旧在前），因此新增 `newestFirstOf(paths, false)` 显式反转，让两个
数据源同义。`mtimeMs` 仍然随行返回，只是不再参与排序。

**理由。**
- **两个数据源必须同义。** 主源按 tick 倒序、回落源按调用顺序正序，不倒序的话同一张卡在「有会话状态」
  与「只有本轮 transcript」两种情形下会给出相反的顺序——而用户看到的是同一张卡。
- **`mtime` 回答的是另一个问题，且答案不同。** 卡片的标题是「产出文件」，语义是「这次会话里我改过哪些」。
  构建步骤碰了一个旧文件、`touch` 了一次时间戳、或者一个文件被别的工具重写，`mtime` 都会把它顶到最上面，
  于是这张卡讲的是「文件系统最近发生了什么」，不是「这段对话最近做了什么」。
- **成熟实现也这么排。** 宿主自己的 changed-files 卡：「Rows appear in the recorded display order, so
  repository files above the working directory and files outside it sort first.」——按记录顺序，不按时间。

**代价。** 用户若在编辑器里手改了一个文件而不经过本会话的工具调用，它不会因此跳位；「最近修改」这种
跨来源的排序不再可用，需要时得自己看 mtime（行里仍然带着）。

**教训。** 一张卡的排序键必须与它的标题回答同一个问题。「最近修改的文件」与「这段对话改过的文件」
在两个不同的钟上，选哪个不是风格问题，是这张卡在讲谁的故事。

## D-93 · 折叠 4 行，出口钉在卡片底部，展开后列表自己滚动

**决策。** `FOLDED_FILES = 4`（与宿主 changed-files 卡的 `COLLAPSED_ROWS = 4` 一致）。折叠时 `shown` 是前
四行；`ordered.length > FOLDED_FILES || filesOpen` 时渲染 `.dsse-foot` 容器，按钮文案折叠态是
`展开全部 N 个`、展开态是 `收起`。**这个容器是列表的兄弟，不是列表的子节点**：列表是
`.dsse-list dsse-files`，展开时（`data-open="true"`）才拿到
`max-height:${FILE_LIST_MAX_PX}px; overflow-y:auto; overscroll-behavior:contain`（`FILE_LIST_MAX_PX = 8 * 36 + 7 * 3`，
约两个折叠态高）。展开时头部 `meta` 从 `N 个文件` 改成 `全部 N 个`，因为此时列表正在展示全部，
重复总数只是噪声。

**理由。**
- **DEF-51 的根因是出口的位置，不是截断本身。** 「只显示前 N 条」的代价是看不到其余，而补救的入口当时
  住在被裁剪的那个列表末尾——于是截断把**提示**一起截断了。把出口移出列表，两个问题同时消失。
- **折叠数取 4 而不是 5。** 一张卡最多占两屏折叠态；再多的行会把另外两张卡推出视野，而用户此时未必在
  找文件。宿主在同一个侧栏宽度里选的也是 4。
- **展开后必须能滚，否则「展开」只是把侧栏顶长。** 展开是用户明确的「我现在要看全部」；给他一段可滚的
  固定高度区域，比给一张三屏高的卡更接近他要的东西。代价是卡内出现第二个滚动条——这是有意的取舍：
  读者已经进入「看列表」模式，此时列表自己滚比整块侧栏滚更少干扰。

**代价。** 卡内第二个滚动条；展开态高度固定，超长文件名会换行而不再撑高卡片。

**教训。** 折叠与展开是一对矛盾的动作，两者必须住在同一个地方。任何「显示更多」的控件，只要它可能被
它要展开的东西挤出视野，这个设计就已经坏了——判据是问：**用户只看第一屏时，知不知道还有更多、能不能
够到？**

## D-94 · 行点击在右栏预览，走可选注入

**决策。** 服务端 `statTouchedFiles` 为每个文件多返回一个 `address`：
`dsh-resource://file/session/<sessionId>/<相对工作区的路径>`（`resourceAddress()`，与宿主
`fileAddressFor()` 的五条分支逐条等价：工作区根 → 空相对路径、工作区内 → 相对、工作区外 → 保留绝对路径、
反斜杠归一、盘符 `%3A` 还原）。客户端在 `apply` 里用 **`ctx.inject(["sidebarRight"], ...)`** 拿到侧栏，
把 `openResource` 发布到模块级 `let openResource`；行在 `canPreview === true && typeof file.address === 'string'`
时渲染成 `<button>` 并 `onClick` 调用它，否则渲染成 `<div>`（没有任何 handler）。点击包在 `try/catch` 里。

**理由。**
- **不能写进 `module.exports.inject`。** 三契约第三条：`inject` 里声明可选服务，会让没有该服务的 profile
  **整体拒绝加载本插件**。侧栏是宿主自带能力，但不是每个部署都装；少了侧栏，卡片还应该能用。
  `ctx.inject` 是宿主文档自己给的可选路径（「Contributors may preserve optional registration through
  `ctx.inject(['sessionProjections'], ...)`」）。
- **没有侧栏时行是纯文本，不是「点了没反应的按钮」。** 一个按下去什么都不发生的按钮，比一句不可点的文字
  更糟：它让用户怀疑整个面板。
- **`canPreview` 必须在这个闭包里算，不能交给 `Card`。** 行是在 `Cards` 里构造好 JSX 再作为 `children`
  传下去的，`Card` 从不接收 opener 这个 prop；任何在 `Card` 体内读 `props.onOpenFile` 的写法都会恒为
  `undefined`，于是在每个宿主上静默退化成纯文本（DEF-66）。
- **点击要 try/catch。** 宿主 `openResource` 在「当前没有 adopted 会话」时会 throw，而那在跨会话切换的
  瞬间是正常状态；一次失败的预览不该把整列卡片带下去。
- **地址在服务端拼，不在客户端拼。** 服务端才知道会话 `cwd`（`deps.cwdFor(id)`）与真实绝对路径；客户端
  拼就要自己维护「相对还是绝对」的判断，而那正是宿主 `fileAddressFor` 已经解决过的问题。

**代价。** 行多了一个字段与两条 CSS；宿主不提供 `sidebarRight` 时点击能力静默缺席（这是设计，不是缺陷）。
地址里带会话 id，面板跨会话时旧行的地址会指向旧会话——但行也随面板一起换掉，不会残留。

**教训。** 「可选能力」与「必需能力」的区别不在它多有用，而在它缺席时会发生什么：一条降级路径要是
看得见的（纯文本），而不是一个假装可用的控件。

## D-95 · 产出卡的折叠控件改成与上一轮卡片同一个圆标

**日期。** 2026-11-10。**状态。** 生效（细化 D-93 的「出口钉在卡片底部」，取代其中「整宽文字按钮 `.dsse-foot`」的形态）。

**决策。** 产出卡（产出文件卡片）的展开/收起控件不再是列表下方的整宽文字按钮，而是与上一轮卡片**同一个**圆形图标按钮：26px、`border-radius:999px`、绝对定位在卡片底边居中、内置 chevron，展开后翻转向上。两张卡共享 `.dsse-expand` 这一条几何规则，产出卡额外挂 `.dsse-expand-action` 只加行为（指针、光标、焦点环），不改位置与尺寸。

**理由。** 用户原话：「现在产出文件卡片的功能正常，但是实际的图形表现不好，你应该按照上一轮卡片的展开按钮进行设计，让整体的样式统一一些。」同一列里两张卡对同一个手势（「还有更多，点我」）给出两种形状，读者要学两次；而「样式统一」不是把两处 CSS 抄成一样，是让它们**共用一条规则**——抄两份的下一步就是漂移。

**代价。** 圆标只有图形没有文字，所以「还有几个」必须搬到 `aria-label` 与 `title` 上：上一轮卡片的圆标没有 `title`（`pointer-events:none` 让它永远不是命中目标，tooltip 无从弹出，见 DEF-43），产出卡的圆标是**真的可以按**，于是这里的 `title` 是有用的。两张卡因此同形但不同语义，读代码时要靠 `badgeAction` 这个 prop 区分。

**两张卡为什么不能完全一样。** 上一轮卡片的整卡可点（`Card` 收了 `onClick` + `clickable`），圆标是**装饰**：`role="img"`、`pointer-events:none`，点提示等于点卡片，整卡即触发域。产出卡不能照抄——它每一行本身已经是 `<button>`（点击在右栏预览，D-94），卡片若也接点击就会把行点击吃掉。所以产出卡通过 `Card` 的可选 prop `badgeAction` 让圆标**自己当控件**：`type="button"`、自带 `aria-expanded`、自带焦点环、自带 `aria-label`。

**盒模型（本轮审查抓到的真缺陷）。** `width:26px` 加 1px 边框在两种元素上不是同一个尺寸：装饰圆标是 `div`，默认 `content-box`，26px 是内容盒、边框在外面，外径 28px；新圆标是 `button`，浏览器 UA 样式表给按钮 `border-box`，26px 已含边框，外径 26px。**同一条声明、两个直径**——而这轮改动的全部目的就是让两个圆标看起来是同一个东西。修法是在共享规则里写死 `box-sizing:border-box`，一次管住两种元素；写在 `.dsse-expand-action` 上只会让按钮去迁就 `div`，而 `div` 那边仍然是 28px。

**预留的条带跟着圆标走，不跟着其它状态走。** 展开态是否需要给圆标让出底部空间，判据不是「卡片开着」而是「这张卡有没有圆标」——没有圆标的卡片（文件不超过 4 个）一个像素都不该让。旧规则 `.dsse-card[aria-expanded="true"] .dsse-card-body{padding-bottom:44px}` 服务的是上一轮卡片（它的 `aria-expanded` 在卡片本身），新增的 `.dsse-card[data-badge="true"] .dsse-card-body{padding-bottom:44px}` 服务产出卡。两条规则都还活着，不是重复。

**教训。** 「让两个东西看起来一样」里的「一样」，是渲染结果一样还是声明一样？`width:26px;border:1px` 在两种 `box-sizing` 下是两个答案，而只比对规则文本的断言对两者都点头——**当两个元素的标签不同时，它们的默认值也不同，共性必须显式写死，不能指望继承**。

## D-96 · 机器生成的文件不进列表，但进得出

**决策。** 产出卡的列表里出现 `node_modules/`、`dist/`、`build/`、`coverage/`、`__pycache__/`
这些目录下的文件，或者 `package-lock.json`、`yarn.lock`、`Cargo.lock` 这类锁文件，或者
`.min.js`、`.map`、`.pyc` 这类产物时，**默认不画出来**，但也不丢：头部写「N 个文件 · M 个生成」，
展开后有一组标题是「生成文件」。判据在 `packages/ui-evolve/lib/api.js` 的 `isNoisePath(path, cwd)`。

**理由。** 一次安装依赖、一次 `npm run build`、一次 `cargo build`，都会往工具调用的路径记录里塞
进几十个文件，它们和用户真正想看的「我刚才改了哪几个源文件」混在同一个列表里。成熟实现是直接
不列的：Claude Code 的 diff 面板原话是 `The file list skips test files and generated files
outright`（<https://www.getclaudeskills.com/blog/claude-code-diff-panel-fullscreen-mode>）。
我们做不到「完全不列」——这个插件唯一的数据来源是工具调用的路径，它分不清哪次写入是构建产物的
副作用、哪次是用户的编辑，所以只能按路径形态判断。而**按路径形态判断必然有误判**，误判的代价
不对称：多列一行的代价是读者扫一眼跳过，少列一行的代价是他以为自己没改过那个文件。所以判据要
保守，出口要一直在。

**判据为什么这么窄。** 三条：①只看**整段目录名**（`node_modules`、`dist`、`build`……），不做
任何子串或前缀匹配，所以 `src/builder/gen.js` 是源码、`docs/dist.md` 是文档；②只看**完整文件名**
（`package-lock.json`），所以 `package.json` 不会被误伤——它们在同一个目录里，只有后者是生成的；
③不看扩展名以外的东西（`.min.js`、`.map`），因为那是产物的定义性特征。

**`build/` 在任何层级都算，这一条我一开始判断错了。** 我以为只有仓库根下的 `build/` 才是输出目录，
`src/build/gen.js` 应该是源码。实测断言红了之后查了一下：`build/` 作为目录名在整个生态里几乎专指
输出目录，`.gitignore` 的常规写法也是 `**/build/`。于是接受「任何层级的 `build/` 都是输出」，
把「不做子串匹配」那条改成测 `src/builder/gen.js`——前缀相同但不是整段目录名，这才是真正要守的边界。

**工作区自身可能就在「生成目录」里。** 这是审查抓到的真缺陷（DEF-70）。`isNoisePath` 最初拿到的
是绝对路径，于是判据看了**全部祖先段**：CI 把仓库检出到 `/build/<repo>`、开发者的项目在
`D:\build\mine`、或者干脆把 `dist/` 当 workspace 打开——这三种情况下工作区里的每一个文件都被判成
生成文件，卡片一行不显示、头部写「0 个文件 · N 个生成」，连「本轮优先」一起失效。修法是先剥掉
`cwd` 前缀再切段：判据只对**工作区内部**的相对结构说话，工作区自己叫什么名字与它的内容无关。

**剥离前缀要忽略大小写，而且必须在折叠后的字符串上切片。** 两处都是审查抓到的（DEF-71/DEF-72）。
`cwd` 来自会话头，文件路径来自工具参数原文，两边**都不做规范化**；Windows 与 macOS 上同一个目录
常有两种写法，区分大小写会导致剥离失败、静默退回全段判断，也就是刚修完的那个症状。改成
`toLowerCase()` 比较。但小写化**不保长度**（`İ` U+0130 会变成 `i` + 组合点，一个码元变两个），
先折叠再拿折叠后的长度去切**原串**会多吃或少吃一个字符：`node_modules/` 变成 `ode_modules/`、
匹配不上，依赖被当成读者自己的作品列出来；反向少切则会把根名的尾巴混进首段，`xbuild` 剩下 `build`，
真实的源码文件被藏起来。所以整个余下路径都在折叠后的串上切——反正下面每一处比较都不区分大小写，
折叠整段不花什么代价。

**过滤不等于删除，所以「有过滤必有出口」。** 圆标（折叠/展开控件）的出现条件从
`ordered.length > FOLDED_FILES || filesOpen` 改成 `ordered.length > FOLDED_FILES || ordered.length > people.length || filesOpen`。
第二项是新增的：只有生成文件被藏起来（人写的文件不超过 4 个）时，折叠态看起来「就是全部」，
而实际上少了几行——没有出口的过滤与删除在读者眼里没有区别。这一条和 DEF-51 的教训是同一件事的
两面：DEF-51 是「出口在滚动区外」，这里是「出口根本不存在」。

**代价。** ①判据是启发式的，误判永远可能，只能靠「窄 + 有出口」把代价压到可接受；②头部多了一段
「· M 个生成」，比原来的纯数字长；③展开态多一组标题，四个文件的会话也要多读一行「生成文件」——
实测这一组只在真的有生成文件时才画，所以空会话没有额外噪音。

**教训。** 「默认隐藏」是一个**组合承诺**：隐藏 + 告诉读者隐藏了几个 + 让读者随时能看到。只做第一
条就是丢数据。而判据的范围要跟着「谁在提问」走——同一个路径，问「这个文件是不是构建产物」和问
「工作区里这个文件是不是构建产物」是两个问题，前者会把工作区自己的名字也算进去。

## D-97 · 本轮碰过的文件排在更早的前面

**决策。** 产出卡的列表分两层：**本轮**（`turn === true`，当前这一轮的工具调用碰过的）与**更早**
（本会话更早的回合碰过的）。折叠态是最多 4 行，**本轮的全排在更早的前面**；展开态分三组，
顺序是 本轮 → 更早 → 生成文件，后两组各有一个小标题（「更早」「生成文件」），第一组没有标题。

**理由。** 这张卡的语义是「这个会话产出过什么」，但读者的问题通常是「刚才这轮动了什么」。这两
个问题在文件少的时候重合，在文件多的时候分离：会话跑到第二十轮，卡片里三十个文件按编辑先后排，
读者要在一屏里找刚才那三个。成熟实现把这两件事拆成两个视图（VS Code 的 files changed bar 是
「这一轮的每个文件」<https://code.visualstudio.com/learn/foundations/reviewing-and-controlling-agent-changes>，
Claude Code 把「本次会话之前的所有改动」压成底部一行 <https://www.getclaudeskills.com/blog/claude-code-diff-panel-fullscreen-mode>）。
我们只有一张卡，所以用**分层**代替拆分：不新增卡片，也不改「会话累计」这个主语，只是让最近一轮
的那几个浮到上面。

**`turn` 标志必须由服务端算。** 客户端手里只有文件列表（`path`/`bytes`/`mtimeMs`/`address`），
没有「上一轮碰了哪些路径」；而服务端在 `readPanel` 里同时握着 `previous.paths`（上一轮的记录）和
会话累计表，是唯一能回答「这个文件是不是本轮的」的地方。所以 `statTouchedFiles` 多收一个
`turnPaths: Set<string>`，逐条 `turn: turnPaths.has(absolute)`。

**相对路径必须先解析成绝对路径再进集合。** 这是我自己写的第一版就错的地方，探针抓到的：
`previous.paths` 里存的是**工具参数原文**，可能写 `src/app.js`；而 `pathsSeen` 给回来的是
`statTouchedFiles` 拼出来的**绝对路径**。两边一比，一个都不相等，于是每一行都是「更早」——
分层看起来生效（列表还在、顺序也还在），只是本轮那一层永远是空的。所以构造 `turnPaths` 时要走
和 `statTouchedFiles` 完全相同的解析：`raw.startsWith('/') || /^[A-Za-z]:[\\/]/.test(raw) ? raw : join(cwd, raw)`。

**折叠态用 `fresh.concat(earlier)`，不是 `people`。** `people` 是「所有非生成文件」，按数据源顺序
（编辑先后，最新在前）——它和 `fresh.concat(earlier)` 的差别只在**本轮那几个是否被挤到后面**。
我第一版写了 `people.slice(0, FOLDED_FILES)`，注释却写着「本轮优先」，两者矛盾；探针（把折叠态
改回 `people.slice`）杀掉了 1 条断言，说明新写法确实有覆盖。

**代价。** ①展开态多两个小标题，四个文件的会话也要多读几行；②「本轮」这一层在刚打开的新会话里
是空的（还没有回合结束），此时所有文件都在「更早」组、没有标题——看起来就是一张普通列表，不
会出现空标题；③分层只影响**画出来的顺序**，不影响 `files` 的顺序，所以「点击打开第 N 行」这类
断言仍然按渲染顺序验证。

**教训。** 「排序」和「分组」是两种不同的答案。`turnFiles` 这个数字早就在面板返回体里了
（`turnFiles: previous.paths.length`），但一直只被上一轮卡片的头部计数用着，没人想到把它变成
列表的结构——**一个已经算出来的事实，如果没有出现在读者能看见的位置，它对读者就不存在**。

## D-98 · 摘要在回合结束时就生成，不等面板打开

**决策。** `turn/end` 事件处理里，在 `rememberPaths` 之后调一次 `summariser.warm(...)`，**不 `await`**。
面板请求 `readPanel` 不再等到「这一轮第一次被看」才付模型调用的钱。

**理由。** 之前 `readPanel` 里 `await deps.summariser.summarise(...)`，而面板每 8 秒轮询一次
（`client.js:190` `REFRESH_MS`），超时 20 秒（`summarise.js` `SUMMARY_TIMEOUT_MS`）。于是**一轮结束后
第一次打开面板，最长要盯着空白等 20 秒**——一次模型调用被塞在人和卡片之间。这不是本项目的 bug 而是
设计顺序问题：把「什么时候花这个钱」和「什么时候有人看」绑在了同一个时刻。

**被否决的替代方案：**

- **抄 Qoder 的定时器（首次 12 秒、增量 35 秒）。** 否决理由：Qoder 用定时器是因为它的 recap 是**增量
  续写**、需要攒够一批新消息（阈值 `iq0=3`）再跑一次，而且它跑在主进程、没有「回合结束」这个时刻
  可挂。本项目有 `turn/end` 事件，**那是比任何定时器都准的信号**：回合停止变化就是该总结的时刻。
  定时器还会在回合仍在进行时白跑一次。
- **加一个任务调度器 / 队列。** 否决理由：`Summariser` 已有 `inflight` Map 做同键去重、`cache` 做 64 条
  LRU。两个机制合起来已经能回答「这个键是不是正在算 / 算过了」，再加一层调度器只是把同一件事
  说三遍。
- **在面板请求里做「先返回旧的、后台再算」。** 否决理由：那需要服务端维持「上一版摘要」这个额外状态，
  而 `warm` 已经把「新摘要准备好」提前到了回合结束——前者是后者的弱化版，且多一份要维护的状态。

**为什么是 fire-and-forget 而不是 `await`。** `turn/end` 是一个同步事件处理器，`await` 会拖住
`sessionState` 的记账链路（`rememberTurn` / `rememberPaths` 在同一分支里）。摘要失败与账本无关，
不该有机会拖慢它。

## D-99 · 摘要的语言由用户原话决定，不由界面语言决定

**决策。** 删除整条 `?lang=` 管线（`hostLanguage()` → `?lang=<tag>` → `api.js` 的 `langOf` →
`summarise.js` 的 `languageLine` / `LANGUAGE_NAMES` / `LANGUAGE_TAG`），改为：把用户原话作为
prompt body 的第一段 `` `What the user asked:` ``，并在 `INSTRUCTION` 里写「用用户正在使用的语言」。
**语言不再进缓存键。**

**取代 D-78。** D-78（2026-11-07）写的是「总结语言由宿主 `<html lang>` 指定」。它当时不是错的：
读者确实把界面设成了某种语言。但**界面语言是读者选的，说话语言是读者实际用的**，在同一个会话里
两者可以不一致——中文界面上用英文提问、英文界面上用中文提问，都很常见。摘要复述的是**这个人刚才
说的话**，所以判据应该是后者。用户 m01221 的决定即此。

**连带必须一起改的两件事**（否则只改一半会更糟）：

1. **`transcript.js` 之前不记录用户原话。** `record()` 的 `user/message` 分支只调 `beginTurn()`，
   `data.content` 从未被读过（`transcript.js:452-455` 的原实现）。也就是说**模型输入里没有一个字是
   用户写的**——只有工具名、命令、路径、助手说了什么。不补这一环，新的语言句会让模型对着英文的
   工具输出猜语言。补法是 `readUserText(content)`（见 DEF-76 的附件坑）。
2. **语言从缓存键里移除。** 旧键是 `${turn}:${bodyDigest}:${languageLine}`。语言句现在由 body 决定
   （用户原话是 body 的一部分），body 变 digest 就变，第三个分量**无法再区分 body 没有的东西**。
   留着它反而会更糟：`warm()` 在回合结束时运行，手里只有 snapshot、**没有请求上下文**，想算这个键
   就只能猜一种语言；面板请求则会拿真实语言再算一次，猜错就**同一轮买两次**。删掉它之后 `warm`
   不需要请求上下文即可运行——这正是 D-98 能成立的前提。

**被否决的替代方案：** 保留 `?lang=` 但让它退居次位（用户原话优先、界面语言兜底）。否决理由：
兜底值在没有用户原话时（例如只有工具调用的回合）会让同一个 prompt 有两种可能的写法，而
`summaryKey` 必须是一个纯函数。两种写法意味着两个缓存条目，而其中一种永远不会被读到。

## D-100 · 上限 300 字，且输出要清洗；清洗不去下划线

**决策。** `MAX_SUMMARY_CHARS` 400 → **300**。新增 `tidy(text)`：去围栏、去行首 `Summary:` 之类标签、
去成对的 `**粗体**` 星号、按**码点**截断。**明确不抄** Qoder 的 `replace(/[*_`#]+/gu, "")`。

**300 字的理由。** 卡片可见上限是 6 行（`.dsse-clip .dsse-text{max-height:9.3em}` ÷ 行高 `1.55`
= 6 行），320px 面板一行约 25 个中文字，即**约 150 字就满**，超出部分被 34px 渐变遮住、需点开。
300 是「上限」不是「目标」：它约束的是模型别写长篇，而不是让 300 字都显示出来。用户 m01221 的
判断是「还可以更少，300 字左右为上限更好」。

**为什么清洗是必要的，而提示词不够。** `INSTRUCTION` 早就禁了列表，但**没禁前言**：模型仍可能开头写
"Summary:" 或把整段包进 ``` 围栏。提示词约束是概率性的，代码清洗是确定性的——三份外部实现都做了
这一步（Qoder 的 `jhx()` 五步、OpenCode 模板未填满时发 `NUDGE` 重试、Claude Code 先写 `<analysis>`
再写 `<summary>` 且注入时剥掉 analysis）。

**为什么不抄 Qoder 的字符扫描式清理。** Qoder 的 recap 输出是纯中文散文，`*` `_` `` ` `` `#` 这些字符
**必然是装饰**，一把删干净不会误伤。本项目的摘要**可能含路径**，`my_file.py` 的下划线会被毁掉。
测试里有一条断言专门守着这个下划线，突变 `the cleaner eats identifiers` 就是 Qoder 那个实现，它必须被杀。

**粗体为什么只在「恰好两对星号」时才清洗。** 第一版正则 `\*\*([^\n*]+)\*\*` 会把不是 markup 的两颗星
配成一对并**删掉中间的文字**：`Added **kwargs support and **tested** the path.` →
`Added kwargs support and tested** the path.`（DEF-75）。段落级规则分不清强调与运算符/glob，所以判据是：
**留下标记只是外观瑕疵，删掉中间的词是数据丢失**。四条星号（`**kwargs` + `**tested**`）意味着源码
本身有歧义，此时不动。

**`__下划线__` 强调故意不剥离。** `__name__` / `__main__` 是 Python 常见词，markdown 自己也分不清；
星号没有这种冲突（`2 * 3` 需要空格，而正则已要求内侧非空白）。

## D-101 · `warm` 的闸门是「这个会话开过面板」，且必须能被忘掉

**决策。** `Summariser` 维护 `viewed: Set<agentId>`，`markViewed(agentId)` 在 `readPanel` 入口调用、
`warm()` 只对已在集合里的会话生效；`forget(agentId)` 从集合中删除，由 `index.js` 的
`agent/disposed` 处理器调用。**这个集合故意不持久化。**

**理由（保守策略）。** 预生成要花钱。用户 m01221 选的是保守方案：**只有真的有人打开过这个会话的
面板，才为它预生成**。没人看过摘要的会话，回合结束时不花这个钱。这把「预生成」从「每个会话每一轮
都付一次」收敛到「有人在看的会话才付」。

**为什么必须有 `forget`。** 没有它，`warm` 问的问题就从「**现在**有人在看这个会话吗」悄悄变成
「有人**曾经**开过这个会话吗」。宿主同时跑的后台会话正是这个闸门要省的对象——审查实测的场景是：
在约 12 个会话上各开一次面板，然后回到其中一个，其余会话**每回合仍然各付一次模型调用**，
而且是永远不会被看到的那种调用。

**为什么改由处置事件驱动而不是定时清理。** `agent/disposed` 是这个信息的**真实来源**：会话没了，
看它的人也就没了。定时清理需要选一个时长，而任何时长都会在「会话还活着但清理过了」和「会话已经
死了却还留着」之间选一个错的。

**为什么 `warm` 的 catch 要写 `this.log(...)` 而不是 `this.log.warn(...)`。** 见 DEF-74：`log` 在每个
调用方都是裸函数，写 `.warn` 会在 catch 里抛 `TypeError`，把本来要报告的失败升级成 unhandled
rejection——**报错的地方自己报了个错**。

## D-102 · 状态格式升到 v2 但读得动 v1，不做迁移步骤

**背景。** docs/18 要把 `paths` 从 `Map<path, 序号>` 改成 `Map<path, {seq, turn, at}>`，才可能记住
「这个文件是哪一轮写的」。直接 `STATE_VERSION = 2` 并在版本闸门处拒绝 v1，会让**每个既有会话的
产出卡归零**——用户看到的是面板突然空了，而不是「格式升级了」。

**决定。** `READABLE_VERSIONS = new Set([1, STATE_VERSION])`，读端用 `readPathEntry` 把两种形状归一化，
写端只写 v2。老文件被读一次、写一次，就自动变成 v2：**升级发生在写路径上，不需要迁移脚本、不需要备份、
不需要一次性遍历**。

**为什么不写迁移脚本。** 迁移脚本要读全部会话文件、在启动时跑、失败要能回滚，而这三种复杂度换来的
只是「提前几秒完成」——第一次 `turn/end` 就会把那个会话写好。会话文件本来就是可丢的（`keepsDocument`
已经在修剪空记录）。

**反向不兼容，且是故意的。** 只认 v1 的旧构建读到 v2 会在版本闸门处当成「不是我的文件」、从空开始，
与全新会话的观感相同。选择「丢历史」而不是「拖住格式」，因为旧构建只会出现在回滚场景里，
而回滚本身已经是一次有意的降级。

**为什么 `load()` 合并时只移位 `seq`。** `seq` 是本进程的单调计数器，跨进程必须重新编号；
`turn` 和 `at` 是**事实**——第 7 轮写的、什么时候写的。给它们加偏移等于凭空造出转录里没有的轮号与时间戳，
而这正是 S1 要修的 bug 的近亲。

**否决的方案。** ①直接 `STATE_VERSION = 2` 并拒绝 v1（丢光既有会话的卡）；②写迁移脚本（复杂度不换收益）；
③把 `turn`/`at` 塞进 `previous` 而不落盘（重启就丢，等于没做）。

## D-103 · 被删的文件留在卡上、进折叠态，划删除线

**背景。** `statTouchedFiles` 的 catch 分支原来有注释「missing is a legitimate answer and needs no warning」，
逻辑上没错——面板承诺描述「改过什么」，不承诺「还在不在」。但代价是**用户无法区分「我删了它」与
「它从没存在过」**，而这两件事对用户的下一步动作完全不同。

**决定。** 三态 `available` / `missing` / `invalid`；`missing` 与 `invalid` 的行保留在列表内、划删除线、
不可点、`cursor:default`、hover 不变色，右侧不显示大小而显示「已删除」/「无法读取」。

**为什么缺失行进折叠态（推翻 docs/10 的原建议）。** 折叠态实际回答的是「这一轮做了什么」，
**写了又删也是这一轮做的事**。不进折叠态会制造一个无法解释的数字：写了 3 个、删了 1 个，头部说 3，
列表只有 2 行。代价是极端情况四条全是删除线——这是诚实呈现，不是 bug。

**为什么只有三态而不是 Qoder 的四态。** Qoder 多一个 `checking`，因为它有一套按需拉取、带 80ms 合批
的存活状态服务。我们的状态是同一次面板请求里同步 `stat` 出来的，**结构上不存在中间态**。
少一个态是结构差异，不是简化。

**`missing` 与 `invalid` 的区别只看一件事：用户能不能自己修。** 删了就重建，读不了要查权限。

## D-104 · 「本轮」以路径快照为准，存储的轮次号只作 fallback

**背景。** 审查在 `api.js` 报了一条 P1：我最初让**存储的轮次号优先**于本轮路径快照（`turnPaths`）。
但 `turnNow` 来自 `previous.turn`，是**本进程的计数器**（重启从 1 起），而 `session-state` 里的 `turn`
戳来自写它的那个进程。重启后先跑完一回合再开面板时，`previous.turn` 变成 1，任何在很久以前被盖上
`turn: 1` 的旧文件都会被判成「本轮」改过。反方向同样有毒：存储号与新快照冲突时存储号获胜，
会把快照刚列出的文件否决掉。

**决定。** 有快照时快照说了算，存储号只在该文档的 `previous` 没有路径列表时兜底：

```js
const turn =
  turnPaths !== undefined
    ? turnPaths.has(absolute)
    : Number.isFinite(recordedTurn) && Number.isFinite(turnNow)
      ? recordedTurn === turnNow
      : false
```

**为什么快照必须赢。** 卡片描述的是 `previous`，它的头部计数和路径列表**都来自那里**。
一个数字和一个列表讲同一件事实时，讲得出细节的那个应该被相信。

**否决的方案。** ①存储号优先（就是被修掉的那个 P1）；②两边都要一致才算本轮（会让一次正常编辑在
存在陈旧戳时被判成「更早」，用户看到自己刚写的文件落到「更早」组）；③把序号也持久化成绝对轮号
（宿主的轮次计数在恢复会话时从中间开始，绝对号会在用户眼前跳过几十轮）。


### D-105 · 图标用八个桶的线稿，不逐扩展名、不用彩色

`client.js:388` `fileBucket(name)` 把扩展名收进七个互不相交的 Set
（`CODE_`/`MARKUP_`/`STYLE_`/`DATA_`/`DOC_`/`IMAGE_`/`ARCHIVE_EXTENSIONS`），
落到 `code`/`markup`/`style`/`data`/`doc`/`image`/`archive`/`file` 八桶；
`FileIcon`（`client.js:440`）与既有 `Icon` 并列，共享同一张纸、只换记号。

否决过的方案：

- **逐扩展名一个图标**（Qoder 的做法）：它的图标是 App 图标级的彩色设计，
  放进这套 24 网格线稿里像贴纸；而且八十个图标意味着八十次判断「这个画得对不对」。
- **引第三方图标包**：面板是手写 bundle，没有构建步骤，引资源就得引打包器。
- **未知扩展名按最近似猜一个**：错图标比通用图标更糟 —— 通用图标说「我不知道」，
  错图标说一件假事。

Set 互不相交是刻意的：判定因此不依赖检查顺序，加一个扩展名不会因为顺序而改变结果。

### D-106 · 目录从 payload 的 `cwd` 减出来，不靠路径尾段猜

`fileParts(path, cwd)`（`client.js:352`）用 `readPanel` 新发的 `cwd`

## D-111 · 申报与推断共用一个读取点，工具自身不记状态

**决定。** `report_output_files` 的 `execute` 不写任何状态；路径由 `transcript.js` 在 `noteCall` 里从 `tool/call` 事件读出，和 `edit` 的 `path`、`bash` 的重定向走同一个 `this.paths`。

**为什么。** 三个理由，权重递减：

1. **结果与调用解耦。** 工具结果可能迟到、可能不到（回合被中断），而卡片描述的是「这一轮发生了什么」，不是「哪次调用成功了」。写在 `execute` 里意味着一次没等到结果的调用会丢文件。
2. **一处规则。** 卡片上每一行的来历都能在 `transcript.js` 一个文件里读完。分成两处之后，「为什么这个文件在卡上」需要读两个模块。
3. **不需要跨包桥。** `execute` 拿到的 `exec.agent` 能给出 agentId，但写进 `TranscriptStore` 要么把这个 store 暴露成服务，要么让 `tools.js` 依赖 `transcript.js`。而 `tool/call` 事件本来就带着 agentId。

**被否决的：**

- *在 `execute` 里直接写 `transcript`*：需要把 store 从 `apply` 闭包里提出来做成服务，或者从 `ui-evolve` 到 `skill-evolve` 再绕回来。为一个数组加了两个包之间的耦合。
- *工具放进 `skill-evolve`*（工具注册的既有位置）：它服务的是面板的产出卡，不是技能检测。包拆分依据是「按功能」——把记文件这件事放进检测器，正是那种「装卡片就得装中断式检测器」的旧结构。
- *用 `write` 工具一并处理*：会改变一个已被十几个测试覆盖的函数，为了支持它不认识的一种调用。

## D-114 · 申报路径与推断路径分开存，声明在快照里排前面

**背景。** 第一次实现把 `present` 的路径与 `edit`、shell 重定向的路径一起 push 进 `this.paths`。

**决定。** 新增 `this.declared`，两种来源分道；`snapshot()` 合并时 `[...this.declared, ...this.paths]`，声明在前。

**为什么。** 两条独立的理由，都来自审查：

1. **语义。** `present` 是「声明交付物」，不是「写入」。一个预先就存在、只是被模型点名交付的文件，混进 `paths` 后会被算成「本轮碰过」，卡片上标成 `turn: true`——那是在说一件没发生的事。
2. **容量。** `snapshot()` 保留**前** 40 条，而模型在回合**末尾**才 `present`。按调用顺序 push，申报恰好是最容易被截掉的那一条。shell 每次调用最多贡献 20 个目标（`packages/core/lib/shellpaths.js:24`），两三条多重重定向就能把预算吃光。我原来那段注释写的是「放在 shell 分支之前，所以能保住」，那是错的——顺序由调用序列决定，不由代码位置决定。

**代价。** 两个数组要一起清空（`beginTurn` 与 `endTurn` 的放弃分支各一处），漏一处就会出现「上一轮的申报污染这一轮」。已由 `a presentation adds to the turn, it does not replace it` 与 `a busy turn still shows what the model named` 两条断言守着。

## D-115 · 容量只有一个常量

**决定。** `MAX_CARD_PATHS = 40`（`transcript.js:84`），`MAX_REPORTED_PATHS = MAX_CARD_PATHS`（`:100`）。

**为什么。** 曾经是两个数：schema 的 `maxItems: 50`、卡的 `slice(0, 40)`。于是一次 schema 合法的五十条调用会被**静默**截断十行，而 `execute` 返回 `{ ok: true, recorded: 50 }`、`render` 对模型说「50 files recorded，它们会出现在产出卡上」。两个模块分别写下了同一个承诺的两半，然后互相违背。

**代价。** 改容量要动一个常量，而不是两个。这正是想要的。

## D-116 · 超出容量的申报如实汇报，不返回失败

**决定。** `report-tool.js:145-147` 保留前 `MAX_REPORTED_PATHS` 条，返回 `{ ok: true, recorded: kept.length, ignored, dropped }`，`render` 在 `dropped > 0` 时补一句「N 条后面的没装下，已丢弃」。

**为什么。** 原来的实现返回 `{ ok: false, code: 'too-many' }` 并提示「拆成几次调用」。这个拒绝是**假的**：路径在 `execute` 运行**之前**就已经被 `tool/call` 事件读走了，`ok: false` 撤不回已记录的事实。模型信以为没记，重发一次，重复的条目再占一遍预算。同时「拆成几次调用」这个建议也是错的——上限是**每回合** 40 行，不是每次调用，拆开只会更快撞上总数。

工具能诚实说的只有一件事：能装下几条，丢了几条。

**代价。** 模型可能据 `dropped` 重新挑重点再申报一次，覆盖不了的部分仍然丢失。这是容量本身的上限，不是汇报方式的缺陷；至少要让它知道自己丢过东西。

## D-117 · 产出采集的第三路是 git 差分，且按回合夹逼

**决定**：`git status --porcelain=v1 -z --untracked-files=all` 作为第三种产出采集来源，与「工具参数」和「模型申报」并列。但记下的不是它输出的集合，而是**回合开始与结束两次读数的差集**。

**为什么**：`git status` 是累计的，它把五轮以前未提交的改动也列出来。直接记，等于每回合都把旧工作顶到卡片最上面并标成「本轮」——这是关于「哪一轮做了这个」的谎，而卡片唯一的职责就是回答这件事。

**为什么是 A 方案而不是别的**：S5 已经证明「依赖模型申报」会漏——真机回合里模型一次没调我们给的工具，`empty.bin` 这类谁都没提的文件永远缺席。git 不问意愿。

**被否决**：

- **监听文件系统**（`docs/19` 里已否决，这里重述理由）：大仓库事件量比面板本身贵；而且 `fs.watch` 报的是「谁碰了这个盘」，不是「这一轮写了什么」。
- **照抄 `git status`**：见上。
- **解析脚本源码找路径**：等于自写一个 Python/Node 解释器，猜错比不猜更糟。
- **把 `git status` 当 diff 展示**：那是另一件事（`docs/19` §八已列）。

**代价**：一个回合结束要 spawn 两个 `git` 进程。用一个纯文件系统的 `.git` 上溯预检把「不是仓库」挡在 spawn 之前——大多数工作区都不是仓库，这是常态而非异常。

## D-118 · 基线存的是 promise，不是数组

**决定**：`GitWatch.start` 把 `this.changes(cwd)` 的 **pending promise** 存进 map，而不是 await 出数组再存。

**为什么**：`git status` 在大仓库上可能比 `turn/start` 到第一个工具调用的间隔还长。存数组意味着要么阻塞住那段时间（回合启动变慢），要么接受竞态（迟到的读数被装进一个已经关闭的区间）。存 promise 让「迟到」无害：`finish` 会 await 它，两次读数的顺序永远成立，与各自多慢无关。

**被否决**：

- **`start` 里 await**：会拖住回合启动。
- **加定时器/重试**：Qoder 那套 12s/35s 定时器是为它自己的后台生成服务的，我们的触发点是 `turn/start`，比定时器准。

**代价**：map 里存的是可能永远不被消费的 promise（会话被销毁而没结束回合）。`forget` 负责清，而 `start` 里就地 catch 掉拒绝——否则一个可选的兜底能把宿主拖垮。

## D-119 · git 的四类失败一律答空

**决定**：`changedFiles` 对「不是仓库」「没有 git 二进制」「超过 2000 个改动」「什么都没改」四种情况全部返回 `[]`，不抛错、不打日志、不在面板上显示任何错误。

**为什么**：这四种情况对面板的含义完全相同——「这条路这次没找到东西」。另外两条采集路可以自由地不同意。把其中任何一种变成错误都会让面板显示一个用户无法行动的问题：没人会为了看侧栏去 `git init`。

**被否决**：

- **区分「不是仓库」与「git 挂了」并给提示**：面板不是诊断工具。真要诊断，日志里已有。
- **超限时只取前 2000 个**：那会把「这个仓库大得没法回答」伪装成「这一轮改了 2000 个文件」。

**代价**：真正的配置问题（比如 PATH 里没有 git）也会静默。这是有意的：`git` 缺席时另外两条路照常工作。

## D-120 · 多根发现：先向上找，再向下看一层

**决定**：`sweepChanges` 先 `findRepositoryRoot(cwd)` 向上找；找不到就 `findChildRepositories(cwd)` 列**一级**子目录里带 `.git` 的；子仓库数达到 `MAX_CHILD_ROOTS = 20` 就把 coverage 记成 `partial`。**工作区本身在某个仓库内时，不再找子仓库。**

**为什么**：真实失败案例——用户工作区 `F:\test`，`git init` 在 `F:\test\test8`，向上永远找不到。这是「我打开了父文件夹，在里面建了个项目」这一常见形状，按构造只有一层。

**为什么有仓库在内部时不再往下找**：那时上级仓库已经回答了下面全部内容；再找子仓库会把同一批文件按两个基准读两遍，`paths` 去重能挡住重复，`roots` 却会变成一个错的名字。

**被否决**：

- **递归搜到底**：依赖树里每个包都可能带 `.git`，一次 20 万次 `existsSync` 比面板本身贵。
- **超过上限就返回空**：那会把「这个目录里有太多仓库」伪装成「这里什么都没有」——正是 S6 补丁要消灭的那种沉默。
- **每层都找**：一层就够覆盖那个失败案例，多一层多一倍目录读取。

**代价**：仓库在两层以下时仍然看不见。记 `partial` 而不是假装看见了。

## D-121 · worktree 的判据是 `--absolute-git-dir` 与 `--git-common-dir` 不相等

**决定**：`describeRepository` 用一次 `rev-parse --show-toplevel --absolute-git-dir --git-common-dir` 拿到三行，`resolve(gitDirectory) !== resolve(commonDirectory)` 即为 worktree。

**为什么**：`--git-dir` 返回的是**相对当前目录**的路径（仓库根下是 `.git`，`deep/inner` 下是 `../../.git`），拿它和 `--git-common-dir` 比会在子目录里误判成 worktree。`--absolute-git-dir` 恒为绝对路径。

**为什么用一次 spawn 而不是三次**：这一层每次回合要跑两次（基线 + 收尾），每次多两次 `execFile` 在 Windows 上约 30–60ms。

**被否决**：`--git-common-dir` 单独调用再拼（多一次进程，且两者之间仓库状态可能变）；只看 `.git` 是不是文件（worktree 是文件、submodule 也是文件，分不开）。

**依据**：这正是 Qoder shell 脚本里的判据——`test "$git_directory" = "$common_git_directory"` 决定 `workspace_kind=local|worktree`。

## D-122 · coverage 取两端较弱者，并且写在早退之前

**决定**：一次 sweep 的 coverage 是「基线那次」与「收尾那次」中较弱的一个；`rememberSweep` 在 `turn/end` 的第一行就调，**在 `if (reading.paths.length === 0) return` 之前**；面板拿不到申报时 `sweep` 是 `null`，不是 `'complete'`。

**为什么两端取弱**：区间的可信度由较弱的一端决定。基线时半瞎、收尾时全看见，这个区间里仍然可能有没看见的变化。

**为什么写在早退之前**：一个在只能半读的仓库里**没有产出任何文件**的回合，与一个**确实什么都没产出**的回合，在 `paths` 里完全相同。前者有疑虑、后者没有，而这个区别只在 sweep 自己知道——早退就等于把疑虑丢掉。

**为什么 `null` 不等于 `'complete'`**：历史会话从未被扫过。把「没扫过」读成「扫干净了」会让所有旧记录都像被验证过。这与 `readSweep` 里「不认识的值读成 complete」不矛盾：那里是**已经有一条记录、只是词不认识**，这里是**根本没有记录**。

**被否决**：三者合并成一个 `'unknown'`（面板要区分两件事：没人扫过 vs 扫了没扫全）；coverage 记在 `paths` 的每条上（同一次 sweep 里所有路径的覆盖度相同，逐条重复 200 次）。

## D-123 · 合并落盘计数时，重新编号已经打开的那一轮

**决定**：`TranscriptStore.hydrate` 在把落盘的 `turns` 加到内存计数之后，如果
`existing.turn !== undefined`，就把它设成合并后的 `existing.turns`。

**为什么需要**：重启的时间顺序不是想当然的那样。宿主的 `user/message` 会在
`SessionState.load()` 的异步读盘返回**之前**到达，于是 `beginTurn(undefined)` 从
`turns + 1` 起算，得到 1；读盘随后到，`hydrate` 把文件里的 1 加上去，`turns` 变成 2，
但已经开始的那一轮仍停在 1。`turn/end` 取 `ending.turn` 作为 `endedTurn`，
于是 `previous.turn`、`rememberSweep(...)` 的 turn、以及每条路径的 `turn` 全部写成 1。

**证据**：样本 A 第二轮的状态文件同时存在 `turns: 2` 与 `sweep.turn: 1`、
`previous.turn: 1`。三者只能由「先开轮、后读盘」这一个顺序产生。

**影响**：卡片目前按 `previous.paths` 的布尔集合分组，所以还看不出错——但
`sweep.turn` 一旦被客户端读出来（S8），界面会说「第 1 轮扫描不完整」，
而第 1 轮早就结束了。

**被否决**：
- *不修，当作「面板自增计数」的设计*。计数本身是局部的，这没错；错的是**同一个数字有两个来源**。
  既然是同一个号，就必须是同一个值。
- *在 `endTurn` 里重新编号*。`previous` 与 `sweep` 由两个不同的调用点消费，
  在那里修只能盖住一个；而且 `endTurn` 并不知道这一轮开始前文件说了什么。
- *让 `beginTurn` 等读盘完成*。那是给一条同步路径加异步等待，
  且 `record` 是宿主事件回调，阻塞它会拖住每个事件。

**代价**：`hydrate` 多一次赋值，没有别的。已经关掉的轮不受影响（`turn === undefined` 时不改），
所以从第二个回合起行为完全不变。


## D-124 · 第四路 mtime 扫描，且只在 git 无答案时采用

**背景。** A（git）与 C（申报）都依赖「有人说出路径」。真机上两条都哑过：
`F:\test` 不是仓库（A 直接无效），而已是 `??` 的文件被改写时 `git status`
逐字节不变（A 看得见状态码变化，看不见内容变化）。

**决定。** 加一条基于修改时间的通路：回合开始记时刻，结束时遍历 `cwd` 收
`mtime >= since` 的文件。但**只在 `fromGit.length === 0` 时采用它的结果**。

**为什么不是并列合并。** `mtime` 说「被动过」，不说「这轮写的」。`git checkout`、
`npm install`、一次构建都会成批改 mtime。把它们和 git 的结果并在一起，
卡片会把「不是我产出的」和「我产出的」列在同一个标题下。

**被否决的方案。**
- *内容哈希快照*（Qoder 的做法）：每回合对全量文件取哈希是几百 MB IO，
  它敢做是因为只对「被 checkpoint 的工具调用涉及的路径」取且存在自己的 sqlite 里。
- *`fs.watch`*：大仓库事件量爆炸，且跨平台语义不一致。
- *解析脚本源码*：等于自己写一个解释器，猜不准。
- *与 git 结果求并集*：见上，会把构建产物记成产出。

**代价。** 每回合结束时多一次目录遍历。靠三个上限（5000/8/1500ms）与
`isGeneratedDirectory` 挡在 `node_modules` 之前；遍历完全在后台，
不阻塞 `turn/end`。

## D-125 · 噪声规则提升到模块级，并导出 isGeneratedDirectory

**背景。** 规则原本全写在 `isNoisePath` 函数体内，遍历器够不着。
docs/19 §6.3 明确要求「复用现成的，不要新写一套」。

**决定。** 把 `GENERATED_DIRS` / `GENERATED_FILES` / `GENERATED_SUFFIXES` /
`TEMP_DIRS` / `scratchName` / `configName` / `dotName` 等提到模块级，
`isNoisePath` 改为使用它们；另导出 `isGeneratedDirectory(segment)` 供遍历器
在下潜前逐层询问。

**为什么必须复用。** 写第二份必然漂移，而漂移是**静默**的：
遍历器收进来卡片又滤掉（白花预算），或跳过卡片本该显示的文件（丢数据）。
两种症状都不会报错，只会让某个文件莫名出现或消失。

**被否决的方案。** *遍历器自己调 `isNoisePath(join(dir, name))`*：
对目录而言那个函数会按扩展名/文件名规则误判，它不是为目录设计的。

**代价。** 一个内部实现细节变成了模块的公开接口。用 JSDoc 写清了它回答的问题
（「这个目录该不该下潜」），而不是它长的样子。

## D-126 · scanReading 接收预算参数

**背景。** `truncated → 'partial'` 这条翻译零覆盖：`scan-watch.test.mjs` 全部注入

## D-127 · 遍历的目录过滤默认值就是卡片的过滤谓词

**背景**：S7 的遍历器 `scanChanges` 有一个 `skipDirectory` 选项，默认 `() => false`。
`scan-watch.js` 调它时不传，于是生产路径上一个目录都不跳。
卡片那边早就有 `isNoisePath` / `isGeneratedDirectory`，但只在渲染前过滤。

**决策**：`scanChanges` 的默认值就是 `isGeneratedDirectory`，不是 `() => false`。
调用方想换自己的谓词仍然可以传，但「什么都不跳」不再是默认。

**理由**：默认值就是那个「没人想过时会发生什么」的答案，而没人想过时，
它的作用范围是整个文件系统。一个遍历器在没有过滤的情况下走进 `node_modules`，
不是「少了一次优化」，是**把预算花在了卡片一定会扔掉的东西上**——
实测 `node_modules` 6000 文件能让扫描返回 4997 条依赖、真正的产出一条不进。

**被否决的方案**：
- **让 `scan-watch.js` 显式传参，默认值保持 `() => false`。**
  这就是当前代码的样子，它已经错过了两次（DEF-105 与 DEF-106 同形）。
  默认值不该是那个危险值，因为下一个接线的人也会忘记。
- **在 `scan-watch.js` 里再写一份目录表。**
  两份表必然漂移，而且漂移是静默的：遍历器收进来、卡片又滤掉。
  实测 `git-changes.js` 的 `SKIP_DIRECTORIES` 与 `GENERATED_DIRS` 已经漂移过（`.git` 只在一边）。
- **让 `isNoisePath` 直接当遍历谓词。**
  它按**文件名与扩展名**判断（`package-lock.json`、`*.min.js`），把它套在目录上会让
  遍历器在不该停的地方停下。目录谓词必须只回答目录问题。

**代价**：`api.js` 的内部实现细节变成公开接口（已在 D-125 记过）。
方向是单向的：卡片能事后过滤一行，遍历剪掉的子树永远拿不回来，
所以两边不一致时，遍历谓词必须是**更窄**的那一个。

## D-128 · coverage 三个词，合并规则收敛到 `mergeCoverage`

**背景**：`coverage` 原本两个词（`complete` / `partial`）。S7 之后暴露出第三件事：
**没机会看**。没有基线、没有工作区、reader 从没接上——这些都发生在「扫描」之前，
所以它们既不是「看全了」也不是「看了一半」。

**决策**：
1. 三个词：`none`（没看）/ `partial`（看了没看完）/ `complete`（看完了）。
2. 合并规则 `none > partial > complete`，最弱胜出，只在 `packages/ui-evolve/lib/coverage.js` 里写一次。
   三个调用点（`index.js` 的 `coverageOf`、`GitWatch.finish` 的前后合并、
   两个 `asReading` 的形状规整）全部问它。

**理由**：这不是措辞洁癖。`complete` 的意思是「我看了，就这些」，把它用在「没看」上，
后果是**替一轮没人扫过的回合背书**——宿主每重启一次就会发生一次，
而且它会覆盖掉上一轮的 `partial`，让提醒单向变弱、永不恢复。

合并必须有唯一实现，因为已经被写坏了三次：`git-watch.js` 的 `asReading`、
`scan-watch.js` 的 `asReading`、`GitWatch.finish` 的内联三元式，三处都是
`=== 'partial' ? 'partial' : 'complete'`——多一个词时三处同时把它吞掉。
DEF-107 就是这么发现的：端到端断言红在 `{"coverage":"complete"}`。

**被否决的方案**：
- **在三处各打一个补丁（把 `=== 'partial'` 改成 `=== 'partial' || === 'none'`）。**
  三份相同逻辑能同时错，就能同时再错一次。而且下一处新增的判断点不会有任何东西提醒它。
- **用数字排序（0/1/2）代替字符串。**
  读日志时 `coverage: 1` 没有意义。这个词最终要出现在面板上，也出现在状态文件里，
  能读的字符串比能算的数字更值钱——而且它一共只有三个值，算与不算没有区别。
- **让 `none` 等于 `partial`（都是「不完整」）。**
  它们对读者说的不是一件事：`partial` 意思是「我找了，可能还有」，
  `none` 意思是「我没找」。合并成一个词之后，面板无法告诉用户
  「这次没产出」和「这次没检查」的区别，而后者正是需要用户警惕的那一种。

### D-129 · 合并规则按语义分工，不按谁有答案

**背景。** `turn/end` 手里有两份名单：git 差分（看见被跟踪文件的改动与 untracked 文件）和 mtime 走查（看见时间窗内被碰过的任何文件）。原规则是 `fromGit.length > 0 ? fromGit : fromScan`。

**问题。** 这两份名单的盲区**不重叠**：git 结构上看不见被 `.gitignore` 忽略的文件——探针里写 `dist/bundle.js`，`git status --porcelain` 只报 `src/new.js`，一个字都不提 `dist/`。于是「只要 git 有一个字就全盘采用 git」等于在 git 最看不见的地方闭上了另一只眼。这不是罕见情形：往 `dist/`、`build/`、`logs/`、`*.log` 里写产物是脚本最常见的动作，而这几个恰好都在 `.gitignore` 里。

**决定。** 合并改成分工：git 提供可见的路径，走查只补 git 看不见的那一部分。判据是「这个路径对仓库是不是透明的」——**语义判据，不是时间判据**（不比较两边的 mtime，也不比谁先跑）。实现是 `git check-ignore --stdin -z`，它对每条路径回答「是/否被忽略」，并且不需要文件存在。

**被否决的方案。**

- **求并集（`[...fromGit, ...fromScan]`）。** 最省事，但会把「走查看见但 git 没报」的路径全算成产出，其中包括已提交文件被 `touch` 的情形——`build` 脚本 `touch` 一下几十个文件，卡片上就多几十行没变过的东西。
- **按时间窗过滤走查结果。** 需要相信 mtime，而 mtime 会被 `touch`、被同步工具、被解压程序改写；`git status` 与 mtime 之间没有共同的时钟。
- **让 git 也用 `--ignored` 参数列出 ignored 文件。** `git status --ignored` 只在工作区**已经有**这些目录时列出目录级别，拿不到具体文件路径，而且它对「本轮新写的」与「上一轮就在的」不作区分。
- **自己实现一份 `.gitignore` 匹配。** 嵌套 `.gitignore`、否定 `!`、`**`、目录继承、`core.excludesFile`、`.git/info/exclude`——自己写的第二份一定比 git 的那份更错，而且错了没人会发现。

**代价。** 每回合多一次 git 子进程（只在走查给出了东西、且找到了仓库时才跑）。合并逻辑从一行三元式变成一个 `async` 函数块，需要 `try/catch` 兜住——记账失败不能冒泡成 unhandled rejection。

### D-130 · 每个路径记下是哪个 bracket 找到的

**背景。** 合并后卡片一行一个路径，看不出它是 diff 找到的还是走查找到的。

**决定。** `paths` 的值多一个 `source` 字段：`'git'` / `'scan'` / 缺席。`rememberPaths` 增第四参，`pathsSeen` 带出来，`document()` 写进状态文件，`statTouchedFiles` 原样透传，读不出的值归 `null`。

**理由。** 合并是一次**信息销毁**：「git 看不见这个文件，只有走查看见了」这件事本身就是最有用的诊断线索（它精确等于「这个产物在 `.gitignore` 里」）。如果不在落盘时记下来，以后只能从路径形状去猜。

**被否决的方案。**

- **只在内存里记，不落盘。** 重启后就没有了，而「为什么这一行出现过」正是重启后才问的问题。
- **让 `api.js` 重新推导。** 那一层只有路径、大小、mtime，没有「谁看见的」；从 `path` 猜窗口边界等于编。
- **让 v1 旧文档缺 `source` 时默认成 `'git'`。** 旧文档说不出是谁找到的，默认成 `'git'` 就是替一个没人做过的判断背书。给 `undefined`，卡片显示未知。

**代价。** 每个路径多一个字符串字段；状态文件 v2 的形状多一个可选键（`readPathEntry` 要认）。收益是这一行从哪里来，以后不用再猜。

### D-131 · 头部说总数、徽标说剩余、coverage 三态各说各话

**背景。** 卡片头部原来写「N 个文件 · M 个生成」，展开/折叠徽标写「展开全部 N 个」。两处都在报总数，读者要自己做减法才算得出折叠态还有几行没看见。

**决定。** 三件事各归各位：头部只写总量 `${ordered.length} 个文件`（生成文件也是产出，由「生成文件」组标签区分）；徽标写 `显示其余 N 个`（展开态 `收起文件`）；`coverage` 三态各说一句——`partial` 说「目录没读完，可能还有文件没列出」，`none` 说「这一轮没有检查目录，列表可能不全」，`complete` **不说**。

**理由。** 头部回答「这一轮产出了多少」，徽标回答「屏幕上少了几个」，这是两个不同的问题，同一个数回答不了两个问题。`complete` 保持沉默是有意的：每张卡都挂一句「可能不全」，这句话就变成了背景噪音，等于没人读。

**被否决的方案。**

- **保留「M 个生成」。** 「生成文件」组已经有自己的标签，头部再拆一次，等于让读者在两个口径之间换算。
- **徽标写「展开全部 N 个」。** 控制上的数字应当是它将要改变的那个量（余数），不是你已经看见的那个量（总数）。
- **`complete` 也说一句「已完整检查」。** 那是把「一切正常」变成一条需要读的文案；安静才是正常的样子。
- **`partial` 与 `none` 用同一句话。** 合并后面板若分不开「我找了可能还有」与「我没找」，「没产出」和「没检查」就混成一件，而后者正是要警惕的。

## D-132 · 遍历用比卡片更窄的目录谓词，两个问题分开答

**决策。** `scanChanges` 的默认目录过滤改为新导出的 `isUnwalkableDirectory`，不再复用 `isGeneratedDirectory`。两张表分工：

| 表 | 回答的问题 | 含 `dist`/`build`/`out`/`target`/`coverage` | 含 `node_modules`/`.git` |
| --- | --- | --- | --- |
| `GENERATED_DIRS` | 读者想不想看到这一行 | 是 | 是 |
| `UNWALKABLE_DIRS` | 这一轮产出的东西可能在不在里面 | **否** | 是 |

**理由。** D-127 定过一条方向：两套规则不一致时，遍历谓词必须是更窄的那一个，因为卡片能事后过滤一行，剪掉的子树永远拿不回来。那条决策当时只把 `scratchName` 摘了出去，没意识到还有一类目录方向相反——**`dist/`、`build/`、`out/` 恰恰是「卡片不该显示、但走查必须进去」的地方**：它们是脚本写文件的默认去处，而且在每个同类项目里都写在 `.gitignore` 里，也就是说它们同时是 git 的盲区和卡片的隐藏集合。S8 的整条走查通路存在的理由就是补 git 的盲区，在 `dist/` 上却和 git 一样瞎。真机实测：过滤含 `dist` 时走查回四条、`check-ignore` 一个也没被问到；换成窄表后回九条、四个被忽略文件全部补上。

**被否决的做法。**

- **把 `dist` 从 `GENERATED_DIRS` 里删掉，让两张表重新合并。** 那样 `dist/bundle.js` 会以普通文件身份出现在卡片里，和源码并排。它不是人写的，卡片把它归进「生成文件」是对的。
- **保留一张表，让 `scanChanges` 接收一个「我要不要补盲区」的开关。** 开关的值由调用方决定，而调用方只有一处、写死成 `true`——那就等于默认值，等于没解决问题，还多一个没人会传的参数。
- **走查照旧剪掉，改由 `ignoredPaths` 自己去找被忽略的文件。** 那要把 `.gitignore` 的匹配规则实现一遍（嵌套、否定、`**`、逐目录继承），写第二份必然有一份是错的。

**代价。** 走查会比以前进入更多目录，`dist`、`build` 在有些项目里很大，会多吃条目预算。这是有意的：预算本来就是「看不全就如实说 `partial`」的机制，而剪掉这些目录是**静默**的看不全——两种都看不见，只有一种会说。另一处代价是两张表要一起维护，所以测试里钉了一条：两个谓词对 `dist`/`build`/`out`/`target`/`coverage` 必须给出不同答案，折叠回一起就红。

## D-133 · 前缀匹配前两边都解析成真实路径并折叠大小写

`ignoredPaths` 判断某条路径属于哪个仓库根，用的是字符串前缀比较。两侧的来源不同：根来自 `git rev-parse --show-toplevel`（规范大小写、真实路径），路径来自目录走查（沿用会话工作区的大小写、可能经过 junction 或 subst 映射盘）。Windows 的路径比较对大小写不敏感，git 也不敏感，只有我的字符串比较敏感。

后果不是「少一行」，而是**确信地说错话**：匹配失败时返回 `{ignored: [], known: true, repository: true}`——「有仓库，我问过了，一个被忽略的路径都没有」。调用方看到 `known: true` 就把整份走查丢掉，于是被 `.gitignore` 藏起来的产物全部消失，而卡片显示「查过了」。审查者用「只有盘符小写」就复现了：精确大小写得两行（一行 git、一行 scan），小写 cwd 只剩 git 那一行。

修法：新增 `comparable(path)` 做斜杠归一与去尾斜杠、`realPath(path)` 用 `realpathSync.native` 解析后失败回退原文、`ownerOf(path, prefixes)` 先文本小写比较、失败再真实路径小写比较。**已否决**：只在比较时 `toLowerCase()`（解决大小写，解决不了 junction/subst——那条路径连字符都对不上）；信任调用方传规范路径（走查的路径来自文件系统枚举，它没有「规范路径」这个概念）。

附带一条实测事实：`realpathSync.native` 对**已存在文件**的错误大小写路径也能解析成功，所以 `ownerOf` 里那一层纯文本的 `toLowerCase` 在已有文件上是冗余的，真正承重的是 realpath 回退。删掉它会有 1 条 junction 断言变红（已用注入验证），所以保留——但不要以为它单独就能解决问题。

## D-134 · `check-ignore` 按所属根分批，每批用自己那个根当工作目录

`check-ignore --stdin` 只认识「相对当前工作目录的那个仓库」里的路径。跨仓库的路径送进去，git 整批 `fatal: Invalid path` 退出 128。原实现把多个根的路径拼成一批、固定跑 `roots[0]`，于是多根工作区里**一批全废**。

真机探针纠正了一个我原本的假设：跨仓库批次不是「一条正确答案都不返回」，而是「退出码 128，但 stdout 里已经带着本仓库的命中」。所以修法有两件事，缺一不可：按 owner 分组（每批只含同一个根的路径、用那个根当 cwd），以及 `code !== 0` 时不要只是 `break` 就丢掉已经到达的答案——分组之后这一点自然消失，因为同组内不会再有「仓库外」的路径。

**已否决**：每批都把所有根依次试一遍（进程数 × 根数，双仓工作区就是 2×2，而 20 个根时是 400 次子进程）；让调用方按根拆好再传（调用方是 `turn/end`，它没有「根」这个概念，那个概念属于这一层）。

## D-135 · 跑不起来的 git 用 -1，和「退出码 1：这批没有忽略项」分开

`runGit` 原来把异常一律兜成 `code: 1`。而 `check-ignore` 的退出码 1 有精确含义：「这批路径一条都不被忽略」——一个**答案**。超时、ENOENT、EACCES 全都变成了这个答案。

后果链条很长但每一步都通：`GIT_TIMEOUT_MS = 2000`，大仓库 `check-ignore` 超时 → `code: 1` → 当作「这批没忽略项」→ `known` 保持 true → 调用方相信「git 说没有」→ 丢掉整份走查。**一个跑挂了的 git 说起来和跑得好好的 git 一模一样。**

修法：`const code = error === null || error === undefined ? 0 : typeof error.code === 'number' ? error.code : -1`。`-1` 是 `code !== 0 && code !== 1`，落进「跑挂」分支。注意 `typeof null === 'object'`，`execFile` 超时的 `error.code` 是 `null`，这正是原来兜底成 1 的原因。

**已否决**：给 `runGit` 加一个 `failed` 布尔返回值（返回值形状变化会波及 6 个调用点，而它们全都只关心退出码；多一个字段就多一个要同步的地方）；用 128 表示失败（128 是 git 自己「仓库外路径」的真实退出码，会被 D-134 的分组逻辑误读）。

## D-136 · 重记路径时保留已经知道的来源，而不是写成未知

`rememberPaths(sessionId, paths, turn, source)` 收到 `source === undefined` 时，原实现把整条记录写成 `source: undefined`。而 `turn/end` 每回合都会拿 `ended.paths`（来自 transcript 的 report/present 声明，天然没有 bracket）重记整份表。于是 provenance 的寿命恰好是一个回合。

修法：`const kept = origin === undefined && previous !== undefined ? previous.source : origin`。两种情形方向相反，这是有意的：**没有具名来源**的重记是「我的话不比已有的多」，保留；**有具名来源**的重记是「我这一轮又找到它了」，替换（最近一次找到才是「它从哪来」的真答案）。

**已否决**：让 `turn/end` 只重记它真正知道的（那等于要求调用方判断哪些路径「没有新信息」，而这个判断需要读存储——把存储知识泄漏到调用方）；给路径记录加 `sources` 数组（一个文件确实可能被两个 bracket 找到，但这个字段要回答的是「为什么这行在卡片上」，复数会让答案变成「随便挑一个」）。

## D-137 · sweep 的声称按回合号定新旧，没有号让位给有号

`rememberSweep` 无条件替换 `entry.sweep`。而它在一个 `git check-ignore` 子进程 `await` 之后才被调用——慢回合可能在下个回合已经说过话之后才到，于是旧回合的 `none` 覆盖新回合的 `complete`，卡片对新回合说了一句关于旧回合的话。

修法比较 `previous.turn` 与 `stamp`。**第一版我写成 `stamp !== undefined && previous.turn > stamp`**，意思是「只有两边都有号才比较」——结果是无号的声称可以覆盖有号的，被我自己的新断言抓出 `FAIL a claim with no turn number yields to a numbered one — {"coverage":"none"}`。正确写法是 `(stamp === undefined || previous.turn > stamp)`：**号是测量时刻的证据，没有号不是**，所以在有号记录面前让位。

**已否决**：让调用方排队（那是给每个回合引入一个序号签发者，而回合号本来就有）；直接丢掉迟到的那次（迟到的 `partial` 也是真实信息，只是不能代表新回合——同号仍可覆盖自己，这是「纠正」而不是「覆盖」）。
