## D-01 · 双触发电机：结构检测 + 回合反思

**决策**：两个独立触发源。结构检测看工具/命令序列是否重复出现；回合反思按回合数与工具调用数门槛定期问模型"这一轮有没有值得记的"。

**理由**：结构检测只看结构，对**非结构性知识全盲**——哪个 API 返回零行、为什么放弃第一种做法、人真正想要什么。这些恰好是最有价值的部分，而它们不会表现为"同样的三个工具又来一遍"。反思补这个盲区，但反思贵且噪声大，所以必须与确定性的检测器并存，而不是替代它。

**可观测的证据**：真实会话回放里，同一工具序列在 2 次后触发；反思路径在修复 `service()` bug 后 12 轮精确发布 2 次。

## D-02 · 证据闸门按角色分档，禁止模型自证

**决策**：证据分四类（`user` / `tool` / `action` / `self`），不同类支持不同强度的结论。`action` 类引文（模型自己做过的事）**不能单独支撑**一条技能。插件自己的 7 个工具从所有 lane 排除。

**理由**：如果模型能引用自己刚说的话作为"证据"，闸门等于没有——它会为任何提案找到"证据"。插件自己的工具经 `tool/call`/`tool/result` 到达，外观与第三方机器输出一样，所以必须按名字排除。

**代价**：跨会话批准需要候选在**源会话**里已通过校验。这条曾导致全部 candidate 卡在 `no-evidence`，见 `03-defects.md` 的 DEF-07。

## D-03 · 技能列表只列"本会话加载过的"

**决策**：面板第二模块显示本会话实际加载过的技能（按新到旧），不是已安装的全部。

**理由**：技能库可以有几十个，全列出来回答的是"没人问的问题"，还把真正重要的那一个埋了。**已安装 ≠ 被用过。**

## D-04 · MCP 列表从 `tool/call` 事件归集

**决策**：不从 `mcp_connector` 的存储或配置文件读 MCP 服务器，而是从插件自己监听的事件流里按 `mcp__<server>__` 前缀归集实际出现过的 server 名。

**理由**：配置文件写的是"配了什么"，不是"现在能用什么"。自己解析 connector 的存储会与其真实连接状态不一致，而**当前实际被调用过的**才是可信的。

## D-05 · 先写确定性检测器，反思作为补充

**决策**：P0–P2 阶段先做不依赖 LLM 的检测器并跑真实回放定阈值；反思是后来的补充。

**理由**：确定性部分可以离线验证、可以变异测试、不烧钱。把一个统计问题先做成确定性的，才知道反思该在哪些点上补。

## D-06 · 面板放在对话列旁的浮层，不占用宿主右栏

**决策**：用 `shell.overlay` + 绝对定位，贴在对话列一侧的空隙；不注册到宿主右栏。

**理由**：右栏是宿主放文件预览的地方，占了它意味着面板与预览不能同时出现。宿主也**没有**提供"对话列内部"的扩展点（会话级插槽只有 header 与 composer）。所以唯一的空间是对话列两侧的空隙。卡片**故意不设 `z-index`**，让宿主决定层级，侧栏展开时自然遮挡。

**被否决的替代方案**：
- 宿主右栏 tab —— 与文件预览互斥。
- `conversation.content` 全接管 —— 官方指引禁止，等于替换整个会话体。
- 固定偏移 —— 窗口一改或宽度手柄一拖就错，所以几何全部由 `measure()` 测量。

## D-07 · 面板可写，但只走同一个 `approve()`

**决策**：`POST /candidates` 委托给 `/skill-capture` 用的同一个 `approve()`。路由自己不实现批准。

**理由**：在路由里自己写文件等于**多开一扇没锁的门**——证据闸门与 confirm 握手都会被绕过。任何"为了快"而重实现批准的路由，都会在半年后变成两个行为不同的批准路径。

## D-08 · 候选按 `id` 解析，`id` 命中不了就是 miss

**决策**：`byIdThenName(queue, id, name)`——给了 `id` 就按 `id` 精确找，找不到返回 `undefined`（报 not-found）；只有调用方**没给** `id` 时才回退名字。

**理由**：同名候选可以共存（旧条目 stale 后模型再次提案同名），而 `findByName` 优先返回 live 行。于是「按名字操作一条 stale 行」会打到它的 live 孪生体——忽略会删错行，批准更会把用户没看过的候选写成技能。第一版为"兼容只传名字的旧客户端"而回退，这个回退就是缺陷本身。

## D-09 · 总结调用不使用 `system` 通道

**决策**：总结的指令拼进唯一的 `user` 消息正文前部，`options` 里删掉 `system` 字段。指令自带分隔符（`<transcript>`），正文入参前把该标签洗掉。

**理由**：宿主把 `system` 渲染成 wire 上的 `developer` 角色，有些 provider 直接拒绝——面板曾在被正确选中的模型上报 `400 unsupported message role: developer`。拼进 user 消息是**任何 wire protocol 都接受**的做法。分隔符必须洗掉，否则一个内容里带 `</transcript>` 的工具输出会提前结束块，让剩余部分被当作指令读。

## D-10 · 总结默认借用本会话自己的模型路由

**决策**：默认从会话自己的 `request/context` 事件读路由，而不是从目录里挑第一个模型。

**理由**：会话正在用的路由**已知可达且对这个账号有授权**；目录条目只证明某个 adapter 声称支持它。早期版本挑目录第一个，在用户机器上报 "no model route is available"——那就是信任目录而非信任正在跑的会话的失败模式。

## D-11 · 测试必须配变异验证，`NOT APPLIED` 算失败

**决策**：每个守卫断言要有一个"把实现改坏"的变异证明它真的会失败。变异脚本必须先断言源码真的变了；锚点失配报 `NOT APPLIED` 并计入失败。

**理由**：不能失败的测试等于没在测。而**"变异没应用"会被误读成"存活"**——本仓库历史上多次因此得出错误结论（一次引号转义导致 `replace` 未命中，报 SURVIVED，实际什么都没改）。

## D-12 · 删除不可观测的参数，而不是为它补测试

**决策**：`placeNear` 的 `alignTop` 参数已删除。它的两条臂是同一表达式（`clampTop` 幂等），126 组合零差异。

**理由**：守它的变异"存活"，看起来像覆盖缺口，会诱导下一个人去覆盖一个**任何输入都到不了**的分支。**不可观测的参数比没有参数更糟。**

## D-13 · 技能收益先补 L1

**决策**：先做「加载后发生了什么」的观察窗口（`outcomeTurns`，默认 2 个回合，写 `skill_result` 账本行），不做逐技能验收，不做对照实验。

**理由**：
- `uses` 的语义是**加载次数**，不是"用了并且有效"。
- `helpful`/`harmful` 是模型自评——刚花一回合照技能做完事的模型，最不可能判断这技能值不值。
- 真实账本里 `helpful`/`harmful` **全为 0**，效应侧是**空的**，不是差的。
- 需要先有一条"加载之后发生了什么"的记录，才谈得上收益。验证器只对声明了验收条件的少数技能存在（要改技能格式），且验证脚本是被执行的输入，需要单独审。
- 对照实验不该做进插件：无法保证隔离、会烧钱、属于实验设计，合理形态是仓库里的 CLI 脚本。

## D-14 · 三卡同屏与点击式候选审核

**决策**：保留分卡片侧栏，不用页签隐藏信息。「上一轮」「技能与 MCP」「产出文件」三张卡同时展示；技能和 MCP 在同一张卡内分组。「从本轮提炼」与「候选审核」是两个独立动作，审核使用点击打开的 modal，不再使用双层 hover 清单。

**理由**：用户需要同时扫读多种信息，页签会制造不必要的视图切换。hover 把发起提炼与查看队列混在一个按钮上，连续两层 hover 也让键盘和触摸操作不可靠。modal 让候选列表、证据和审批动作处于同一个明确上下文。

**保留的边界**：审批仍按候选 `id` 走既有 `/candidates` 与 `approve()`；confirm 模式保留行并显示等待定稿，stale 只读且可忽略，不新增第二条写入路径。

## D-15 · 排版实时跟随宿主

**决策**：面板、头部开关和 modal 不声明平台字体栈。客户端读取会话计算样式中的 `fontFamily`、`fontSize`、`lineHeight`，从宿主 `code` / `pre` 读取等宽字体，并监听宿主属性变化及代码元素插入/删除。

**理由**：硬编码字体会让插件在宿主修改字体、中文字体或辅助阅读字号后显得突兀，甚至破坏布局。使用计算样式而不是猜测宿主变量名，可以跟随当前实际渲染结果。

**实现约束**：普通流式文本插入不触发重复排版写入，只有相关属性或代码元素变化才同步；插件卸载时必须断开 observer 并移除全部 `--dsse-font-*` 变量。

## D-16 · 合并活动列表、空卡隐藏与紧凑操作行

**决策**：技能与 MCP 不再分区，合并为一个按最近使用排序的列表，用不同图标区分；没有内容的卡片默认隐藏；面板顶部不再显示标题块，只保留刷新、候选审核、设置一排。

**理由**：用户扫读面板时关心“这个会话最近用了什么能力”，分区和标题都会增加视觉成本。空卡片只会制造“这里应该有内容但没有”的疑问。顶部标题不承载操作，占用的是一排宝贵空间。

**实现约束**：最近使用需要一个跨类型可比较的序号，因此 `index.js` 维护单一 `recentUse` 时钟，技能加载和 MCP 工具调用都写入；`/panel` 为两类行输出 `lastUsed`，客户端只负责合并排序。没有 `lastUsed` 的旧响应保持稳定顺序，不会乱跳。

## D-14 · 面板配色只用宿主主题 token，不自带一套

**决定**：面板里所有颜色、边框、字体都写成 `var(--dsw-alias-*, 回退值)`，且回退值只作为「宿主样式表还没加载」时的兜底，不作为任何模式下的主色。

**理由**：宿主用 `body` 与 `body[data-ds-dark-theme]` 两套变量切换明暗主题，插件若自带颜色就必然要自己实现一遍深色模式，而它对宿主的配色演进永远滞后。用 token 则天然跟随，代价是名字必须真实存在 —— 这正好是 DEF-25 踩的坑：四个名字是照着假 fixture 抄的，取不到值就静默落到浅色回退上，浅色下看起来正常，深色下错得离谱。

**代价与对策**：token 名字属于宿主的内部契约，升级可能失效。因此把它变成可回归的：`scripts/extract-host-tokens.mjs` 从 asar 解出宿主当前定义的全部 token 写入 `test/host-tokens.txt`，`test/tokens.test.mjs` 断言 bundle 引用的每个 token 都在清单里。宿主升级后重跑抽取脚本即可，测试会在名字失效当天失败而不是等到某个人在深色模式里发现。

**被否决的替代方案**：
- 自带一套明暗配色：要维护两份，且在宿主的主题切换上再叠一层自己的判断，容易出现「插件是深色、宿主是浅色」的错配。
- 只在浅色下保证可读、深色交给用户：面板是常驻元素，深色下不可读等于坏了。

## D-15 渐隐是否出现由测量决定，不由 CSS 常量决定

**决定**：`Clip` 组件用 `useLayoutEffect` 比较 `scrollHeight` 与 `clientHeight`，据此设置 `data-clipped`；CSS 只在 `data-clipped="true"` 时画遮罩。`max-height` 保持无条件生效。

**理由**：截断高度是排版预算（标题栏是按这个高度设计的），所以它必须恒定；但是否溢出是运行时的布局事实，写成常量就必然在两种情况下错：短摘要被遮罩压暗，或长摘要被截断却没有提示。这两件事的判据不同，就不该共用一个开关。

**为什么用 layout effect 而不是 passive effect**：passive effect 在浏览器已经绘制之后才运行，首帧必然出现「文字被切、但没有渐隐」。对没有布局阶段的环境（测试桩、未来的非 DOM 渲染器）回退到 `useEffect`。

**被否决的替代方案**：
- 全用 `useEffect`：每次进入会话闪一帧，正是用户报告的「闪烁」这一类体感。
- 用 CSS `mask-image` 让遮罩自然只在溢出时出现：无法区分「溢出」与「刚好填满」，且 `mask-image` 在不支持的宿主里会静默失效，退化成无提示的截断。
- 按字符数估算：中英文混排与换行位置让字符数完全不能预测高度。

## D-16 面板隐藏卡片时保留设置弹窗

**决定**：卡片全空时返回 `settings`（通常是 `null`），而不是无条件 `return null`。

**理由**：设置弹窗由 `settingsOpen` 状态驱动。把整棵返回树短路掉，DOM 被卸载而状态仍为 `true`，等下一次有卡片时弹窗会自己复活 —— 用户没有重新打开它。渲染分支的短路只能吞掉「没有状态支撑的东西」，不能吞掉由状态驱动的节点。

**代价**：空态时返回的顶层节点从 `div.dsse-rail` 变成 `null` 或 `section.dsse-dialog`，宿主 overlay 里这个插槽的 DOM 结构会跳变。这是可接受的：overlay 是 `pointer-events:none` 的绝对定位层，没有布局依赖它。

## D-17 待审候选算作内容

**决定**：`hasAnyCard` 纳入 `pendingCandidates > 0`。

**理由**：顶栏那个「建议」按钮是面板里通往候选审核弹窗的唯一入口。一个没有上一轮内容、没有技能、没有文件、但队列里躺着三条待审候选的会话，如果按「没内容就全隐藏」处理，用户就只剩 slash 命令一条路。可见性规则的目的不是「空就干净」，而是「别让空面板看起来像面板」—— 有工作可做时不适用。
