# D-20261128-lifecycle · 建议的生命周期与三条纪律

冻结台账里的细节：`D-268`（中断的回合不画）、`D-269`（命中率人工评估，见
`D-20261128-rules`）、`D-272`（测试替身必须执行 teardown）、`D-273`（发现了就修）；
缺陷链 `DEF-214`、`DEF-220`、`DEF-221`、`DEF-222`。

## 决定

1. **没有时钟。** 生存期 = 「上一轮完成」到「下一轮开始」；没有 TTL 定时器，
   回合边界处清空（`forgetOffer` / `closeOffer`）。
2. **只持久化一句**（给输入栏幽灵用），芯片不回放历史建议；恢复出来的那句
   **永远 `stale: true`**，只画幽灵。
3. **中断的回合什么都不画。** 宿主 `turn/end` 的 `reason.kind !== 'completed'` 时，
   transcript 记 `interrupted`，路由直接返回空 + `the last turn was interrupted`；
   这个标记必须落盘（`session-state` 的 `document`/`keepsDocument`/`load`），
   否则重启后闸门失效。
4. **回合边界与答案落地谁先到都要能显示。** 边界处打一个 `closedAt = turn` 的
   标记、4 秒后自行解除：两种事件顺序里总有一种会让它指向本该显示的那一行。
5. **发现了就修，不写「已知问题」。** 只有需要用户拍板的事才留一行待裁决（D-273）。

## 代价

- 「答案后到」的顺序下，芯片最多晚 4 秒出现（DEF-222 的已知代价）。
- 只持久化一句意味着重启后看不到上一轮的三条候选，只有一个幽灵。

## 纪律（不是产品的，是流程的）

测试替身必须执行它所替的那条生命周期：`ctx.effect` 的桩若不调用 cleanup，
插件的 teardown 在所有测试里都是死代码，监听器泄漏这类缺陷永远测不出来（DEF-217）。
