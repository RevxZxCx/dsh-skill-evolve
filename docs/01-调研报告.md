# 同类方案调研报告：会话经验 → 可复用技能

> 调研时间：2026-10-22
> 目标：搞清楚「自动从当前对话提炼技能」这件事，别人已经做到什么程度，哪些设计值得抄，哪些坑别人已经踩过。
> 结论先行：**这件事不是新想法，商业 IDE（Qoder/CowAgent）和开源框架（MemOS/EverOS/GenericAgent）都做了，但没人在 DSH 上把三件事（提炼 → 建档 → 外部检索）串成一条闭环。**

---

## 一、需求原文拆解

用户提出的诉求，实际是三件独立的事，必须分开评估：

| 编号 | 需求 | 本质 |
|---|---|---|
| **A** | 自动从当前对话提炼内容 | 判断「这段会话里有没有值得固化的经验」 |
| **B** | 从提炼结果生成一个 skill | 把经验写成 `SKILL.md`，落到技能目录 |
| **C** | 去外部搜索现成技能解决当前问题 | 市场检索 + 安装 |

用户的原话是「手动创建太慢、而且会忘」——这两个痛点在 A 和 B，C 是另一种痛（重复造轮子）。三者技术栈完全不同，不能当一个需求做。

## 二、商业 IDE

### 2.1 Qoder —— 唯一一个把这个功能做成一等公民的

**功能名：Skill evolution suggestions**（设置 → 通用 → 开启）

官方原文流程（`docs.qoder.com/qoder/skills.md`）：

> Enable **Skill evolution suggestions** under **Settings → General** to let Qoder analyze reusable lessons after local tasks and suggest creating or improving Skills. **Not every task generates a suggestion.**
>
> Inspect suggestions in the Skill and MCP area of the task monitor. Check the goal and source, then create an improvement task or ignore the suggestion. **Multiple suggestions support batch creation or dismissal.**
>
> **Accepting opens a new conversation to confirm the plan before creating or updating a Skill; task creation does not mean the Skill has already changed.**
>
> If a suggestion expires, its source is unavailable, or Skill files have changed, regenerate or handle it against the latest state. Turning the setting off stops new suggestions.

拆出来的五个设计决策，每一条都值得抄：

1. **默认关闭**。不是装了就自动写——这是「持续性系统提示词污染」风险的最小防线。
2. **"不是每个任务都会产生建议"**，明确写进文档。这等于承认了提炼是低召回、低命中率的，不承诺覆盖面。
3. **建议是独立实体，不是写入动作**。建议有目标（goal）和来源（source），可批量创建、可忽略、会过期。
4. **接受 ≠ 已写入**。接受只是**开一个新会话去确认计划**，真正改技能是下一步。把「决策」和「执行」切成两次人机交互。
5. **过期与失效处理**：来源没了、技能文件被改过，建议要重新生成，不能拿旧结论往新文件上盖。

**它还有一套三层知识引擎**（`user-guide/knowledge-engine/`）：

| 类型 | 来源 | 内容 |
|---|---|---|
| Repo Wiki | 代码库 | 结构化文档：架构、模块关系、实现细节 |
| Knowledge Card | 代码 | 高密度知识单元：架构文档、代码规范 Spec、技术栈信息 |
| Conversation Memory | 对话 | 踩坑、决策理由、项目经验 |

官方明确了两条自动积累路径：
- **代码侧**：生成 Repo Wiki 时，顺带把代码意图、设计方案、上下文讨论抽成 Knowledge Card；
- **对话侧**：交互中的踩坑、决策理由、项目经验，自动抽成 Memory。

存储位置 `.qoder/repowiki`，**跟着代码仓库走**（可 commit、可 git pull 同步给团队），支持中英文分目录。

**Memory 的作用域设计**（`qoder/memory.md`）：Global（跨项目偏好）+ Project（仓库规则/经验）两层，各自独立开关，设置页显示「文件数 + 最后更新时间」，可打开目录直接看，可清空。原文还特意写了「及时处理过时、不准确、不再需要的信息」和「不要存密码、验证码、API Key、临时任务状态」。

> **关键洞察**：Qoder 把「对话经验」存成 **Memory**，把「可复用工作流」存成 **Skill**，两者是分开的。`Skill evolution suggestions` 只是让 Memory 里的经验**有资格升级成 Skill**。这个分层非常关键——绝大多数自研方案失败就失败在把两者混成一个东西。

### 2.2 CowAgent（zhayujie，开源但产品化程度高）

| 能力 | 官方描述 |
|---|---|
| Memory | 三层架构（context → daily → core），**Deep Dream 自动蒸馏**，关键词 + 向量混合检索 |
| Knowledge | 自动整理成 Markdown wiki，构建可可视化浏览的演进知识图谱 |
| **Evolution** | "Self-Evolution **reviews conversations automatically** to improve skills, **follow up on unfinished tasks**, and consolidate memory and knowledge" |
| Skills | 从 Skill Hub / GitHub / ClawHub 一键装；或用自然语言对话创建自定义技能 |

**注意 Evolution 那一行是三合一**：改技能 + 跟进未完成任务 + 整合记忆/知识。这是个重要设计——「自进化」不是只管技能，它和「任务续做」「记忆整合」共用同一个审查循环。只做技能不做另外两个，用户感知会弱很多。

## 三、开源框架

### 3.1 MemOS（★17k+，`MemTensor/MemOS`）—— 分层最完整

`@memtensor/memos-local-plugin` 的四层结构（README 原文）：

- **L1 trace** — 步级接地记录（action + observation + **reflection** + value）
- **L2 policy** — 跨多条 trace 归纳出的子任务策略
- **L3 world model** — 从 L2 + L1 压缩出的环境认知
- **Skill** — **可调用、已结晶的能力，agent 能直接 invoke**

两条反馈通道：
- **步级**：模型 ↔ 环境（工具结果、观察增量）
- **任务级**：人 ↔ 模型（显式评分 + 隐式信号）

机制核心：**反思加权的奖励沿 trace 反向传播，高价值模式结晶成可复用 Skill**；推理时三级检索器（Skill → trace/episode → world model）在对的时机注入对的上下文。

**已提供 DSH 适配器**：`adapters/deepseek-harness/`（"In-process Cordis bundle for DSH"），数据落在 `$DSH_HOME/memos-plugin/`（默认 `~/.dsh/memos-plugin/`）。

> MemOS 是唯一把「Skill 是 L1-L3 之上的第四层，且需要奖励信号驱动」这件事说清楚的项目。它的代价是重——需要 trace 级别的埋点，DSH 的插件接口给不到那么细的观测面。

### 3.2 EverOS + `evermind` DSH 插件 —— 已有可跑通的中文方案

`leeseo39/dsh-everos-memory` 的完整链路（README）：

```
DSH 会话 --agent/turn-stopping--> evermind 插件 --批量 flush--> EverOS API 127.0.0.1:8000
   ^                                                                  |
   +---------- agent/pre-step 回忆注入 <-------------------------------+
                                                                      v
                                          SQLite + LanceDB --> OME 自进化策略
                                          （画像 / 聚类 / 每周 Reflection / 技能）
                                                                      v
                                                          Markdown 记忆文件
```

关键参数与约束：
- 触发阈值：**空闲 15 分钟 / 500 条消息 / 20 万 token** 三选一达成就提炼。
- **每周 Reflection** 整合散落记忆、自动聚类构建用户画像、**把解决过的问题提炼成可复用的 Agent 技能**。
- 硬依赖：**Windows + WSL2（Ubuntu + systemd）、两个 API Key（DeepSeek 做提炼、阿里云百炼做 embedding/rerank）、内存约 2GB**。
- flaky 点自己写明了：「该插件针对 dsh **0.1.0-rc.6** 编写；在桌面运行时 **0.1.1-rc.1** 实测捕获正常」——**这是对旧版本的验证，本机是 0.2.1-rc.2**。

> 这是目前「端到端最像」的方案，代价是重（WSL2 + 双 Key + 2GB）且版本滞后。

### 3.3 GenericAgent（`lsdefine/GenericAgent`）—— 设计哲学最激进

> 设计哲学 —— **don't preload skills, evolve them.**
>
> Every time GenericAgent solves a new task, it **automatically crystallizes the execution path into a reusable Skill**. The longer you use it, the more skills accumulate — forming a personal skill tree grown entirely from 3K lines of seed code.

~3K 行种子代码 + 9 个原子工具 + ~100 行 agent loop，仓库里每个 commit 都是它自己提交的（自我 bootstrap 证明）。

**它的取值不在实现，在主张**：技能库不该预置，只能长出来。这也意味着它接受「长歪」——靠后续使用淘汰，不靠前置审批。

### 3.4 ReMe（`agentscope-ai/ReMe`，★3667）

把 DSH 接入 ReMe 本地优先、自进化的个人知识库：自动把**已完成的主 Agent 对话**沉淀为用户掌控的 Markdown 记忆，`reme_search` 结合 BM25 + 可选向量 + wikilink 展开，**按日整理长期记忆**。

> 产物是「记忆」，不是「技能」。属于 B 的前置步骤，不解决 A 的最后一公里。

### 3.5 distill-kura（`lna-lab/distill-kura`，★54）—— 写入闸门设计最好

> A long-term memory for agents that is **distilled, not accumulated**. **Recall works by meaning, writing is gated by evidence.**

两个失败模式，作者描述得很准：
1. **按关键词检索会漏**：问「SSD inference chips」，记忆标题是「在 SSD 层跑 2.6T 模型」，一个词都不重合。解法不是 embedding，而是**识别（recognition）**：整个索引（每条记忆一行，写成"识别触发器"）塞进一个 prompt，让一个小模型点名哪些相关。**约 500 条记忆 ≈ 6k token**，占现代上下文窗口几个百分点，且躺在前缀缓存里。
2. **什么都写会毒化存储**：agent 一断言就存，垃圾迅速淹没有效记忆。

它的写入流水线：

```
journal → classed evidence → candidates → GATE
        → new? → composed → draft → judged → poured
```

**GATE 和 judged 两道闸**是重点：证据要先分类，候选要先过闸，草稿要再被判定一次才落地。

### 3.6 graph-memory（`adoresever/graph-memory`，★658）

> **Summary, SPO, and communities only navigate; original question and final answer remain the evidence.**

- 写入一个已完成回合**正好花一次辅助 LLM 调用**；社区检测和 PPR 是本地算法。
- 明确的自我约束：「没有硬编码的节点/边数上限、没有语义方向闸门、没有把非法输出修成可接受数据的 JSON 修复」。
- 1.6 版本的关键转向：从「从消息里直接抽 TASK/SKILL/EVENT」改成「先写一句自包含的回合摘要，再从同一句派生 SPO」——**因为图节点会变成事实载荷，而事实必须是原文**。

> 这条教训直接适用于技能提炼：**提炼产物的定位是"导航"，不是"事实"**。技能里写的步骤如果和实际代码对不上，技能就是负资产。

### 4.1 `dsh-memory-evolve` —— 与本需求重叠度最高

`lib/review.js` 头注释原文（这是它最值钱的部分）：

> The **main LLM reviews its own session** (it holds the full context — **no subagent, no digest, no transcript reconstruction**). The plugin only provides the pace-maker and the write paths.
>
> **pace** `agent/turn-stopping` counts completed message-triggered turns per session; when the count reaches `reviewInterval` the review is DUE. **The counter is never auto-reset** — only the model's `memory_review_status complete` call resets it, so a **missed or interrupted review stays due on the next turn instead of being silently dropped**. Subagent sessions are not counted.
>
> **hint** the snapshot carries a static review section (fixed text, no content) telling the model to check `memory_review_status` at the end of every turn and, when due, silently run the review: suggest global-track facts (`memory_suggest`) or write them directly in auto mode, **optionally touch skills (`skill_manage`)**, then complete.

四个可直接抄的设计：

1. **主模型自审，不起子 agent**。子 agent 拿不到完整上下文，只能拿到摘要——而提炼恰恰最依赖上下文细节。
2. **计数器永不自动清零**。只有模型显式 `complete` 才归零，所以「这一轮跳过了」不会被静默吞掉，下轮仍然 due。这是一个**抗遗忘**的节奏器。
3. **提示词是静态的，不含内容**。快照里只有固定的一句话（"每轮结束检查一下状态"），所以**不会因为记忆内容变化而击穿 prompt cache**。
4. **待确认队列**。`lib/skills.js` 的 `create` 分支：除非 `skillReviewEnabled` 打开，否则技能一律写进 `<memoryDir>/pending-skills/`，等用户在面板里批准后才 `move` 进正式技能目录。`patch` 分支还要求**先读过才能改**（`hasReadSkill` → `skillmsg.readFirst`）。

它的三条原则（README）：「**AI 只提议，你确认**」。

> ⚠️ **与本机的冲突**：该 README 明写「原独立插件 dsh-skills-manager 已合并进本插件，旧插件用户升级前先按安装文档卸载旧插件」。本机已装 `@michengai/dsh-skills-manager` 1.2.8，**两者会撞**。

### 4.2 两个 `dsh-skill-forge` —— 直接对标，但都不适合直接用

**`necos98/dsh-skill-forge`**（机制最巧，但硬伤最重）

- 触发：把每次完成的工具调用**只留工具名**（参数丢弃），追加进 per-session 历史；**连续重复的工具名窗口**就是"过程"。
- 三条规则：**非重叠计数**（`a,b,c,a,b,c` 算两个过程不是四个窗口）；**三调用下限**（窗口 <3 不报；`read,read,read` 重复两次直接拒绝——"连读六个文件是习惯，不是工作流"）；**最宽匹配优先**。
- 自身工具永不记录（forging 不能触发 forging）。
- 写入 `<projectRoot>/.agents/skills/<name>/SKILL.md`，**永不写到调用工作区之外**。
- 每个产出带 `metadata: { forged-by: dsh-skill-forge }`；**已存在但无此标记的文件永不覆盖**。
- 写前校验（因为非法 frontmatter 会被 provider 静默跳过，模型分不清"不存在"和"非法"）。
- **硬伤**：`peerDependencies` 把 `@deepseek-ai/dsh-session-query`、`dsh-skill`、`dsh-system-prompt`、`dsh-workspace` 全部锁死在精确版本 `0.2.0-rc.2`，本机是 `0.2.1-rc.2` → 安装会被判不兼容。可用版本豁免绕过，但那是显式风险接受。
- 政策文本明确要求「**Do this without being asked and without asking the human to confirm first**」——与 Qoder / memory-evolve 的"必须人审"完全相反。

**`@dsh-cortex/dsh-skill-forge` 0.1.0**

- 每 **10 个用户回合** fork 一个子 agent（工具路径触发被禁用为 999999），180s 超时，toolFilter 白名单 + 影子人格，checkpoint 增量持久化。
- 产出三样：技能 + 经验条目 + 独立的 `USER.md` 用户画像。
- **落地方式是暂存人控入库，唯一入口是面板的「入库」按钮**——作者明确移除了 auto-promote，理由是"agent 不能绕过人的控制"。
- 作者自己的 `docs/skill-forge现状与启停说明.md` 说这个插件**在作者本机是禁用的**（`profiles/web/cordis.patch.yml` 里 `disabled: true`）。未实机验证项：fork 子 agent 形态、同名合并路径、删除标记流程、fork 成本/延迟。

**矩阵读出来的三件事**：

1. **A 和 B 不稀缺**。十一个方案里十个都能做 A，七个能落 B。真正稀缺的是 **C（外部检索 + 装进来）**，只有 Qoder 和 CowAgent 有，而它们在 DSH 上不可用。
2. **人审闸门分裂成两个阵营**：Qoder / memory-evolve / Cortex 坚持必须人审；necos98 / GenericAgent 明确不问人。**没有中间态**——没有谁做"低风险自动采纳、高风险询问"的分级。
3. **淘汰（遗忘）几乎全员缺失**。只有 Qoder 写了"建议过期要重新生成"、distill-kura 有证据门、ReMe 按日整理。**没有人解决"技能库长到 50 条以后怎么办"**。

## 六、可借鉴的设计（按价值排序）

### ① 节奏器：计数器永不自动清零

来自 `dsh-memory-evolve`。只有模型显式 `complete` 才归零，「这轮跳过了」不会被静默吞掉，下轮仍然 due。

**为什么重要**：所有"每 N 轮审查"的方案都有同一个 bug——第 N 轮模型正忙于正事，跳过审查，然后计数器悄悄 +1，机会永远错过。**抗遗忘的节奏器比审查质量更决定成败。**

### ② 主模型自审，不起子 agent

同上来由。原文：`no subagent, no digest, no transcript reconstruction`。

**为什么重要**：提炼质量的上限是"能看到多少上下文"。子 agent 只能看摘要，而摘要恰好丢掉了"为什么这么做"这类最关键的信息。代价是审查会占用主会话的注意力——用静态提示词（不含内容）把成本压到最低。

### ③ 写入闸门：证据 → 候选 → 草稿 → 判定 → 落地

来自 distill-kura。`journal → classed evidence → candidates → GATE → new? → composed → draft → judged → poured`。

**为什么重要**：直接"提炼完就写"必然毒化技能库。中间必须有至少两道判定：**是不是新东西**、**值不值得写**。

### ④ 索引即提示词，靠识别而非检索

同上来由。整个索引（每条记忆一行，写成识别触发器）塞进一个 prompt，让模型点名。**500 条 ≈ 6k token，躺在前缀缓存里**。

**为什么重要**：向量检索在"零词面重合"的场景必漏。而技能恰恰是最容易零词面重合的东西（技能名是抽象的，用户问的是具体的）。

### ⑤ 建议与执行分离

来自 Qoder。接受建议 ≠ 已写入，接受只是**开新会话确认计划**。

**为什么重要**：一次交互里既做决策又做写入，用户没有反悔窗口。分成两次，成本几乎为零，安全性翻倍。

### ⑥ 归属标记（ownership marker）

来自 necos98。每个产出带 `forged-by` 标记，**无标记的同名文件永不覆盖**。

**为什么重要**：这是"只改自己写的、绝不碰手写的"的最小实现。比权限系统便宜，比命名约定可靠。

### ⑦ 写前校验

同上来由。非法 frontmatter 会被 provider **静默跳过**，模型无法区分"不存在"和"非法"。

**为什么重要**：静默失败是所有自动化的头号杀手。宁可在写之前报错，也不要写完发现没生效。

### ⑧ 只记工具名做重复检测

同上来由。参数丢弃，只留工具名序列；非重叠计数；三调用下限；最宽匹配优先。

**为什么重要**：这是一个**极低成本的过程信号**。不需要 LLM 参与就能判断"这个 agent 刚才在重复同一个套路"。可以作为"该审查了"的触发器，把 LLM 审查留给真正值得的时机。

### ⑨ 节点只导航，原文才是证据

来自 graph-memory 与 Qoder 的知识分层。

**为什么重要**：技能里写的步骤如果和实际代码对不上，技能就是负资产。**提炼产物的定位必须是"导航"**——指向具体文件、具体命令、具体决策记录，而不是复述。

### ⑩ 技能 ≠ 记忆

来自 Qoder 的三层知识引擎 + Claude 的 Skills/Memory 分家。

**为什么重要**：记忆是"发生过什么"，技能是"该怎么做"。混在一起会导致：记忆太快太多淹没技能；技能写得像日记没法执行。

## 八、本报告的结论

1. **A（自动提炼）和 B（生成技能）已有成熟做法**，`dsh-memory-evolve` 在 DSH 上把这两个都做了，且设计（主模型自审 + 永不自动清零的节奏器 + pending 队列）明显优于多数同类。
2. **C（外部检索）在 DSH 上是真空**。已装 `@michengai/dsh-skills-manager` 有 ClawHub 检索能力但**只暴露给 Web UI，不是模型可调用的工具**；`dsh-skill-hub` 的 npm 版同样如此，只有 GitHub main 分支（1.0.0）才有 `skill_hub` 工具。
3. **"自动提炼"的质量天花板不高**。Qoder 自己写"不是每个任务都会产生建议"；GenericAgent 靠"长歪了再淘汰"兜底；两个 forge 一个不问人一个自己禁用。**没有谁证明自动提炼的产出质量稳定可用**。
4. **真正的差异化不在提炼，在淘汰**。矩阵里九个方案只有三个勉强处理"失效/过期"，没有一个解决"技能库规模膨胀后的检索与去重"。

详细的功能需求清单与可行性判断见 `02-可行性分析.md`。
