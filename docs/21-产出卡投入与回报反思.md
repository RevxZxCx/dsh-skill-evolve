# 21 · 产出卡片的投入与回报：一次带实测的反思

> 起因：用户 m25048 提出三个问题 ——
> ①这些功能是否值得，投入与回报是否成正比？
> ②文档里记录过「文件索引不值得投入，因为比现在的流程重」，这个判断今天我们还能不能站住？
> ③这些做法是否真的比文件索引轻量，是否真的让系统响应更快？
>
> 本文只写有实测或代码依据的结论。任何一处「大概」「应该」，都在文中标出是推断。

---

## 0. 先纠正一个流传了三轮的说法

`docs/19` §八「明确不做」表格首行的原文是：

> **文件系统监听（`fs.watch` / `chokidar`）**：Qoder 都不做。大仓库会炸，事件会重名漏报，且 Windows 上 `fs.watch` 的递归支持有历史缺陷。

**这句话说的是「文件系统监听」，不是「文件索引」。** 后来在讨论中被复述成「文件索引投入高、比现状重」，但那不是文档写的东西。两者是不同的方案：

| 方案 | 做法 | 每次回合的代价 |
| --- | --- | --- |
| 文件索引 | 建一份全量文件表，之后增量维护 | 建表一次 + 增量更新 |
| 文件系统监听 | 常驻 `fs.watch`，收集事件 | 常数（事件驱动） |
| **本次被拒绝的是后者** | | |

这个区分不是抠字眼：`docs/19` 给监听列的三条理由（大仓库会炸、事件漏报、Windows 递归缺陷）**其中两条今天被实测推翻，一条需要限定条件**。而这套系统最终选了「四路采集」，恰恰是比这两者都更重的那条路。

---

## 1. 实测：三条路线的真实价格

同一台机器、同一个工作区（**24,946 个目录、34,881 个文件**）、同一个问题「这一回合写了哪 12 个文件」。

| 路线 | 回合耗时 | 找到 | coverage | 说明 |
| --- | --- | --- | --- | --- |
| git 差分（有仓库） | **0 ms** | 0 / 12 | `complete` | **假零，见 §2** |
| 目录走查（小目录 12 文件） | **5 ms** | 10 / 12 | `complete` | **漏 2 个却报 complete，见 §3** |
| 目录走查（大工作区） | **404 ms** | **0 / 12** | `partial` | 撞 5000 条上限，够不到新文件 |
| 常驻监听（回合前武装） | **3 ms** | **12 / 12** | — | 答案在 10 ms 内齐 |
| 常驻监听（大工作区） | 3 ms | — | — | 空闲 2 秒内**零**无关事件 |

监听的真实成本（Node 原生 `fs.watch` recursive，零依赖，Windows 走 `ReadDirectoryChangesW`）：

```
启动: 0 ms      常驻内存: 56 MB     关闭: 0.15 ms
一次写入: 1 ms 后收到事件，共 5 个（含父目录），无重复风暴
同一路径再写一次: 2 个事件
空闲 2 秒: 0 事件
```

**结论 1（对「轻量」这个说法）**：在被拒绝的那条路上，成本是 0 ms 启动、56 MB 常驻、每回合 3 ms。而今天在跑的两条路，一条是 371–404 ms 的进程级扫描，一条在大工作区里**根本够不到新文件**。

「监听更重」这个判断，在今天的实测数据上不成立。

### 1.1 但这不是「应该改用监听」的意思

监听换来的是**正确答案与 100 倍的速度**，代价是三件本文没有验证的事：

1. **常驻 56 MB**。插件生命周期与宿主一致，进程跑几周，这是持续占用。
2. **`fs.watch` 在 Windows 上的漏报**是有真实报告的（`ReadDirectoryChangesW` 的缓冲区溢出会丢事件，且不报错）。本次只测了 12 次写入，没有测缓冲区打满的情况。
3. **网络盘、WSL 挂载、容器卷**上 `fs.watch` 可能完全不工作，而这套系统要面对各种工作区。

所以正确的结论不是「当初选错了」，而是：**当初用一条没有实测的判断否掉了一个可能更好的方案，然后为此建了 1,707 行的规则层。**

---

## 2. 发现一个真缺陷：git 基线的吸收窗口

实测（`git_zero2.mjs`，用生产接缝 `readChanges`）：

```
写入后立即结束回合            → 找到 0 个，coverage = complete
写入后让出一个微任务          → 找到 0 个，coverage = complete
写入后 setTimeout(0)          → 找到 0 个，coverage = complete
写入后等 300 ms               → 找到 1 个，coverage = complete
```

根因在 `packages/ui-evolve/lib/git-watch.js:139`：

```js
this.baselines.set(agentId, Promise.resolve().then(() => this.changes(cwd)).then(...))
```

`start` 存的是一个**惰性 Promise**，所以基线真正取值的时刻是 `git status` 跑完的那一刻，**不是 `turn/start`**。一次 sweep 在本机小仓库 102 ms、真实仓库 107 ms。

**后果**：任何在回合开始后约 100 ms 内落盘的文件，会被吸进基线，然后被减法抵消，而 `coverage` 仍然报 `complete` —— 也就是对读者说「我看过整个工作区，就这些」。

对比目录走查那条路，`scan-watch.js:99` 存的是**纯数字时间戳**，立即定格，没有这个窗口。

真实回合通常先等工具调用返回（数百毫秒），所以多数情况不触发。但「回合开始立刻写文件」的路径会静默丢行，而**卡片会以完整的语气报告一个不完整的答案** —— 这正是 `coverage` 字段存在的理由，这里没有被守住。

> 这一条应记为缺陷，不是文档问题。

---

## 3. 第二个真缺陷：走查报 `complete` 却漏了文件

小目录 12 个文件、同一毫秒内写入，走查返回 10 个，`coverage: 'complete'`。

单独复测（加 20 ms 间隔）返回 12/12，所以**不是 mtime 边界的判断错**，而是同一时间戳戳内多个文件落在同一秒、`mtimeMs >= since` 的取整或去重在某处少算。这条没有继续定位到具体行 —— 但它和 §2 是同一类问题：**coverage 说「完整」而实际不完整。**

## 5. 成本里最容易被忽略的一项

`packages/ui-evolve/lib/config.js` 原文：

> `panelSummary: z.boolean().default(true)` —— *"This is the only feature in this plugin that spends money on its own: every completed turn becomes one small model call."*

**每个完成的回合触发一次独立的 LLM 调用**（`summarise.js` 784 行，`SUMMARY_TIMEOUT_MS = 20000`，失败后一分钟内不再重试）。

这条与「产出文件」无关，它是「上一轮总结卡」。但它在同一张面板上、由同一次 `turn/end` 触发。所以回答「这个面板是否轻量」时，不能只算文件采集的 371 ms —— **真正的经常性成本是每回合一次模型调用**，而它不在任何一版的「投入/回报」讨论里出现过。

## 6. 结论

### 6.1 这些功能是否值得？

**分三块回答，答案不一样。**

**值得的**：采集层（`shellpaths` 431 行 + `transcript` 913 行 + 两条差分 1,174 行）解决的是一个真实问题 —— 「这一回合到底改了什么文件」。这个问题在没有它的时候，读者只能自己回忆或翻 `git status`。每次 371 ms、单个会话 200 条上限、状态文件几十 KB，**成本可接受，产出被真实使用**（本机 193 个状态文件、最大 200 条、真机验收里 25 条路径分类全对）。

**存疑的**：展示层 5,167 行是产品代码的 37%，而它服务的是「把已经算对的列表画出来」。这一层在最近十轮里持续产生缺陷（`client.js` 是缺陷点名最多的模块，20 条）。真机验收抓到的问题（图标太小、路径撑布局、菜单显示路径、`0 个文件` 措辞、折叠后零行）**全部在这一层**，没有一条在采集层。

**需要重新评估的**：规则层 1,808 行（`api.js` 的噪声/过期/五态判定）。它的出发点是对的（读者不该看见 200 行 `_probe5.mjs`），但最近三次真机缺陷（`_prototype` 被判生成、全生成时折叠成零行、`folder` 态缺失）**全部由它误判引起**。它做的事情，Qoder 一件都不做 —— Qoder 只做「按 `origin` 标注 + 显示前 7 个 + 折叠」，没有噪声概念。

### 6.2 是否比文件索引轻量？

**不确定，而且当初的对比从未做过。**

被拒绝的是「文件系统监听」，实测每回合 3 ms；现在在跑的是「每次 `turn/end` 起一个 `git status` 子进程」，实测 371–404 ms。**在这两个数字上，被拒绝的方案快 100 倍。** 这不是说当初该选它（§1.1 的三条代价仍然成立），而是说：**当初否掉它的理由（「大仓库会炸」）今天被 24,946 目录、34,881 文件的实测推翻了一半** —— 大仓库里炸的不是监听，是走查。

### 6.3 是否让系统响应更快？

**没有证据表明它是「响应」的瓶颈，也没有证据表明它是「响应」的贡献者。**

- 面板读取本身：200 行会话 `stat` 最快 5 ms。
- 面板轮询：`REFRESH_MS = 60000`，60 秒一次。
- 真正的延迟在模型调用：摘要的 `SUMMARY_TIMEOUT_MS = 20000`，虽然它在 `turn/end` 时就预热（不等读者打开），但**读者看到总结的时间取决于模型，不取决于文件采集**。

所以「更快」这个说法，对文件采集部分成立（5 ms 能接受），对这个面板整体不成立 —— 面板的响应时间由一个 20 秒超时的模型调用决定。

## 7. 建议（按优先级）

**P0 · 修两个 `coverage` 说谎的地方**（§2 §3）。这是唯一一条「现在的实现会给出错误断言」的问题，其余都是取舍。
- git 基线改为在 `turn/start` 同步取值（`await` 一次 `git status` 再开回合，或改成 `scan` 那样的时间戳 + 内容对比）。
- 走查报 `complete` 前要能解释「为什么结果是 10 个而不是 12 个」，或者干脆不报 `complete`。

**P1 · 把「每回合一次 LLM 调用」写进配置说明的第一行**。`panelSummary` 默认 `true` 是对的（摘要是面板存在的理由），但一个会花钱的功能，它的成本应该出现在读者看得到的地方，而不是埋在 `summarise.js` 的文件头。

**P2 · 停止扩大规则层**。`api.js` 1,808 行、三次真机缺陷全由它引起。建议是**收窄到「只标不藏」**：噪声行不再被默认折叠、不再从主数字里扣掉，只加一个标记（Qoder 的做法：标 `origin`，显示前 7 个，其余折叠）。这样规则判错时，代价只是「多了一个标记」，而不是「这一轮什么都没产出」——最近两次真机事故都是后者。

**P3 · 展示层 5,167 行需要一次减法**。不是重写，是逐个回答「这条规则服务哪一个真机验收」；答不上来的就删。最近十轮它贡献了最多缺陷，而它的职责只是画一张列表。

**不建议做的**：不要现在改用 `fs.watch`。它更快、更准，但带来常驻内存、Windows 缓冲区漏报、网络盘不工作三个未验证的风险，而**先修 P0 能让现有方案正确**，正确比快重要。

## 8. 本文没有证明的事

- 监听在**缓冲区溢出**时的漏报率（只测了 12 次写入，未打满）。
- 网络盘 / WSL 挂载上 `fs.watch` 的行为。
- 展示层 5,167 行里有多少是死代码（没有逐条审计）。
- 摘要模型调用的**真实金额**（只确认了「每回合一次」，没有 token 数）。
- 165 条缺陷里那 91 条「谁也没点名」的，逐条分类到「方法/文档/过程」的准确性（按关键词粗分，未人工核对）。

以上任何一条被读者当作已证明的结论，都会比本文没写更糟。
