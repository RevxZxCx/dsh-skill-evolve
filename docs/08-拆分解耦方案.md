# 08 拆分解耦方案

> 状态：**建议稿，未执行**。本文回答三件事：现在该怎么拆、仓库该怎么组织、插件该怎么发布。
> 基线 commit：`ece8372`（`node test/run.mjs` 1791 passed / 0 failed）。

## 1. 先看事实：现在的耦合面到底有多宽

数字来自基线仓库，不是估计：

| 部分 | 行数 | 依赖方向 |
|---|---|---|
| 技能进化逻辑（20 个模块） | 8,809 | 自成一体，不 import 任何 UI 文件 |
| 面板 HTTP 层 `lib/api.js` | 693 | import 只用 `node:path` 和 `node:fs/promises` —— **零插件内依赖** |
| 面板客户端 `lib/client.js` | 2,063 | 只 require `react` 与 `react/jsx-runtime` —— **零插件内依赖** |
| 几何层 `lib/gutter.js` | 504 | 纯几何，由 `scripts/sync-gutter.mjs` 内联进 `client.js` |

面板的 2,756 行占了总量的 24%，而它与技能逻辑之间**只有 `lib/index.js` 里一处 `createPanelApi({...})` 的 12 个依赖函数**这一条缝。

这 12 个依赖按归属分成两半：

**属于会话信息（与技能无关）**
`transcripts`、`summariser`、`mcpTools`、`recentUse`、`skillsUsed`、`cwdFor`、`modelCatalog`、`config`

**属于技能进化**
`listCandidates`、`pendingCandidates`、`approveCandidate`、`discardCandidate`、`requestProposal`、`isOwned`、`execFor`

一个佐证：`lib/transcript.js` 的文件头写着「The panel shows three things about the session a person is looking at」，它的存在理由就是面板 —— 技能逻辑虽然也在读同一批 `session/event`，但它读的是 `signal.js` / `reflection.js` 关心的形状，与 transcript 是两套。

所以结论是：**拆分成本比行数比例看起来低得多。** 面板侧三个文件（`api.js`、`client.js`、`gutter.js`）可以原样搬走，不需要改写。

## 2. 拆成什么

### 建议的包划分

```
dsh-evolve-core         （或 dsh-evolve-kit）
  ├── session-cards     ← 会话信息面板（原 client.js/api.js 的一半）
  ├── skill-evolve      ← 技能进化（大部分逻辑 + 候选审核）
  └── mcp-evolve        ← 未来的 MCP 进化
```

关键判断：**「会话信息面板」不应该叫 ui-evolve，也不应该是最底层的 core。**

理由：用户说的「ui evolve 用于改善原版的 ui 界面」，和现在这 2,756 行做的事不是一回事。现在的东西是**在一块空白处画三张信息卡**；「改善原版 UI」是**替换/增强宿主已有的组件**（改消息气泡间距、改输入框、改侧栏行为）。后者需要的是完全不同的能力：宿主 65 个插槽里没有一个允许替换官方组件（`conversation.content` 是 Component Factory，官方禁止接管整个会话体），所以「改善原版 UI」在这个宿主上只能靠**全局 CSS 覆盖 + 往插槽里注入新元素**，这是一套新机制，不是从现在的面板搬过去。

因此正确的关系是：

| 包 | 是什么 | 能不能独立 |
|---|---|---|
| **session-cards** | 会话信息卡（上一轮/技能与MCP/产出文件） | 能，而且应该有独立开关 —— 不装技能进化也应该能看到上一轮做了什么 |
| **skill-evolve** | 检测→提案→证据门→生命周期 | 能，纯后端也能跑（工具 + 斜杠命令已足够） |
| **ui-evolve** | 覆盖/增强宿主原版界面 | **新项目**，与上面三者无代码关系 |
| **mcp-evolve** | MCP 服务器的使用检测与提案 | 应复用 skill-evolve 的 core |

### 谁依赖谁

```
        ┌──────────────────┐
        │  evolve-core     │  store / evidence / candidates /
        │  （无面板）       │  lifecycle / outcome / skillfile
        └────────┬─────────┘
                 │
      ┌──────────┼──────────┐
      │          │          │
 skill-evolve  mcp-evolve  （未来的其他 evolve）
      │
      │ 面板是可选的 peer
      ▼
 session-cards（独立，也能单独装）
```

`session-cards` 与 `skill-evolve` 之间**不需要互相依赖**。它们唯一的交点——「候选审核按钮」——通过一个可选钩子解决：

- `skill-evolve` 在宿主侧提供一个 `skillEvolve: { listCandidates, approve, discard, pending }` 服务（`ctx.provide` + `ctx.get`）。
- `session-cards` 启动时 `ctx.get('skillEvolve')`，拿到就把「建议」按钮画出来，拿不到就不画。**不装 skill-evolve 时面板依然完整，只是少一个按钮。**

这样两者可以任意组合安装，且没有硬依赖。

## 3. 仓库结构建议

### 推荐：单仓多包（monorepo），一个仓库

```
dsh-evolve/
├── packages/
│   ├── core/                 @scope/dsh-evolve-core
│   │   ├── lib/{store,evidence,candidates,lifecycle,outcome,skillfile}.js
│   │   └── package.json
│   ├── skill-evolve/         @scope/dsh-skill-evolve
│   │   ├── lib/{index,signal,reflection,hint,tools,commands,config,paths}.js
│   │   └── package.json
│   ├── session-cards/        @scope/dsh-session-cards
│   │   ├── lib/{api,client,gutter}.js
│   │   ├── scripts/{sync-gutter,extract-host-tokens}.mjs
│   │   └── package.json
│   ├── mcp-evolve/           （占位，未来）
│   └── ui-evolve/            （独立的另一个项目，不建议放进来 —— 见下）
├── docs/
│   ├── handover/             append-only 接手指南
│   └── ...
├── test/                     跨包集成测试
├── pnpm-workspace.yaml
└── package.json              根，私有，不发布
```

**为什么 monorepo 而不是多仓**：

1. **共享的 core 会被三个包同时改动**。多仓意味着每次改 core 都要在三个仓库里各发一版并协调版本，而一个人维护时这是纯开销。
2. **测试是跨包的**。现在 1791 条断言里，`index.test.mjs` / `review-fixes.test.mjs` 走的是「面板 API → 技能队列 → 落盘」的完整链路。拆仓后这条链路要么变成易碎的跨仓集成测试，要么消失。
3. **commit 历史本身就是文档**。这个项目的 `docs/handover/` 记了十几条「为什么这么改」，拆仓会把相关改动切碎到不同历史里。

**为什么 ui-evolve 不放进来**：它的失败模式和依赖完全不同（CSS 覆盖要跟宿主版本强耦合；技能进化是纯逻辑），放在一起会让「全量测试」这个概念失真 —— 一次宿主升级会让 ui-evolve 的测试全红而其他包全绿。

### 分支 / tag 策略

- 分支：`master` 保持可发布。做拆分的整个过程在 `refactor/split-packages` 分支上，完成后一次性合并。
- tag：`core@1.0.0`、`skill-evolve@1.2.0`、`session-cards@0.1.0` —— 用带前缀的 tag 让 `git tag -l 'skill-evolve@*'` 能筛出某个包的版本历史。
- **不要**在每个包里再放一份 `docs/handover/`；接手指南留在仓库根，它讲的是「这套东西为什么长这样」，不是某个包的事。

## 4. 发布方式

### 4.1 包名：必须先改名

**`dsh-skill-evolve` 在 npm 上已被 `dmso` 占用**（版本 0.1.0，创建于 2026-08-14，无 repository 字段）。当前 `package.json` 里的 `"name": "dsh-skill-evolve"` 无法直接发布到 npm。

已实测可用的候选名（npm registry 返回 404 = 未占用）：

| 名字 | 状态 | 备注 |
|---|---|---|
| `@revxz/dsh-skill-evolve` | 可用 | 推荐，scope 下不会被抢，且与 GitHub 账号一致 |
| `dsh-ui-evolve` | 可用 | ui-evolve 可用 |
| `dsh-mcp-evolve` | 可用 | mcp-evolve 可用 |
| `@revxz/dsh-session-cards` | 需确认 | 建议先建 scope |
| ~~`dsh-evolve`~~ | 已占用 | |
| ~~`dsh-skill-evolve`~~ | 已被 dmso 占用 | |

**建议**：所有包收在一个 scope 下（`@revxz/*`），这样 `npm publish --access public` 后，用户装插件时能一眼看出是一套东西，也省掉逐个抢名的风险。

### 4.2 用户怎么装

DSH 的插件安装方式从已装插件的 `package.json` 看，有四种并存：

```json
"@873360545/dsh-auto-shutdown": "github:873360545/dsh-auto-shutdown",   // GitHub 直装
"dsh-unlag": "1.14.2",                                                  // npm
"dsh-skill-evolve": "link:F:/dsh-plugin/dsh-skill-evolve",              // 本地开发
"dsh-qq-notify": "file:./.local-plugins/dsh-qq-notify"                  // 本地 tgz
```

建议按此顺序提供：

1. **npm 发布**（主路径）—— `npm i @revxz/dsh-session-cards`。这是唯一能升级的方式。
2. **GitHub 直装**（免发布）—— `github:RevxZxCx/dsh-evolve#path:packages/session-cards`。适合还没想好要不要发版时。
3. **本地 link**（开发）—— 保持现状，你已经在用。

**发布前必须做的一件事**：`lib/client.js` 是**手写 bundle，没有构建步骤**。这意味着发布出去的 `client.js` 必须是 `sync-gutter.mjs` 跑过、`extract-host-tokens.mjs` 生成过的最新副本。建议加 `prepublishOnly` 钩子：

```json
"scripts": {
  "prepack": "node scripts/sync-gutter.mjs && node scripts/extract-host-tokens.mjs && node test/run.mjs"
}
```

`prepack` 会在 `npm pack` / `npm publish` 前自动跑 —— 发布一个漂移的 bundle 是这个项目最容易犯且最难发现的错（历史上已经犯过两次：一次 gutter 没同步，一次 `bundle.js` 用旧拷贝测）。

### 4.3 版本号怎么走

- `core` 走语义化版本，因为三个包都依赖它。
- 两个插件包对 `core` 用 `peerDependencies` + 宽范围（`>=1.0.0 <2`），避免用户装两个包时被迫装两份 core。
- **不要**用 workspace 的默认 `workspace:*` —— 发布时它会变成精确版本，用户装 `skill-evolve` 会被钉死在某一个 core 版本上，而 `session-cards` 可能钉在另一个，pnpm 会装两份，`ctx.get('skillEvolve')` 就会因为两个实例而失效。

## 5. 拆分对现有能力的风险

这些是必须处理的，不是提醒：

1. **「建议」按钮会短暂消失。** 拆分期间 kind 不同步，用户会看到面板少一个按钮。建议用一个版本做**双路径**：新包起来的按钮先默认隐藏，配置项打开后才显示，确认稳定再翻转默认值。
2. **附录：路由前缀是硬编码的。** `ROUTE_PREFIX = '/api/skill-evolve'`（`lib/api.js:51`）和客户端里的 `'/api/skill-evolve/panel'` 是两处独立字符串。拆包后 `session-cards` 的路由必须改成 `'/api/session-cards'`，而 `client.js` 里散落的 URL 需要逐处改。**建议先把这个前缀提成一个常量并从一处注入**，否则这是拆分中最容易漏的地方 —— 漏一处就是「面板永远加载不出来」。
3. **`transcript.js` 归谁。** 它在 `skill-evolve` 里被 `record()` 喂数据，但只为面板存在。建议**复制而非共享**：两个包各留一份接收 `session/event` 的逻辑，因为它们关心的字段不同（技能侧要 `tool/call` 的 name/arguments，面板侧要完整的一轮）。共享一份会让任何一侧的字段需求变成另一侧的回归风险。
4. **`outcome.js` 的观察窗口**只服务技能生命周期，跟面板无关，留在 core。
5. **客户端缓存键**：`document.getElementById('dsh-skill-evolve:style')`（`lib/client.js:325`）这类 id 带插件名，拆包后必须各用各的，否则两个包抢同一个 style 节点，后挂载的会被前一个的 `if (exists) return` 挡掉。

## 6. 建议的执行顺序

分五步，每步都能独立交付、独立回滚：

| 步骤 | 做什么 | 验收 |
|---|---|---|
| 1 | 把 `ROUTE_PREFIX` 与客户端 URL 提成单点注入，仍用一个包 | 全部断言绿，行为零变化 |
| 2 | 建 monorepo 骨架，`core` 与 `skill-evolve` 先拆，`session-cards` 暂留在 `skill-evolve` 里 | `test/run.mjs` 全绿 |
| 3 | 抽出 `session-cards`，路由改 `/api/session-cards`，用可选服务连回技能侧 | 面板在「只装 session-cards」时完整可用 |
| 4 | 发布 `@revxz/dsh-session-cards` 与 `@revxz/dsh-skill-evolve` 到 npm | 干净环境装一次能跑起来 |
| 5 | `mcp-evolve` 复用 core；`ui-evolve` 另开仓库 | — |

**不建议一次拆到四个包再测试。** 这个项目的历史教训是：拆得越多、一次性验证越少，越容易在「宿主重启才生效」这一步栽跟头（客户端 bundle 要重建整个插件图，`package.json` 变化不触发）。

## 7. 关于 mcp-evolve

现在就可以确认一件事：**它应该复用 core，不该复制。** `store.js`（候选队列、账本、registry）、`evidence.js`（证据闸门）、`candidates.js`（过期判据）三份逻辑与「提炼的是技能还是 MCP 服务器」无关 —— 它们操作的是一组带证据的候选条目。

真正需要新的只有两块：

- **检测**：`signal.js` 现在认的是工具序列重复；MCP 进化要看的是「同一个 MCP 服务器反复被用于同类任务」，判据不同。
- **落盘**：`skillfile.js` 写的是 `SKILL.md`；MCP 服务器配置的写入格式与位置完全不同，而且**写 MCP 配置比写技能文件危险得多** —— 技能文件写坏了是「一个技能不能用」，MCP 配置写坏了可能让整个工具链启动失败。

所以 `mcp-evolve` 的第一步不是写代码，是把 `evidence.js` 与 `store.js` 从「知道 skill 这个词」里解放出来 —— 这两个文件里现在各有 10 处和 21 处提到 skill，大多是注释，但 `store.js:367` 的 `action: 'skill_used'` 是真实写进账本的值。**core 化必须同时定义「账本条目与 skill 无关」这件事**，否则第一个非技能消费者就得改账本格式，而账本是历史记录。

## 8. 一个不推荐的替代方案

**不要按「前端/后端」拆。** 看起来 `client.js` 2,063 行很独立，但它的独立性是假的：它认识的 12 个 API 端点、每个端点的 payload 形状、每个字段的语义，全部由 `api.js` 定义，而 `api.js` 的 12 个依赖里 7 个来自技能侧。按前后端拆会得到一个「什么都不知道的渲染层」，它要么把业务逻辑重新写一遍，要么靠一个又长又脆的契约对象活着 —— 而现在这个契约对象就是 `createPanelApi` 的参数，它至少有 JSDoc 和测试。

按**功能**拆（会话信息 / 技能进化 / MCP 进化）而不是按**层**拆，是这个方案的核心判断。
