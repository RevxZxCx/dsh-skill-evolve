## 3. 测量方法（可复现）

数据源是真实的会话状态文件，不是构造的 fixture：

```
~/.dsh/plugin-data/skill-evolve/sessions/*.json      （Windows: C:/Users/<user>/.dsh/...）
```

探针脚本：`F:/dsh-plugin/.tmp-test/probe_card_perf2.mjs`（工作区根目录的 `.tmp-test/`，不在仓库内）。

**一个必须先知道的形状陷阱**：状态文件里的 `paths` 是**以绝对路径为键的对象**，值是 `{ seq, turn, at, description, source }`。

```json
"paths": { "/abs/path/report.md": { "seq": 12, "turn": 3, "at": 1770000000000, "description": "..." } }
```

所以取路径必须 `Object.entries(doc.paths)` 拿**键**；写成 `Object.values(doc.paths).map((v) => v.path)` 会全部得到 `undefined`。我第一版就是这么写的，跑出「0 行 / 0 交付」的无效结论，差点用它下判断。**探针第一步先打印一条真实记录的形状。**

测量方式：直接 import 仓库里的函数（`statTouchedFiles`、`isDeliverable`）并对每个真实会话调用，**不是端到端**（活宿主的插件可能还是旧代码，见 §8）。

## 4. 发现

### F1（值得修）`/panel` 为 200 条路径付 `stat`，92% 被丢弃

#### 现象

`readPanel()`（`packages/ui-evolve/lib/api.js:1341`）把会话记录过的全部路径交给 `statTouchedFiles()`（`packages/ui-evolve/lib/api.js:674`），后者对**每一条**发 `stat`，组装成 `files` 原样返回。客户端拿到之后才在 `packages/ui-evolve/lib/client.js:3300` 过滤：

```js
const delivered = ordered.filter((file) => file.deliverable === true)
```

`deliverable` 这个标志在 `packages/ui-evolve/lib/api.js:748` 就已经算出来了——**信息是有的，只是没有被用来减少工作**。

#### 实测数字（237 个真实会话文件）

| 指标 | 数值 |
| --- | --- |
| 会话文件数 / 总大小 | 237 个 / 1.12MB（单会话最大 41KB） |
| 有 `paths` 记录的会话 | 209 个 |
| 记录路径总数 | **2,953 条** |
| 其中可交付 | **281 条（9.5%）** |
| 每会话行数 | 中位 0 / p90 21 / 最大 200 |
| 最坏会话（200 条）`statTouchedFiles` | **16.56ms 冷 / 5.35ms / 5.02ms 热** |
| 同一会话客户端最终保留 | **16 行** |
| 同一列表只处理交付文档 | **0.48ms（约 10× 快）** |
| 载荷大小 | 200 行 **64.5KB** → 过滤后 **5.8KB（11.2×）** |

最坏会话是 `09c85c1b-13a1-4dd2-9f0b-f44a4f6609b4.json`，200 条记录里只留 16 行。

#### 为什么这件事贵

因为**每帧都付一次**。SSE 每推一帧客户端就 `load()` 一次，而一轮里 `revisions.bump` 至少发生在这些位置（`packages/ui-evolve/lib/index.js`）：技能加载 `:306`、`turn/start` `:426`、`turn/end` `:462`、`:504`、每次 MCP 工具调用 `:530`、摘要落地 `:616`，共 8 处。

最坏会话 + 一轮 30 次 MCP 调用 ≈ **36 帧 ×（5ms + 64KB）**。

#### 前提核实（这条是承重的，我验证过才敢提）

非交付行**没有任何消费者**：

- 卡片头部那个数字数的是 `delivered.length`（`packages/ui-evolve/lib/client.js:3803`），不是 `files.length`；
- 上一轮那个文件计数数的是 `previous.paths.length`（`packages/ui-evolve/lib/api.js:1423`），与 `files` 无关；
- `data.files` 的唯一读取点是 `packages/ui-evolve/lib/client.js:3265`，紧接着就被 `:3300` 过滤。

所以把非交付行**在发出去之前**去掉，界面上一个像素都不会变。

#### 建议修法（两个选择，推荐 A）

**A. 给 `statTouchedFiles()` 加一个开关，由 `readPanel` 打开**

在 `packages/ui-evolve/lib/api.js:750` 的 `pending.push(...)` 之前跳过：

```js
if (onlyDeliverable === true && base.deliverable === false) continue
```

调用点 `packages/ui-evolve/lib/api.js:1398` 传入 `onlyDeliverable: true`。默认 `false`，所以既有调用方与既有单元测试全部不受影响。

**注意语义变化**：`MAX_TOUCHED_FILES`（`packages/ui-evolve/lib/api.js:697` 的 `if (pending.length >= MAX_TOUCHED_FILES) break`）从此计的是「交付行」而不是「前 200 条路径」。这是好事（老会话的 2,953 条里能翻出更多交付件），但要在注释里写明，否则下一个人会以为上限的意思变了。

**B. 在调用点先过滤再传**

`readPanel` 里对 `remembered` / `fallback` 先筛。**不推荐**：`isDeliverable` 判定的是**绝对路径**，而这两个来源里既有对象也有裸字符串、还有相对路径，需要在这里重新做一遍 `join(cwd, ...)`。路径解析逻辑一旦有两份拷贝，早晚会分叉。

#### 不要做的事

**不要在 `statTouchedFiles()` 内部无条件跳过非交付路径。** 该函数有十几条单元测试直接用 `.js` 路径调用它（`test/api.test.mjs:505-620`），例如：

```js
const present = join(dir, 'present.js')
const files = await statTouchedFiles({ paths: [present, join(dir, 'absent.js')] })
check('every candidate is listed', files.length === 2, ...)
```

它的契约是「把交给我的每一条都回答」，契约本身是对的——**筛选是调用方的决定**。

### F2（可接受，但不该无界）`delivered` 回合内没有上限

`Transcript#deliver()`（`packages/ui-evolve/lib/transcript.js:533`）用线性 `find` 去重：

```js
const existing = this.delivered.find((entry) => entry.path === absolute)   // :547
```

而 `MAX_CARD_PATHS = 40`（`packages/ui-evolve/lib/transcript.js:107`）只在 `snapshot()` 里 `slice`（`packages/ui-evolve/lib/transcript.js:490`），**数组本身在回合内没有上限**。单次 `readPathListArgument` 最多 40 条，正常一轮几次调用也就几千次字符串比较，可忽略。但代价随「模型把 `report_output_files` 调很多次」平方增长。

建议：在 `:549` 的 `push` 处封顶即可（例如超过 4×`MAX_CARD_PATHS` 就停）。不改也不会出事。

### F3（潜在）`HEAD /panel` 也跑完整 `readPanel`

`packages/ui-evolve/lib/api.js:1045`：

```js
return json(res, 200, { ok: true, data: await readPanel(deps, agentId) }, headOnly)
```

`headOnly` 只决定要不要写 body，`readPanel` 无条件先跑。今天的客户端不对 `/panel` 发 HEAD，所以**没有实际成本**；但任何探活工具一打就是一次完整的 200 条 `stat`。修 F1 的时候顺手加一个 `if (headOnly === true)` 早返回也可以，成本几乎为零。

### F4（外观级）同一份信息存了两处；注释与实现不一致

- `snapshot()` 同时产出 `paths: this.delivered.slice(0, MAX_CARD_PATHS).map(...)` 与 `delivered: this.delivered.slice(0, MAX_CARD_PATHS)`（`packages/ui-evolve/lib/transcript.js:490-491`）。实测 214 个带 `previous` 的文件里只有 4 个带 `previous.delivered`，且都是空数组——**目前没有成本**，上限 40 也不会长。
- `deliver()` 的 JSDoc 仍写「Deduplicated by path, first mention wins」，而实现是「后来的非空 description 会覆盖」。改注释即可。

## 5. 验收判据

修 F1 之后逐条过：

1. **像素零变化**。同一个真实会话，过滤前后 `files` 里 `deliverable === true` 的那些行必须**内容与顺序完全相同**。做法：改前改后各 dump 一次 `readPanel().files`，用 §3 的探针思路对比。
2. **工作量真的降了**。最坏会话 `files.length` 从 200 → 16（该会话），`stat` 调用次数从 200 → 16，载荷 64.5KB → 5.8KB。这三个数要重新量，不要引用本报告的数字。
3. **全量测试**。当前 HEAD 的基线是 **3854 passed / 0 failed**，修完不得下降。
4. **三套变异脚本必须继续全杀**（改动前先各跑一遍记录基线数字）：

   | 脚本 | 当前条目数（grep 计数） |
   | --- | --- |
   | `scripts/mutate-persistence.mjs` | 69 |
   | `scripts/mutate-checklist-panel.mjs` | 141 |
   | `scripts/mutate-language-and-files.mjs` | 166 |

   `node test/mutations.test.mjs` 当前 **48 passed / 0 failed**（它校验每条变异的锚点是否还在源码里）。**改完实现必须重跑它**——锚点会失效，历史上踩过很多次。
5. **新变异必须被杀死**。加一条「删掉 `onlyDeliverable` 的跳过逻辑」的变异，必须变红。测试写法：`statTouchedFiles` 接受 `readStat` 注入，用它数调用次数，断言「200 条路径里 184 条不可交付时只发生 16 次 `stat`」。这比断言 `files.length` 强，因为它同时锁住了「省掉的是系统调用」这件事。

> 变异脚本**必须串行跑**，而且被中断时源码会留在「已变异」状态。跑完用「`to` 出现且 `from` 不出现」扫描残留，别只信 `git status`。

## 6. 不能弄坏什么

- **`statTouchedFiles()` 的现有契约**（见 §4「不要做的事」）。这是本次修复最容易踩的坑。
- **`deliverable` 字段本身不能删**。哪怕修完 F1 之后它恒为 `true`，客户端仍在读它；它是接口的一部分。
- **`turnFiles` 的语义**（`packages/ui-evolve/lib/api.js:1423`）：它数的是 `previous.paths.length`，描述「刚结束的那一轮」，与 `files` 是两个不同的东西。不要把两者合并。
- **老记录的重新判定必须保留**。`packages/ui-evolve/lib/api.js:748` 上方那段注释说的就是这个：`deliverable` 必须在**每次读取时**重新问，否则老规则放进去的源码文件会一直留在卡片上。按 §4 方案 A 改，这个性质不变（`isDeliverable` 仍每次调用），只是问完之后拿它当过滤器用。

## 7. 已核实「没有问题」的部分（别重复排查）

- **删掉的五个模块没有残留引用**。全仓唯一提到文件名的是 `test/index.test.mjs:2611` 的一句注释。
- **事件路径是 O(1) 的**。`deliver()` 只在工具调用和 `deliverables/presented` 上跑；状态写盘仍是 1 秒合并；`viewOf()`（`packages/ui-evolve/lib/api.js:1309`）每会话只读一次盘。
- **SSE 帧不带载荷**，只 `{agent, revision}`，客户端自己去取。
- **客户端不会空转重渲染**：`panelSignature`（`packages/ui-evolve/lib/client.js:293-311`）没变就不 `setState`。签名里带 `formatAgo(data?.summary?.at)` 是必要的——相对时间由渲染时的时钟推导，不进签名会冻住。
- **状态文件本身不贵**：237 个共 1.12MB，单会话最大 41KB；`paths` 在写入时按 `MAX_PATHS`（`packages/ui-evolve/lib/session-state.js:95` 的 200）裁到最新。
- **`pathsSeen()` 的排序**（`packages/ui-evolve/lib/session-state.js:879`，按 `seq` 降序）是有意的：`seq` 更大的描述更新。

## 8. 残余不确定性（诚实声明）

1. **没有端到端测量**。所有的毫秒数来自直接调用函数 + 真实 237 个会话文件。活宿主的插件可能仍跑旧代码（此前 `/panel` 首次 3017ms、后续 5ms 但磁盘 `hasSummary: false` 就是这个现象）。要端到端数字，得先重启宿主，再用签名 cookie 打 `/panel` 自计时。
2. **冷缓存数字（16.56ms）在真实使用中不常出现**。热路径是 5ms 量级，因为文件系统缓存会命中。报告里的 11.2× 载荷差与 10× 计算差是稳的，毫秒数会浮动。
3. **老记录会一直被按 200 条付费**，直到那个会话再次写入（append-only，写入时才裁剪）。修 F1 之后这笔钱就不花了。
4. **F1 的前提是「卡片只显示交付文档」这条产品决定成立**。如果将来要恢复「显示所有改动过的文件」，那 200 条 `stat` 就是必要成本，本报告失效。
