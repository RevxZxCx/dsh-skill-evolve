## 一、一句话定位

**它不给模型加记忆，它给模型加一个"该记点什么了"的闹钟，和一个"记的东西靠不靠谱"的账本。**

三句话概括设计取舍：

1. **插件负责确定性的事**（什么时候该记、记的东西有没有证据），**模型负责需要理解力的事**（记什么内容）。
2. **不额外调用 LLM 做提炼**——模型本来就在会话里、本就有全部上下文，再起一个子 agent 重读一遍是浪费且是已知的失败模式。
3. **不删除技能，只降级和反转**——错误的经验反转成警告比删掉它更有价值。

> 这一条决定了整个架构，也回答了 02 文档 §6.1 的遗留问题：**不需要会话级作用域**。因为技能是落到磁盘文件、由现有 `dsh-skill-filesystem` provider 发现的，"临时技能随会话消失"这个需求直接不做了（见 §十一）。

## 二、用户实际看到什么

### 2.1 正常跑任务时（无需任何操作）

```
[第 6 个用户回合结束]
┌─ system-reminder ─────────────────────────────────┐
│ [skill-evolve] 你刚重复了一次 4 步的固定流程：        │
│   bash → read → edit → bash                       │
│ 这个流程在本次会话已出现 2 次、历史上出现 5 次。      │
│ 如果它值得复用，用 skill_candidate_submit 记下来：    │
│   先写 Procedure（怎么做），再写 Pitfalls（踩过什么坑）│
│ 不值得就忽略，本会话不会再提同一流程。                │
└───────────────────────────────────────────────────┘
```

**要点**：提示只出现一次，不重复骚扰；提示里没有候选内容（不替模型写草稿，避免幻觉注入）；明确给出"忽略"这个选项。

### 2.2 模型决定记录时

模型调用 `skill_candidate_submit`，参数带**证据引用**：

```json
{
  "name": "pdf-table-extraction",
  "description": "从扫描版 PDF 中提取表格为 CSV，需要先做版面检测再 OCR，直接 OCR 会丢列",
  "whenToUse": "当用户要求从 PDF 提取结构化表格且 PDF 是扫描件时",
  "procedure": "1. 用 pdfplumber 检查是否存在文本层\n2. 无文本层则先跑 layout 检测...",
  "pitfalls": "- 直接 OCR 会丢列边界，必须先做版面检测\n- 双栏 PDF 要关闭自动旋转",
  "verification": "打开输出 CSV，确认列数和原表头一致",
  "evidence": [
    {"sessionId": "abc123", "note": "此前 3 次直接 OCR 都丢列"},
    {"sessionId": "def456", "note": "加上版面检测后成功"}
  ]
}
```

插件立刻做**确定性校验**（不调 LLM、不看内容质量，只看结构）：

| 校验 | 失败处理 |
|---|---|
| `name` 匹配 `/^[a-z0-9]+(?:-[a-z0-9]+)*$/` | 拒绝，提示正确格式 |
| `description` 非空且 ≤ 200 字 | 拒绝 |
| `procedure` / `pitfalls` / `verification` 三者非空 | 拒绝，指出缺哪段 |
| `evidence` 至少 1 条，且 `sessionId` 真实存在 | 拒绝，**列出现存的 sessionId 前缀供模型改** |
| 不存在同名活跃技能（除非显式 `update: true`） | 拒绝，提示改用 update |
| 不存在同名候选 | 拒绝，避免刷同一个 |

通过 → 写入**候选队列**（不是正式技能库），返回：

```
已记录候选 "pdf-table-extraction"（confidence 0.5，状态 unverified）。
累计使用 3 次且无有害标记后自动晋升为正式技能。
当前候选队列：7/50。
```

### 2.3 用户随时可以干预

```
/skill-review              # 打开面板，逐条批准/拒绝候选
/skill-capture             # 强制立刻提炼当前会话（不等信号）
/skill-feedback <name> harmful --note "在 3.x 版本已经失效"
/skill-stats               # 技能库健康度：多少活跃、多少未验证、多少该退役了
```

## 三、核心数据模型

### 3.1 技能文件格式（正式技能，落到磁盘）

沿用 04 文档结论：`planning` 与 `experience` 分离（Agent-KB），四段固定。

```markdown
---
name: pdf-table-extraction
description: 从扫描版 PDF 中提取表格为 CSV，需要先做版面检测再 OCR，直接 OCR 会丢列
confidence: 0.5
state: active          # candidate | active | inverted | retired
created: 2026-10-22
last_used: 2026-10-22
last_validated: 2026-10-22
success_count: 0
harmful_count: 0
inverted_at: null
evolved-by: dsh-skill-evolve   # 归属标记，只改带这个标记的文件
---

## When to use

当用户要求从 PDF 提取结构化表格且 PDF 是扫描件时。

## Procedure

1. 用 pdfplumber 检查是否存在文本层
2. 无文本层则先跑 layout 检测，再按检测出的格子分区 OCR
3. 合并单元格按坐标去重

## Pitfalls

- 直接 OCR 会丢列边界，必须先做版面检测
- 双栏 PDF 要关闭自动旋转

## Verification

打开输出 CSV，确认列数和原表头一致。
```

**`evolved-by` 标记是硬约束**（借自 dsh-skill-forge 与 dsh-memory-evolve）：**没有这个标记的文件永远不被本插件改写**。手写的、市场装的、其他插件生成的技能，本插件只读不写。

### 3.2 候选文件（JSON，未进技能库）

```json
{
  "id": "cand_20261022_143022_a1b2",
  "name": "pdf-table-extraction",
  "description": "...",
  "whenToUse": "...",
  "procedure": "...",
  "pitfalls": "...",
  "verification": "...",
  "evidence": [{"sessionId": "abc123", "note": "..."}],
  "evidenceVerified": true,
  "createdAt": "2026-10-22T14:30:22Z",
  "sourceSessionId": "xyz789",
  "state": "unverified",
  "trigger": "repeat-pattern"
}
```

`state` 枚举：`unverified`（待用）→ `pending`（等人批准，仅 `auto` 关掉时出现）→ 已晋升则删除候选记录。

### 3.3 账本（append-only，唯一真相源）

`<dataDir>/ledger.jsonl`，一行一个事件，只追加不修改：

```jsonl
{"t":"2026-10-22T14:30:22Z","e":"candidate_submitted","id":"cand_...","name":"pdf-table-extraction","evidenceCount":2}
{"t":"2026-10-22T16:02:11Z","e":"evidence_rejected","name":"foo","reason":"sessionId def456 not found"}
{"t":"2026-10-23T09:11:00Z","e":"skill_used","name":"pdf-table-extraction","sessionId":"..."}
{"t":"2026-10-23T09:15:00Z","e":"skill_harmful","name":"pdf-table-extraction","note":"3.x 已失效"}
{"t":"2026-10-23T09:15:01Z","e":"skill_inverted","name":"pdf-table-extraction","harmfulCount":3}
{"t":"2026-11-01T00:00:00Z","e":"skill_retired","name":"pdf-table-extraction","reason":"confidence 0.12 < 0.2"}
```

**为什么账本而不是数据库**：可 `git diff`、可人工审、损坏了能重建索引、出问题能回答"这条技能是谁什么时候因为什么写进去的"。

`<dataDir>/index.json` 是派生缓存，随时可删可重建。

### 3.4 数据目录

```
<DSH_HOME>/skill-evolve/            # 默认 ~/.dsh/skill-evolve
  ledger.jsonl
  index.json
  candidates/
    cand_20261022_143022_a1b2.json
```

正式技能文件**不在这个目录**，直接写进技能根：

| `targetRoot` | 实际路径 | 适用 |
|---|---|---|
| `user`（默认） | `~/.dsh/skills/<name>/SKILL.md` | 跨项目复用的经验 |
| `project` | `<projectRoot>/.agents/skills/<name>/SKILL.md` | 只对这个仓库成立的约定 |

`projectRoot` 的判定：从会话 cwd 向上找最近的含 `.git` 的目录，找不到就用 cwd。

## 四、四个核心流程

### 流程 A：信号检测（每个工具调用都在跑，**零 token、零延迟**）

借用 dsh-skill-forge 已验证的算法，但只用来**触发提示**，不用来生成内容：

```
维护每个 agent 的滑动窗口（只记工具名，丢弃参数）：
  ["bash","read","edit","bash","read","edit"]
        ↑ 检测到重复片段 ["bash","read","edit"] × 2

规则：
  1. 最短序列长度 3（minWindow）——单个工具重复不算流程
  2. 至少重复 2 次（minRepeats）
  3. 非重叠计数：a,b,c,a,b,c 算一次流程出现两次，不算两个窗口
  4. 最宽匹配优先：从最宽窗口往下扫，命中就停
  5. 自己的工具（skill_candidate_*）永不记录——防止"记录行为"本身被当成流程
```

**为什么只记工具名**：参数里有用户隐私、有文件路径、有命令全文；只需要判断"是不是同一串动作"，名字足够。

**第二次信号源（更便宜）**：用户纠正。若某回合内用户消息命中 `/^(不对|不是|错了|重新|我说的是)/`，或连续两次用户消息语义重复（长度相似 + 编辑距离低），标记"上一个回合有问题"，这是 `pitfalls` 段最好的素材来源。

> **注意（§16 修订）**：上面这条「正则匹配用户纠正」的设想**最终没有实现**。取而代之的是**回合结束时的整体反思**——让模型自己在回合末尾回答三个问题（用户是否纠正过我 / 我是否踩了死路又找到出口 / 我是否学到这个项目或库的非显然事实）。理由：正则只能抓中文的几种开场词，而纠正往往不带这些词（"其实……"、"嗯，不过……"、"换成……"），且模型本来就握着全部上下文，比任何正则都更能判断"这次有没有被纠正"。重复检测则保留下来，但降级为**触发之一 + 反思时的附带证据**。

**节流**：同一流程名在一个会话内只提示一次；两次提示之间至少间隔 `cadence`（默认 8）个用户回合。

### 流程 B：提示注入（用 `ctx.systemPrompt.context`）

```js
ctx.effect(() => ctx.systemPrompt.context({
  name: 'skill-evolve:hint',
  order: ctx.systemPrompt.getContextOrder('SUBAGENT_DELEGATION') + 1,  // 120 之后
  text: (context) => { /* 读当前 agent 的待提示队列，空则返回 '' */ }
}))
```

**为什么用动态 context 而不是 section**：`context()` 每步重新求值（`refreshContext`），提示发出后立刻能清空；`section()` 是静态的，改不了。

**代价警告**（写在代码注释里）：动态 context 内容一变，**该会话的 prompt cache 全失效**。所以：
- 每步只输出**最多一条**提示；
- 没有新提示时**返回空字符串**（不是返回"暂无提示"）；
- 提示只在**用户回合边界**产生，不在工具调用中间变。

> 这是本设计里唯一会伤害性能的地方，必须严格克制。

### 流程 C：候选写入 + 证据闸门

```
模型调 skill_candidate_submit
    ↓
结构校验（字段、正则、非空）
    ↓ 通过
证据闸门：
  1. evidence 至少 1 条
  2. 每条 sessionId 用 ctx.sessionQuery.listSessions() 确认存在
  3. 该会话确实有工具调用记录（observeSession → 事件里含 tool/call）
  4. 候选里声明的工具名（若有）在该会话出现过
    ↓ 通过
写入 candidates/，记 ledger
    ↓
返回"已记录，当前 N/50"
```

**闸门只做可机械判定的事**。它**不**判断"这条经验对不对"——那做不到，也没有方案做到（04 文档结论）。它只保证：**这条经验至少来自一次真实发生过的会话**。

**闸门失败的处理很重要**：不能只说"证据无效"，必须**回传可用选项**，例如：

```
证据校验失败：sessionId "def456" 不存在。
当前会话可引用的 ID：
  - 8f3a21c0（本会话）
  - a91b77e2（2026-10-21，含 bash/read/edit 调用）
请用真实 ID 重新提交。
```

否则模型会开始瞎编 ID。

### 流程 D：晋升、衰减、反转、退役（`/skill-stats` 或空闲时跑，纯本地计算）

```
每次会话结束（agent/turn-stopping）或用户执行 /skill-stats：
  for 每个本插件拥有的技能：
    days = (now - last_validated) / 86400
    confidence = base * 0.5 ** (days / halfLife) - harmfulCount * harmfulWeight * 0.1
    若 state == 'unverified' 且 uses >= promoteAfterUses:
        state = 'active'，重写 frontmatter
    若 harmful_count >= invertAfterHarmful 且 state != 'inverted':
        state = 'inverted'
        在正文最前面插入 "## ⚠️ PITFALL（此流程已被标记为有害）" 段
        保留原 Procedure 作为"曾经的做法"，不删
        记 ledger: skill_inverted
    若 confidence < retireBelowConfidence 且 days > 180 且 state != 'retired':
        state = 'retired'
        移动到 <dataDir>/retired/<name>/SKILL.md（不删除）
        记 ledger: skill_retired
```

**四个参数全部可配**，默认值来自 04 文档的调研：`halfLife=90`、`harmfulWeight=4`、`invertAfterHarmful=3`、`retireBelow=0.2`。

**为什么退役是移动不是删除**：删除后无法回答"我以前是不是记过这个"，而搬家之后 `grep` 还能找到。

**`uses` 什么时候变**：只有流程 E 会计数（模型真的加载了这个技能）。`skill_feedback` 抬高的是 `helpful`，不抬高 `uses`——"被读到"和"起了作用"是两件事，混在一起会让一个被反复加载但毫无作用的技能看起来像成功。晋升条件因此是 `uses >= promoteAfterUses`，代表"它确实被反复取用，不是只在被写出来的那一轮里见过"。

### 流程 E：使用计数（唯一需要监听工具调用的地方）

技能被加载的唯一可靠信号：模型调用 `skill` 工具且参数 `name` 命中我们的技能。技能目录是内存服务，模型读目录不碰文件系统，所以没有任何 provider 回调——`tool/call` 是唯一入口。

**假设已证伪修正一次**（原设计写的是 `event.data?.args?.name`）：真实事件里字段名是 `arguments` 而不是 `args`，且它是**原始流式文本（JSON 字符串）**，不是对象。落地实现按两种形状都接受：

```js
function readSkillArgument(raw) {
  if (raw && typeof raw === 'object') return raw.name
  if (typeof raw !== 'string') return undefined
  try {
    const parsed = JSON.parse(raw)
    return parsed && typeof parsed === 'object' ? parsed.name : undefined
  } catch { return undefined }
}

ctx.on('session/event', safe('usage', (session, event) => {
  if (event?.type !== 'tool/call') return
  if (event?.data?.name !== 'skill') return
  const name = readSkillArgument(event?.data?.arguments)
  if (typeof name !== 'string' || name.length === 0) return
  const agentId = session?.id
  const agent = ctx.agents?.get?.(agentId)
  return countUse({ name, agent, agentId })
}))
```

**归属校验在 `countUse` 里，不在监听器里**：名字先对到真实文件（`skills/<name>/SKILL.md`），文件必须存在、且 frontmatter 带 `evolved-by: dsh-skill-evolve` 才是我们的技能。别人的技能、不存在的名字都直接返回，不写账本、不动计数。

**三个刻意的取舍**

1. **计数发生在派发时，不是结果时。** 要把调用和结果配对，就得维护 `callId → name` 映射并指望结果一定到达；调用被打断就会静默丢一次使用，而少计是更糟的那种错——它让一个好技能永远停在 `unverified`。归属校验已经排除了最常见的误计（模型点名了别人的技能），所以残余误差偏向"多计一次失败的调用"，而不是"漏计成功的调用"。

2. **不受 `mode` 门控。** `mode` 管的是检测与创建（能不能打断会话、能不能自己加技能）。已有技能的使用记账是另一回事：把提示关掉的人，不等于停止使用他批准过的技能。在这里门控会让所有计数器冻结在开关被拨动那一刻的值，而且比静默更糟——`/skill-stats` 会继续把这些陈旧数字当作现状报告。

3. **每次加载都重写技能文件，不只在阶段跃迁时写。** 注册表是读路径，frontmatter 是持久副本。注册表丢了，下一次加载会用文件重建条目——前提是文件里那行 `uses` 是对的。

**子 agent 的加载要计。** 提示不能发给子 agent（它不许写技能，发了也无法照做），但一次加载就是一次加载，不论谁做的。在这里排除子 agent，会系统性地少计恰好是那些"值得固化成流程"的委派工作。

**账本行**：`{ e: 'skill_used', name, sessionId, at }`，走 `appendFile` 真追加（不是读全量再重写），理由见 §store 的并发说明。

```
dsh-skill-evolve/
├── package.json
├── cordis.patch.yml          # - insert: [{ id: skill-evolve, name: 'dsh-skill-evolve' }]
├── lib/
│   ├── index.js              入口：export name / inject / Config / apply
│   ├── config.js             schemastery Config 定义
│   ├── signal.js             流程 A：序列检测 + 纠正检测
│   ├── command.js            流程 A：shell 命令展开为语义步骤
│   ├── hint.js               流程 B：动态 context 注入
│   ├── capture.js            流程 C：候选构造 + 结构校验
│   ├── evidence.js           流程 C：证据闸门（sessionQuery）
│   ├── store.js              账本读写 + 索引重建
│   ├── skillfile.js          技能文件读写 + frontmatter + 归属标记
│   ├── lifecycle.js          流程 D：晋升/衰减/反转/退役
│   ├── usage.js              流程 E：使用计数
│   ├── tools.js              三个模型工具
│   ├── commands.js           四个斜杠命令

├── locale/{en,zh}.json

```

| `capture.js` + `tools.js` | `ctx.tools.register(defineTool({name, description, parameters, output:{schema, render}, execute}))` | `dsh-tools/lib/index.js` 的 `ToolRuntime.register` |
| `evidence.js` | `ctx.sessionQuery.listSessions()`、`observeSession(sessionId, opts)` | `dsh-session-query/lib/index.js` |
| `commands.js` | `ctx.commands.register({name, description, input:{hint}, handler})` | `dsh-commands/lib/index.js`；名字须匹配 `/^[a-z][a-z0-9_-]*$/u` |
| `skillfile.js` | 纯 `node:fs`，无宿主 API | — |
| `routes.js` + `client.js` | `ctx.webServer.register({kind:'prefix', path:'/api/skill-evolve', handler})`；客户端 `inject:['slots','locale']` + `slots.register({name:'sidebar.panellist',...})` + `slots.register({name:'main', key:...})` | 参考 `@michengai/dsh-skills-manager` 与 `dsh-client-ui-plugin-manager` |
| `config.js` | `z` from `@deepseek-ai/schemastery` | 同 `dsh-tool-skill` 的 `Config` |

**特别说明：不需要 `ctx.skills.register()`。**
技能落盘后由现有的 `dsh-skill-filesystem` provider 自动发现、自动进目录、自动随步注入。自己 `register()` 一个 runtime 技能反而会和文件系统层重复，且绕过了用户的直接编辑。**这是本设计比 dsh-skill-forge 简单的地方。**

## 六、模型工具（三个）

全部用 `defineTool`，`output.schema` 必填（否则 `defineTool` 内部 `valueSchemaSpecToJsonSchema` 会抛错）。

### 6.1 `skill_candidate_submit`

```
参数：
  name            string  必填，kebab-case
  description     string  必填，≤200 字，写清触发条件
  whenToUse       string  必填
  procedure       string  必填，只写规则不写故事
  pitfalls        string  必填（没有就写"暂无"，但不许空）
  verification    string  必填
  evidence        array   必填，[{sessionId, note?}]，至少 1 条
  update          boolean 可选，默认 false；true 表示更新同名活跃技能
  trigger         string  可选，record 来源信号（repeat-pattern / user-correction / manual）

返回：{ ok, id?, name, state, reason?, hints? }
```

### 6.2 `skill_candidate_list`

```
参数：state? ('all'|'unverified'|'pending')，默认 'all'
返回：候选摘要数组（name / state / evidenceVerified / age）
```

### 6.3 `skill_feedback`

```
参数：
  name    string  必填
  outcome string  必填，'helpful' | 'harmful' | 'unknown'
  note    string  可选，写清为什么（会进 ledger）

返回：{ ok, name, state, successCount, harmfulCount, confidence }
```

> 模型自己也能调 `skill_feedback`——它刚用完一个技能、发现没用，应该立刻能标记。这比等用户手动标记可靠得多。

## 八、配置项（schemastery）

```js
export const Config = z.object({
  mode: z.union(['off', 'suggest', 'auto']).default('suggest'),
  // off     完全不工作
  // suggest 只提示，模型可自由决定记不记（推荐）
  // auto    信号触发后不提示，直接让模型在下一步必须处理（更激进）

  cadence: z.natural().min(1).default(8),          // 最少间隔多少个用户回合才提示
  minWindow: z.natural().min(2).default(3),        // 最短流程长度
  minRepeats: z.natural().min(2).default(2),       // 重复几次算模式

  targetRoot: z.union(['user', 'project']).default('user'),
  evidenceRequired: z.boolean().default(true),     // 关掉后闸门只做结构校验
  promoteAfterUses: z.natural().min(1).default(3),

  decayHalfLifeDays: z.natural().min(1).default(90),
  harmfulWeight: z.natural().min(1).default(4),
  invertAfterHarmful: z.natural().min(2).default(3),
  retireBelowConfidence: z.number().min(0).max(1).default(0.2),

  maxCandidates: z.natural().min(1).default(50),
  dataDir: z.string().default(''),                 // 空 = <DSH_HOME>/skill-evolve
  notifyOnPromote: z.boolean().default(true),
  dryRun: z.boolean().default(false),              // 只记账本，不写技能文件
})
```

`mode` 默认 `suggest` 而不是 `auto`——这是第三次在调研里看到同一个结论（Hermes Curator 默认关、SkillClaw validation 默认关），**自动维护类功能必须默认温和**。

## 九、分期交付与验收标准

### P0 —— 探针 + 信号 + 手动闭环（0.5 天）

**只做一件事：证明"提示能发出去、模型会响应、文件能写对"。**

包含：
- `signal.js` 序列检测
- `hint.js` 动态 context 注入
- `tools.js` 的 `skill_candidate_submit`（**只写文件，不做证据闸门**）
- `skillfile.js` 写入 + `evolved-by` 标记

**必须先跑的探针**（半天里最前面 1 小时）：
```js
// 临时插件，只打印，判断三件事
ctx.on('session/event', (s, e) => {
  if (['tool/call','tool/result','turn/end','agent/turn-stopping'].includes(e.type))
    console.log(e.type, JSON.stringify(e.data).slice(0, 500))
})
```
要确认：
1. `tool/call` 事件里 `data.name` / `data.arguments` 到底是什么形状（决定流程 E 能不能做）——**已核实：`name` 是字符串，`arguments` 是 JSON 字符串，不是对象**
2. `systemPrompt.context` 的 `text` 是函数还是字符串（决定提示能否按步变化）
3. 写入 `~/.dsh/skills/<name>/SKILL.md` 后，下一步的技能目录是否**立刻**包含它

**P0 验收**：
- [ ] 做一次重复性任务（连续 read→edit→bash 两轮），收到一条提示
- [ ] 让模型调 `skill_candidate_submit`，文件正确落到 `~/.dsh/skills/<name>/SKILL.md`
- [ ] 同一会话下一步，技能目录里出现该技能
- [ ] 手写一个技能（无 `evolved-by`），本插件拒绝改写它

### P1 —— 证据闸门 + 候选队列 + 去重（1 天）

- `evidence.js`：`sessionQuery` 校验 sessionId + 工具名
- 候选队列落盘、`maxCandidates` 上限、结账提示
- `skill_candidate_list`
- 去重：同名活跃技能 / 同名候选 → 拒绝并给出选项

**P1 验收**：
- [ ] 提交一个瞎编的 sessionId → 被拒，且回传真实可用 ID
- [ ] 提交 51 个候选 → 第 51 个被拒，提示先清理
- [ ] 提交已存在的技能名 → 被拒，提示用 `update: true`

### P2 —— 生命周期（1 天）

- `usage.js` 使用计数
- `lifecycle.js` 晋升 / 衰减 / 反转 / 退役
- `skill_feedback` 工具
- `/skill-stats` `/skill-feedback` 命令

**P2 验收**：
- [ ] 一个候选被用 3 次 → 自动变 `active`，frontmatter 更新
- [ ] 标记 harmful 3 次 → 自动插入 PITFALL 段，原 Procedure 保留
- [ ] 手工把 `last_validated` 改成 200 天前 → `/skill-stats` 报"该退役"，且退役是**移动**不是删除
- [ ] 账本可重建索引（删 `index.json` 后重启，状态一致）

### P3 —— 面板（2 天，占全项目 60% 工作量）

- `routes.js` 六个路由：`list` / `approve` / `reject` / `edit` / `stats` / `ledger`
- `client.js`：`sidebar.panellist` 图标 + `main` 整页
- 面板功能：候选列表（批准/拒绝/编辑）、技能健康表（置信度排序）、账本时间线

**P3 验收**：
- [ ] 侧边栏出现图标，点击打开面板
- [ ] 面板里批准一个候选 → 文件出现在技能根
- [ ] 面板能显示每个技能的 confidence 与 harmful 次数
- [ ] 所有写操作有二次确认

### 总计

| 阶段 | 工期 | 累计可交付 |
|---|---|---|
| P0 | 0.5 天 | 能自动提示 + 手动存技能（**已经比现在强**） |
| P1 | 1 天 | 幻觉技能进不来 |
| P2 | 1 天 | 技能库能自己变老、变坏、退役 |
| P3 | 2 天 | 可视化 |

**P0 半天就能验证这个方向成不成立**——这是最该先做的实验。

## 十、明确不做的（写下来防止范围蔓延）

| 不做 | 原因 |
|---|---|
| **自动调用 LLM 提炼**（见 §16 修订） | 本插件不发起任何 LLM 调用；它让**已在会话里的模型多做一次判断**。真正的第二遍提炼——起子 agent 重读 transcript——仍不做，distill 插件的失败根因正是它去调了一个不存在的 `ctx.subagents.start` |
| **起子 agent 重读会话** | Cortex 的 fork 形态作者自己标注"未实机验证"，且成本高 |
| **会话级临时技能** | 技能落盘后由现有 provider 发现，"随会话消失"要额外作用域机制，收益不明确 |
| **自动覆盖人工技能** | `evolved-by` 标记之外的写操作一律拒绝 |
| **语义去重（embedding）** | 需要向量库，且实测方案（distill-kura）明确弃用 embedding 改用"识别"；v1 只做精确同名去重 |
| **跨设备同步** | 落到 `~/.dsh/skills`，用户自己用 git 管就行 |
| **外部技能市场检索** | 这是独立需求（02 文档 F6），应交由 `dsh-skill-hub` 之类，不混进来 |
| **自动改 AGENTS.md** | 侵入性太强且容易和用户手写内容冲突 |

## 十一、已知限制与风险

| # | 限制 | 影响 | 应对 |
|---|---|---|---|
| 1 | **提示可能击穿 prompt cache** | 动态 context 一变，该会话缓存失效 | 每步最多一条、空时返回空串、只在回合边界变 |
| 2 | **单机无法独立验证技能质量** | SkillClaw 靠多客户端消除自评偏差，我们没有 | 只做"证据存在性 + 使用后反馈"，不假装能验证质量 |
| 3 | **使用计数依赖事件结构未验证** | 若 `tool/call` 不含 `args`，流程 E 做不了 | P0 探针第一项就查这个；退化方案是只看 `tool/result` 的技能内容回显 |
| 4 | **置信度衰减会让排序动态变化** | 若把置信度写进注入的目录文本，缓存频繁失效 | 置信度**只用于退役决策**，不写进技能 `description` |
| 5 | **模型可能不响应提示** | 提示是建议，模型可以一直忽略 | 这是形态 C 的固有缺陷；`mode=auto` 可以强制，但会打扰 |
| 6 | **技能多了会稀释系统提示** | 每个技能 description 都进目录 | `maxCandidates` + 退役机制 + `/skill-stats` 主动提醒"该清理了" |
| 7 | **技能文件格式变更会破坏旧文件** | frontmatter 加了新字段 | 所有读取都带默认值，缺字段按默认处理 |

## 十二、完成出来的样子（一句话验收）

装好并重启 DSH 后：

1. **你在做重复性工作时，模型会收到一次提示**，指出"你刚重复了这串动作"，并告诉它怎么写一条合格的经验（含 pitfalls 和 verification 两段）。
2. **模型记下来的东西先进入候选队列**，带证据引用；瞎编的 sessionId 会被当场拒绝并列出真实可用的 ID。
3. **候选被用够 3 次才变成正式技能**；被标 harmful 3 次会**反转成警告**而不是删掉。
4. **`~/.dsh/skills/` 下出现的是标准 SKILL.md**，你能直接打开改、直接删、直接 git 管理——插件下次读取时尊重你的修改，只在不含 `evolved-by` 时完全不碰。
5. **`/skill-stats` 随时告诉你技能库的健康度**：哪些是未验证的、哪些该退役了、最近发生了什么。

**它不会**替你提炼、不会自动写一堆技能、不会偷偷改你的文件。

## 十三、下一步（需要你拍板的三个点）

1. **`targetRoot` 默认 `user` 还是 `project`？** 我倾向 `user`（跨项目经验更常见），但如果你主要在一个仓库里工作，`project` 更合适。
2. **`mode` 默认 `suggest` 还是先 `off` 等你手动开？** 我倾向 `suggest`，但第一次装上时可以先 `off` 观察。
3. **要不要现在就写 P0 的探针？** 这是我建议的第一个动作——半天内能验证整条链路，且探针代码本身可以直接长成 P0。

## 十四、预期效果（面向人的验收，不是技术验收）

技术验收标准在 §九，这里写的是**装完之后到底能感知到什么**。用同一个任务演两遍最能说明问题。

### 14.1 装之前：同一个问题，每次从零开始

**第一次遇到**（第 1 个会话）：

```
你：这份扫描版 PDF 里的表格帮我转成 CSV

模型：[bash] pdfplumber 读取 → 报错，无文本层
      [bash] 换 pytesseract 直接 OCR → 出来一堆乱码，列全糊在一起
      [bash] 调参数、换语言包、试 3 种预处理
      [bash] 想到可能是双栏 → 加版面检测 → 成了
你：可以了
```

约 40 次工具调用、十几分钟。**最后那步「先做版面检测」是关键，但会话一结束就没了。**

**第二次遇到**（两周后）：

```
你：另一份扫描 PDF 的表格，也转一下
模型：[bash] pdfplumber → 无文本层
      [bash] pytesseract 直接 OCR → 又是乱码 ...
      ← 完全重走一遍上个月踩过的坑
```

**这是现在的真实状态。不是没解决过，是解决过之后就忘了。**

### 14.2 装之后：第二次直接走对路

第 1 个会话和上面基本一样，但结尾多一步：

```
[第 6 回合结束]
┌─ system-reminder ──────────────────────────────────┐
│ [skill-evolve] 你刚重复了一次 4 步的固定流程：          │
│   bash → bash → bash → bash                        │
│ 这个流程在本次会话已出现 2 次。                        │
│ 如果它值得复用，用 skill_candidate_submit 记下来：      │
│   先写 Procedure（怎么做），再写 Pitfalls（踩过什么坑）  │
│ 不值得就忽略，本会话不会再提同一流程。                  │
└────────────────────────────────────────────────────┘

模型：[skill_candidate_submit]
      name: scanned-pdf-table-extraction
      procedure: 1. pdfplumber 检查文本层 2. 无文本层先跑版面检测
                 3. 按检测出的格子分区 OCR 4. 合并单元格按坐标去重
      pitfalls: - 直接 OCR 会丢列边界，必须先版面检测
                - 双栏 PDF 要关闭自动旋转
      verification: 打开输出 CSV，列数和原表头一致
      evidence: [{sessionId: "8f3a21c0", note: "直接 OCR 三次都丢列"}]

插件：已记录候选（confidence 0.5，状态 unverified）。
      累计使用 3 次且无有害标记后自动晋升。
```

**第 2 个会话 —— 这就是效果所在：**

```
你：另一份扫描 PDF 的表格，也转一下

模型：[skill] 加载 scanned-pdf-table-extraction
      ← 看到 Pitfalls 段，知道直接 OCR 会丢列
      [bash] pdfplumber 检查文本层 → 无
      [bash] 直接跑版面检测，按格子分区 OCR
      [bash] 合并单元格，输出 CSV
你：可以了
```

**40 次调用变成 6 次，而且没有重走死路。**
第三次、第四次使用时，候选攒够 3 次成功，自动晋升为 `active`，置信度从 0.5 抬高。

### 14.3 效果的真实来源（四件很朴素的事）

| 效果 | 机制 | 用户能感知到的 |
|---|---|---|
| **不重走死路** | `Pitfalls` 段被加载时直接读到 | 少花十几分钟试错 |
| **不重复造轮子** | 技能目录自动注入，模型按 description 匹配 | 模型主动说「我以前做过类似的」 |
| **错误不会反复发生** | 标 harmful 3 次 → 自动反转成警告 | 一个坑不会踩第四次 |
| **无效经验会淡出** | 90 天半衰 | 库不会长成垃圾场 |

第一条**比「记住正确做法」更重要**。self-learning-skills 说得更准：

> including the failures, since **skipping a known dead-end next session is often worth more than the win itself**.

### 14.4 一个月后的技能库长什么样

```
~/.dsh/skills/
├── scanned-pdf-table-extraction/    active     confidence 0.82   用过 7 次
├── dsh-plugin-install/              active     confidence 0.71   用过 4 次
├── windows-gbk-encoding/            active     confidence 0.90   用过 11 次
├── pdf-merge-diff/                  unverified confidence 0.5    用过 0 次
└── old-api-v1-migration/            inverted   confidence 0.31   ← 有 PITFALL 警告段
```

`/skill-stats` 输出：

```
技能库健康度
─────────────────────────────
活跃        3 条（平均 confidence 0.81）
未验证      1 条 ← pdf-merge-diff 已 21 天未被使用，建议清理
已反转      1 条 ← old-api-v1-migration（3 次有害标记，已自动生成警告）
建议退役    0 条
候选队列    2/50
─────────────────────────────
最近：11-03 skill_used windows-gbk-encoding（第 11 次）
      11-02 skill_inverted old-api-v1-migration
```

**这一屏才是真正交付的东西 —— 不是「更多技能」，是「能看见技能库的状态并干预」。**

### 14.5 什么情况下完全没有效果（必须说清楚）

| 情况 | 结果 |
|---|---|
| **任务都是一次性的** | 技能攒不起来，50 条 description 白占系统提示 |
| **很少开新会话** | 技能价值主要在跨会话复用，同会话内模型本来就有上下文 |
| **模型不理提示** | 提示是建议不是命令，形态 C 的固有缺陷；`mode=auto` 能强制但会打扰 |
| **技能写得很空泛** | 「要注意细节」这种技能零价值，只会稀释系统提示 |

**50 条没用的技能比 0 条更糟。** 每个技能的 description 都常驻系统提示，等于给模型戴 50 副有色眼镜，且没有证据证明它们是对的。这是必须有退役机制和 `/skill-stats` 的原因。

### 14.6 怎么量化它到底有没有用

| 指标 | 怎么取 | 期望方向 |
|---|---|---|
| **同任务第二次的工具调用数** | 数会话里的 `tool/call` 事件 | 显著下降（核心假设） |
| **技能命中率** | `ledger.jsonl` 里 `skill_used` / 候选总数 | > 50% 说明技能有辨识度 |
| **反转率** | `skill_inverted` / `skill_used` | < 10% 说明提炼质量可以 |
| **退役率** | `skill_retired` / 总技能数 | 有退役是**好事**，说明淘汰在工作 |
| **系统提示增量** | 技能目录占多少 token | 控制在 2k token 以内 |

**账本从第一天就在记这些。** 一个月后若判断「这东西没用」，可以用数据定位是哪个环节失效 —— 提炼质量差、根本没有重复任务、还是提示未被响应。而不是靠感觉争论。

### 14.7 一句话

**它真正的效果：让「这个坑我踩过」从一个人的记忆，变成一份能被下一个会话读到的文件。**

而它真正在赌的一件事是：**这些任务里有足够多的重复**。若这个假设不成立，整个项目价值就是零 —— 这正是 P0 只花半天先验证、而不是直接做完 4.5 天的原因。

## 十五、开发路径

### 15.1 总原则：先证伪，再建功能

这个项目最大的风险不是「做不出来」，而是**做出来了但没用**（没有重复任务 / 模型不响应提示 / 技能质量差）。所以开发顺序按「**最快暴露致命假设**」排列，而不是按「功能依赖」排列。

```
阶段 0  探针          0.5 天   验证 3 个宿主假设
   ↓ 假设成立才继续
阶段 1  P0 骨架       1 天     提示能发 + 技能能写 + 模型会响应
   ↓ 观察到真实响应才继续
阶段 2  P1 闸门       1 天     幻觉技能进不来
   ↓
阶段 3  P2 生命周期   1 天     技能库能自己变老变坏
   ↓
阶段 4  P3 面板       2 天     可视化（可选，随时可停）
```

**每个 `↓` 都是真实的检查点，允许停在这里。** 阶段 1 结束后若观察到「模型对提示毫无反应」，正确决策是**停下来重新设计提示策略**，而不是继续做 P1-P3。

### 15.2 阶段 0：探针（0.5 天）—— 必须先做

**目的**：验证三个决定架构生死的宿主假设。**在验证之前不写任何正式代码。**

| 假设 | 验证方法 | 若不成立 |
|---|---|---|
| **H1** `tool/call` 事件里带 `data.name` 和 `data.arguments` | 解压真实会话日志直接读事件，未跑探针 | **✅ 成立**。字段名是 `arguments`（非 `args`），值是 JSON 字符串；`data = {turn, step, callId, name, arguments}` |
| **H2** `systemPrompt.context` 的 `text` 支持函数形式或能按步变化 | 写入递增文本，观察注入结果 | 提示只能静态：改用 `agent/pre-step` 直接改 `decision.messages` |
| **H3** 写入 `~/.dsh/skills/<name>/SKILL.md` 后，**下一步**技能目录立刻包含它 | 写文件后看下一步的 `<available_skills>` | 需要调用 provider 的 `invalidate()`，或改为 runtime 注册 |

**阶段 0 验收**：

### 15.8 开发顺序的三个反直觉决定

1. **先做提示，后做证据闸门。** 直觉是先保证质量再放出来，但没有提示就没人提交，闸门无从验证。**先让数据流起来，再加过滤器。**
2. **面板放最后，且允许不做。** 面板是唯一「看起来最像产品」的部分，但它不增加任何能力。前三个阶段已经可以通过斜杠命令和技能文件完全使用。
3. **`mode` 默认 `suggest` 而不是 `auto`。** 这是调研里第三次看到同一结论（Hermes Curator 默认关、SkillClaw validation 默认关）——**自动维护类功能必须默认温和**，否则第一次打扰就让人卸载。

## 十六、设计修订：从「单一重复检测」到「双触发电机」

> 本章记录写完之后被推翻的一个设计决定。原文保留在上面的章节里不动，因为**改动的理由比改动本身更值得留下**。

### 16.1 原设计的缺口

原方案把「工具名序列重复」当作**唯一**触发信号。当时的论证是：

> 不额外调 LLM 提炼。模型本就在会话里；distill 插件的失败根因正是它去调了一个不存在的 `ctx.subagents.start`。

**这个论证混淆了两件不同的事**：

| | 做法 | 成本 |
|---|---|---|
| (a) 起子 agent 重读 transcript | `@loserfox/distill` | 整份会话再喂一遍，且调用了不存在的宿主 API |
| (b) 让**已在会话里**的模型在回合结束前反思一句 | **Qoder 的做法** | 不重读、不额外发起调用 |

原文论证的是 (a) 不可取，结论却否掉了 (b)。**Qoder 做的是 (b)，它没有 (a) 的任何毛病。**

更严重的是替代方案的代价：**重复检测只能看见结构，看不见内容**。它能说「`read`,`grep`,`edit` 又按这个顺序出现了」，但永远看不见「这个库的分页参数从 0 开始」——而后者才是会话产出的最值钱的东西，因为它根本不是一串工具名。

### 16.2 Qoder 的实际设计（一手文档，`docs.qoder.com/qoder/skills.md`）

- 位置：Settings → General → **Skill evolution suggestions**
- 触发：**任务结束后**分析「可复用的经验教训」，建议创建或改进 Skill
- 明确免责：「**Not every task generates a suggestion.**」
- 处置：任务监视器的 Skill and MCP 区查看 → 创建改进任务 或 忽略 → **支持批量**
- 确认：「**Accepting opens a new conversation to confirm the plan** before creating or updating a Skill; task creation does not mean the Skill has already changed.」
- 失效：「If a suggestion **expires**, its source is unavailable, or **Skill files have changed**, regenerate or handle it against the latest state.」

### 16.3 三条宿主事实，决定了改造成本

改造前先核实了三件事，全部来自真实源码或真实日志，不是推测：

| 事实 | 证据 | 意义 |
|---|---|---|
| 回合边界可用 | 会话日志里 `turn/end {turn, reason:{kind:"completed"}}`、`turn/start {turn}` | 反思能挂在正确的时间点上 |
| **真人说话与系统注入可区分** | `user/message` 的 `source.kind` 有 `user` / `user-approval` / `agent-instructions` / `runtime-context` / `skill-catalog` 五种，真实会话里五种都出现过 | 只数 `kind === "user"` 才是真回合 |
| 静态提示段零成本 | `dsh-system-prompt` 的 `section({name, order, text})` 是静态文本，不进每步 `refreshContext` 的重解析 | 反思提示不会每步都击穿 prompt cache |

第二条尤其关键：真实会话里 15 个真人回合，`runtime-context` 却出现了 **86 次**。把注入消息当回合数，反思会在每一步都触发。

### 16.4 新架构：两条触发各自独立节流

```
                    ┌──────────────────────────────┐
   turn/end ───────►│ ReflectionPacer              │
   (completed)      │  只数 kind==="user" 的回合    │──┐
                    │  cadence 3 → 6 → 12（退避）   │  │
                    │  minToolCalls 4（内容门槛）   │  ├──► 同一条 hint 通道 ──► 系统提示词
                    │  max 2 次/会话（硬预算）      │  │        （单一稳定字符串）
                    └──────────────────────────────┘  │
                    ┌──────────────────────────────┐  │
   tool/call ──────►│ 重复流程检测器（沿用原算法）   │──┘
                    │  按步骤形状去重               │
                    │  maxHintsPerSession 4        │
                    └──────────────────────────────┘
```

**为什么必须共用一条通道**：`ctx.systemPrompt.context` 每个 agent 只有一条稳定字符串。两条触发各发一条会让文本互相覆盖，每次覆盖都击穿一次 prompt cache。共用一条意味着两个机制要协商「当前该显示谁」。

**为什么反思要豁免程序去重**：沿用的去重逻辑是「一段步骤序列是否已被展示过」。反思没有自己的步骤，若传占位标记，第二次反思会和第一次撞在同一个标记上被误判为重复——**这是实现时真实踩到的 bug**（见 16.6）。

### 16.5 新配置项

| 键 | 默认 | 含义 |
|---|---|---|
| `triggers` | `['turn','repeat']` | 启用哪些触发；`[]` 全关 |
| `reflectionCadence` | `3` | 首次反思前的真人回合数，此后每次翻倍 |
| `reflectionMinToolCalls` | `4` | 一个回合至少发生多少次工具调用才值得反思 |
| `maxReflectionsPerSession` | `2` | 每会话回合反思硬上限 |

### 16.6 实现中发现的三个真实缺陷

这三个都不是设计问题，是写完代码、跑测试、跑真实日志才暴露的：

**缺陷 1：`cadence` 没有归零。** 原实现只累加 `turns`，反思后不清零，导致「第 3 回合起每回合都触发」——cadence 从节流器变成了**一次性门槛**。修法：单独维护 `sinceReflection`，反思后归零。

**缺陷 2：反思被程序去重误杀。** 第二次反思传入的占位步骤与第一次相同，`isSubRun` 判定为「同一段已被展示过」，返回 `duplicate`，第二次反思永远发不出来。修法：`hint.publish` 增加 `distinct: true` 豁免，反思的节流交给 pacer 自己的预算。

**缺陷 3：预算在前半段就花光。** 在真实会话上回放：15 个真人回合，cadence 3、预算 2，**两次反思分别落在第 3 和第 7 回合，后 8 个回合完全没覆盖**。这不是配给，是一次性发放。修法：**cadence 每次翻倍**（3 → 6 → 12），第二次反思落到第 9 回合附近，接近会话中点。

修复后同一条真实会话的回放结果：

```
fire #1 at turn/end seq=344 : 3 turns since the last reflection, 31 tool calls
fire #2 at turn/end seq=1695: 6 turns since the last reflection, 61 tool calls
human turns: 15 | tool calls: 487 | reflections fired: 2 (cap 2)
user/message by kind: {user:15, runtime-context:86, user-approval:1, agent-instructions:1, skill-catalog:1}
```

### 16.7 和 Qoder 的差距（诚实版本）

改造只对齐了 Qoder 的**触发方式**，没有对齐它的**确认流程**。差距如实列出：

| 维度 | Qoder | 本插件 | 判断 |
|---|---|---|---|
| 触发时机 | 任务结束 | 真人回合结束（近似） | 基本对齐 |
| 前置判断 | 选择性产生建议 | 回合数 + 工具调用数 + 预算 | 更粗糙，但零成本 |
| 确认流程 | **接受后开新对话确认计划** | `/skill-capture` 直接写盘 | **本插件更弱** |
| 改已有技能 | **支持 updating** | `skill_candidate_submit` 撞名直接拒绝 | **本插件更弱** |
| 建议过期 | **有 expires 处理** | 队列只增不减 | **本插件更弱** |
| 防幻觉证据 | 未公开说明 | 逐字引文闸门 | 本插件更严 |
| 生命周期/淘汰 | 无 | 四态 + 90 天半衰 + 反转 | 本插件更完整 |
| 归属围栏 | 未知 | `evolved-by` 标记，非本插件写的文件只读 | 本插件更严 |

**后三条差距（确认流程、改已有技能、过期处理）是真实短板**，不是设计取舍。其中「改已有技能」影响最大：一个只能新建不能修改的库，早晚会积满第一版就知道该怎么写、后来越用越发现不对的技能。

### 16.8 修订后的判断

原方案 §十「明确不做」里的这一行：

> | **自动调用 LLM 提炼** | 模型本就在会话里、本就有上下文 |

**结论仍然成立，但表述需要更精确**：本插件确实不发起任何 LLM 调用（`inject = ['tools','commands','systemPrompt']`，全程无 `fetch`、无 `subagents`）。它做的是**让已经在跑的模型多做一次判断**。差别类似于：

- ❌ 调用一个函数算结果（额外成本）
- ✅ 在同一个函数里多加一个分支（边际成本接近零）

这也解释了为什么它可以每会话反思两次还不贵——**真正的成本不是 token，是模型注意力的分配**，所以 `maxReflectionsPerSession` 和 `reflectionMinToolCalls` 这两个「少说」的旋钮比任何优化都重要。

## 十七、修订二：补齐 16.7 表里的三条短板

§16.7 列出的三条「真实短板」已全部实现。本章记录**怎么补的、补的时候发现了什么、还剩什么**，因为补的过程中有三处判断和被调研项目写下的假设不一样。

### 17.1 改已有技能：撞名不再等于冲突

原来的 `skill_candidate_submit` 遇到同名技能一律拒绝。问题在于它把两种情况混为一谈：

| 情况 | 原来 | 现在 |
|---|---|---|
| 同名文件带 `evolved-by: dsh-skill-evolve` | 拒绝 | **修改提案（`kind: 'update'`）** |
| 同名文件是人类或其他插件写的 | 拒绝 | 仍然拒绝（归属围栏不变） |

**修改提案必须记录它写在什么版本之上**，否则批准时无法判断中间有没有人改过。所以提交时存一份 `base`：

```json
{ "path": ".../SKILL.md", "digest": "<正文的 FNV-1a>", "stage": "unverified", "uses": 3, "created": "2026-10-01" }
```

`base` 不只是哈希。**它带着生命周期记录一起穿过这次修改**——`uses`、`helpful`、`harmful`、`created` 全部保留。这是有意为之：编辑一个技能时重置它的使用计数，等于把「这个技能到底值不值得留」的证据擦掉，而那个判断恰恰是插件存在的理由。新增技能才从零开始记。

代价是：`id` 也保留原件。这让「同一个技能的第 N 版」在账本里可追，不必靠名字猜。

**发现**：`approve()` 和 `finalize()` 两条写盘路径都要处理这个分支，最初只改了一处。测试 `the base keeps the existing lifecycle record` 就是为这个漏改补的。

### 17.2 候选过期：四条判据，只读不删

调研里 Qoder 的说法是「suggestion 过期就要重新生成」。照做时发现，「过期」不是一条规则，是四种不同的死法，而且**判据必须每次读队列都跑一遍，不能只在批准时检查**——否则面板上会把一条已经不可能通过的候选显示成可批准。

| 判据 | 触发 | 为什么需要它 |
|---|---|---|
| `expired` | 超过 `candidateTtlDays`（默认 30） | 队列最常见的腐烂方式就是没人看 |
| `source-missing` | 引用的会话在 `sessionQuery.listSessions()` 里不存在 | 引文无法复核时，证据就不再是证据，只是主张 |
| `name-taken` | 等待期间出现了同名技能 | 暂存的意义就是先不占坑；坑被占了，暂存就失效 |
| `base-changed` | 修改提案的目标被删、被改、或不再归本插件所有 | 盲写会静默回滚掉别人这段时间的编辑 |

实现放在 `lib/candidates.js` 的 `evaluateStaleness()`，批量的 `annotateQueue()` 负责把结论写回队列并在**结论未变时保留原时间戳**——否则 `stale.at` 的含义会从「什么时候开始过期」退化成「我们上次什么时候看过」。

三条设计纪律：

1. **过期的候选只报告、不删除。** 它里面有已经验证过的引文和已经写好的正文。`--preview` 能读，`--discard` 能丢（用户显式动作），但插件自己不动手。
2. **探针失败不算过期。** `sessionExists()` 抛错时返回 `true`。索引读不到不等于会话没了，用一次 IO 故障去判死一条候选是错的。
3. **同名的新提交不受过期条目阻挡。** 查询用 `isLive()` 过滤，只用活条目判断「已存在」和队列容量——过期条目的存在理由是它还能被读，不是它还能占名额。

**发现**：`name-taken` 和「撞名即拒绝」看起来是同一条规则的两种写法，其实相反。前者是**等待期间被占**（该失效），后者是**提交时就已存在**（该变成修改提案）。两者必须分开判断，合在一起会把修改提案误判成冲突。

### 17.3 两段式确认：批准不等于写完

原来 `/skill-capture <name>` 直接写盘。改成默认 `confirm` 模式后：

1. `/skill-capture <name>` 把候选标记为 `approvedAt` + `awaitingFinal: true`，**不写任何文件**；
2. 模型下一步调 `skill_candidate_submit` 带 `final: true`，重新提交正文，此时才落盘。

第二步不是多余的。它的全部价值在于**模型能带着当前目录再看一眼**：一份草稿从提交到被批准可能隔了几小时或几天，这期间可能出现一个正好覆盖同样内容的技能。Qoder 的文档说得很直白：「task creation does not mean the Skill has already changed.」批准的是**这一刻的计划**，不是**那一刻的正文**。

安全上有一条不能松：`final` 仍然要走完整的证据闸门。批准的是「这份草稿可以写」，不是「之后写什么都行」。所以 `finalize()` 里没有任何绕过 `runGate()` 的捷径，`final` 分支只是把闸门结果拿去写盘。

`approvalMode: 'direct'` 保留原行为——调研里第三次看到同一个教训（Hermes Curator、SkillClaw、self-learning-skills 都把「先问」设成默认），但强制所有人走两段式会让人烦到关掉整个功能。**默认温和、允许一键关闭**比「正确但没人用」好。

**发现**：两段式一旦引入，`skill-review` 就必须能显示「已批准但还没写」这个中间态，否则用户点了批准、什么都没发生、再点一次会看到还在队列里，会以为坏了。文案因此改成 `APPROVED — waiting for the model to write the final version`。

### 17.4 改完后和 Qoder 的差距表

| 维度 | Qoder | 本插件 | 判断 |
|---|---|---|---|
| 触发时机 | 任务结束 | 真人回合结束 + 重复流程 | 近似，多一条结构化触发 |
| 前置判断 | 选择性产生建议 | 回合数 + 工具调用数 + 预算 | 更粗糙，零成本 |
| 确认流程 | 接受后**开新对话**确认计划 | 接受后**在当前会话**下一步定稿 | 仍更弱：少了新上下文的重读，但省掉一次缓存重建 |
| 改已有技能 | 支持 updating | **已支持**，带基版本校验与计数保留 | 对齐，且多了「中间被改过就拒绝」 |
| 建议过期 | 有 expires 处理 | **已有四条判据**，只报告不删除 | 对齐，且过期条目仍可读 |
| 防幻觉证据 | 未公开说明 | 逐字引文闸门 + 四类分级 | 更严 |
| 生命周期/淘汰 | 无 | 四态 + 90 天半衰 + 反转 + 保留原文 | 更完整 |
| 归属围栏 | 未知 | `evolved-by` 标记 | 更严 |

**剩下的唯一实质差距是「开新对话」**。不补的理由写在这里以免以后被当成疏漏：新对话的价值是强制重新读一遍现状，代价是整段上下文从零重建。DSH 的 `refreshContext` 每个 step 都重解析，所以本插件选择「在同一条链上多走一步」——省下的缓存重建，换来的是模型只有一次机会重读目录，而不是被迫重读全部。这是取舍，不是遗漏。

### 17.5 还不做的三件事（以及为什么现在不做）

| 不做的 | 现在为什么不做 |
|---|---|
| 面板显示「正在检测中的流程」 | 检测器不理解流程含义，只知「这三个工具名又按同样顺序出现」。真实会话回放 487 次调用得出 0 个，直接展示原始检测结果会是几十条无意义片段。要显示它，得先有解释力 |
| 并发编辑的完整保护 | 基版本哈希能挡住「批准前被改过」，挡不住「检查与写入之间那一毫秒」。加锁需要跨进程协调，收益与成本不成比例 |
| 语义去重 | 仍需阈值和向量库，而目录本身就是去重表面：模型在 `skill_candidate_list` 里能看到全部名字 |

### 17.7 命令级检测（v0.6 追加）

原设计只记录工具名，在真实会话上被证伪：一个 6,145 次调用的 Android 模拟器会话里 85% 是 `bash`，检测器看到的全是 `bash, bash, bash`，**在该窗口内一次也没触发**。而该会话最有价值的工作流——截图 → 解析 UI dump → 看图 → 点击 → 再截图——在结构上完全不可见。

修法是给 `tool/call` 装一层命令展开（`lib/command.js`），把一次 shell 调用拆成它实际执行的命令，再喂同一个检测器：

| 命令 | 记录为 |
|---|---|
| `cd /f/bot && pnpm test && git diff --stat` | `pkg test`、`git diff` |
| `adb -s emulator-5554 shell input tap 100 200` | `adb shell` |
| `python parse_ui.py s.png` | `py` |
| `npx tsc --noEmit` | `build` |

三条实现决定，每条都由回放暴露的缺陷逼出来：

1. **引号感知分段。** `node -e "a(); b()"` 是一次调用，朴素按 `;` 切分会把程序文本切成步骤名。真实会话上产生了 `n.cd`、`['+n.cd+']')).slice(0,54).padEnd(56)` 这类片段，它们会直接变成提示文本。
2. **heredoc 剥离。** 未剥离前单会话产出 16,718 个伪标签。
3. **旋转视为同一习惯。** 周期为 4 的循环经 3 宽窗口观察会得到四个互不为旋转的窗口，实测 `adb,py,read_image` 与 `read,adb,py` 被连续发布两次。判据是「共享的子串在两者中出现在**不同**偏移」；同偏移分叉的 `read,edit,bash` 与 `read,edit,grep` 仍算两个不同流程。

回放结果（同一份 6,145 次调用记录）：

| `minRepeatCount` | 工具名检测 | 命令标签检测 |
|---|---|---|
| 2 | 4 次（含 `bash,bash,todo_write,read` 噪声） | 4 次（预算耗尽） |
| 3 | 1 次 | 4 次，含上述截图循环 |
| 4 | 1 次 | 4 次 |

代价是阈值语义变了：`minRepeatCount: 2` 在长会话上会花光预算，3 才是生产环境的推荐值。默认值仍留在 2，因为短会话未必能凑出三次干净的重复。
